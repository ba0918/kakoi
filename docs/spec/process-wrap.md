# `process-wrap` 0.1 仕様

Status: Draft

置き場所: `process-wrap` を開発するソースツリーの `docs/spec/process-wrap.md`。

## 1. 結果

`process-wrap` は、ポリシーファイルとワークスペースと実行したいコマンドを受け取り、bubblewrap
（`bwrap`）のマウント名前空間の中でそのコマンドを起動し、コマンドの終了コードをそのまま返す
コマンドラインツールである。Rust で実装する。

隔離の境界は起動時に一度だけ組み立てられ、起動後に変わらない。`process-wrap` は包んだコマンドの
引数を書き換えない。包んだコマンドから見た自分の名前（argv[0]）も `COMMAND` に与えた文字列その
ままで、解決したパスに置き換えない（第 4.2 節）。

成功の観測条件: 同じポリシー、同じワークスペース、同じカレントディレクトリ、同じ環境、同じファイル
システムの状態で起動すると、同じ計画（第 2 節）が算出され、包んだコマンドの終了コードが
`process-wrap` の終了コードになり、包んだコマンドの argv[0] が `COMMAND` に与えた文字列である。
反例: 起動のたびに境界や引数列の順序が変わる、あるいは `process-wrap` が包んだコマンドの引数に
何かを足す。`sh` と与えたコマンドの argv[0] が `/usr/bin/sh` になる。

## 2. 用語

用語の読みと禁止語は `CONTEXT.md` に記録する。本節が意味の典拠である。

### 隔離

プロセスを実行するとき、利用者が安全を確保できるかどうかの境界。0.1 では 4 つの次元を持つ。
ファイルシステム（見える範囲と書ける範囲）、ネットワーク（ホストと共有するか切るか）、環境変数
（ホストから何を引き継ぎ、何を足すか）、認証情報（隠すファイルと注入する秘密）。プロセス ID、IPC、
UTS、cgroup、ユーザーの各名前空間は常に切る。次元として選べない。

認証情報の次元が扱うのはファイルと環境変数だけである。UNIX ソケットを通した認証の転送
（ssh-agent、gpg-agent、D-Bus など）は、そのソケットのパスが隔離の中から見えれば、環境変数を消しても
パスを直接指定して使える。ソケットの経路を止めるのは `hide` であり、`env.unset` は補助にすぎない。
同梱プロファイル（第 16 節）はこの両方を行う。

### ポリシー

`process-wrap` が bwrap の引数列と環境を組み立てるのに使う指定の内容。段の合成（第 5 節）を
終えた後のもの。

### ポリシーファイル

ポリシーを書いた TOML ファイル一般。プロファイルもポリシーファイルの一種。

### プロファイル

グローバルスコープにある名前付きのポリシーファイル。`--profile NAME` で名前を指定する。置き場所は
設定ディレクトリの `profile/NAME.toml`。

### ホームディレクトリ

ホストの環境変数 `HOME` の実体のパス。`HOME` が無い、空、絶対パスでない、実体のパスを得られない
（存在しない、途中が辿れない）、または実体がディレクトリでないときは、ポリシーが `~` を使うかにかかわらず、第 13 節の段階 4 で種類
`env` の診断で終わる（`--help`、`--version`、`--print-plan` の無い入れ子は例外で、この段階に至らない）。

### 設定ディレクトリ

`$XDG_CONFIG_HOME/process-wrap/`、`XDG_CONFIG_HOME` が未設定なら `~/.config/process-wrap/`。空文字と
絶対パスでない値は未設定と同じに扱う（XDG Base Directory の慣習）。成功の観測条件: `XDG_CONFIG_HOME`
を相対パスにして起動すると `~/.config/process-wrap/` のプロファイルが読まれる。反例: カレント
ディレクトリの下の `process-wrap/profile/default.toml` が読まれる。
プロファイルは `profile/`、秘密ファイルは `secrets/` に置く。`secrets/` は常に隠される（第 6.3 節）。

### 段

ポリシーの項目に優先順位を与える 4 つの層。下から順に、グローバルスコープ、プロセススコープ、
コマンドライン（`--rw` と `--hide`）、生成（第 6.3 節で `process-wrap` が生成する項目）。下 3 つが
書かれた段、最上位が生成された段。上の段が下の段に足すか、上書きする。

### グローバルスコープ

一番下の段。`--profile` で選んだプロファイルが与える。

### プロセススコープ

下から 2 番目の段。`--policy-file` で指定したポリシーファイルが与える。

### ワークスペース

変数 `${workspace}` の値であり、ワークツリーを導出する起点となるディレクトリ。`--workspace PATH` で
指定し、省略時はカレントディレクトリ。ワークスペースそのものはマウントされない。マウントされるかは
ポリシーが変数で指定するかで決まる。

### ワークツリー

ワークスペースから親へ向かって最初に `.git` を持つディレクトリ。`.git` はシンボリックリンクを
辿らずに見て、ディレクトリまたは通常ファイルであるものだけを数える。無ければワークスペース自身。

### 指令

マウント表の 1 行の種類。`rw`、`rw-file`、`ro`、`hide` の 4 つ。

### 走査

`mounts.scan` の指定に従い、起点以下のファイルを名前で探して `hide` の項目を生成すること。

### 秘密

`secrets` に書かれた環境変数名とファイルの組、およびファイルから読んで環境変数に入れる値。

### 計画

ポリシーと収集した事実から算出した、bwrap に渡す引数列（ファイル記述子の位置は記号）、環境、
各マウント項目の適用結果、解決したコマンドのパスの組。`--print-plan` はこれを表示する。

### 診断

`process-wrap` 自身の失敗を伝える標準エラーへの 1 行（第 13 節）。

### 入れ子

環境変数 `PROCESS_WRAP` が `1` の状態で `process-wrap` が起動されること。既に隔離の中で動いている
プロセスが `process-wrap` を起動した場合がこれに当たる。

### 解決が参照するもの

あるパスを実体へ解決する途中で、成分を探すために中身を見るディレクトリの実体（`..` で戻る前に通った
ものを含む）と、辿るシンボリックリンクの置き場（親ディレクトリの実体とリンクの名前）。
そのパス自身の実体は、中身を見ないので含まない。解決の結果を変えるにはこのどれかを書き換えるしか
ない。第 5.6 節で使う。

### 根の項目

書き込める項目（合成後の `rw` または `rw-file` の項目。その中とは同一か子孫）のうち、自身の解決が
書き込める項目の中（自身の中を含む）にあるものを一切参照しないもの。隔離の中からの書き換えで解決の結果を変えられないので、第 5.6 節の信頼の
起点になる。

### 露出する組

書き込める項目の中を参照して解決される項目と、それが無効にする `hide`・`ro` の項目の組のうち、
新しく見えるものや書けるものが生まれるもの。項目が `rw`・`rw-file` で相手が `hide`・`ro` のとき、
および項目が `ro` で相手が `hide` のとき。相手には書かれた項目のほか、祖先として効いている生成された
`hide`（第 6.3 節）も含む。`hide` の項目は何も露出しないので、どの相手とも組にならない。第 5.6 節で
使う。

手順の順番を指すときは「段」ではなく「段階」を使う。

成功の観測条件: 仕様書と `CONTEXT.md` の中で、これらの語が本節の意味以外で使われていない。
反例: 「設定」や「config」がポリシーの意味で使われている。

## 3. 対応環境

Linux の x86_64、bubblewrap 0.9.0 以上。WSL2 を含む。aarch64 は未対応。x86_64 以外のターゲット向けの
ビルドはコンパイル時に失敗する。

隔離の中で 32 ビットと x32 のバイナリは動かない（第 11 節）。

成功の観測条件: x86_64 の Linux で第 15 節のテストが通り、x86_64 以外のターゲットでビルドが
失敗する。反例: aarch64 でコンパイルが通ることを理由に対応環境に含める。

## 4. コマンドラインインターフェース

### 4.1 文法

```
process-wrap [OPTIONS] -- COMMAND [ARGS]...
process-wrap [OPTIONS] --print-plan [-- COMMAND [ARGS]...]
process-wrap --version
process-wrap --help
```

| オプション | 意味 |
|---|---|
| `--profile NAME` | グローバルスコープのプロファイル名。省略時は `default`。`default` を明示しても同じ。`NAME` は UTF-8 として正しく、空でなく、`/` を含まず、`.` と `..` でもない 1 つのパス要素。それ以外は種類 `usage` の診断 |
| `--policy-file PATH` | プロセススコープのポリシーファイル。省略可。指定して存在しなければ種類 `policy` の診断 |
| `--workspace PATH` | ワークスペース。省略時はカレントディレクトリ |
| `--rw PATH` | コマンドライン段の `rw` 指令。繰り返し可 |
| `--hide PATH` | コマンドライン段の `hide` 指令。繰り返し可 |
| `--print-plan` | 計画を標準出力に表示して終了する。コマンドは実行しない |
| `--version` | 版を標準出力に出して終了コード 0 |
| `--help` | 使い方を標準出力に出して終了コード 0 |

`--` より後ろは、そのまま包んだコマンドの引数になる。`--print-plan` を付けない場合、`COMMAND` は必須。
未知のオプション、`COMMAND` の欠落、その他の文法の誤りは、種類 `usage` の診断を出して終了コード
125 で終わる。上の 4 つの形は排他である。`--help` と `--version` は単独でだけ使え、他のどの引数
（オプション、`--`、`COMMAND`）と併用しても種類 `usage` の診断で終わる。`--rw` と `--hide` 以外の
オプションは 1 回だけ書ける。2 回以上書けば種類 `usage` の診断で終わる。値を取るオプションは
`--opt VALUE` と `--opt=VALUE` のどちらの形でも書け、意味は同じ。語を分けた形では、値は `-` で
始まらない。`-` で始まる語が続けば値の欠落として種類 `usage` の診断で終わる。どちらの形でも空文字の
値は値の欠落として種類 `usage` の診断で終わる。

コマンドラインで受け取るパス（`--policy-file`、`--workspace`、`--rw`、`--hide`）は、相対パスなら
カレントディレクトリからの相対として解釈する。コマンドラインでは `~` と変数を展開しない。第 5.2 節の
書式はポリシーファイルに書く値についての規則である。

### 4.2 コマンドの解決

`COMMAND` に `/` が含まれていればそのパスを使い、存在して実行可能であることを確認する。含まれて
いなければ、隔離の中で使われる `PATH`（第 8 節の規則で決まる値）を順に探す。`PATH` が無ければ
探さない。どちらの場合も見つからなければ、種類 `command not found` の診断を出して終了コード 127 で
終わる。`--print-plan` で `COMMAND` を省略したときは解決を行わず、計画の該当欄は「無し」になる。入れ子
（第 12.1 節）では、`--print-plan` の有無にかかわらず、隔離の中の `PATH` の代わりに受け取ったホストの
`PATH` で探す。

見つかったコマンドの exec が失敗したとき（インタプリタが無いスクリプト、実行できないファイル
形式など）は、通常は bwrap の失敗として bwrap の出力と終了コードがそのまま返る（第 13 節）。入れ子
では `process-wrap` 自身が exec するので、種類 `command not executable` の診断を出して終了コード
126 で終わる。説明はそのパスとエラー。2 つの経路で失敗の見え方が違うことは許容する。

起動したプロセスの argv[0] は、隔離の中でも入れ子でも、`COMMAND` に与えた文字列そのものである。
bwrap には第 14 節の固定部分の `--argv0` で渡し、入れ子では exec の際に同じ値を渡す。解決したパスは
exec するファイルの指定にだけ使う。シェルが `PATH` で見つけたコマンドに打った名前を argv[0] として
渡すのと同じで、argv[0] で振る舞いを変えるコマンド（多重呼び出しバイナリなど）が打ったとおりに動く。

探索はホストのファイルシステムで行う。`hide` で隠したディレクトリの中にあるコマンドは「見つかった」と
判定され、その後 bwrap の exec 失敗として終わる。この隙間は許容し、README に書く。引き継いだ `PATH` の
要素が `rw` の中にあっても検査しない。解決したコマンドは隔離の中で動くので、その差し替えは境界を
越えない。

成功の観測条件: 上の表のオプションだけを受け付け、それ以外は終了コード 125 で終わり、`--help` と
他のオプションの併用も 125 で終わり、存在しないコマンドは `/` の有無にかかわらず終了コード 127 で
終わり、入れ子で見つかったが exec できないコマンドは終了コード 126 で終わり、隔離の中と入れ子の
どちらでも `COMMAND` に `sh` と与えたプロセスの argv[0] が `sh` である。反例: 未知のオプションを
黙って無視して起動する。`--profile ../x` が `profile/` の外のファイルを読む。入れ子でインタプリタの
無いスクリプトが `command not found` の 127 で終わる。

## 5. ポリシーファイルの形式と合成

### 5.1 形式

TOML。固定のキー名は以下のとおりで、これ以外の固定キーはポリシー読み込み失敗。TOML として解析できない
ファイルもポリシー読み込み失敗。`env.set`、`secrets`、`git.instead-of` の 3 つのテーブルだけは、
キー名が利用者の書く値である。

```toml
[mounts]
rw      = ["${workspace}", "${worktree}", "${git_common_dir}", "/tmp/process-wrap", "~/.cache"]
rw-file = ["~/.claude.json"]
ro      = ["~/.codex/AGENTS.md"]
hide    = ["/tmp", "/run/user", "~/.ssh", "~/.aws", "/run/WSL"]

[[mounts.scan]]
root    = "${worktree}"                # 必須
names   = [".env", ".env.*"]           # 必須、空は不可
exclude = ["*.example", "*.sample", "*.dist", "*.template"]   # 省略時は空
prune   = [".git", "node_modules"]     # 省略時は空

[[mounts.hide-mounts]]
under  = "/mnt"                        # 必須
fstype = ["9p", "drvfs"]               # 必須、空は不可

[network]
mode = "host"            # "host" | "none"。省略時 "host"

[env]
mode         = "inherit" # "inherit" | "clear"。省略時 "inherit"
pass         = []        # 合成後に mode が "clear" のときだけ意味を持つ（第 5.5 節）
set          = { }
unset        = ["SSH_AUTH_SOCK", "DISPLAY", "WAYLAND_DISPLAY", "XAUTHORITY", "*_TOKEN", "*_API_KEY"]
path-prepend = []

[secrets]
GH_TOKEN = "${config_dir}/secrets/gh-token"

[git.instead-of]
"git@github.com:" = "https://github.com/"
```

この例は形式を示すためのもので、値は例である。同梱する `examples/profile/default.toml` の値は
第 16 節で定める。

セクションは省略できる。空のファイルは有効なポリシーファイルである。`mounts.scan` の項目では
`root` と `names` が、`mounts.hide-mounts` の項目では `under` と `fstype` が必須で、欠けているか
空ならポリシー読み込み失敗。

### 5.2 パスの書き方

ポリシーファイルに書くパスを取る値（`mounts` の 4 指令、`scan.root`、`hide-mounts.under`、`secrets` の
値、`env.path-prepend`）は、絶対パス、`~` 単独、`~/` で始まるパス、変数で始まるパスのどれかで書く。
相対パスと `~ユーザー名` の形はポリシー読み込み失敗。`~` はホームディレクトリ（第 2 節。`HOME` の実体のパス）に展開する。字面の `HOME` は使わない。
`HOME` の検査は第 2 節のとおりで、第 13 節の段階 4 で常に行う。

変数は 4 つ。値はすべて実体のパスで、変数の導出時に解決する。設定ディレクトリの実体のパスを得られなければ
種類 `path` の診断で終わる（プロファイルの読み込みが先に通るため、通常は到達しない）。

| 変数 | 値 |
|---|---|
| `${workspace}` | ワークスペースの実体のパス |
| `${worktree}` | ワークツリーの実体のパス |
| `${git_common_dir}` | 下の規則で検証した共有 `.git` の実体のパス。ワークツリーに `.git` が無ければ値を持たない |
| `${config_dir}` | 設定ディレクトリの実体のパス |

`${git_common_dir}` は次のとおり決める。ワークツリーの `.git`（シンボリックリンクを辿らずに見る）が
ディレクトリならそのディレクトリ。通常ファイルなら、その中の `gitdir:` が指すディレクトリを G とし、
次のどちらかが成り立つ場合だけ値を持つ。

- リンクされたワークツリー: G の `commondir` ファイルの内容を G からの相対で解決したものを C とする。
  G が `C/worktrees/` の直下にあり、かつ `G/gitdir` ファイルの内容がワークツリーの `.git` ファイルを
  指している。このとき値は C。
- サブモジュール: G に `commondir` が無く、G の `config` ファイルの `core.worktree` が G からの相対で
  ワークツリーを指している。このとき値は G。

リンクされたワークツリーの形では、さらに C の直下に通常ファイル `HEAD` が存在しなければ相互リンクの
不成立とする（`HEAD` 自身がシンボリックリンクなら辿らず、内容は読まない）。それ以外は種類 `path` の
診断で終わる。これらの比較はすべて実体のパスで行う。どちらの相互リンクも git 自身が作るものである。
ただし C は G の場所だけで決まるので、隔離の中から書ける場所を G にして `commondir` を上へ向ける偽造
（ワークツリーやその親の名前が `worktrees` のとき、または `rw` の項目の名前や親の名前が `worktrees` の
とき）は `.git` ファイルとワークツリーの中身だけで組める。`HEAD` の要求がこれを止める: `C/HEAD` を
隔離の中から作れるなら C は既に書き込める場所で、新しく露出するものが無い。`HEAD` が既にある書き込めない
C の `worktrees/` の直下に書き込める項目がある配置は、git も第 16 節の同梱プロファイルも作らない。`.git` と G の下で
読むファイル（`commondir`、`gitdir`、`config`）は、開くファイル自身がシンボリックリンクなら辿らない
（解決の途中のリンクは辿る）。通常ファイルでないものは相互リンクの不成立と同じく種類 `path` の
診断で終わる。git 自身はこれらをシンボリックリンクで作らず、
G は隔離の中から書ける領域にありうるためである。読む長さの上限は第 14 節。

値を持たない変数を含む項目は、存在しないパスと同じ扱いで飛ばす。マウント項目、走査の `root`、
`hide-mounts` の `under`、`env.path-prepend` の項目のどれでも、飛ばしたことは計画に理由付きで表示する。
`secrets` の値がそうなったときは、存在しない秘密ファイルとして第 9 節の警告になる。未知の変数名は
ポリシー読み込み失敗。変数展開はパスを取る値にだけ効く。`env.set` の値には効かない。これらの値は git コマンドを
実行せずファイルシステムから導出する。

ワークスペースが存在しないか、実体がディレクトリでなければ、種類 `path` の診断で終わる。

成功の観測条件: 4 変数がすべて実体のパスで計画に表示され、`--workspace` に通常ファイルを渡すと
終了コード 125 の `path` で終わる。反例: `${config_dir}` だけが `XDG_CONFIG_HOME` の字面で表示される。

### 5.3 段の合成

書かれた段は最大 3 つ。下から、`--profile`（省略時 `default`）、`--policy-file`、コマンドライン。
`--profile` で `default` 以外を指定したとき `default.toml` は読まない。指定したプロファイルの
ファイルが無ければポリシー読み込み失敗。組み込みの既定ポリシーは持たない。

合成規則は値の種類ごとに決まる。

| 種類 | 対象 | 規則 |
|---|---|---|
| リスト | `mounts.rw` `rw-file` `ro` `hide` `scan` `hide-mounts`、`env.pass` `unset` `path-prepend` | 連結。上の段が下の段に足す |
| スカラー | `network.mode`、`env.mode` | 上の段が上書き |
| テーブル | `env.set`、`secrets`、`git.instead-of` | キー単位でマージ。同じキーは上の段が勝つ |

`env.path-prepend` の連結は上の段の項目が先頭側に来る。`PATH` に足したとき、上の段の項目ほど前に
置かれる。

削除の演算子は無い。下の段の項目を上の段で消すことはできない。テーブルのキーを「無し」に戻すことも
できない。それが必要なら別のプロファイルを作る。

合成後に `env.set` と `secrets` に同じキーがあれば、ポリシー読み込み失敗。`env.unset` の項目は
シェルのワイルドカード（`*`、`?`）を使える。ワイルドカードの意味は本仕様の全体（`env.unset`、第 6.3 節の
走査の `names`・`exclude`・`prune`）で共通で、`*` は 0 文字以上の任意の並び（名前の先頭の `.` にも
一致する）、`?` は任意の 1 バイト、それ以外の文字はすべて字面どおりに一致する。文字クラスや
エスケープは無い。

### 5.4 マウント項目の同一性

`mounts` の 4 指令の項目は、チルダと変数を展開し、シンボリックリンクを解決した実体のパスで同一性を
判定する。実体が存在しないパスは、チルダと変数を展開した後の文字列で判定する（書いたままの字面では
ない）。

同じ段の中（同じポリシーファイルの中、またはコマンドラインの中）で、同じパスに同じ指令が 2 回
現れたら 1 つにまとめる。同じパスに違う指令が現れたら、ポリシー読み込み失敗（コマンドラインなら
種類 `usage`）。段をまたいで同じパスに指令が現れたら、上の段の指令が下の段の指令を置き換える。

### 5.5 効かない指定の拒否

合成後の `env.mode` が `inherit` のとき `env.pass` が空でないなら、ポリシー読み込み失敗。下の段が
`inherit` で、上の段が `clear` と `pass` を両方書く形は通る。

### 5.6 ポリシーを書き換えられない置き場

この節は、起動時に実体へ解決するパスについて、隔離の中からの書き換えで解決の結果を変えられないことを
求める。「解決が参照するもの」と「根の項目」は第 2 節の用語である。「合成後の `rw` または `rw-file` の
項目」は、第 6.3 節の生成の段が書かれた項目を置き換えた後の集合を指す。生成された項目は毎回の起動で
事実から作り直すので、参照するものを持たず、根の判定の対象にもならない。「書き込める項目の中」は
同一か子孫を指す。「与えられたパス」は解決前のパスであり、設定ディレクトリについては第 2 節の規則で
組み立てた実体化する前のパスである。第 5.4 節で同じ実体にまとまる書き込める形（`rw` または `rw-file` で書かれたもの）が複数あるときは、
そのすべてが根の項目の条件（書き込める項目の中にあるものを参照しない）を満たすときだけ根の項目とする。
`ro` や `hide` で書かれた形は根の判定に関わらない（それ自身は書かれた項目として検査される）。

**保護対象のパスの検査。** 読み込んだすべてのポリシーファイル、設定ディレクトリ、`secrets` の値が指す秘密
ファイル、`env.path-prepend` の項目について、その解決は合成後の `rw` または `rw-file` の項目の中にある
ものを一切参照してはならない。参照すれば種類 `path` の診断で終わる。加えて、与えられたパス自身の実体も
書き込める項目の中にあってはならない（参照するものにはパス自身が入らないため、別に求める）。次の 3 つを
この順に検査し、最初に当たったものを出す（通ったディレクトリの中では最初に通ったもの）。

1. 与えられたパスの各前置き（各祖先ディレクトリと、そのパス自身）の実体が書き込める項目の中にある
2. 辿るシンボリックリンクの置き場が書き込める項目の中にある
3. 通るディレクトリの実体が書き込める項目の中にある

秘密ファイルが存在しない（第 9 節の警告になる）ときも、存在する前置きと、存在しない成分に至るまでに
参照したものについて同じ検査を行う。存在しない前置きは実体を持たないので検査の対象にならず、存在する
最も深い祖先が書き込める項目の中にあれば止まる。この診断の説明は、そのファイル、ディレクトリ、または
リンクのパス、それを含む `rw` 項目のパス、「隔離の中から差し替えられるため」という理由の 3 つを含む。
複数の保護対象が同時に当たるときの順は第 13 節が定める。

解決の記録は次のとおり（本節のすべての検査に共通）。通るディレクトリは同じ実体を 1 回ずつ記録する。
存在しない成分、読めない成分、先を読めないリンクに至ったら解決をそこで打ち切り、そこまでに参照した
もの（先を読めないリンクはその置き場）を検査する。複数の参照が同時に当たるとき、どれを診断に
名指すかは第 20 節で委譲する。

**それ以外の解決されるパス（根の項目の検査）。** 書かれた `rw`、`rw-file`、`hide` のマウント項目
（どの段のものも、コマンドラインのものも）、`--workspace` で与えたパス、走査の `root`、`hide-mounts` の
`under` について、その解決が合成後の `rw` または `rw-file` の項目の中にあるものを参照するなら、その
パス自身の実体はいずれかの根の項目の中になければならない。外にあれば種類 `path` の診断で終わる。
書かれた `ro` の項目だけはこの検査の対象外で、下の露出する組の検査だけを受ける。`ro` はリンクを
差し替えられても消されても、どこかが読み取り専用になるか読み取り専用が外れるだけで、新しく見える
ものが生まれるのは露出する組の形に限られるためである。`hide` は対象に残す: `rw` の中のリンクで
書いた `hide` が `rw` の外を指す配置は、隔離の中でリンクを消されると次の起動で項目が飛ばされ、
隠し先がホストのまま見える（2026-09-06 に bwrap 0.9.0 で実測）。走査の `root` と `hide-mounts` の
`under` を対象に含めるのは、差し替えられた起点は本物の木を走査せず、隠すべき `.env` やマウントが
隠れないためである。この 2 つの検査は第 6.3 節の生成（走査、`hide-mounts`、秘密ファイル、`secrets/` の
すべて）の前に行い、書き込める項目と根の項目は、書かれた段だけに第 5.4 節の置き換えを適用した集合
（生成の段を適用する前）で判定する。生成は `hide` しか足さないので、この集合は生成後の集合を含み、
参照の検出は厳しい側に倒れる。着地の判定は、生成がこれから隠す書き込める項目（生成された `hide` と
同一の実体の `rw`）の中への着地を通す点で緩いが、そこは結局隠されるので新しく見えるものは無い。この
2 つの診断は、書かれた項目の検査より先に出る（第 13 節）。書かれた `hide` の項目は、さらに、その解決が
書き込める項目の中に置かれたシンボリックリンクを辿るなら、着地先を問わず（根の項目の中でも）種類
`path` の診断で終わる。隔離の中でそのリンクを消されると次の起動で項目が飛ばされ、隠し先が露出する
ためである（2026-09-06 に bwrap 0.9.0 で実測。深さ 1 のマウント点は改名できないので、実体のパスで
書いた `hide` なら外れない配置でも、リンクの形は外れる）。実体のパスで書いた `rw` の中の `hide`
（第 6.4 節の表の形）はリンクを辿らないので通る。ここで見るのは項目自身の解決だけで、ワークスペース
由来の変数で引き継いだ参照は数えない（引き継いだリンクを消されると `--workspace` 自身が種類 `path` で
止まる）。この診断の説明は、その項目のパス、辿ったリンクのパス、理由の 3 つを含む。書かれた `hide` が
根の項目の検査とこの規則の両方に当たるときは、この規則の診断を出す（辿ったリンクが利用者の直す場所を
直接指すため。明示の `--workspace` の先例とは逆）。走査の `root` と `hide-mounts` の `under` は、さらに、
その解決が書き込める項目の中を参照するなら、その実体が書き込める項目の実体と同一（`rw` のマウント点
そのもの）でなければ種類 `path` の診断で終わる。起点はマウントされないので、`rw` の下位を起点にすると
隔離の中で改名や向け直しができ、次の起動が空の木を走査して隠すべき `.env` が丸ごと隠れなくなる
（2026-09-06 に bwrap 0.9.0 で実測）。`rw` のマウント点そのものは改名できず、走査はそこから再帰するので
外れない。この診断の説明は、その起点のパス、参照した `rw` 項目のパス、理由の 3 つを含む。実体を持たない項目（存在しないもの、第 14 節のリンク追跡の
上限を超えたもの）は第 6.2 節どおり飛ばし、この検査の対象にならない（次の起動でそこに実体が
できれば、その時に検査される）。`--workspace` は次の 2 つの場合に検査の対象外で、参照するものを持たない: 省略したとき
（カレントディレクトリはカーネルが inode で解決する）と、明示した実体がカレントディレクトリの実体と
同一なとき。それ以外のとき、ワークスペース由来の変数（`${workspace}`、`${worktree}`、
`${git_common_dir}`）で展開した項目（走査の `root` と `hide-mounts` の `under` を含む）は `--workspace` の
解決が参照したものを引き継ぐ。対象外のときは引き継ぐものが無い。除外されない明示の `--workspace` については、さらに、その解決がシンボリックリンクを
辿るなら、その実体はワークスペース由来の変数で展開した項目以外の根の項目の中になければならない。外に
あれば種類 `path` の診断で終わる。書き込める項目の集合自体がワークスペースから導かれるため、差し替え
られたワークスペースを基準にすると、差し替え前に書き込めた場所（例: `rw = ["${worktree}"]` で前回
`rw` だった `~/proj`）が書き込める項目に見えなくなる。差し替えの手段はリンクに限られる（改名や移動では
書き込める項目の外へ出られず、隔離の中から bind mount やディレクトリのハードリンクは作れない）ので、
リンクを辿る解決だけを対象にする。実体のパスを書くか、そこをカレントディレクトリにして起動すれば通る。
字面の形とワークスペース由来の形が第 5.4 節で同じ実体にまとまった項目は、ワークスペース由来の変数で
展開した項目として扱う（リンクを辿る明示の `--workspace` はそこに着地できない）。明示の
`--workspace` が根の項目の検査とリンクを辿る規則の両方に当たるときは、根の項目の検査の診断を出す。
この診断の説明は、そのパス、解決の途中で参照した（または `--workspace` から引き継いだ）`rw` 項目の
パス、「隔離の中から差し替えられるため」という理由の 3 つを含む。リンクを辿る `--workspace` の診断では
2 つ目の要素は辿ったリンクのパスとする。検査の順は、走査の `root` を合成後の並び順で、次に
`hide-mounts` の `under` を合成後の並び順で（この 2 つは第 13 節の段階 7 で生成の前に先に見る）、次に
書かれた項目を第 6.4 節の順序で、次に `--workspace`。

**露出する組の検査。** 解決が書き込める項目の中を参照した書かれた項目（指令を問わない）は、次の
どちらかで `hide` または `ro` の項目と露出する組（第 2 節。項目が `rw` または `rw-file` で無効にする
先が `hide` または `ro` のとき、および項目が `ro` で無効にする先が `hide` のとき）になるとき、種類
`path` の診断で終わる。リンクを辿らない実体のパスの項目でも、その解決が書き込める項目の中を参照
するなら対象である。

1. その項目の実体が、下の段の `hide` または `ro` の項目の実体と同一である。「下の段の項目」は、
   第 5.4 節の置き換えを段の順に適用したときに、その項目の段の直前にその実体で残っている項目を指す。
2. その項目の実体の真の祖先のいずれかに、段を問わず（同じ段と上の段、生成の段を含む）`hide` または
   `ro` の項目が効いている。祖先に効いている項目は、すべての段に第 5.4 節の置き換えを適用した後にその
   実体に残っている項目であり、真の祖先を内側から順に見て、最初に項目が効いている祖先だけで判定する。
   そこに残っているのが `rw` なら、その場所は既に露出しているので止めない。実体のパスで書いた `rw` でも、
   書き込めない場所だけを通るリンク越しに書いた `rw` でも同じである。

この診断の説明は、その項目のパス、無効にする先の `hide` または `ro` の項目のパス、「隔離の中から差し替え
られるため」という理由の 3 つを含む。第 6.3 節で生成した `hide` は、同一の実体では書かれた項目を
置き換える（第 6.3 節）ので規則 1 の相手にならないが、規則 2 の祖先に効いている項目には数える。
設定ディレクトリの `secrets/` や `hide-mounts` で隠したディレクトリの中へ `ro` や `rw` の項目が
リンク越しに着地すると、第 6.4 節の順序で狭い項目が後に乗り、隠していた中身が見えるためである。
`--workspace` 自身はこの検査の対象でなく、ワークスペース由来の変数で展開した書かれた項目が、引き継いだ
参照によって検査される。理由と境界の例は下の「なぜ根の項目という考え方が要るか」に書く。

**固定部分への着地の拒否。** どの指令の項目でも、その実体が `/` と同一か、`/dev` または `/proc` と
同一かその中（第 14 節の固定部分がマウントする場所）であるときは、参照の有無を問わず種類 `path` の
診断で終わる。
`/proc` の上に `ro` を重ねると隔離用の `/proc` がホストのもので覆われ、ホストのプロセスが見える
（2026-09-06 に bwrap 0.9.0 で実測）。`/dev` や `/` に重ねると隔離の土台が壊れる。この診断の説明は、
その項目のパスと理由を含む。

**広さの拒否。** 合成後の `rw` または `rw-file` の項目の実体が、`/`、ホームディレクトリ、ホーム
ディレクトリの祖先のいずれかであるときも、種類 `path` の診断で終わる。ホーム全体を書けるようにする
指定は、どの段からも受け付けない。

第 13 節の段階 7 の中では、走査の `root` と `hide-mounts` の `under` の根の項目の検査（生成の前）、
生成、保護対象のパス、書かれた項目と `--workspace` の根の項目の検査と露出する組の検査（書かれた
項目ごとにこの順。項目をまたぐ交互の順は第 20 節で委譲）、固定部分への着地の拒否、広さの拒否の順に
検査する。

なぜ根の項目という考え方が要るか。書き込める項目の中にあるものを参照して解決されるパスは、隔離の
中からその参照先を書き換えることで、次の起動に別の実体を読ませたり、別の実体へ指令を適用させたり
できる。前置きの実体だけを見ると、前置きではない場所にあるリンク（`~/policies` が `~/cache/link/pol`
を指し、`~/cache/link` が `rw` の中）を張り替えられる。リンクの置き場まで見ても、リンク先が `..` で
`rw` の中のディレクトリを通り抜ける形（`~/policies` が `~/cache/x/../../real/pol` を指し、`~/cache/x`
が `rw` の中の実ディレクトリ）では、そのディレクトリをリンクに差し替えられる。保護対象だけを守っても、
入れ子の項目（`rw = ["~/cache", "~/cache/pip/http"]`）は `~/cache/pip` をホストの別の場所へのリンクに
差し替えると、次の起動がそこへ `rw` を適用する。飛び先が「いずれかの書き込める項目の中」であればよい
とすると、差し替えた飛び先同士が互いを正当化し、`rw = ["${worktree}", "~/cache"]` で `--workspace` を
`rw` の中のリンク越しに与えた場合は `${worktree}` の項目自身が飛び先を正当化する。この例では引き継ぎが無ければ、変数の値は実体のパスなのでその項目自身は書き込める項目の中を参照しない
ことになる。
カレントディレクトリと、それと同じ実体の `--workspace` を対象外にするのは、既にそこにいるプロセスは
差し替えで移動しないためで、第 14 節で受け入れた起動環境への信頼（カレントディレクトリを含む）と同じ
水準である。根の項目は、
この連鎖を「自身の解決が書き込める項目の中を参照しない項目」で断ち切る。通った項目の中に限らず
「いずれかの根の項目の中」とするのは、`rw` の項目については別の根の項目の中へ着地しても新しく
露出するものが無い、と考えたためである。ただし、飛び先の根の項目の中に `hide` または `ro` で
書いた項目があると、リンク越しに着地した項目がそれを無効にする。同一の実体なら、上の段から着地した
項目が第 5.4 節の同一性で下の段の `hide` や `ro` を置き換える。同一でなくても、`hide` や `ro` の中（真の
子孫）に着地すれば、第 6.4 節の順序で狭い項目が後に乗り、隠していた中身が見える。後者は段に依らない:
下の段の `rw` がコマンドラインの `hide` の中へ着地しても、同じ順序で後に乗る。新しく露出するのは、
着地した項目が `rw` または `rw-file` で無効にする先が `hide` または `ro` のとき、および着地した項目が
`ro` で無効にする先が `hide` のときである（`hide` は何も露出せず、`ro` が `ro` に重なっても新しく見える
ものは無い）。この 2 つを「露出する組」と呼び、検査の規則は上の「露出する組の検査」に定める。別の
根の項目の中へ飛ぶこと自体（下の観測条件の「別の根の項目への着地」の形）は残す。何も参照しない
項目（実体のパスで書いた `rw = ["/tmp/process-wrap"]` を `hide = ["/tmp"]` の中に置く第 6.4 節の表の形）は
この規則に当たらない。正直な配置で項目を `hide` の中へリンク越しに置きたいとき、その `hide` が書き込める
項目の外にあるなら、実体のパスを書けば通る。`hide` が `rw` の中にあるなら、実体のパスで書いてもその `rw` を
参照するので、`rw` も `rw-file` も `ro` も通らない（規則 2）。そこでは項目を `hide` の中に置く配置そのものを
諦める。`rw` の中の `hide`・`ro` の項目は着地先を変えられると元の対象を隠せなくなるが、
それは下の「読み取り専用で重ねるだけでは足りない理由」のとおり祖先の改名でも起きることで、この規則の
穴ではない。入れ子を禁じないのは、
第 6.4 節の表にある `rw` の中の `ro` のような形を残すためである。利用者が `rw` の中に置いたリンク
（先が `rw` の外）のパスを `rw`、`rw-file`、`hide` の項目に書くと、正直な配置でもこの規則に当たって
1 回目の起動から拒否される。リンク先の実体のパスを書けば通る。同じリンクのパスを `ro` の項目に書く
配置（dotfiles へのリンクを `ro` にする形）は通るが、その守りは第 16 節の既知の隙間 15 の水準で
ある: 隔離の中でリンクを消して同じ名前の通常ファイルを置けば、同じ起動の中で読む側のパスの内容を
変えられ（守られるのはリンク先の実体だけ。2026-09-06 に実測）、リンク先が書き込める項目の外なら
`--ro-bind / /` で既に読み取り専用なので `ro` の項目は何も足していない。秘密ファイルを
保護対象にするのは、`rw` の中の秘密ファイルを隔離の中からホストの任意のファイルへのシンボリック
リンクに差し替えると、次の起動がその内容を環境変数として隔離に持ち込むためである。

読み取り専用で重ねるだけでは足りない理由: 重ねたファイル自体は動かせないが、その祖先ディレクトリの
改名は許され、同じパスに別のファイルを置けば次回の起動がそれを読む（2026-09-03 に bwrap 0.9.0 で
実測）。

成功の観測条件: 上の表の規則で合成した結果が `--print-plan` に表示され、削除の演算子に相当する
書き方はどの段でも読み込み失敗になり、ワークツリーの中に置いたポリシーファイルを `--policy-file` で
指すと理由付きの診断で止まり、`rw` の中を指す `secrets` の値も同じ診断で止まり、`rw` の外にある
ポリシーファイルを `rw` の中に置いたシンボリックリンク越しに指しても同じ診断で止まり、リンク先が `..` で
`rw` の中のディレクトリを通り抜ける形でも同じ診断で止まる。書かれた項目と `--workspace` については
次の対がそれぞれ観測される: `rw = ["~/cache", "~/cache/pip/http"]` の正直な配置は通り、`~/cache/pip` を
ホストの別の場所へのリンクに差し替えると `path` で止まる。`rw = ["~/a", "~/b"]` と `hide = ["~/b/creds"]`
と `~/a/l -> ~/b/x` で `ro = ["~/a/l/y"]` は通り、`l` をどの項目でもない場所へ差し替えても通り（`ro` は
新しく露出しない）、`l` を `~/b/creds` の中へ差し替えると止まる。`rw = ["${worktree}", "~/cache"]` に
`--workspace ~/cache/proj` は通り、`proj` を別の場所へのリンクに差し替えると止まる。`rw = ["~/cache"]`
の中の `rw-file` は、正直な配置は通り、差し替えると止まる。`rw = ["~/cache"]` の中の実体のパスで書いた
`hide` は通る。`rw = ["~/proj"]` で `~/proj/secrets` がどの項目でもない `~/vault` を指す
`hide = ["~/proj/secrets"]` も、`rw = ["~/a", "~/b"]` で `~/a/l` が `~/b/creds` を指す `hide = ["~/a/l"]` も、
1 回目の起動から止まる。書き込めない場所だけを参照する
解決は影響を受けない: `rw = ["${worktree}"]` だけのプロファイルで `--workspace ~/cache/proj`（`~/cache` は
どの項目でもない）は通る。明示した `--workspace` がカレントディレクトリと同じ実体なら、`rw` の
ワークツリーの下位でも通る。リンクを辿る明示の `--workspace` については: `rw = ["${worktree}"]` で
`~/proj/sub` を別の場所へのリンクに差し替えた後、別のカレントディレクトリから `--workspace ~/proj/sub` を
与えると `path` で止まり、`rw = ["~/work"]` で `~/work` がリンクでも `--workspace ~/work/proj` は通る。
`rw = ["~/a", "~/b"]` と `hide = ["~/b/creds"]` のプロファイルに、`~/a/link` が `~/a/real` を指す正直な配置で
`--rw ~/a/link` は通り、`~/a/link` を `~/b/creds` へ向け直しても `~/b/creds/sub` へ向け直しても `path` で
止まる。`rw = ["~/a", "~/b", "~/a/link"]` のプロファイルで `~/a/link` を `~/b/creds/sub` へ向け直し、
`--hide ~/b/creds` を与えても `path` で止まり、同じ `hide` をプロファイルに書いても止まる。
`rw = ["~/b"]` と `hide = ["~/b/creds"]` のプロファイルに `--hide ~/b/creds` も `--hide ~/b/creds/sub` も通る。
別の根の項目への着地: `rw = ["~/a", "~/b"]` で `~/a/link` を `~/b/real` へ向けた `--rw ~/a/link` は通る。
生成された `hide` の中への着地: `rw = ["~/a"]` と `~/a/link` が `${config_dir}/secrets/other`（`secrets` に
書かれていないファイル）を指す `ro = ["~/a/link"]` は `path` で止まり、`hide-mounts` で隠した `/mnt/c`
の中を指す `ro` も止まる。固定部分: `ro = ["/proc"]` と、`~/a/link` を `/proc` へ向けた
`ro = ["~/a/link"]` は `path` で止まる。走査の起点: `rw = ["~/a"]` で `~/a/link` がどの項目でもない
`~/proj` を指す `root = "~/a/link"` は `path` で止まり、`rw = ["~/b"]` で `root = "~/b/tree"`（`rw` の
下位）も `path` で止まり、`root = "~/b"` と `root = "${worktree}"` は通る。反例: 上の段の `rw` が下の段の
`hide` と同じパスを指したとき、どちらが勝つかが段の順序以外で決まる。差し替えた飛び先が別の差し替えた
項目によって正当化される。`ro` のリンクを `secrets/` の中へ向けると次の起動で秘密ファイルが読める。

## 6. マウントの解決

### 6.1 指令の意味

| 指令 | 対象 | 隔離の中での見え方 |
|---|---|---|
| `rw` | ディレクトリ | 読み書きできる |
| `rw-file` | ディレクトリ以外（通常ファイル、ソケット、FIFO） | その場での書き込みができる。一時ファイルを作ってからの置き換え（rename）は失敗する |
| `ro` | ディレクトリまたはファイル | 読み取り専用 |
| `hide` | ディレクトリまたはファイル | ディレクトリは空のディレクトリで、書けるが内容は終了時に消える。ファイルは空の読み取り専用ファイル |

`rw` にディレクトリ以外を指定したら、種類 `path` の診断で終わり、`rw-file` を案内する。`rw-file` に
ディレクトリを指定した場合も種類 `path` の診断で終わる。

隔離の中のファイルシステム全体は、ポリシーに書かれていない範囲を読み取り専用で見せる。`/dev` と
`/proc` は隔離用のものを用意する。読み取り専用で見えている範囲にあるホストの UNIX ソケットには
接続できる。それを止めるには `hide` を使う。

### 6.2 実体への解決と存在しないパス

すべての指令は、シンボリックリンクを解決した実体のパスにマウントする。実体が存在しない項目は
飛ばす。飛ばした項目は計画に「飛ばした」と理由付きで表示する。起動のたびの警告は出さない。

存在しないパスにマウントしない理由: bwrap はマウント先を作ろうとし、書ける領域では 0 バイトの
実ファイルがホストに残る（2026-09-03 に実測）。帰結として、起動後に現れたファイルは隠れない。
これは README に既知の隙間として書く。

### 6.3 生成される項目

ポリシーに書かれた項目に加えて、次の項目が生成の段に置かれる。

- 走査（`mounts.scan`）: `root` 以下を探索し、`names` のいずれかに一致する名前のエントリのうち、
  ディレクトリと、解決先がディレクトリのシンボリックリンクを除いたものを `hide` にする。`exclude` に
  一致する名前は対象外。読み込んだポリシーファイルは対象外。`prune` に一致する名前のディレクトリは
  中に入らない。シンボリックリンクのディレクトリには入らない。一致したエントリがシンボリックリンク
  なら、第 6.2 節のとおり解決先を隠す。ただし、その解決先が、書かれた段に第 5.4 節の置き換えを適用した
  後に残っている `ro` の項目の実体と同一かその中（子孫）なら、隠さない。その `ro` の解決が書き込める
  項目の中を参照しない（隔離の中から差し替えられない）なら、隠さずに計画に理由付きで表示して起動を
  続ける。参照する（差し替えられうる）なら、種類 `path` の診断で終わる。この判定の書き込める項目は、
  走査の `root` の検査と同じく、書かれた段だけに第 5.4 節の置き換えを適用した集合で見る。該当する
  リンクが複数あれば、リンクのパスのバイト順で最初のものを名指す（走査の探索順に依らない）。説明はそのリンクのパス、
  `ro` の項目のパス、理由を含む。隔離の中で `.env` の名前のリンクを張って、読み取り専用にした自分の
  設定や指示を次の起動で空にする経路（2026-09-06 に実測）と、`ro` のリンクを向け直して走査が隠すべき
  ファイルの隠しを外す経路の両方を、診断で見える形で塞ぐためである。解決先がディレクトリのリンクは
  元から対象外。`names`、`exclude`、`prune` はシェルのワイルドカード
  （`*`、`?`。意味は第 5.3 節）を使える。走査で隠したファイルが git に追跡されていると、隔離の中の
  git には空になった変更として見える。
- マウント種別による隠蔽（`mounts.hide-mounts`）: `under` 以下にあるマウントのうち、ファイル
  システム種別が `fstype` のいずれかであるものを、そのマウント先ごとに `hide` にする。マウント先が
  ワークスペース、ワークツリー、`${git_common_dir}` の実体と同一なら生成しない。利用者が選んだ
  作業場所そのものを隠さないためである。マウント一覧（第 14 節）は `hide-mounts` が 1 つでも書かれて
  いるときだけ読み、読めなければ種類 `path` の診断で終わる。隠すべきマウントを隠さずに起動しない
  ためである（別のサンドボックスの中など `/proc` が制限された環境からの起動で起きうる）。
- 秘密ファイル: `secrets` に書かれたファイルのうち存在するものを `hide` にする（第 9 節）。
- 設定ディレクトリの `secrets/`: 存在すれば `hide` にする。参照されていない秘密ファイルを隔離の中から
  読めなくするため。

生成された項目には第 5.4 節の同一性判定を同じように適用し、生成された項目は書かれた項目を置き換える。
生成された項目同士が同じパスを指したときは、同じ指令なら 1 つにまとめる。生成される指令は `hide`
だけなので、違う指令の衝突は起きない。第 5.6 節、第 6.1 節、第 6.5 節の検査は、生成の段を適用した
後の項目の集合に対して行う。例外は走査の `root` と `hide-mounts` の `under` の根の項目の検査
（第 5.6 節。生成の前に行う）と、走査で一致したリンクの先の `ro` が差し替えられうるかの判定（上。
走査の最中に行う）で、どちらも書かれた段だけに第 5.4 節の置き換えを適用した集合で見る。生成の
4 つは、走査、`hide-mounts`、秘密ファイル、`secrets/` の順に行う。

### 6.4 順序

同一性判定を終えた項目を、実体のパスで、祖先が先、子孫が後の順にマウントする。互いに祖先でも
子孫でもないパス同士は、実体のパスのバイト順に並べる。この規則により、狭いパスの指令が広いパスの
指令に勝ち、同じ入力からは同じ順序が得られる。

| 場面 | 結果 |
|---|---|
| `/mnt/c` を `hide`、その中のワークツリーを `rw` | ワークツリーは読み書きできる |
| `~/.codex` を `rw`、`~/.codex/AGENTS.md` を `ro` | `AGENTS.md` は読み取り専用 |
| ワークツリーを `rw`、走査で見つけた `.env` を `hide` | `.env` は空 |
| `/tmp` を `hide`、`/tmp/process-wrap` を `rw` | `/tmp` は空で、`/tmp/process-wrap` だけがホストと共有される |
| `~/.cache` を `rw`、`~/.cache/x/.env` を走査で `hide` | `.env` は空 |

### 6.5 作業場所への警告と危険な広さの拒否

合成と飛ばしを終えた項目のうち、ワークスペースかワークツリーかそれらの祖先を指す `rw` が 1 つも
無いとき、`process-wrap: warning:` で始まる 1 行を標準エラーに出す。起動は止めない。

ワークツリーまたはワークスペースの実体が、`/`、ホームディレクトリ、ホームディレクトリの祖先の
いずれかであるとき、種類 `path` の診断で終わる。git 管理外のホームディレクトリで `--workspace` を
省略して起動すると、この規則に当たる。

カレントディレクトリの実体について、第 6.4 節の順序でそれを含む項目のうち最後に適用されるものが
`hide` であるとき、種類 `path` の診断で終わる。bwrap がそこへ移れないためである。`hide` の中に
`rw` で再露出したディレクトリは、この規則に当たらない。カレントディレクトリそのものが取得できない
（消されている、辿れない）ときも、種類 `path` の診断で終わる。第 14 節の `--chdir` に渡す値が
無いためである。

ワークツリーの `.git` を隔離の中から消すと、次回の起動でワークツリーの導出が祖先のリポジトリに
変わりうる。ホームとその祖先は上の規則で止まるが、それより下の祖先は止まらない。これは README に
既知の隙間として書く。

成功の観測条件: 第 6.4 節の表の 5 場面が、計画の表示と隔離の中からの読み書きの両方で表のとおりに
なり、ホームディレクトリをワークツリーとする起動と、`hide` の中を作業ディレクトリとする起動と、消された
ディレクトリからの起動が終了コード 125 で終わる。反例: 設定ディレクトリの `secrets/` の `hide` より後に祖先のマウントが来て、
本物の秘密ファイルが隔離の中から読める。

## 7. ネットワーク

`network.mode` は `host` か `none`。`host` はホストのネットワークをそのまま使う。`none` は
ネットワーク名前空間を切り、ループバックだけが残る。

ドメイン単位の許可は作らない（第 18 節）。`none` にしたうえで、外で動かすプロキシの UNIX ソケットを
`rw-file` で通し、`env.set` でプロキシの環境変数を指す構成は、0.1 の部品で組める。組めることは
未検証で、この仕様はそれを保証しない。

成功の観測条件: `none` で起動した隔離の中から外部アドレスへの接続が経路なしで失敗し、`host` では
ホストと同じに振る舞う。反例: `none` でホストのインターフェースが見える。

## 8. 環境変数

`process-wrap` は隔離の中の環境の最終形を自分で組み立て、bwrap にそのまま引き継がせる。環境変数の
値を bwrap の引数に載せない。引数はプロセス一覧から他のプロセスに見えるためである。マウントする
パスと秘密ファイルのパスは引数に載る。パスが見えることは許容する。隔離の中のプロセスの環境は、
ホスト側からは `/proc` を通して読める。ホストは信頼する側なので、これも許容する。

組み立ての順序は次のとおり。

1. `env.mode` が `inherit` ならホストの環境から始める。`clear` なら空から始め、`env.pass` に
   列挙した変数だけをホストから写す。
2. `env.unset` に一致する変数を消す。
3. `env.set` の変数を入れる。
4. 秘密（第 9 節）を入れる。
5. git の書き換え（第 10 節）を入れる。
6. `PATH` の先頭に `env.path-prepend` を足す。項目は実体のパスで足し、実体が存在しない項目は
   飛ばして計画に理由付きで表示する。この時点で `PATH` が無ければ `path-prepend` だけが
   `PATH` になる。`path-prepend` も空なら `PATH` は無いままで、警告は出さない。
7. `PROCESS_WRAP=1` を入れる。

成功の観測条件: `--print-plan` が最終の環境を表示し、bwrap の引数列に環境変数を設定する引数が
含まれない。反例: 秘密の値が bwrap の引数列に現れる。

## 9. 認証情報

`secrets` は環境変数名をキー、ファイルパスを値とするテーブルである。項目は環境変数名のバイト順に
処理し、各項目は次の 2 段階で動く。

1. その名前の環境変数を、由来にかかわらず消す。
2. ファイルが存在すれば、その内容を値として環境変数を入れ、そのファイルを `hide` にする。

値はファイルの内容から末尾の改行を 1 つだけ取り除いたもの。改行は LF 1 バイト、または CR LF の
2 バイトのどちらかで、どちらも 1 つの改行として取り除く（Windows 側のエディタで書いたファイルの
末尾の CR を値に残さないため）。取り除いた後が 0 バイトのとき、ファイルが
読めないとき、NUL バイトを含むとき、値が 64 KiB を超えるときは、種類 `secret` の診断で終わる。上限は
Linux が環境変数 1 個に許す長さ（128 KiB、名前と終端を含む）の半分で、第 14 節の読み込みの上限より
先に効く。

ファイルが存在しなければ環境変数を入れず、`process-wrap: warning:` で始まる 1 行を標準エラーに出して
起動を続ける。

秘密の値は、計画の表示、警告、診断のどこにも出さない。表示するのは環境変数名とファイルパスだけで、
値は伏せる。

ホストの環境にある認証情報は、`inherit` ではそのまま隔離に入る。名前で落とすのは `env.unset` の
ワイルドカードの役目で、名前が規則に合わないものは残る。これは README に既知の隙間として書く。

成功の観測条件: ファイルがあるとき隔離の中でその環境変数が読め、ファイル自体は空として見え、
ファイルが無いときホストの同名変数も隔離の中に存在しない。反例: ファイルが無いときホストの
`GH_TOKEN` が隔離の中に残る。200 KiB の秘密ファイルが検査を通り、bwrap の exec で失敗する。

## 10. git の URL 書き換え

`git.instead-of` は元の URL の先頭をキー、置き換え先を値とするテーブルである。項目が 1 つでもあれば、
各項目についてキーのバイト順に、git が設定ファイルの代わりに読む環境変数の組（`GIT_CONFIG_KEY_n`、
`GIT_CONFIG_VALUE_n`、`GIT_CONFIG_COUNT`）を追加する。番号は、第 8 節の 4 段階目までを終えた環境に
ある `GIT_CONFIG_COUNT` の続きから始め、その環境に無ければ 0 から始める。その環境が既に持つ組は
保持する。項目があり、`GIT_CONFIG_COUNT` があって数値でない（空、符号付き、空白を含む、桁が
多すぎるものを含む。git 自身は空を 0 と読むが、ホストが壊れた値を渡している状況なので止める）か、
数値でも項目の数を足すと番号が扱える上限を超えるなら、種類 `env` の診断で終わる。項目が
無ければ検査しない。

既存の環境変数の値を読んで別の変数の値を決める処理は、`process-wrap` の中でこれと `PATH` の先頭追加
だけである。

成功の観測条件: 隔離の中で `git config --list` にキー `url.<置き換え先>.insteadof` が値
`<元の先頭>` で現れ、ホストで設定していた組も残っている。反例: ホストの `GIT_CONFIG_*` が上書きで
消える。

## 11. 端末の保護

隔離の中のプロセスが制御端末にキー入力を注入する `ioctl`、`TIOCSTI` を seccomp フィルタで塞ぐ。
フィルタは bwrap の `--seccomp` で渡す。

フィルタの規則は次の 3 つだけである。

- 呼び出しのアーキテクチャが x86_64 でないシステムコールは、そのプロセス全体（全スレッド）を
  終了させる。
- システムコール番号に x32 のビット（`0x40000000`）が立っているシステムコールも、そのプロセス全体を
  終了させる。これら 2 つによって 32 ビットと x32 のバイナリは隔離の中で動かない。
- `ioctl` のうち、第 2 引数の下位 32 ビットが `TIOCSTI` に等しいものは `EPERM` で失敗させる。比較を
  下位 32 ビットで行うのは、カーネルが第 2 引数を 32 ビットとして受け取るためで、上位ビットを立てた
  呼び出しを素通しにしないためである。

これ以外のシステムコールは通す。塞ぐのは `TIOCSTI` だけである。仮想コンソール向けの別の注入経路
（`TIOCLINUX`）、端末への書き込みと端末の応答を使った注入、ディスプレイサーバのソケットを通した
入力の合成は対象外で、README に既知の隙間として書く。最後の 1 つは同梱プロファイルの `hide` と
`unset` で経路を消す。

bwrap の `--new-session` は使わない。制御端末との関係を切ると対話的なプログラムの挙動が変わりうる
ためである。

成功の観測条件: 隔離の中で `TIOCSTI` を呼ぶと `EPERM` で失敗し、上位ビットを立てた要求番号でも
`EPERM` で失敗し、x32 のビットを立てた番号でシステムコールを呼ぶとプロセスが終了し、フィルタの
先頭がアーキテクチャの検査であることがフィルタのバイト列の検査で確かめられ、隔離の中の対話的な
プログラムが制御端末を持ち続ける。反例: フィルタが `TIOCSTI` 以外の `ioctl` を拒否して端末のサイズ
取得が失敗する。

## 12. 入れ子と並列

### 12.1 入れ子

入れ子のとき、`--print-plan` を除き、`process-wrap` はポリシーを読まず、bwrap を起動せず、環境を
変えず、`process-wrap: warning:` で始まる 1 行で内側のプロファイルが適用されないことを標準エラーに
出してから、コマンドをそのまま exec する。コマンドの解決（第 4.2 節）は入れ子でも行い、見つから
なければ種類 `command not found` の診断で終了コード 127 で終わり、見つかったが exec に失敗すれば
種類 `command not executable` の診断で終了コード 126 で終わる。exec の argv[0] は `COMMAND` に
与えた文字列である。解決には、`--print-plan` の有無にかかわらず、`process-wrap` が受け取ったホストの
`PATH` を使う。`--print-plan` の無い入れ子ではポリシーを読まないので第 8 節の `PATH` が無く、
`--print-plan` のある入れ子でも実際に exec されるとすればホストの環境だからである。`PATH` が無ければ
探さない。カレントディレクトリとホームディレクトリの検査は行わない（第 13 節の順序）。

`--print-plan` は入れ子でもポリシーを読んで計画を表示し、計画の先頭に入れ子であることを示す。
表示する計画の `PATH` は隔離の中のものだが、解決したコマンドの欄はホストの `PATH` で解決した結果で
ある。

検出は環境変数だけに頼る。この設計には 2 方向の隙間がある。

- 隔離の中で環境を空にしてから `process-wrap` を起動すると検出が外れ、隔離の中に二重の隔離を
  作ろうとする。二重の隔離は外側より広がらない。秘密ファイルが外側で空にされているため、秘密を持つ
  ポリシーでは種類 `secret` の診断で起動できない。
- ホスト側で `PROCESS_WRAP=1` を設定してから起動すると、隔離なしでコマンドが動く。その起動では
  必ず入れ子の警告が出るので、意図しない場合は標準エラーで気づける。

どちらも 0.1 では塞がず、README に書く。

### 12.2 並列

`process-wrap` は永続状態を持たない（第 14 節）。同時に起動した複数の `process-wrap` は互いに干渉しない。

成功の観測条件: 隔離の中から `process-wrap` を起動すると警告 1 行が出てコマンドが外側の境界で動き、
入れ子でない `process-wrap` を 2 つ同時に起動しても両方が第 1 節の結果を満たす。反例: 入れ子で
bwrap が二重に起動する。

## 13. 出力と終了コードの契約

診断は標準エラーに 1 行、`process-wrap: <種類>: <説明>` の形で出す。種類は契約であり、説明は
自由文である。警告は `process-wrap: warning: <説明>`。警告は下の表のどの行にも先行して出うる。

`process-wrap` 自身が書く文字列（診断、警告、計画の表示、使い方、版）に埋め込む値（パス、キー名、
変数名、コマンドライン引数）は、改行（LF、CR）とその他の制御文字（0x00〜0x1F、0x7F）を含んで
いれば、見える表記に逃がして出す。診断と警告はこの規則で末尾の改行 1 つを除いて改行を含まず、
1 行になる。計画の表示と使い方は複数行でよく、行の構造は第 20 節の整形の委譲に含まれる。Unicode の
行区切り（U+2028、U+2029、U+0085）は制御文字に数えない。包んだコマンドの出力は対象外。見える
表記の形と、UTF-8 として不正なバイト列の表し方は第 20 節で委譲する。

| 種類 | 状況 |
|---|---|
| `usage` | コマンドラインの誤り。未知のオプション、`COMMAND` の欠落、文法の誤り、`--profile` の名前が第 4.1 節の制約に反する、`--help` または `--version` と他の引数の併用、`--rw` と `--hide` 以外のオプションの繰り返し、コマンドラインの中での同じパスへの違う指令 |
| `policy` | ポリシーファイルの読み込みと合成の失敗。プロファイルまたは `--policy-file` の不在、TOML の解析失敗、未知の固定キー、必須キーの欠落または空、相対パス、`~ユーザー名`、未知の変数、同じ段での同じパスへの違う指令、`inherit` での `pass`、`env.set` と `secrets` の同じキー、ポリシーファイルが通常ファイルでないか第 14 節の上限を超える |
| `path` | ワークスペースが存在しないかディレクトリでない、カレントディレクトリが取得できない、設定ディレクトリの実体のパスを得られない、`rw` にディレクトリ以外、`rw-file` にディレクトリ、ワークツリーまたはワークスペースが `/`・ホーム・ホームの祖先、`rw` または `rw-file` が `/`・ホーム・ホームの祖先、`${git_common_dir}` の相互リンクの不成立（`.git` と G の下のファイルが通常ファイルでないか上限を超える場合を含む）、保護対象のパス（ポリシーファイル・設定ディレクトリ・秘密ファイル・`path-prepend`）自身が書き込める項目の中にあるか、その解決が書き込める項目の中を参照する、書かれた `rw`・`rw-file`・`hide` の項目、`--workspace`、走査の `root`、`hide-mounts` の `under` の解決が書き込める項目の中を参照して実体が根の項目の外、書かれた `hide` の項目の解決が書き込める項目の中のリンクを辿る、走査の `root` または `hide-mounts` の `under` の解決が書き込める項目の中を参照して実体が書き込める項目のマウント点でない、書き込める項目の中を参照して解決される項目が `hide`・`ro` と露出する組になる（下の段の項目と同一か、生成の段を含め段を問わず祖先に効いている）、どの指令の項目でも実体が `/` と同一か `/dev`・`/proc` と同一かその中、リンクを辿って解決される明示の `--workspace` の実体がワークスペース由来でない根の項目の外、`hide` の中のカレントディレクトリ、`hide-mounts` が書かれていてマウント一覧が読めない、走査で一致したリンクの解決先が差し替えられうる `ro` の項目の中（第 6.3 節） |
| `secret` | 秘密ファイルが空、読めない、NUL バイトを含む、通常ファイルでない、第 9 節の値の上限を超える |
| `env` | `HOME` が第 2 節「ホームディレクトリ」の条件に反する、`GIT_CONFIG_COUNT` が数値でない（空を含む）か項目を足すと上限を超える |
| `bwrap` | `bwrap` がホストの `PATH` に無い、`bwrap` に渡すファイル記述子を用意できない（第 14 節）、`bwrap` の exec 自体に失敗した |
| `command not found` | コマンドが見つからない。説明はコマンド名 |
| `command not executable` | 入れ子で、見つかったコマンドの exec に失敗した。説明はそのパスとエラー |

| 状況 | 標準出力 | 標準エラー | 終了コード |
|---|---|---|---|
| `command not found`・`command not executable` 以外の診断 | 無し | 診断 1 行 | 125 |
| `command not found` | 無し | 診断 1 行 | 127 |
| `command not executable`（入れ子のみ） | 無し | 診断 1 行 | 126 |
| bwrap 自身の失敗（マウントの失敗、コマンドの exec の失敗） | 無し | bwrap の出力 | bwrap の終了コードをそのまま |
| コマンドが終了コード n で終了 | コマンドのもの | 警告があれば + コマンドのもの | n |
| コマンドがシグナル s で終了 | コマンドのもの | 警告があれば + コマンドのもの | 128 + s |
| `--print-plan`、診断なし（入れ子を含む） | 計画 | 警告があれば | 0 |
| `--print-plan`、診断あり | 無し | 診断 1 行 | 上の診断の行と同じ |
| `--version`、`--help` | 版または使い方 | 無し | 0 |
| 入れ子（`--print-plan` なし） | コマンドのもの | 警告 1 行 + コマンドのもの | コマンドのもの。コマンドが見つからなければ 127、見つかったが exec できなければ 126 |

`--print-plan` は bwrap の起動の直前までのすべての処理（ポリシーの読み込み、事実の収集、秘密の
読み込み、`bwrap` の所在確認、コマンドの解決）を行い、診断が出る状況では計画を表示せずその診断で
終わる。

検査は次の順で行い、最初に当たった診断で終わる。複数の診断が同時に成り立つ入力でも、出る診断は
この順で決まる。段階は検査を行う時点を定めるもので、診断の種類は段階と独立である。

1. `--help` と `--version` の形（終了コード 0。カレントディレクトリを必要としない）
2. 文法（第 4.1 節の規則。`usage`。パスの同一性は含まない）。この後、入れ子（第 12.1 節）で
   `--print-plan` が無ければ、段階 3〜8 を飛ばし、入れ子の警告を出して段階 9 へ進む
3. カレントディレクトリの取得（`path`）
4. ホームディレクトリ（第 2 節。`env`）
5. ポリシーファイルの読み込みと合成（`policy`）
6. ワークスペースと変数の導出（第 5.2 節。`path`）
7. マウントの解決。この中は、第 5.4 節の同一性（同じ段の中は `policy`、コマンドラインの中は
   `usage`。展開と実体化の後でしか判定できないためここに置く）、走査の `root` と `hide-mounts` の
   `under` の根の項目の検査（`path`。生成の前。`root` が先、`under` が次）、第 6.3 節の生成（走査で
   一致したリンクの先が差し替えられうる `ro` の中なら `path`、マウント一覧が読めなければ `path`）、
   第 6.1 節と第 6.2 節の種類の検査（`rw` にディレクトリ以外など。`path`）、第 5.6 節の
   保護対象のパスの検査と根の項目の検査と露出する組の検査と固定部分への着地の拒否と広さの拒否
   （`path`）、第 6.5 節の位置とカレントディレクトリの拒否（`path`）、第 9 節の秘密の読み込み
   （`secret`）、第 8 節の `GIT_CONFIG_COUNT`（`env`）の順
8. `bwrap` の所在（`bwrap`）
9. コマンドの解決（`command not found`。入れ子でも効き、見つからなければ終了コード 127）
10. 起動。通常は記述子の用意（失敗は `bwrap`、125）と bwrap の exec（失敗は `bwrap`、125）。入れ子は
    コマンドの exec（失敗は `command not executable`、126）

1 つの検査の中で複数の項目が診断になるときは、マウント項目は第 6.4 節の順序、環境変数と秘密は名前の
バイト順で最初のものを出す。第 5.6 節の保護対象のパスの検査では、プロファイル、`--policy-file`、設定ディレクトリ、秘密
ファイル（名前のバイト順）、`path-prepend`（合成後の並び順）の順で最初のものを出す。走査の `root` と
`hide-mounts` の `under` の根の項目の検査は段階 7 の中で生成の前に行うので、その診断は書かれた
項目の検査より先に出る。書かれた項目の根の項目の検査と露出する組の検査では書かれた項目を第 6.4 節の
順序で、次に `--workspace` を見る（項目をまたいで 2 つの検査をどう交互に行うかは第 20 節で委譲する。
最初に出る診断だけが変わる）。

`process-wrap` は bwrap を子プロセスとして待つのではなく exec する。bwrap の失敗がそのまま
呼び出し元に見えるのはこのためである。bwrap 自身の exec に失敗したとき（見つけた後に消された、
実行できない）は、まだ `process-wrap` が動いているので種類 `bwrap` の診断になる。包んだコマンドの
exec 失敗は、通常の起動では bwrap の失敗としてそのまま返り、入れ子では `command not executable` に
なる。この非対称は許容する（第 4.2 節）。

計画の表示形式は 0.1 の契約ではない。人が読むための出力で、内容は合成後のポリシー、使ったポリシー
ファイルの実体のパス、4 変数の値、各マウント項目の適用か飛ばしかとその理由、最終の環境（秘密の値は伏せる）、
解決したコマンドのパス、bwrap の引数列を含む。

成功の観測条件: 上の 2 つの表のすべての行が第 15 節のテストで観測され、隣り合う段階の診断が同時に
成り立つ入力では先の段階の種類が出て、改行や ESC を含むプロファイル名やキー名を与えても標準エラーが
1 行のままである。反例: ポリシーの誤りが終了コード 1 で終わり、
コマンドの失敗と区別がつかない。キー名に含めた ESC がそのまま端末に届く。

## 14. 実行時の境界

`process-wrap` は永続状態を持たず、ファイルを書かない。読むのは、ポリシーファイル、秘密ファイル、
`.git` とその中の `gitdir:`、`commondir`、`worktrees/*/gitdir`、C の直下の `HEAD` の存在と種類、マウント一覧、走査で辿るディレクトリ、
各候補パスの存在と種類と実体、第 5.6 節で解決するパスが参照するものを得るための、通るディレクトリとシンボリック
リンクの先、サブモジュールの `config` である。`bwrap` 以外の外部コマンドを
実行しない。`bwrap` はホストの `PATH` から探し、無ければ種類 `bwrap` の診断で終わる。`hide` の
空ファイルと seccomp フィルタは、実行時にファイル記述子で bwrap に渡す。記述子を作る前に、開ける
ファイル数の soft 上限を hard 上限まで上げる。常に上げるので、包んだコマンドは上げた後の soft 上限を
引き継ぐ（同じ入力から同じ結果を保つため、必要なときだけ上げることはしない）。入れ子は記述子を
作らないので上げない。それでも記述子を用意できなければ種類 `bwrap` の診断で終わる。`hide` のファイルが
数千あるモノレポで、既定の soft 上限が 1024 の環境で止まらないためである。

ファイルの読み方: ポリシーファイル、秘密ファイル、`.git` と G の下のファイルは、通常ファイルだけを
読む。待たずに開き（FIFO で止まらない）、開いた記述子で通常ファイルであることを確かめる。読む長さは
1 ファイルあたり 1 MiB を上限とし、超えるものは通常ファイルでないものと同じ扱いにする（秘密ファイルは
第 9 節の値の上限 64 KiB がこれより先に効く）。違反したときの
診断の種類は、ポリシーファイルなら `policy`、秘密ファイルなら `secret`、`.git` 関連なら `path`。
ポリシーファイルと秘密ファイルはシンボリックリンクを辿る（利用者が dotfiles へのリンクで置くため。
辿った先は、どちらも第 5.6 節の保護対象のパスの検査が実体で見る）。`.git` と G の下のファイルは、開くファイル自身がリンクなら辿らない（第 5.2 節）。
マウント一覧と走査で辿るディレクトリはこの規則の対象外。第 5.6 節の解決では、シンボリックリンクを
カーネルと同じ 40 本まで辿る。超えたら存在しない成分と同じ扱いにする。保護対象のパスではそこまでに
参照したものを検査し、書かれた項目は実体を持たない項目として飛ばし、`--workspace` は第 5.2 節の規則で
種類 `path` の診断になる。

`process-wrap` は自分が起動された環境（`HOME`、`XDG_CONFIG_HOME`、`PATH`、`PROCESS_WRAP`、カレント
ディレクトリ）を信頼する。それらをホスト側で操作されると、読むプロファイルや入れ子の判定、作業場所が
変わる。これは README に書く。

bwrap で実現できない機能は作らない。cgroup による資源制限、ドメイン単位の通信許可はこれに当たる。

bwrap に渡す引数は、この順で固定の部分から始まる。`--ro-bind / /`、`--dev /dev`、`--proc /proc`、
`--unshare-all`、`network.mode` が `host` のときの `--share-net`、`--die-with-parent`、
`--chdir <カレントディレクトリ>`、`--seccomp <ファイル記述子>`、`--argv0 <COMMAND に与えた文字列>`。
その後に第 6.4 節の順序でマウント項目が続き、最後に `--` を 1 つ置き、その後ろに解決したコマンドの
パスと `ARGS` が続く。`--` が無いと `-` で始まる相対パスの `COMMAND` を bwrap がオプションとして
読む。`--print-plan` で `COMMAND` を省略した形では、`--argv0` とその値、末尾の `--` とその後ろは無く、
計画の引数列にも含めない。固定の部分はポリシーで変えられない。計画ではファイル記述子の位置を記号で
表し、番号は起動の直前に割り当てる。

成功の観測条件: `process-wrap` 自身の起動によってファイルシステムが変わらず、振る舞いが引数と
ポリシーと環境とファイルシステムの状態だけで決まり、FIFO を `--policy-file` に指定しても診断で
終わり、1 MiB を 1 バイト超えるポリシーファイルが `policy` で終わり、`G/commondir` をシンボリック
リンクにすると `path` で終わり、soft 上限を 1024 にした環境で `hide` のファイルが 1100 ある走査の
起動が終了コード 0 で終わり、隔離の中の soft 上限が hard 上限に等しい。反例: 前回の起動結果を保存して
次回の振る舞いが変わる。FIFO を指定すると起動が止まる。

## 15. 検証の契約

### 15.1 純粋な関数の境界

計画の算出は、合成前のポリシー各段、コマンドラインの引数、ホストの環境、収集した事実だけから決まる
純粋な関数として実装する。収集した事実とは、各候補パスの存在と種類と実体、マウント一覧、走査の
結果、ワークツリーと `.git` の相互リンクの内容、秘密ファイルの内容、第 5.6 節で解決するパスが
参照するもの（通るディレクトリと、辿るシンボリックリンクの置き場と先）、マウント一覧が読めなかった
こと、カレントディレクトリである。
事実の収集、ファイル記述子の割り当て、bwrap の起動はこの関数の外に置く。

この関数のテストは、合成した事実を入力に与え、期待する計画（記号付きの bwrap 引数列、環境、各項目の
適用結果、解決したコマンド）を比較する。テストは次を含む。

- 第 5.2 節の `${git_common_dir}` の相互リンク（成立と不成立。C に `HEAD` が無い形を含む）、
  第 5.3 節の 3 種類の合成規則と `path-prepend` の向きとワイルドカードの意味、第 5.4 節の同一性
  （存在しないパスの展開後の文字列を含む）。
- 第 5.6 節の保護対象の 3 つの検査（秘密ファイルを含む）。
- 第 5.6 節の根の項目の検査。対象は `rw`・`rw-file`・`hide` の項目、`--workspace`、走査の `root`、
  `hide-mounts` の `under`（生成の前の集合で判定し、診断が先に出ること）。入れ子の項目、`..` で通り
  抜けるリンク先、ワークスペース変数の引き継ぎ（走査の `root` を含む）、カレントディレクトリと同一の
  `--workspace` の除外、リンクを辿る明示の `--workspace`、書き込める項目の中のリンクを辿る `hide` の
  拒否（着地が `rw` の外と根の項目の中の両方）と実体のパスで書いた `rw` の中の `hide` の許容、`rw` の
  下位を起点にする走査の `root` の拒否と `rw` のマウント点を起点にする `root` の許容を含む。
  対象外の確認として、`ro` のリンクをどの項目でもない場所へ向けた形が通ること。
- 第 5.6 節の露出する組の検査。拒否は、下の段と同一、段を問わない祖先、生成された `hide` の中への
  着地。許容は、`hide` の再指定、間の段の `rw` の遮り、別の根の項目への着地。
- 第 5.6 節の固定部分への着地の拒否（`/`、`/dev`、`/proc`）と広さの拒否。
- 第 6.3 節の生成の段と走査（シンボリックリンクとポリシーファイルの除外、差し替えられない `ro` の
  項目の中を指すリンクを隠さないこと、差し替えられうる `ro` の項目の中を指すリンクからの `path` を
  含む）と `hide-mounts`（作業場所の除外と、マウント一覧が読めない事実からの `path` を含む）と
  `secrets/`、第 6.4 節の表の 5 場面と兄弟の順序、変数展開と相対パスの拒否、
  第 6.5 節の警告と 2 種類の拒否（再露出したカレントディレクトリの許容を含む）。
- 第 8 節の 7 段階と `unset` のワイルドカードと `path-prepend` の実体化と飛ばし、第 9 節の 2 段階と
  改行の扱い（LF と CR LF）と不在の警告と値の上限、第 13 節の制御文字の逃がし、第 10 節の番号
  （空の `GIT_CONFIG_COUNT` を含む）、第 4.2 節のコマンド解決、第 14 節の引数列（`--argv0` と `--`）。

### 15.2 ビルド済みバイナリのテスト

x86_64 の Linux で実際の bwrap を使って、ビルド済みのバイナリを起動して確認する。対象は第 13 節の
2 つの表のすべての行と検査の順序（隣り合う段階の診断が同時に成り立つ入力）、第 14 節の読み方
（FIFO、上限超過）と記述子の上限（soft 上限 1024 での 1100 件の走査）、第 6.4 節の表の 5 場面を
隔離の中から読み書きして確認すること、第 7 節の `none`、第 9 節の隔離の中からの観測、第 11 節の
`EPERM`（上位ビットを立てた呼び出しを含む）と x32 のビットを立てた呼び出しによる終了、第 12.1 節の
警告と `command not executable`、第 1 節の argv[0]（隔離の中と入れ子）。テストはネットワークへの
接続を必要としない。

### 15.3 移行の確認

現行の codex 用 jail（bash スクリプト）からの移行時に 1 回だけ、利用者の実機で、現行 jail が bwrap に
渡す引数列と `--print-plan` の出力を並べ、マウントの集合が同じであることを人が確認する。この確認は
テストとして残さない。現行のスクリプトは製品の一部ではないためである。

成功の観測条件: 第 15.1 節と第 15.2 節のテストがネットワークに依存せずに通る。反例: 純粋な関数だけを
テストして、ビルド済みのバイナリを一度も起動しない。

## 16. 公開ドキュメント

README（英語）に、目的、インストール、ポリシーファイルの書き方、コマンドラインの使い方、既知の隙間を
載せる。既知の隙間は次の 15 である。

1. `hide` したディレクトリの中のコマンドが「見つかった」と判定される（第 4.2 節）。
2. 起動後に現れたファイルは隠れない（第 6.2 節）。
3. 走査で隠したファイルが git に追跡されていると、隔離の中で空の変更として見える（第 6.3 節）。
4. bind mount やハードリンクによる別経路は隠せない。`hide` は指定した実体のパスにだけ効く。
5. マウントするパスと秘密ファイルのパスは bwrap の引数に載り、秘密の値は `/proc` を通してホストから
   読める（第 8 節）。
6. 名前が規則に合わないホストの認証情報の環境変数は `inherit` で隔離に入る（第 9 節）。
7. `TIOCLINUX`、端末の応答を使った注入、ディスプレイサーバ経由の入力合成は seccomp で塞がない
   （第 11 節）。同梱プロファイルは経路を `hide` と `unset` で消す。
8. 環境を空にした入れ子と、ホスト側で `PROCESS_WRAP=1` を立てた起動（第 12.1 節）。
9. `process-wrap` は起動された環境を信頼する（第 14 節）。カレントディレクトリも含む: `rw` の中を通る
   パスで `cd` し直してから起動すると、隔離の中で差し替えたリンクの先が作業場所になる。
10. `rw` で渡した領域は、利用者がホスト側で後から実行するものの置き場になりうる。`.git/hooks` と
    `.git/config` は利用者の `git` 操作で自動的に読まれる。隔離の設計では防げず、利用者が差分を
    見るしかない。
11. 32 ビットと x32 のバイナリは動かない（第 11 節）。
12. ワークツリーの `.git` を消すと、次回の起動でワークツリーの導出が祖先のリポジトリに変わりうる
    （第 6.5 節）。
13. `git init --separate-git-dir` で作ったメインのワークツリー（`.git` が通常ファイルで、指す先に
    `commondir` も `core.worktree` も無い）は、第 5.2 節の相互リンクのどちらの形にも当たらず `path` で
    止まる。
14. 第 5.6 節の根の項目の検査は今回の起動の書き込める項目を基準にする。ワークツリーの下位を字面で書いた
    項目（例: `rw = ["${worktree}", "~/work/a/b"]`）は、ワークツリーが `~/work` の起動の隔離の中で
    `~/work/a` をリンクに差し替えられ、次にワークツリーが別の場所になる起動ではその差し替えが見えず、
    リンクの先に `rw` が付く。項目のパス自身がリンクに差し替えられる形（`~/work/a/b` を差し替え、
    次の起動で `--workspace ~/work/a/b/inner` を別の場所から与える）も同じ。同じワークツリーから
    起動すれば止まる。閉じるには前回の起動の書き込める項目を覚える必要があり、第 14 節に反するので
    受け入れる。ワークツリーの下位は変数で書く。
15. `rw` の中にある `ro` と `hide` の項目の守りは完全ではない。リンクで書いた `ro` が守るのはリンク先の
    実体だけで、隔離の中でリンクを消して同じ名前の通常ファイルを置けば、同じ起動の中で読む側のパスの
    内容を変えられる（一時ファイルと rename で保存するエディタもリンクを置き換える）。リンク先が
    書き込める項目の外なら、そこは元から読み取り専用で、`ro` の項目は何も足していない。次の起動では
    リンクの差し替えで別の場所が読み取り専用になるか、削除で読み取り専用が外れる（新しく見えるもの
    は第 5.6 節の露出する組の検査が止める。リンクで書いた `hide` は根の項目の検査が 1 回目から止める）。
    リンクでなくても、祖先ディレクトリの改名と同じパスへの別ファイルの配置で、次の起動が読む内容を
    変えられる（第 5.6 節）。`ro` で守れるのは、エージェントが読む実体の内容が意図せず書き換わらない
    ことまでで、エージェントが別の内容を読むように仕向ける迂回は止められない。

README は、第 5.6 節の拒否が直感に反しうることを認めたうえで、その理由（祖先の改名による差し替え）と、
dotfiles のように設定ディレクトリの実体をワークツリーに含む場合の書き方（`--workspace` で下位
ディレクトリを指し、`rw = ["${workspace}", "${git_common_dir}"]` とするプロファイル）を載せる。`rw` のワークツリーの下位
ディレクトリを `--workspace` で明示するときは、そこをカレントディレクトリにして起動すること（第 5.6 節の
根の項目の検査の対象外になる）と、リンクを経由するパスを別の場所から `--workspace` で明示すると止まる
ので実体のパスを書くかそこで起動すること（エイリアスのリンク越しの `--workspace` も同じ）も載せる。
`rw` の中に置いたリンクのパスを `rw`、`rw-file`、`hide` に書くと止まるのでリンク先の実体のパスを
書くこと、同じ形の `ro` は通るがその守りは既知の隙間 15 の水準であることも載せる。
秘密ファイルは設定ディレクトリの `secrets/` に置くこと、`/tmp/process-wrap` は利用者かシムが作り
`process-wrap` は作らないこと、無ければその項目が飛ばされて `/tmp` が空のままになることも載せる。

`examples/profile/default.toml` に、WSL2 向けのプロファイルを置き、README から指す。内容は、現行の
codex 用 jail のマウント表を本仕様の形式に写したもの（パスは書かれたとおりで、リンクを実体に解決して
書き直さない）に、次を加えたものである。

- `rw`: `${workspace}`、`${worktree}`、`${git_common_dir}`、`/tmp/process-wrap`
- `hide`: `/tmp`、`/run/user`
- `.env` の走査、`/mnt` 以下の `9p` と `drvfs` の `hide-mounts`
- `env.unset`: `SSH_AUTH_SOCK`、`DISPLAY`、`WAYLAND_DISPLAY`、`XAUTHORITY`、`*_TOKEN`、`*_API_KEY`、
  `*_SECRET*`、`*_PASSWORD`、`AWS_*`、`GH_*`、`GITHUB_*`
- `secrets`: `${config_dir}/secrets/` 以下を指す

`/tmp` を `hide` にする理由（ホストのソケットが名前で隠せない）と、`/tmp/process-wrap` がホストとの
共有場所であることを README に書く。

成功の観測条件: README だけを読んでプロファイルを書き、`process-wrap` を起動できる。反例: 既知の
隙間が仕様書にしか書かれていない。

## 17. 版とリリース

版の典拠は `Cargo.toml` だけである。リリースごとに `CHANGELOG.md` に項目を足し、版の名前で tag を
打つ。CI と配布物の作り方はこの仕様に含めない。

成功の観測条件: `--version` の出力と `Cargo.toml` と tag の版が一致する。反例: 版の典拠が
ソースコードの 2 か所にある。

## 18. 0.1 で作らないもの

- cgroup による CPU やメモリの制限。bwrap で作れない。
- ドメイン単位の通信許可。bwrap 単体では作れない。外部プロキシとの組み合わせは第 7 節を参照。
- 段の合成における削除の演算子。
- `default.toml` を常に読む合成（書かれた段を 4 つにする形）。
- カレントディレクトリからのポリシーファイルの自動探索。
- bwrap の `--new-session`。
- 入れ子での二重の隔離と、環境変数以外の入れ子検出。
- aarch64、32 ビット、x32 のバイナリ。
- 組み込みの既定ポリシー。
- `.git/hooks` や `.git/config` の保護。
- ポリシーファイルの読み取り専用の重ね掛け。第 5.6 節の拒否で置き換えた。
- `git init --separate-git-dir` のメインワークツリーの相互リンク（第 5.2 節の 3 つ目の形）。既知の
  隙間として README に載せる。
- codex や opencode のシム。それらは利用者の dotfiles 側で、`--profile`、`--workspace`、`--rw` を
  使って書く。
- CI、配布物、リリースの自動化。

成功の観測条件: `--help` と README がこれらを提供すると書いておらず、これらを有効にするオプションや
ポリシーのキーが存在しない。反例: 文書に無いキーで `default.toml` を常に読む合成が有効になる。

## 19. 却下した代替案

本節は記録であり、要件ではない。

- blocklist 型の hook をコマンド化する案。完全な防御が不可能で筋が悪い。
- `@anthropic-ai/sandbox-runtime`（srt）の採用。Linux 版が `.env*` のパターン指定を持たず、
  ディレクトリのシンボリックリンクを読み取り禁止にすると bwrap が起動時に落ち、無制限のネットワークを
  指定できない（2026-09-03 の実測）。
- 0.1 を現行 jail の挙動保存だけに限定する案。ネットワーク、環境変数、認証情報は後から入れると
  ポリシー形式と CLI の変更になる。
- プロファイルを単一ファイルで完結させ合成しない案。グローバルとプロセスの 2 段が利便性で勝る。
- `default.toml` を常に読む合成。プロファイル単体で隔離の全体像が読めなくなる。
- 段の合成における削除の演算子。順序依存が生まれ、上書きで足りる。
- ドメイン単位の通信許可。bwrap 単体では不可能。`none` と外部プロキシの組み合わせで 0.1 の部品から
  組める（未検証）。
- カレントディレクトリからのポリシーファイルの自動探索。clone した時点で他人のポリシーが効く経路になる。
- 同じ環境変数名の秘密を 2 段で書いたらエラーにする案。ワークスペース別に秘密を差し替える用途が塞がる。
  キー付きテーブルで上の段が勝つ形に置き換えた。
- ポリシーファイルを `hide` で守る案。ワークツリー内のファイルだと git に空の変更として見え、
  空ファイルがコミットされうる。
- ポリシーファイルと設定ディレクトリを `ro` で守る案。祖先ディレクトリの改名による差し替えを防げず、
  参照されない秘密ファイルを平文で見せる。第 5.6 節の拒否と `secrets/` の `hide` に置き換えた。
- `/tmp` を丸ごと `rw` で渡す案。ホストの X11 と ssh-agent のソケットが見え、名前がランダムで
  `hide` できない。`hide` と共有用サブディレクトリの `rw` に置き換えた。
- `.git/hooks` と `.git/config` を `ro` にする案。`core.hooksPath` で迂回でき、`config` の `ro` は
  `git push -u` を壊す。既知の隙間として明記する。
- bwrap の `--new-session`。制御端末を切ると対話的なプログラムの挙動が変わりうる（未検証）。seccomp で
  `TIOCSTI` の経路だけは塞げる。
- `TIOCSTI` 対策を sysctl の確認と警告だけにする案。カーネルの素の設定では `TIOCSTI` は有効のままで、
  塞いだことにならない。
- 現行 jail の順序規則（rw を覆う hide、rw、他の hide、ro の順）。ro の祖先が hide した秘密ファイルを
  再露出する。
- 入れ子で実際に二重の bwrap を作る案。外側が空にした秘密ファイルを内側が読んで起動に失敗する。
  内側で狭める価値より規則の増加が大きい。
- CI と配布物の作り方をこの仕様に含める案。別の製品で検証の検証が発生した。
- `--help` と `--version` を他の引数があっても勝たせる案（GNU の慣習）。併用時に他のオプションを
  検査するかという次の問いが生まれる。排他の方が単純。
- `--policy-file` は利用者が明示したパスだから読み方を守らない案。境界は破れないが、無言のハングは
  第 13 節の診断の契約に反し、防御は数行で足りる。
- `--workspace` がファイルなら親ディレクトリを使う案。指定ミスの可能性が高く、意図が読めない。
- `XDG_CONFIG_HOME` の空文字と相対パスを字面どおり使う案。XDG Base Directory の慣習に反し、相対の
  設定ディレクトリを使う意味が無い。結果として第 18 節が作らないカレントディレクトリからのポリシー
  探索と同じ経路にもなる。
- `${config_dir}` の実体化を展開時に任せる案。変数の間に非対称が残り、第 5.6 節の検査で実体化を
  忘れる余地ができる。
- 共通の読み込み上限（第 14 節）を 64 KiB にする案。大きな `config` を持つリポジトリでの誤爆を避けたい。1 MiB でも
  桁で余裕がある。
- `HOME` が無い、または存在しない実行専用アカウントでの起動を支える案。`~` の展開先、設定
  ディレクトリ、第 6.5 節のホームの比較の前提が覆る。0.1 では第 2 節のとおり起動時に `env` の診断で止める。
- 秘密ファイルを第 5.6 節の対象にせず、第 14 節の根拠の文だけを直す案。`rw` の中の秘密ファイルを
  リンクに差し替える漏洩経路が残る。
- 診断の順序を委譲する案。テストが種類を観測する以上、順序で結果が変わる。第 1 節の決定性を
  診断にも及ぼす。
- 秘密の値の上限を置かず、exec の失敗（E2BIG）を第 13 節の表に足す案。`secret` で「大きすぎる」と
  言う方が利用者に親切。
- `~` を `HOME` の字面に展開し、実体化を比較とマウントの時点に任せる案。パスを取る値はすべて実体で
  一貫させる。字面を `PATH` に見せたい場面が無い。
- `ro` の項目にも根の項目の検査を課す案（0.1 の当初の形）。dotfiles へのリンクを `ro` に書く
  配置が 1 回目の起動から拒否され、`ro` は差し替えられても消されても露出する組の形以外で新しく見える
  ものが無い。`ro` については露出する組の検査（生成された `hide` と固定部分のマウント先を含む）に
  置き換えた。
- `hide` の項目も根の項目の検査から外す案。`rw` の中のリンクで書いた `hide` はリンクを消されると隠し先が
  露出し、着地点しか見ない露出する組の検査では止まらない（2026-09-06 に実測）。
- 書き込める項目の中のリンクを辿る `hide` を、着地が根の項目の中なら通す案（0.1 の当初の形）。同じ
  機構（リンクを消す → 項目が飛ばされる → 隠し先が露出）で外れ、深さ 1 のマウント点なら実体のパスで
  書いた `hide` は改名できず外れないのにリンクの形は外れる（2026-09-06 に実測）。着地先を問わず止める。
- 走査の `root` と `hide-mounts` の `under` を、書き込める項目の中を参照しても着地が根の項目の中なら
  通す案。起点はマウントされないので `rw` の下位を起点にすると改名や向け直しで走査が空振りし、
  `.env` の隠しが丸ごと外れる（2026-09-06 に実測）。`rw` のマウント点そのものに限る。
- 走査で、起点の外へのリンクを一切辿らない案。起点の外にある本物の秘密へのリンク（`.env -> ~/shared/.env`）が
  隠れなくなる。`ro` の項目の中を指すリンクだけを別扱いにする形に置き換えた。
- 走査で、`ro` の項目の中を指すリンクを差し替えの可否を問わず隠さない案。差し替えられる `ro` を走査の
  隠し先へ向け直すと本物の秘密の隠しが外れる（2026-09-06 に実測）。差し替えられうる `ro` の中は
  `path` で止める形に置き換えた。
- `ro` と `hide` の項目を実体のパスで書き直す運用（利用者側でのプロファイル生成）で凌ぐ案。リンクを
  足すたびにプロファイルを直す運用になり、診断が 1 起動 1 行なので項目を 1 つずつ潰す体験が残る。
- 入れ子で見つかったコマンドの exec 失敗を `command not found` の 127 のまま返す案。シェルの慣習
  （見つからない 127、実行できない 126）と食い違い、原因が分かりにくい。
- 記述子の soft 上限を必要なときだけ上げる案。同じ入力で包んだコマンドの上限が変わり、第 1 節の
  決定性に反する。常に上げる。
- 包んだコマンドの argv[0] を解決した絶対パスにする案（0.1 の当初の実装）。argv[0] で振る舞いを
  変えるコマンドが打ったとおりに動かず、シェルの慣習とも違う。`--argv0` で与えた文字列を渡す。

## 20. 未決と委譲

未決: 無し。

委譲（どの選択でも本仕様の振る舞いが保たれるもの）:

- 内部のモジュール構成と、TOML の読み込みに使うライブラリ。
- seccomp フィルタを bwrap に渡すファイル記述子の作り方（パイプかメモリ上のファイルか）と番号の割り当て。
- 計画の表示の整形。第 13 節の内容を含むことだけが条件。
- 警告と診断の説明部分の文言。接頭辞と種類、および第 5.6 節と第 6.3 節が検査ごとに要求する要素
  （多くは 3 つ、固定部分への着地の拒否は 2 つ）だけが契約。
- 走査の探索順と並列化。結果を第 6.4 節で並べ直し、走査の中で出る診断が名指すリンクはパスの
  バイト順で決まる（第 6.3 節）ため、順序は結果に影響しない。
- 制御文字の見える表記の形と、UTF-8 として不正なバイト列の表し方（第 13 節）。どの形でも「1 行、
  制御文字なし」は保たれる。
- 第 5.6 節と第 6.3 節の診断の要素に出すパスの形（書いたまま、展開後、実体のどれでもよい）。検査ごとに
  要求する要素が含まれることだけが契約。
- 第 5.6 節で、根の項目の検査と露出する組の検査を項目をまたいでどう交互に行うか（項目ごとに 2 つを
  行ってから次の項目へ進むか、検査ごとに全項目を見るか）。最初に出る診断だけが変わる。
- 第 5.6 節で、診断に名指すリンクや書き込める項目が複数あるときの選び方、保護対象の 3 つの規則の
  どれを出すか、通ったディレクトリがディレクトリでない成分だったときの名詞、理由の文言。
