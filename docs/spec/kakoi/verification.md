## 15. 検証の契約

検証は二つの層で行う。計画の判断を合成した事実で調べるテストと、実際の隔離で読み書きして確かめるテストである。両方を通すことで、「計画は正しいが実行すると違う」という見落としを防ぐ。

### 15.1 純粋な関数の境界

計画の算出は、次の入力だけから結果が決まる純粋な関数として実装する。

| 入力 | 含めるもの |
|---|---|
| ポリシー | 合成前の各段。出所がファイルの実体パスか組み込みの既定かも含む |
| 起動条件 | コマンドライン引数、ホストの環境、カレントディレクトリ |
| パスの事実 | 候補パスの存在・種類・実体、解決時に通るディレクトリとリンクの置き場・先 |
| 収集結果 | マウント一覧と取得失敗、走査結果、ワークツリーとGitの相互リンク、秘密の内容、rw-copyの複製元の木 |

事実の収集、ファイル記述子の割り当て、bwrapの起動は、この関数の外に置く。テストでは合成した事実を与え、記号付きbwrap引数列、環境、各項目の適用結果、解決したコマンドを期待値と比べる。

#### 設定・変数・合成

- `${git_common_dir}` の相互リンクの成立と不成立。共通ディレクトリCに通常ファイルの`HEAD`がない場合も含める。
- 3種類の合成規則、`path-prepend`の向き、ワイルドカードの意味。
- パスの同一性。存在しないパスは展開後の文字列で判定する場合も含める。
- 変数展開と相対パスの拒否。
- `init`の文法。NAMEの制約と、他の引数との併用を含める。

組み込み既定への置き換えはファイル読み込み時に決まるため、純粋関数の外の検証として15.2節で観測する。

#### 配置保護

[配置保護](policy-placement.md)について、拒否だけでなく、許可すべき境界も確認する。

| 対象 | 確認する条件 |
|---|---|
| 保護対象のパス | 3つの検査すべて。秘密ファイルも対象に含める |
| 根の項目の検査対象 | `rw`、`rw-file`、`hide`、明示のworkspace、走査のroot、hide-mountsのunder |
| 生成前の起点検査 | rootとunderは生成前の集合で判定し、その診断が後続の検査より先に出る |
| パス解決の参照 | 入れ子の項目、`..`で書込領域を通り抜けるリンク先、workspace変数からの参照の引き継ぎ。走査rootへの引き継ぎも含む |
| workspace | cwdと同じ実体の指定は除外する。リンクを辿る明示指定の規則も確認する |
| hideのリンク | 書込領域内のリンクを辿るhideは、着地先がrw外でも根の中でも拒否する。rw内を実体パスで指定したhideは許可する |
| 走査起点 | rwの下位のrootは拒否し、rwのマウント点のrootは許可する。rw内のリンク経由でマウント点を指すrootとunderは拒否する |
| 根の検査の対象外 | roとrw-copyのリンクは、どの項目でもない場所へ向けても通る |
| 固定部分と広さ | `/`、`/dev`、`/proc`への着地と、広すぎる書込範囲を拒否する |

「露出する組」の検査では次を確認する。

- **拒否する形**：下の段と同じ実体、段を問わない祖先、生成されたhideの中への着地、hideの中へのrw-copy、rw-copyの中へのrwとrw-file。
- **許可する形**：hideの再指定、間の段のrwが遮る形、別の根の項目への着地、roの中へのrw-copy。

#### マウントと複製

- rw-copyをホストの書込可能項目に数えない。内部のポリシーファイル・設定ディレクトリ・秘密ファイルが保護対象の検査を通ること、根の検査の対象外であること、作業場所の警告ではrwとして数えないことを確認する。
- rw-copyの複製元がなければ飛ばす。生成する引数は、ディレクトリのtmpfsとエントリ順、通常ファイルの`--bind-data`、モードの引き継ぎを確認する。
- 生成の段と走査は、シンボリックリンクとポリシーファイルの除外を含める。差し替えられないroの中を指すリンクは隠さず、差し替えられうるroの中を指すリンクはpath診断になる。
- hide-mountsは作業場所の除外と、マウント一覧を読めない事実からのpath診断を確認する。設定ディレクトリのsecretsの隠しも確認する。
- マウントの6場面の重なりと兄弟の順序を確認する。
- 作業場所の警告と、広すぎる位置・隠されたcwdの2種類の拒否を確認する。再露出したcwdは許可する。

#### 環境・起動・表示

- 環境構成の7段階、unsetのワイルドカード、path-prependの実体化と飛ばし。
- 秘密注入の2段階、LFとCR LFの扱い、不在の警告、値の上限。
- Git設定の番号付け。空の`GIT_CONFIG_COUNT`も含める。
- 出力に埋め込む制御文字のエスケープ。
- コマンドの解決と、bwrap引数列の`--argv0`および末尾の`--`。

### 15.2 ビルド済みバイナリのテスト

Linux x86_64でビルド済みkakoiを起動し、実際のbwrapを使って確認する。外部ネットワークへの接続は必要としない。

#### 診断・終了・実行境界

- [出力と終了](process.md)の診断表と結果表の全行。隣り合う検査段階の診断が同時に成立するときは、先の段階の診断が出ること。
- ファイルの読み方：FIFOでも停止せず診断になることと、読取上限の超過。
- 記述子上限：soft上限1024の環境で1100件の走査を行うこと。
- マウントの6場面を、隔離内から読み書きして確認すること。
- network.modeのnone、秘密が隔離内からどう見えるか。
- TIOCSTIのEPERM。上位ビットを立てた呼び出しと、x32ビットを立てた呼び出しによる終了も含める。
- 入れ子の警告とcommand not executable。argv[0]は隔離内と入れ子の両方で確認する。

#### rw-copy

| 場面 | 隔離内とホスト側で確認すること |
|---|---|
| 通常ファイル | ホストの内容を読める。書込成功と読み戻しを確認し、ホストの元ファイルは変わらず、終了後に残骸がない |
| ディレクトリ | 既存内容を読め、新規作成と上書きができる。実行ビットが引き継がれ、内側で作った実行可能ファイルも実行できる。ホストのディレクトリは変わらず残骸もない |
| 複製元の不在・型 | 不在なら飛ばす。根がソケットやFIFOならpathになる |
| 上限・複製できない内容 | エントリ数超過はpath。複製できないエントリは計画に出る |
| リンクと重なり | リンクはリンクのまま複製する。内側の狭いrwへの書込はホストに届く |
| 計画 | print-planとJSONの両方に項目と指令が出る |
| 内部のポリシーファイル | 起動を許可し、隔離内での書換えはホストに出ない |

#### initと既定プロファイル

- 設定ディレクトリがない状態から書き出せる。`~/.config`もない場合はそこから作る。
- 書き出した内容が`examples/profile/default.toml`とバイト単位で一致する。
- secretsディレクトリのモードが0700で、既存のものも0700に狭まる。
- 書き出し先が既存またはリンク切れならpath。profileディレクトリの位置が通常ファイルの場合もpath。
- stdoutはパス1行。設定ディレクトリがリンクならリンク先へ書き、表示は組み立てたままのパス。
- `KAKOI=1`でもinitはstderrを出さず、終了コード0で書く。
- 設定ディレクトリが通常ファイルならpolicy。既定ファイルまたは設定ディレクトリがリンク切れの場合もpolicy。
- 設定ディレクトリ不在では組み込み既定のprint-planが0で終了し、計画に`kakoi init`が出る。同じ状態で追加ポリシーのroにconfig_dirを使うと、その項目が飛ばしとして出る。
- 設定ディレクトリがなく、その存在する最も深い祖先が書込領域にある場合は配置保護のpath診断になる。

#### JSONの契約

print-planのJSONが解析でき、[出力契約](process.md)のトップレベルキーを持ち、秘密の値がnullになっていることを確認する。

### 15.3 移行の確認

現行のcodex用jail（bashスクリプト）からの移行時に、利用者の実機で一度だけ確認する。旧スクリプトがbwrapへ渡す引数列とprint-planを並べ、マウント集合が同じであることを人が確認する。

旧スクリプトは製品の一部ではないため、この比較はテストとして残さない。

**成功の観測条件**：15.1節と15.2節のテストが外部ネットワークに依存せず通る。**反例**：純粋関数だけをテストし、ビルド済みバイナリを一度も起動しない。

### ネットワーク改訂の検証

coreの純粋性を維持し、DNS応答の採否と許可期限の判断をOS操作から分けて検証する。追加要求の成功条件・反例は責務別仕様に対応するIRに置く。実ネットワークと故障時の保証は[実証の完了条件](proof-gate.md)を先に満たす。

今回の本体仕様整理では、kotowariの照合対象に本体IRと既存テストの要求IDを追加する。テストの動作は変更せず、対応がない要求や矛盾は問題として記録する。
