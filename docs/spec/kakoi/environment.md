# 環境変数・認証情報・Git設定

Status: Approved（2026-09-16。IR抽出・対応付けを承認。文章の追加校正は別件）

隔離へ渡す環境は、ホストの環境に設定を順番に適用して作る。秘密ファイルの値は注入するが、計画や診断には表示しない。

## 8. 環境変数

`kakoi` は隔離の中の環境の最終形を自分で組み立て、bwrap にそのまま引き継がせる。環境変数の値を bwrap の引数に載せない。引数はプロセス一覧から他のプロセスに見えるためである。マウントするパスと秘密ファイルのパスは引数に載る。パスが見えることは許容する。隔離の中のプロセスの環境は、ホスト側からは `/proc` を通して読める。ホストは信頼する側なので、これも許容する。

### 適用する順序

組み立ての順序は次のとおり。

1. `env.mode` が `inherit` ならホストの環境から始める。`clear` なら空から始め、`env.pass` に
   列挙した変数だけをホストから写す。
2. `env.unset` に一致する変数を消す。
3. `env.set` の変数を入れる。
4. 秘密（第 9 節）を入れる。
5. git の書き換え（第 10 節）を入れる。
6. `PATH` の先頭に `env.path-prepend` を足す。項目は実体のパスで足し、実体が存在しない項目は
   飛ばして計画に理由付きで表示する。この時点で `PATH` が無ければ `path-prepend` だけが
   `PATH` になる。`path-prepend` も空なら `PATH` は無いままで、警告は出さない。
7. `KAKOI=1` を入れる。

成功の観測条件: `--print-plan=full` が最終の環境を表示し、`--print-plan` がホストとの差分を表示し、bwrap の引数列に環境変数を設定する引数が含まれない。反例: 秘密の値が bwrap の引数列に現れる。

## 9. 認証情報

`secrets` は環境変数名をキー、ファイルパスを値とするテーブルである。項目は環境変数名のバイト順に処理し、各項目は次の 2 段階で動く。

1. その名前の環境変数を、由来にかかわらず消す。
2. ファイルが存在すれば、その内容を値として環境変数を入れ、そのファイルを `hide` にする。

### 改行と値の検査

ファイル末尾の改行を、次の規則で1つだけ取り除く。

| ファイル末尾 | 除去するもの |
|---|---|
| LF | 最後の1バイト |
| CR LF | 最後の2バイトを1つの改行として除去 |
| それ以外 | 何も除去しない |

CR LF は Windows のエディタで書いたファイルの CR を値へ残さないための扱い。たとえば `value` の後ろに LF が2個あれば、環境の値には LF が1個残る。

次の場合は種類 `secret` の診断で終わる。

- ファイルを読めない。
- 改行を除いた値が空。
- 値に NUL バイトを含む。
- 値が 64 KiB を超える。

64 KiB は Linux の環境変数1個の長さ上限（名前と終端を含め128 KiB）の半分である。[一般の読込上限](runtime.md)より先にこの値の上限を検査する。

### ファイルがない場合

ファイルが存在しなければ環境変数を入れず、`kakoi: warning:` で始まる 1 行を標準エラーに出して起動を続ける。

### 表示とホストからの継承

秘密の値は、計画の表示、警告、診断のどこにも出さない。表示するのは環境変数名とファイルパスだけで、値は伏せる。

ホストの環境にある認証情報は、`inherit` ではそのまま隔離に入る。名前で落とすのは `env.unset` のワイルドカードの役目で、名前が規則に合わないものは残る。これは README に既知の隙間として書く。

成功の観測条件: ファイルがあるとき隔離の中でその環境変数が読め、ファイル自体は空として見え、ファイルが無いときホストの同名変数も隔離の中に存在しない。反例: ファイルが無いときホストの`GH_TOKEN` が隔離の中に残る。200 KiB の秘密ファイルが検査を通り、bwrap の exec で失敗する。

## 10. git の URL 書き換え

`git.instead-of` は、元の URL の先頭をキー、置換先を値とする。

```toml
[git.instead-of]
"git@example.com:" = "https://example.com/"
```

この例では Git に `url.https://example.com/.insteadof = git@example.com:` を渡す。ホストの Git 設定ファイルは書き換えず、Git が読む `GIT_CONFIG_KEY_n`、`GIT_CONFIG_VALUE_n`、`GIT_CONFIG_COUNT` を環境へ追加する。

1. 秘密の注入まで終えた環境の `GIT_CONFIG_COUNT` を読む。不在なら番号0から始める。
2. 既存の番号と設定の組を保持する。
3. `git.instead-of` のキーのバイト順で、続きの番号に設定を追加する。

`git.instead-of` が1件以上ある場合だけ、COUNT を検査する。

| COUNT の状態 | 結果 |
|---|---|
| 不在 | 0から追加 |
| 番号として読め、追加後も上限内 | 続きから追加 |
| 空、符号付き、空白入り、数値でない、桁が多すぎる | `env` の診断 |
| 数値だが追加で番号の上限を超える | `env` の診断 |

Git 自身は空の COUNT を0として読むが、kakoi は壊れた値を受け取ったとして拒否する。`git.instead-of` が空なら COUNT を検査しない。

既存の環境変数の値を読んで別の変数の値を決める処理は、`kakoi` の中でこれと `PATH` の先頭追加だけである。

成功の観測条件: 隔離の中で `git config --list` にキー `url.<置き換え先>.insteadof` が値`<元の先頭>` で現れ、ホストで設定していた組も残っている。反例: ホストの `GIT_CONFIG_*` が上書きで消える。
