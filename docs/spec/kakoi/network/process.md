# プロセスの寿命と終了

草案。実装前に[実証の完了条件](../proof-gate.md)を満たす必要がある。

`filtered`では、主コマンドの実行中もkakoiが通信を監督する。主コマンドの終了や外部からの終了要求を受けたら、通信を止めてから残るプロセスを片付ける。

## filteredで監督を続ける理由

`filtered` では監督プロセスを残し、通信障害からの復帰と主コマンド終了後の子プロセス回収を担う。bwrapへのexec契約を `filtered` に限り改訂し、`host` と `none` は維持する。

## 対話中と終了待ちのCtrl+C

`filtered` の対話中のCtrl+Cはアプリ側へ割り込みを届ける。アプリが操作をキャンセルして続行するなら隔離環境も継続し、主コマンドが終了したら決定済みの片付けを行う。

`filtered` で主コマンド終了後の終了猶予中にCtrl+Cが来たら、残りの猶予を打ち切り、残った子プロセスを強制終了して片付けを進める。

主コマンド終了後の猶予をCtrl+Cで打ち切っても、確定済みの主コマンドの終了結果を維持する。猶予を打ち切ったことは通知する。

## 終了を待つ時間の指定

終了猶予設定はTOMLの `process` 内の `shutdown-grace-seconds` に置く。既定は5秒、指定範囲は1〜300秒の整数とする。

新しい終了猶予は今回は `filtered` だけに適用し、`host`・`none` の終了方式は既存どおりとする。`host`・`none` に明示的な終了猶予設定が残っていれば、使われない旨を警告する。

`process.shutdown-grace-seconds` は上位の明示値で上書きし、省略なら継承、全段省略なら5秒とする。`host`・`none` でも整数かつ1〜300秒の範囲を検査する。猶予設定がある場合は `network.mode` の明示を必須とし、別の段からの継承も認める。

`filtered` の終了処理で通信・公開を止めて最初の終了要求を送ったら、その時点から設定済みの猶予時間を計り、主コマンドと子プロセス全体で1本の期限を使う。主コマンドの途中の終了や新しい子プロセスの出現で期限を延長しない。

## 外部から終了要求を受けた場合

例えば、実行中にSIGTERMで終了を要求され、アプリが後片付けを終えて0を返しても、kakoiは143を返す。すでに主コマンドの終了を確認した後なら、その確定済み結果を維持する。安全上の故障がある場合は[125の優先規則](#安全上の故障を終了結果へ反映する)が先になる。

`filtered` で外部からkakoiへSIGTERMによる終了要求が届いたら、隔離環境全体の終了処理に入る。通信・公開を止め、主コマンドと子プロセスに終了を要求し、設定済みの猶予後も残るプロセスは強制終了する。

主コマンドの実行中にSIGTERMを受けて環境の終了処理を始めた場合、主コマンドが後処理後に0を返しても終了コード143を返す。ただし安全上の故障による125優先規則に該当する場合はそちらを優先する。

SIGTERMで開始した終了猶予中に再度SIGTERMが来ても、最初の猶予期限を維持し、延長も短縮もしない。主コマンド終了後のCtrl+Cによる打切りは引き続き行う。

主コマンドの終了を確認して子プロセスの終了猶予に入った後にSIGTERMが来ても、確定済みの主コマンドの結果と既存の猶予期限を維持する。

## 安全上の故障を終了結果へ反映する

通信制限と遮断の双方を保証できない安全上の故障で環境を終了する場合、主コマンドの成功・失敗やSIGTERMの143よりkakoiの終了コード125を優先し原因を通知する。通信制限を維持できている通常のDNS失敗にはこの優先規則を適用しない。
