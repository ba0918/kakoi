# filteredのネットワーク仕様

隔離環境のアプリから、必要なAPIには接続したい。内側で起動した開発サーバーは、ホストのブラウザーから開きたい。`filtered`は、こうした通信をあらかじめ許可した範囲に絞るモード。

設定では「誰が、どちらへ接続するか」を分けて考える。アプリから外へつなぐ許可と、ホストから内側のサービスへつなぐ公開は、別々に指定する。
責務別仕様は会話で承認済み。今回の[初版範囲の改訂](initial-release.md)と実装計画はレビュー対象。
実装開始と提供前の確認を[実証条件](../proof-gate.md)で分ける。

## まず通信の向きを選ぶ

![外部接続はallow、ホスト接続はhost-loopback、ホストから内側への公開はpublishを使う。](figures/directions.svg)

| やりたいこと | 読む場所 |
|---|---|
| 特定のAPIやIPだけにつなぐ | [通信許可の書き方](policy.md) |
| 日本語の名前やワイルドカードを使う | [DNS名の指定](dns-input.md) |
| ホストで動くサービスにつなぐ | [ホスト宛て接続](host.md) |
| 内側の開発サーバー等をホストから開く | [初版の固定公開](initial-release.md#固定公開) |
| 内部ネットワークや特殊なIPにつなぐ | [IPの入力と分類](address.md)、[IPv6リンクローカル](link-local.md) |

隔離環境内の`localhost`とホストの`localhost`は別の宛先。
内側のループバックは既定で使えるが、それだけでホストへ接続できるようにはならない。

## DNSで得た許可はどう変わるか

DNS名による許可は、名前から得たIPと指定ポートを通す仕組み。
同じIP・ポートを使う別名やIP直打ちの通信も通り得る。
起動時のポリシーが許可の正本であり、アプリの申告によって範囲を広げることはない。

1. [応答の検査](dns-trust.md)で、別名の参照や禁止IPの混在を扱う。
2. [許可の寿命](dns-lifetime.md)で、TTL切れと既存TCP/UDPの継続を分ける。
3. [上流DNSの設定](dns-upstream-config.md)と[ホストDNSの変更](dns-host-settings.md)で、問い合わせ先の選択と追従を扱う。

さらに詳しい契約は、[照会の種類・失敗応答](dns-protocol.md)、
[時間と問い合わせ回数の上限](dns-work-limits.md)、[同時処理と共有](dns-capacity.md)を参照。

## 公開・故障・終了を理解する

初版の公開は[明示的な固定公開](initial-release.md)。次の公開3文書は後続の動的公開を定義する。

- [公開対象と割当](publish-target.md): アプリを特別扱いせず、許可範囲の待受を公開する。
- [公開の寿命](publish-lifetime.md): ポート不足時の再試行、待受終了、UDP公開の扱い。
- [通信の障害と復帰](recovery.md): 確実に遮断して処理を続ける条件と、直ちに終了する条件。
- [プロセスの終了](process.md): Ctrl+C、SIGTERM、終了猶予、終了コード。
- [通知](notification.md): どこへ何を知らせ、出力が詰まったらどうするか。

## 実装と検証へ進むとき

[ライブラリの責務](library.md)は、純粋な計画と通信の実行を分ける契約。
TTLゼロの猶予は既定1秒・100〜10000ミリ秒で合意済み。対応環境と期限を守る機構は[実証工程](../proof-gate.md)で確認する。

仕様の正本はこの文書群で、IRは成功条件と反例を検査用に整理した表現。
本文を読む際に要求IDを追う必要はない。検証や仕様変更の際は
[仕様の節とIRの対応表](../../../decision/brainstorm/2026-09-16-kakoi-net-spec-map.md)を使い、意味の一致を確認する。
