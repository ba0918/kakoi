# ホストDNSの設定追従

草案。実装前に[実証の完了条件](../proof-gate.md)を満たす必要がある。

ホストDNSを使う構成では、起動後のDNS設定変更にも追従する。変更前の応答を再利用することと、すでに許可した通信を続けることは別に扱う。

## 起動時に引き継げない構成

DNS名の許可を使う `filtered` でホストDNSを選び、起動時にその構成を安全に引き継げないと判明した場合は起動エラーとし、上流DNSの明示指定を案内する。勝手に公開DNSへ切り替えない。DNS名の許可を使わない構成までホストDNS対応を必須にしない。起動後の設定取得失敗は[新しい設定を取得できない場合](#新しい設定を取得できない場合)に従う。

## 実行中にホストDNSが変わった場合

例えば、ホストの接続先ネットワークが変わり、使うDNSの設定も変わったとする。kakoiが変更を検出すると、それ以降に始める上流への問い合わせには新しい設定を使う。ポリシーに問い合わせ先を書いている構成は、この追従の対象外。

変更時には、保存している情報を次のように扱う。

| 情報・処理 | 変更を検出した後の扱い |
|---|---|
| kakoiが保存した古いDNS応答 | 破棄する。次の解決は新しい設定で行う |
| すでに与えたIP許可 | 元の期限まで維持する |
| 確立済みTCP・継続中UDP | [それぞれの継続規則](dns-lifetime.md#期限が切れた後のtcpとudp)で扱う |
| アプリ自身が保存したIP | kakoiが消すことは保証しない |
| 旧設定で送信し、まだ完了していない問い合わせ | 新設定でやり直す |

変更の検出後に旧問い合わせの応答が届いても、アプリに返さず、キャッシュやIP許可の追加・更新にも使わない。問い合わせ先IPと通信方式が同じ場合も、設定変更後は別の解決条件としてやり直せる。

ただし、再試行のたびに時間を計り直すことはない。それまでに消費した時間と問い合わせ回数を引き継ぎ、設定変更が続いても元の上限内で解決する。[再問い合わせの規則](dns-lifetime.md#失敗の保持と再問い合わせ)も参照。

## 新しい設定を取得できない場合

ホストDNS設定の変更を検知しても新しい設定を取得・解釈できない間は、上流への問い合わせを失敗として扱い、旧設定や別のDNSへ自動で切り替えない。環境全体は終了せず、既存IP許可と継続中の通信には既存規則を適用する。
