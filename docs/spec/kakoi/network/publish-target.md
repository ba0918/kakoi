# 公開対象と通知

草案。実装前に[実証の完了条件](../proof-gate.md)を満たす必要がある。

隔離環境内で起動した開発サーバーやレビュー画面を、ホストのブラウザー等から利用するための機能。許可した範囲の待受を検出し、ホストのlocalhostへ自動で公開する。アプリ名による特例は設けない。

## 許可範囲の待受を自動で公開する

隔離環境内で開発サーバーやレビュー画面を起動したら、ホストのブラウザーから開きたい。そのために、公開対象にする内側のポート範囲と、ホストで公開してよい範囲をあらかじめ指定する。範囲外の待受は、この指定による自動公開の対象にならない。

kakoiはその範囲内の待受を検出すると、自動でホストのlocalhostへ公開する。アプリ側でkakoiへの登録処理を実装する必要はない。kemiも利用例の一つだが、同じ範囲で待ち受ける他のサービスにも同じ規則を適用する。

アプリが選ぶ番号を事前に一つへ固定する必要はない。許可した範囲の中で空きポートを動的に選べる。ただし、アプリの申告によって事前定義の外へ範囲を広げることはできない。

初版の公開先はホストのlocalhostに限る。LANなど、ホスト以外の機器へ公開する指定は含めない。

## 一件の公開として扱う単位

公開対象は待受ソケット単位で数える。単一ソケットがIPv4とIPv6の両方を受けるなら1件、同じプロセスでも別々のソケットなら別件として公開する。ただし、同じIP・TCP/UDP・ポートを共有する待受ソケット群は例外として1件にまとめる。

隔離環境内の同じTCP/UDP・ポート番号でIPv4とIPv6に別々の待受があり両方が公開対象の場合、別々のホスト公開ポートを許可範囲内で割り当て、各転送先との対応を知らせる。

同じIP・TCP/UDP・ポートを複数の待受ソケットで共有する場合は、共有先を1件の公開にまとめ、各ソケットへの配送はOSに任せる。

## ホスト側の番号を選ぶ順序

障害復帰時に同じ待受が継続し以前の公開番号が使用可能な場合は、その番号を優先する。それ以外はホスト側の事前許可範囲内で、隔離環境側と同じポート番号を優先する。同じ番号が使用中なら範囲内で別の空きポートを選ぶ。同じ番号が範囲外の場合も、範囲内から選ぶ。実際の公開先をkakoiが知らせる。

## 通知された接続先を使う

例えば、アプリが`http://localhost:8003/review?token=EXAMPLE_TOKEN`を表示し、通知された対応が「内側TCP・8003番 → ホスト127.0.0.1・18000番」なら、ホストでは次を使う。

```text
http://127.0.0.1:18000/review?token=EXAMPLE_TOKEN
```

これは利用者が対応に従って置き換える例。HTTPという通信方式、パス、トークンはアプリの案内をそのまま使う。kakoiがポート番号からHTTPSを推測したり、このURLを生成したりするわけではない。

公開通知は内側とホスト側の実際のIP・ポート・TCP/UDPの対応を知らせ、アプリの出力は維持する。HTTP/HTTPS・URLのパス・認証トークンは推測せず、アプリからURLを受け取ってホスト向けURLを表示する連携は初版に含めない。URLのホスト・ポート部分を対応表に従って置き換え、パスと認証トークンを維持する使い方を示す。この契約は公開対象のアプリ全般に適用する。
