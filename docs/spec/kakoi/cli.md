## 4. コマンドラインインターフェース

### 4.1 文法

```
kakoi [OPTIONS] -- COMMAND [ARGS]...
kakoi [OPTIONS] --print-plan[=FORM] [-- COMMAND [ARGS]...]
kakoi init [NAME]
kakoi --version
kakoi --help
```

| オプションと形 | 意味 |
|---|---|
| `--profile NAME` | グローバルなプロファイルを選ぶ。省略時は `default` |
| `--policy-file PATH` | 今回だけ重ねるポリシーファイル。省略可能。指定先がなければ `policy` |
| `--workspace PATH` | ワークスペース。省略時はカレントディレクトリ |
| `--rw PATH` | CLI 段へ `rw` を追加。繰り返し可 |
| `--hide PATH` | CLI 段へ `hide` を追加。繰り返し可 |
| `--print-plan[=FORM]` | 実行せず計画を表示。形式は下表 |
| `--version` | 版を標準出力へ出して0で終了 |
| `--help` | 使い方を標準出力へ出して0で終了 |
| `init [NAME]` | 組み込みの既定を `profile/NAME.toml` へ書き出す。省略時 `default` |

`--profile` と `init` の NAME は、有効な UTF-8 の空でない1パス要素である。`/` または制御文字（0x00〜0x1F、0x7F）を含む名前と、単独の `.`・`..`は `usage` で拒否する。`default` の明示と省略は同じ意味。

| FORM | 内容 |
|---|---|
| `summary`（省略時） | 人が読む要約 |
| `full` | 合成後ポリシー、出所、最終環境、bwrap 引数を含む全量 |
| `json` | 全量と同じ内容に環境差分を加えた、ツール向けの JSON 文書 |

FORM は `--print-plan=full` のように `=` で指定する。別の値や空の値は `usage`。出力内容と秘密の伏せ方は[出力契約](process.md)に従う。

### 引数を解釈する規則

`--` より後ろは、そのまま包んだコマンドの引数になる。`--print-plan` を付けない場合、`COMMAND` は必須。未知のオプション、`COMMAND` の欠落、その他の文法の誤りは、種類 `usage` の診断を出して終了コード125 で終わる。上の 5 つの形は排他である。

`--help` と `--version` は単独でだけ使え、他のどの引数（オプション、`--`、`COMMAND`）と併用しても種類 `usage` の診断で終わる。`init` も同じで、`NAME` 以外の引数（オプション、`--`、`COMMAND`）と併用すれば種類 `usage` の診断で終わる。

`--rw` と `--hide` 以外のオプションは 1 回だけ書ける。2 回以上書けば種類 `usage` の診断で終わる。値を取るオプションは`--opt VALUE` と `--opt=VALUE` のどちらの形でも書け、意味は同じ。語を分けた形では、値は `-` で始まらない。

`-` で始まる語が続けば値の欠落として種類 `usage` の診断で終わる。どちらの形でも空文字の値は値の欠落として種類 `usage` の診断で終わる。

### コマンドラインのパス

コマンドラインで受け取るパス（`--policy-file`、`--workspace`、`--rw`、`--hide`）は、相対パスならカレントディレクトリからの相対として解釈する。コマンドラインでは `~` と変数を展開しない。第 5.2 節の書式はポリシーファイルに書く値についての規則である。

### 設定を作る：`init`

`kakoi init [NAME]` は、組み込みの既定（第 2 節）を設定ディレクトリ（第 2 節）の`profile/NAME.toml` に書き出す。`NAME` を省略すれば `default`。`NAME` の制約は `--profile` と同じで、反すれば種類 `usage` の診断で終わる。

書き出す内容は同梱の `examples/profile/default.toml` と同じバイト列である。設定ディレクトリ自身と、その `profile/` と `secrets/` が無ければ作る。設定ディレクトリの祖先（`~/.config`、`XDG_CONFIG_HOME` の指す先）が無ければそれも作る（無いディレクトリは新しい機械の普通の状態で、作るのは利用者の環境変数が指す場所だけである）。

書き出す先の名前より上の成分（設定ディレクトリ、`profile/`、`secrets/`）は通常のパス解決どおりシンボリックリンクを辿る（利用者が dotfiles へのリンクで置くため。第 14 節）。辿った先がディレクトリでない（リンク切れ、通常ファイル）ときは種類 `path` の診断で終わる。

`secrets/` はモード 0700 で作り、既にあればモードを 0700 にする（利用者が手で作った広いままの置き場を残さないため）。`profile/` と書き出すファイルのモードはプロセスの umask に従う（プロファイルは秘密ではなく、利用者が読み、dotfiles に置くものである）。

成功したら、書いたファイルのパスだけを標準出力に 1 行出して終了コード 0 で終わる（`$EDITOR "$(kakoi init)"` のように使える）。出すパスは、設定ディレクトリの規則（第 2 節）で組み立てたままのパスで、シンボリックリンクを実体に解決しない。

#### 既存の設定は上書きしない

書き出す先の名前が種類を問わず既に存在すれば（通常ファイル、ディレクトリ、リンク切れを含むシンボリックリンク）、何も書かず、種類 `path` の診断で終わる。書き出す先の名前自身がリンクでも辿らない。上書きする形（`--force`）は持たない。境界の記述を製品が上書きする手段を置かないためで、書き直したければ利用者が消してから`init` する。`profile/` や `secrets/` を作れない、ファイルを書けない、設定ディレクトリのパスがディレクトリでないときも種類 `path` の診断で終わる。説明は対象のパスを含む。

#### init だけで行う検査

`init` はポリシーを読まず、ワークスペースを導出せず、マウントを解決せず、`bwrap` の所在も確かめず、入れ子の検出（`KAKOI`。第 12.1 節）も行わない（`bwrap` の無い機械でも、隔離の中でも、書ける場所になら設定を置ける）。通る検査は、文法（`usage`）、ホームディレクトリ（第 2 節。
`XDG_CONFIG_HOME` の有無にかかわらず常に行う検査。`env`）、書き込み（`path`）の順である（第 13 節）。`init` はファイルを書く唯一の形で、書く先は、設定ディレクトリの規則で組み立てたパスの各成分（無ければ作る）と、その下の`profile/`、`secrets/`、書き出すファイルだけである（第 14 節）。

`/tmp/kakoi` は作らない。

#### 確認例

成功の観測条件: 設定ディレクトリが無い状態で `init` すると `profile/default.toml` と `secrets/` ができ、`default.toml` が `examples/profile/default.toml` とバイト単位で一致し、標準出力がそのパス 1 行で終了コード 0。

同じ `init` をもう一度行うと種類 `path` の診断で終了コード 125 で終わり、ファイルは変わらない。`init strict` は `profile/strict.toml` を作る。`init ../x` は `usage`。`init -- sh` は `usage`。

書き出す先がリンク切れのシンボリックリンクなら種類 `path` の診断で終わる。設定ディレクトリを別の場所へのシンボリックリンクにして `init` すると、リンク先にファイルができ、標準出力の 1 行はリンクを含む組み立てたままのパスである。`~/.config` が無い状態（`XDG_CONFIG_HOME` 未設定）の `init` は `~/.config` から作って成功する。

反例: 既にあるファイルを黙って上書きする。`bwrap` が無いと `init` が失敗する。`KAKOI=1` の環境で `init` が警告を出す。標準出力に実体のパスが出る。

### 4.2 コマンドの解決

`COMMAND` に `/` が含まれていればそのパスを使い、存在して実行可能であることを確認する。含まれていなければ、隔離の中で使われる `PATH`（第 8 節の規則で決まる値）を順に探す。`PATH` が無ければ探さない。どちらの場合も見つからなければ、種類 `command not found` の診断を出して終了コード 127 で終わる。

`--print-plan` で `COMMAND` を省略したときは解決を行わず、計画の該当欄は「無し」になる。入れ子（第 12.1 節）では、`--print-plan` の有無にかかわらず、隔離の中の `PATH` の代わりに受け取ったホストの`PATH` で探す。

#### 見つかった後に実行できない場合

見つかったコマンドの exec が失敗したとき（インタプリタが無いスクリプトなど）は、通常は bwrap の失敗として bwrap の出力と終了コードがそのまま返る（第 13 節）。入れ子では `kakoi` 自身が exec するので、種類 `command not executable` の診断を出して終了コード126 で終わる。説明はそのパスとエラー。2 つの経路で失敗の見え方が違うことは許容する。

#### 呼び出した名前を維持する

起動したプロセスの argv[0] は、隔離の中でも入れ子でも、`COMMAND` に与えた文字列そのものである。bwrap には第 14 節の固定部分の `--argv0` で渡し、入れ子では exec の際に同じ値を渡す。解決したパスはexec するファイルの指定にだけ使う。シェルが `PATH` で見つけたコマンドに打った名前を argv[0] として渡すのと同じで、argv[0] で振る舞いを変えるコマンド（多重呼び出しバイナリなど）が打ったとおりに動く。

#### 探索と隔離の間に残る制約

探索はホストのファイルシステムで行う。`hide` で隠したディレクトリの中にあるコマンドは「見つかった」と判定され、その後 bwrap の exec 失敗として終わる。この隙間は許容し、README に書く。引き継いだ `PATH` の要素が `rw` の中にあっても検査しない。解決したコマンドは隔離の中で動くので、その差し替えは境界を越えない。

成功の観測条件: 上の表のオプションだけを受け付け、それ以外は終了コード 125 で終わり、`--help` と他のオプションの併用も 125 で終わり、存在しないコマンドは `/` の有無にかかわらず終了コード 127 で終わり、入れ子で見つかったが exec できないコマンドは終了コード 126 で終わり、隔離の中と入れ子のどちらでも `COMMAND` に `sh` と与えたプロセスの argv[0] が `sh` である。

反例: 未知のオプションを黙って無視して起動する。`--profile ../x` が `profile/` の外のファイルを読む。入れ子でインタプリタの無いスクリプトが `command not found` の 127 で終わる。
