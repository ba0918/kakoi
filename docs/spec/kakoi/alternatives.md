# 却下した代替案

Status: Approved（2026-09-16。IR抽出・対応付けを承認。文章の追加校正は別件）

## 19. 却下した代替案

本節は記録であり、要件ではない。

- blocklist 型の hook をコマンド化する案。完全な防御が不可能で筋が悪い。
- `@anthropic-ai/sandbox-runtime`（srt）の採用。Linux 版が `.env*` のパターン指定を持たず、
  ディレクトリのシンボリックリンクを読み取り禁止にすると bwrap が起動時に落ち、無制限のネットワークを
  指定できない（2026-09-03 の実測）。
- 0.1 を現行 jail の挙動保存だけに限定する案。ネットワーク、環境変数、認証情報は後から入れると
  ポリシー形式と CLI の変更になる。
### ポリシーと秘密

- プロファイルを単一ファイルで完結させ合成しない案。グローバルとプロセスの 2 段が利便性で勝る。
- `default.toml` を常に読む合成。プロファイル単体で隔離の全体像が読めなくなる。
- 段の合成における削除の演算子。順序依存が生まれ、上書きで足りる。
- 旧0.3でドメイン単位の通信許可を対象外にした判断。今回の改訂ではfilteredを追加するため、対象外判断を更新する。現在の契約は[ネットワークモード](network.md)を参照。
- カレントディレクトリからのポリシーファイルの自動探索。clone した時点で他人のポリシーが効く経路になる。
- 同じ環境変数名の秘密を 2 段で書いたらエラーにする案。ワークスペース別に秘密を差し替える用途が塞がる。
  キー付きテーブルで上の段が勝つ形に置き換えた。
- ポリシーファイルを `hide` で守る案。ワークツリー内のファイルだと git に空の変更として見え、
  空ファイルがコミットされうる。
- ポリシーファイルと設定ディレクトリを `ro` で守る案。祖先ディレクトリの改名による差し替えを防げず、
  参照されない秘密ファイルを平文で見せる。第 5.6 節の拒否と `secrets/` の `hide` に置き換えた。
- `/tmp` を丸ごと `rw` で渡す案。ホストの X11 と ssh-agent のソケットが見え、名前がランダムで
  `hide` できない。`hide` と共有用サブディレクトリの `rw` に置き換えた。
- `.git/hooks` と `.git/config` を `ro` にする案。`core.hooksPath` で迂回でき、`config` の `ro` は
  `git push -u` を壊す。既知の隙間として明記する。
### 端末と入れ子

- bwrap の `--new-session`。制御端末を切ると対話的なプログラムの挙動が変わりうる（未検証）。seccomp で
  `TIOCSTI` の経路だけは塞げる。
- `TIOCSTI` 対策を sysctl の確認と警告だけにする案。カーネルの素の設定では `TIOCSTI` は有効のままで、
  塞いだことにならない。
- 現行 jail の順序規則（rw を覆う hide、rw、他の hide、ro の順）。ro の祖先が hide した秘密ファイルを
  再露出する。
- 入れ子で実際に二重の bwrap を作る案。外側が空にした秘密ファイルを内側が読んで起動に失敗する。
  内側で狭める価値より規則の増加が大きい。
- CI と配布物の作り方をこの仕様に含める案。別の製品で検証の検証が発生した。
### 入力と診断

- `--help` と `--version` を他の引数があっても勝たせる案（GNU の慣習）。併用時に他のオプションを
  検査するかという次の問いが生まれる。排他の方が単純。
- `--policy-file` は利用者が明示したパスだから読み方を守らない案。境界は破れないが、無言のハングは
  第 13 節の診断の契約に反し、防御は数行で足りる。
- `--workspace` がファイルなら親ディレクトリを使う案。指定ミスの可能性が高く、意図が読めない。
- `XDG_CONFIG_HOME` の空文字と相対パスを字面どおり使う案。XDG Base Directory の慣習に反し、相対の
  設定ディレクトリを使う意味が無い。結果として第 18 節が作らないカレントディレクトリからのポリシー
  探索と同じ経路にもなる。
- `${config_dir}` の実体化を展開時に任せる案。変数の間に非対称が残り、第 5.6 節の検査で実体化を
  忘れる余地ができる。
- 共通の読み込み上限（第 14 節）を 64 KiB にする案。大きな `config` を持つリポジトリでの誤爆を避けたい。1 MiB でも
  桁で余裕がある。
- `HOME` が無い、または存在しない実行専用アカウントでの起動を支える案。`~` の展開先、設定
  ディレクトリ、第 6.5 節のホームの比較の前提が覆る。0.3 では第 2 節のとおり起動時に `env` の診断で止める。
- 秘密ファイルを第 5.6 節の対象にせず、第 14 節の根拠の文だけを直す案。`rw` の中の秘密ファイルを
  リンクに差し替える漏洩経路が残る。
- 診断の順序を委譲する案。テストが種類を観測する以上、順序で結果が変わる。第 1 節の決定性を
  診断にも及ぼす。
- 秘密の値の上限を置かず、exec の失敗（E2BIG）を第 13 節の表に足す案。`secret` で「大きすぎる」と
  言う方が利用者に親切。
- `~` を `HOME` の字面に展開し、実体化を比較とマウントの時点に任せる案。パスを取る値はすべて実体で
  一貫させる。字面を `PATH` に見せたい場面が無い。
### パスの差し替え対策

- `ro` の項目にも根の項目の検査を課す案（0.1 の当初の形）。dotfiles へのリンクを `ro` に書く
  配置が 1 回目の起動から拒否され、`ro` は差し替えられても消されても露出する組の形以外で新しく見える
  ものが無い。`ro` については露出する組の検査（生成された `hide` と固定部分のマウント先を含む）に
  置き換えた。
- `hide` の項目も根の項目の検査から外す案。`rw` の中のリンクで書いた `hide` はリンクを消されると隠し先が
  露出し、着地点しか見ない露出する組の検査では止まらない（2026-09-06 に実測）。
- 書き込める項目の中のリンクを辿る `hide` を、着地が根の項目の中なら通す案（0.1 の当初の形）。同じ
  機構（リンクを消す → 項目が飛ばされる → 隠し先が露出）で外れ、深さ 1 のマウント点なら実体のパスで
  書いた `hide` は改名できず外れないのにリンクの形は外れる（2026-09-06 に実測）。着地先を問わず止める。
- 走査の `root` と `hide-mounts` の `under` を、書き込める項目の中を参照しても着地が根の項目の中なら
  通す案。起点はマウントされないので `rw` の下位を起点にすると改名や向け直しで走査が空振りし、
  `.env` の隠しが丸ごと外れる（2026-09-06 に実測）。`rw` のマウント点そのものに限る。
- 走査で、起点の外へのリンクを一切辿らない案。起点の外にある本物の秘密へのリンク（`.env -> ~/shared/.env`）が
  隠れなくなる。`ro` の項目の中を指すリンクだけを別扱いにする形に置き換えた。
- 走査で、`ro` の項目の中を指すリンクを差し替えの可否を問わず隠さない案。差し替えられる `ro` を走査の
  隠し先へ向け直すと本物の秘密の隠しが外れる（2026-09-06 に実測）。差し替えられうる `ro` の中は
  `path` で止める形に置き換えた。
- `ro` と `hide` の項目を実体のパスで書き直す運用（利用者側でのプロファイル生成）で凌ぐ案。リンクを
  足すたびにプロファイルを直す運用になり、診断が 1 起動 1 行なので項目を 1 つずつ潰す体験が残る。
### 起動と初期設定

- 入れ子で見つかったコマンドの exec 失敗を `command not found` の 127 のまま返す案。シェルの慣習
  （見つからない 127、実行できない 126）と食い違い、原因が分かりにくい。
- 記述子の soft 上限を必要なときだけ上げる案。同じ入力で包んだコマンドの上限が変わり、第 1 節の
  決定性に反する。常に上げる。
- 包んだコマンドの argv[0] を解決した絶対パスにする案（0.1 の当初の実装）。argv[0] で振る舞いを
  変えるコマンドが打ったとおりに動かず、シェルの慣習とも違う。`--argv0` で与えた文字列を渡す。
- 組み込みの既定を持たず、README の手順でプロファイルを置かせる案（0.1 の当初の形）。入れた直後の
  起動が `policy` で止まり、「入れて即使える」にならない。
- `kakoi edit NAME`（`$EDITOR` で開く）。利便性が `$EDITOR <パス>` と同じで、`bwrap` 以外の外部
  コマンドを起動する面が増える。`init` がパスを出力すれば足りる。
- 組み込みの既定で起動するたびに通知を出す案。警告は問題の合図として残したい。毎回の 1 行は `init` を
  促す効果より邪魔が勝つ。`--print-plan` で見えることで足りる。
### シムとセットアップ

- シムの雛形に隔離を外す環境変数を置かない案。ホストは信頼する側で既知の隙間 8 で既に外せるため
  安全は増えず、実体のパスを探す手間だけが残る。
- 同梱プロファイルの `secrets` を有効な項目のまま置く案。入れた直後の起動で毎回、無い秘密ファイルの
  警告が出る。
- LLM ごとに内容の違う組み込みの既定を持つ案（`init codex` で codex 専用の内容を書き出す形）。外側の
  隔離の中で別の CLI が入れ子で動くので、外側のプロファイルが中で動きうる CLI 全部を知っている必要が
  ある。1 つを育てる（`init NAME` は同じ内容を別名で書き出すだけ）。
- シムが入れ子を自分で検出して `kakoi` を通さない案。第 12.1 節の「ホストで `KAKOI=1` を
  立てれば必ず警告が出る」がシム利用者に成り立たなくなる。入れ子でも `kakoi` を呼ぶ（許可リストの
  素通しは利用者が承認した例外なので、この理由は及ばない）。
- シムがサブコマンドごとにモデルが動くかを調べて「隔離に入れる」と「素通し」に分類する案（0.1 の
  当初の形）。包む対象の版が上がるたびに調べ直しが要り、見落としが隔離の外に漏れる（`codex review` で
  2026-09-08 に実測）。既定を全部隔離にし、素通しを利用者が承認した例外だけにした。
- シムが子プロセスとして起動して失敗を見届け、足す一覧のヒントを出す案。対話セッションの端末の扱いと
  終了コードの引き継ぎが増えてシムが厚くなる。ヒントは文章だけにする。
- 許可リストを環境変数に置く案。承認した記録がシムを読んでも分からない。
- 許可リストを設定ディレクトリの別ファイルに置く案。シムが読むファイルが増え、第 5.6 節の保護対象に
  入るかの問いが新しく生まれる。
- `--help` と `--version` をシムの素通しの特別扱いのまま残す案。例外の判断が 1 つ増える。失うのは、
  診断が出る状態では `--help` も 125 で止まることだが、診断は直すべきものなので受け入れる。
- セットアップスキルが、利用者が申告した正本のパス（プロファイルやシムの正本が他所にある場合）を
  3 つ目の書き先として差分承認の下で書く案。隔離の外で動くエージェントが書く場所を、利用者の
  設定リポジトリまで広げない。行の提案で足りる。プロファイルがリンクのときにリンク先を書く案も同じ。
- プロファイルが他所の生成物であることを、ファイル先頭の印で判定する案。生成する側に印を書かせる契約が
  増える。利用者の申告で足りる。
- シムの雛形に位置引数の写し（先頭の非オプション語を `--workspace` にする）を足す案。先頭の語が
  サブコマンドかディレクトリかを雛形は区別できない。`tool exec` は `--workspace exec` になって `path` の
  診断で止まり、`tool /etc` は `/etc` が書ける側に広がる（雛形のヘッダーが言う、緩む向きの誤読と同じ）。
### rw-copy

- 「隔離の中で書けるが外に出ない」を `ro` と `hide` の組み合わせで表す案。`ro` は書けず、`hide` は
  ホストの内容で始まらない。どちらも要求を表せない。第 6.1 節の `rw-copy` を足した。
- `rw-copy` の通常ファイルを bwrap の `--file FD DEST` で作る案。`--file` は newroot 内のパスに実体を
  書くので、DEST の親が `rw` の bind mount だとホスト側のファイルに書き抜ける（2026-09-10 に bwrap
  0.9.0 で実測）。守っているつもりで素通しになる。`--bind-data FD DEST` に置き換えた。これは内容を
  bwrap 自身の tmpfs 上のファイルに書いてから DEST に bind するので、親が何であっても書き抜けない。
  ディレクトリの複製の中では、直前に重ねた自前の tmpfs が親になるので `--file` を使ってよい（そちらは
  各エントリがマウント点にならず、改名も削除もできる利点がある）。
- `rw-copy` のディレクトリをオーバーレイで作る案。第 3 節が下限とする bwrap 0.9.0 にオーバーレイの
  引数が無い（`--overlay-src` は Unknown option。2026-09-10 に実測）。tmpfs に起動時に流し込む形に
  した。
- `rw-copy` の複製で、複製元のシンボリックリンクを辿って内容を写す案。複製が木の外へ広がり、循環と
  展開の爆発がありうる。リンクの先を隔離の中で解決させる形（リンクのまま複製）に置き換えた。木の外を
  指すリンクの先が書けるかどうかは、そこにポリシーが与えたもので決まり、隔離の中のどこからでも同じに
  できることなので、新しい経路にはならない。
- `rw-copy` を第 5.6 節の書き込める項目に数える案。中への書き込みはホストに届かないので、次の起動が
  読むものも解決の結果も変えられない。数えると、`rw-copy` の中にポリシーファイルや設定ディレクトリを
  置いた正直な配置が理由なく拒否される。露出する組の相手側に入れることで、必要な守り（書き込みを
  ホストへ通す `rw` の重なり）は残した。
- `rw-copy` にディレクトリ用とファイル用の 2 つの指令を作る案（`rw`・`rw-file` の対に倣う形）。この
  2 つが分かれているのは bwrap の bind の対象の違いによるもので、`rw-copy` は複製を作るので `ro` と
  同じく両方を 1 つで受けられる。指令を増やさない。
- `rw-copy` の複製に上限を置かない案。複製の内容は記述子と隔離の tmpfs に二重にメモリへ載るので、
  `~/.cache` のような複製元を指した指定が機械を止めうる。項目あたりの上限（第 6.1 節）で先に止める。
- `rw-copy` の複製元が読めないときに、そのエントリを飛ばして起動を続ける案。ホストの内容で始まる
  という約束を、黙って下回る。種類 `path` で止める形にした。ソケットや FIFO のように複製に意味の
  無い種別だけは、計画に出して続ける。
- `rw-copy` の複製を終了時にホストへ書き戻す案。この指令の目的は書き戻さないことである。書き戻しが
  要るなら `rw` を使う。
