# ポリシーを保護する配置

Status: Approved（2026-09-16。IR抽出・対応付けを承認。文章の追加校正は別件）


この検査は、隔離内のプログラムが設定やリンクを書き換え、**次回の起動で許可範囲を広げること**を防ぐ。

たとえば `~/cache` を `rw` にした場合、そこにポリシーファイルを置くと、隔離内から次回の指定を書き換えられる。ファイルが外にあっても、そこへ向かうリンクが `~/cache` の中にあれば同じ問題になる。

| 対象 | 守ること |
|---|---|
| ポリシー・設定ディレクトリ・秘密ファイル・PATH への追加 | 本体や、そこへ辿る途中の名前を差し替えられないこと |
| 書き込み先・隠し先・ワークスペース | 差し替えられても、信頼できる書き込み範囲の外へ出ないこと |
| 走査やマウント探索の起点 | 起点のリンクや下位ディレクトリを消して、隠す処理を外せないこと |
| 別の項目を上書きする組み合わせ | 隠した内容の再露出や、複製からホストへの書き込みを生まないこと |

以下は判定の詳細。`rw-copy` はホストに書き戻さないため、ここでいう「書き込める項目」には数えない。拒否に当たる場合、診断が示したリンクやパスの配置を直す。


## 5.6 ポリシーを書き換えられない置き場

### 判定に使うパスと書き込み範囲

この節が守るのは、**次回の起動が読む内容と、指令を適用する先**である。現在の実体だけでなく、そこへ辿る途中のリンクやディレクトリも調べる。

| 用語 | この節での意味 |
|---|---|
| 与えられたパス | 実体へ解決する前のパス。設定ディレクトリなら、第2節の規則で組み立てたパス |
| 書き込める項目 | 合成後に残る `rw` と `rw-file`。その「中」は同一か子孫を指す |
| 解決が参照するもの | パスを辿る途中で中身を見るディレクトリの実体と、辿るリンクの置き場。対象自身の実体は含めない（第2節） |
| 根の項目 | 自分の解決で、書き込める項目の中を一切参照しない書き込み項目 |

原則として、書き込み範囲は生成された `hide` の適用後に判定する。**走査の `root` と `hide-mounts.under` だけは生成前**の集合で判定する。

`rw-copy` は書き込み範囲に数えない。複製内を書き換えても、ホストの内容や次回のパス解決に届かないためである。ポリシー・設定ディレクトリ・秘密ファイルを複製内に置いても、それだけでは拒否しない。

同じ実体を指す書き込み指定が複数ある場合、すべての書き方が根の条件を満たしたときだけ、その実体を根とする。`ro`・`hide` で書かれた形は根の判定には加えず、書かれた項目として別に検査する。生成項目は参照経路を持たず、根の判定対象にならない。

### 設定・秘密・PATH を差し替えられないこと

保護対象は、読み込んだすべてのポリシーファイル、設定ディレクトリ、`secrets` の値、`env.path-prepend` の項目である。

各対象について、次の順に調べる。最初に書き込み範囲内と分かったものがあれば、種類 `path` の診断で終了する。

1. 与えられたパスの各祖先と対象自身を実体へ解決し、その実体を調べる。
2. 解決時に辿ったリンクの置き場を調べる。
3. 解決時に通ったディレクトリの実体を調べる。該当するものが複数なら、最初に通ったものを使う。

対象自身を1で調べるのは、「解決が参照するもの」に自身を含めないためである。診断には、問題のファイル・ディレクトリ・リンクのパス、それを含む書き込み項目のパス、隔離内から差し替えられるという理由を含める。保護対象が複数あるときの優先順位は第13節で定める。

#### まだ存在しない対象

| 状態 | 調べる範囲 |
|---|---|
| 秘密ファイルが存在しない | 存在する祖先と、存在しない成分までに参照したもの |
| 組み込みの既定を使い、設定ディレクトリが存在しない | 同上。隔離内から設定ディレクトリを作り、次回用のプロファイルを植えられないことを確認する |
| `secrets`・`path-prepend` が値のない変数を含む | 解決するパスがないため対象外。前者は第9節の警告、後者は飛ばしになる |

存在しない名前自身は実体を持たないため調べない。存在する最も深い祖先が書き込み範囲内なら拒否する。

#### 解決を途中で止める場合

通ったディレクトリは、同じ実体を1回だけ記録する。存在しない成分、読めない成分、先を読めないリンクに達したら解決を止め、そこまでの参照を検査する。先を読めないリンクも、その置き場を記録する。この記録方法は本節の全検査に共通する。

複数の参照が同時に条件へ当たる場合の名指し方は、第20節の委譲範囲に従う。

### 書き込み先・隠し先・起点が着地できる範囲

次の対象は、解決中に書き込み範囲を参照した場合、**着地する実体がいずれかの根の中**にあることを求める。外なら種類 `path` の診断で終了する。

- 全段の、書かれた `rw`・`rw-file`・`hide`。コマンドラインも含む。
- 明示の `--workspace`。下記の例外を除く。
- 走査の `root` と `hide-mounts.under`。

`ro` と `rw-copy` はこの条件の対象外で、後述の「再露出する組み合わせ」を調べる。`ro` は新しい書き込みを許可せず、`rw-copy` はホストへ書き戻さない。隠した内容を見せる形は再露出の条件で止め、大きすぎる複製は第6.1節の上限で止める。

実体がない項目は、第6.2節どおり飛ばす。リンク追跡の上限（第14節）を超えて実体がない場合も同じで、ここでは検査しない。次回実体が得られたときに検査する。

診断には、対象のパス、解決途中で参照した書き込み項目のパス、隔離内から差し替えられるという理由を含める。ワークスペースから引き継いだ参照も同じように扱う。

#### `hide` と探索起点：削除できるリンクを使わない

書かれた `hide`、走査の `root`、`hide-mounts.under` が、**書き込み範囲内に置かれたリンクを自分自身の解決で辿る**場合は拒否する。着地先が根の中や `rw` のマウント点そのものでも同じである。

リンクを消されると次回は対象が存在しない扱いになり、隠す処理が飛ばされるためである。実体のパスで書いた `rw` 内の `hide` は、このリンクの条件には当たらない。

ここではワークスペース由来の変数から引き継いだリンクを数えない。そのリンクの削除は `--workspace` 自身の検査で止まる。診断には、対象または起点のパス、辿ったリンクのパス、理由を含める。根への着地条件にも違反する場合は、直すべきリンクが分かるこちらの診断を優先する。

#### 探索起点：書き込みマウントの下位を使わない

走査の `root` と `hide-mounts.under` が書き込み範囲を参照する場合、着地先は**書き込み項目の実体と同一**でなければならない。下位ディレクトリへの着地は拒否する。

起点自体はマウントしない。下位を起点にすると、そのディレクトリを改名されて、次回は別の木を探索してしまう。マウント点そのものは改名できず、そこから再帰するため、この条件を通る。ただし、削除できるリンク越しの指定は前項で拒否する。

診断には、起点のパス、参照した書き込み項目のパス、理由を含める。

両起点は、走査・`hide-mounts`・秘密ファイル・`secrets/` の生成を始める前に調べる。書かれた段だけに同一性の規則（第5.4節）を適用し、書き込み範囲と根を求める。生成が後から隠す `rw` の中への着地はこの時点で通り得るが、その場所は最終的に隠される。

### ワークスペースの例外と追加条件

| 与え方 | 扱い |
|---|---|
| `--workspace` を省略 | 根への着地検査の対象外。現在地はカーネルが inode で保持しているため、解決の参照を持たない |
| 明示した実体が現在地の実体と同一 | 同じく対象外で、参照を持たない |
| それ以外 | 自身の解決を検査し、ワークスペース由来の変数へ参照を引き継ぐ |

`${workspace}`・`${worktree}`・`${git_common_dir}` で展開した項目は、明示ワークスペースの解決が参照したものを引き継ぐ。走査の `root` と `hide-mounts.under` も含む。上表の対象外の場合は、引き継ぐ参照もない。

対象外でない明示ワークスペースがリンクを辿るときは、さらに、**ワークスペース由来の変数に依存しない根の中**へ着地しなければならない。差し替え後のワークスペースから導いた書き込み範囲だけで、自分自身を正当化させないためである。

字面の指定と変数由来の指定が同じ実体へまとまった場合、その項目は変数由来として扱う。実体のパスを書くか、その場所を現在地にして起動すれば、このリンク固有の拒否には当たらない。

この追加条件の診断では、対象のパス、辿ったリンクのパス、理由を示す。根への着地条件にも違反する場合は、根への着地の診断を優先する。`hide` や探索起点での優先順位とは異なる。

### 隠した内容や書き込みを再び通す組み合わせ

書き込み範囲を参照して解決される**書かれた項目**は、次の組み合わせで新たな読み取りやホストへの書き込みを生むとき、種類 `path` の診断で終了する。実体のパスで書いてあっても、書き込み範囲を参照するなら対象になる。

| 後から適用する項目 | 無効にしてはいけない相手 |
|---|---|
| `rw`・`rw-file` | `hide`・`ro`・`rw-copy` |
| `ro`・`rw-copy` | `hide` |
| `hide` | なし。新しく露出させない |

相手を探す位置は2か所ある。

1. **同じ実体の下の段。** 各段へ第5.4節の置き換えを順に適用し、その項目の段の直前に残っていた相手を見る。
2. **実体の真の祖先。** 全段を合成した後、内側から最初に項目が効いている祖先だけを見る。同じ段・上の段・生成の段も含む。最寄りの項目が `rw` なら、すでに露出しているため、この条件では止めない。

生成した `hide` は同じ実体の書かれた項目を置き換えるため、1の相手にはならない。祖先に残る場合は2の相手になる。たとえば、自動で隠す `secrets/` の中へ、差し替え可能な `ro` が着地する形は拒否する。

診断には、対象のパス、無効にする相手のパス、隔離内から差し替えられるという理由を含める。`--workspace` 自身はこの検査の対象外だが、その参照を引き継いだ書かれた項目は対象になる。

### 固定マウントとホーム全体の保護

| 条件 | 対象と結果 |
|---|---|
| 実体が `/` と同一、または `/dev`・`/proc` と同一かその子孫 | 指令を問わず `path` で終了。参照経路の有無も問わない。診断に項目のパスと理由を示す |
| 実体がホームまたはその祖先（`/` を含む） | 合成後の `rw`・`rw-file` は、どの段からの指定でも `path` で終了 |
| ホームを `rw-copy` にする | ホストへ書き戻さないため広さの拒否には含めない。既存仕様では、ホーム全体の複製は第6.1節の上限に当たり `path` で終了する |

`/proc` をホストの内容で覆うと隔離外のプロセスが見え、`/dev` や `/` を覆うと隔離の土台が壊れるためである。

### 検査の順序

第13節の段階7では、次の順に進める。

1. 走査の `root` を合成後の並び順で検査する。
2. `hide-mounts.under` を合成後の並び順で検査する。
3. 自動生成する項目を求める。
4. 保護対象のパスを検査する。
5. 書かれた項目を第6.4節の順で調べ、次に `--workspace` を調べる。各項目では根への着地、再露出の順とする。ただし前述したリンク診断の優先規則を適用する。項目間で検査を交互に進める順は第20節に委譲する。
6. 固定部分への着地を拒否する。
7. 広すぎる書き込み範囲を拒否する。


### 背景：書き込み先どうしで安全性を正当化できない理由

なぜ根の項目という考え方が要るか。書き込める項目の中にあるものを参照して解決されるパスは、隔離の中からその参照先を書き換えることで、次の起動に別の実体を読ませたり、別の実体へ指令を適用させたりできる。前置きの実体だけを見ると、前置きではない場所にあるリンク（`~/policies` が `~/cache/link/pol`を指し、`~/cache/link` が `rw` の中）を張り替えられる。

リンクの置き場まで見ても、リンク先が `..` で`rw` の中のディレクトリを通り抜ける形（`~/policies` が `~/cache/x/../../real/pol` を指し、`~/cache/x`が `rw` の中の実ディレクトリ）では、そのディレクトリをリンクに差し替えられる。保護対象だけを守っても、入れ子の項目（`rw = ["~/cache", "~/cache/pip/http"]`）は `~/cache/pip` をホストの別の場所へのリンクに差し替えると、次の起動がそこへ `rw` を適用する。

飛び先が「いずれかの書き込める項目の中」であればよいとすると、差し替えた飛び先同士が互いを正当化し、`rw = ["${worktree}", "~/cache"]` で `--workspace` を`rw` の中のリンク越しに与えた場合は `${worktree}` の項目自身が飛び先を正当化する。この例では引き継ぎが無ければ、変数の値は実体のパスなのでその項目自身は書き込める項目の中を参照しないことになる。

カレントディレクトリと、それと同じ実体の `--workspace` を対象外にするのは、既にそこにいるプロセスは差し替えで移動しないためで、第 14 節で受け入れた起動環境への信頼（カレントディレクトリを含む）と同じ水準である。根の項目は、この連鎖を「自身の解決が書き込める項目の中を参照しない項目」で断ち切る。通った項目の中に限らず「いずれかの根の項目の中」とするのは、`rw` の項目については別の根の項目の中へ着地しても新しく露出するものが無い、と考えたためである。

ただし、飛び先の根の項目の中に `hide` または `ro` で書いた項目があると、リンク越しに着地した項目がそれを無効にする。同一の実体なら、上の段から着地した項目が第 5.4 節の同一性で下の段の `hide` や `ro` を置き換える。同一でなくても、`hide` や `ro` の中（真の子孫）に着地すれば、第 6.4 節の順序で狭い項目が後に乗り、隠していた中身が見える。後者は段に依らない:下の段の `rw` がコマンドラインの `hide` の中へ着地しても、同じ順序で後に乗る。

新しく露出するのは、着地した項目が `rw` または `rw-file` で無効にする先が `hide`、`ro`、または `rw-copy` のとき、および着地した項目が `ro` または `rw-copy` で無効にする先が `hide` のときである（`hide` は何も露出せず、`ro` が `ro` に重なっても、`rw-copy` が `ro` に重なっても新しく見えるものは無い）。

`rw-copy` を相手側に数えるのは、利用者が「書き込みが外に出ない場所」として指定したところに、差し替えられうる `rw` や`rw-file` が第 6.4 節の順序で後から乗ると、その書き込みがホストへ通ってしまうためである。この形を「露出する組」と呼び、検査の規則は上の「露出する組の検査」に定める。別の根の項目の中へ飛ぶこと自体（下の観測条件の「別の根の項目への着地」の形）は残す。何も参照しない項目（実体のパスで書いた `rw = ["/tmp/kakoi"]` を `hide = ["/tmp"]` の中に置く第 6.4 節の表の形）はこの規則に当たらない。

正直な配置で項目を `hide` の中へリンク越しに置きたいとき、その `hide` が書き込める項目の外にあるなら、実体のパスを書けば通る。`hide` が `rw` の中にあるなら、実体のパスで書いてもその `rw` を参照するので、`rw` も `rw-file` も `ro` も通らない（規則 2）。そこでは項目を `hide` の中に置く配置そのものを諦める。`rw` の中の `hide`・`ro` の項目は着地先を変えられると元の対象を隠せなくなるが、それは下の「読み取り専用で重ねるだけでは足りない理由」のとおり祖先の改名でも起きることで、この規則の穴ではない。

入れ子を禁じないのは、第 6.4 節の表にある `rw` の中の `ro` のような形を残すためである。利用者が `rw` の中に置いたリンク（先がどの根の項目の中でもない。`hide` と走査の `root`・`hide-mounts` の `under` は先を問わない）のパスを`rw`、`rw-file`、`hide` の項目や走査の `root`、`hide-mounts` の `under` に書くと、正直な配置でもこの規則に当たって 1 回目の起動から拒否される。リンク先の実体のパスを書けば通る。

同じリンクのパスを `ro` の項目に書く配置（dotfiles へのリンクを `ro` にする形）は通るが、その守りは第 16 節の既知の隙間 15 の水準である: 隔離の中でリンクを消して同じ名前の通常ファイルを置けば、同じ起動の中で読む側のパスの内容を変えられ（守られるのはリンク先の実体だけ。2026-09-06 に実測）、リンク先が書き込める項目の外なら`--ro-bind / /` で既に読み取り専用なので `ro` の項目は何も足していない。

秘密ファイルを保護対象にするのは、`rw` の中の秘密ファイルを隔離の中からホストの任意のファイルへのシンボリックリンクに差し替えると、次の起動がその内容を環境変数として隔離に持ち込むためである。


### 背景：読み取り専用の重ね掛けでは守れない場合

読み取り専用で重ねるだけでは足りない理由: 重ねたファイル自体は動かせないが、その祖先ディレクトリの改名は許され、同じパスに別のファイルを置けば次回の起動がそれを読む（2026-09-03 に bwrap 0.9.0 で実測）。


### 受け入れる配置と拒否する配置の具体例

成功の観測条件: 上の表の規則で合成した結果が `--print-plan=full` に表示され、削除の演算子に相当する書き方はどの段でも読み込み失敗になり、ワークツリーの中に置いたポリシーファイルを `--policy-file` で指すと理由付きの診断で止まり、`rw` の中を指す `secrets` の値も同じ診断で止まり、`rw` の外にあるポリシーファイルを `rw` の中に置いたシンボリックリンク越しに指しても同じ診断で止まり、リンク先が `..` で`rw` の中のディレクトリを通り抜ける形でも同じ診断で止まる。

書かれた項目と `--workspace` については次の対がそれぞれ観測される: `rw = ["~/cache", "~/cache/pip/http"]` の正直な配置は通り、`~/cache/pip` をホストの別の場所へのリンクに差し替えると `path` で止まる。

`rw = ["~/a", "~/b"]` と `hide = ["~/b/creds"]`と `~/a/l -> ~/b/x` で `ro = ["~/a/l/y"]` は通り、`l` をどの項目でもない場所へ差し替えても通り（`ro` は新しく露出しない）、`l` を `~/b/creds` の中へ差し替えると止まる。`rw = ["${worktree}", "~/cache"]` に`--workspace ~/cache/proj` は通り、`proj` を別の場所へのリンクに差し替えると止まる。

`rw = ["~/cache"]`の中の `rw-file` は、正直な配置は通り、差し替えると止まる。`rw = ["~/cache"]` の中の実体のパスで書いた`hide` は通る。`rw = ["~/proj"]` で `~/proj/secrets` がどの項目でもない `~/vault` を指す`hide = ["~/proj/secrets"]` も、`rw = ["~/a", "~/b"]` で `~/a/l` が `~/b/creds` を指す `hide = ["~/a/l"]` も、1 回目の起動から止まる。

書き込めない場所だけを参照する解決は影響を受けない: `rw = ["${worktree}"]` だけのプロファイルで `--workspace ~/cache/proj`（`~/cache` はどの項目でもない）は通る。明示した `--workspace` がカレントディレクトリと同じ実体なら、`rw` のワークツリーの下位でも通る。

リンクを辿る明示の `--workspace` については: `rw = ["${worktree}"]` で`~/proj/sub` を別の場所へのリンクに差し替えた後、別のカレントディレクトリから `--workspace ~/proj/sub` を与えると `path` で止まり、`rw = ["~/work"]` で `~/work` がリンクでも `--workspace ~/work/proj` は通る。

`rw = ["~/a", "~/b"]` と `hide = ["~/b/creds"]` のプロファイルに、`~/a/link` が `~/a/real` を指す正直な配置で`--rw ~/a/link` は通り、`~/a/link` を `~/b/creds` へ向け直しても `~/b/creds/sub` へ向け直しても `path` で止まる。

`rw = ["~/a", "~/b", "~/a/link"]` のプロファイルで `~/a/link` を `~/b/creds/sub` へ向け直し、`--hide ~/b/creds` を与えても `path` で止まり、同じ `hide` をプロファイルに書いても止まる。`rw = ["~/b"]` と `hide = ["~/b/creds"]` のプロファイルに `--hide ~/b/creds` も `--hide ~/b/creds/sub` も通る。

#### 複製への配置

`rw-copy` については次の対が観測される: `rw-copy = ["~/policies"]` の中にポリシーファイルを置いた起動は通り（保護対象のパスの検査の対象にならない）、同じ配置を `rw` にすると `path` で止まる。`rw = ["~/a", "~/b"]` と `hide = ["~/b/creds"]` のプロファイルに、`~/a/link` を `~/b/creds` へ向けた`--policy-file` の `rw-copy = ["~/a/link"]` は `path` で止まり、同じ形で相手が `ro = ["~/b/creds"]` なら通る。

逆向きに、`rw-copy = ["~/b/creds"]` のプロファイルに、`~/a/link` が `~/b/creds/k` を指す`rw-file = ["~/a/link"]` を `--policy-file` で足すと `path` で止まる。

#### 別の根・自動生成された隠し先・固定部分・起点

別の根の項目への着地: `rw = ["~/a", "~/b"]` で `~/a/link` を `~/b/real` へ向けた `--rw ~/a/link` は通る。生成された `hide` の中への着地: `rw = ["~/a"]` と `~/a/link` が `${config_dir}/secrets/other`（`secrets` に書かれていないファイル）を指す `ro = ["~/a/link"]` は `path` で止まり、`hide-mounts` で隠した `/mnt/c`の中を指す `ro` も止まる。

固定部分: `ro = ["/proc"]` と、`~/a/link` を `/proc` へ向けた`ro = ["~/a/link"]` は `path` で止まる。走査の起点: `rw = ["~/a"]` で `~/a/link` がどの項目でもない`~/proj` を指す `root = "~/a/link"` は `path` で止まり、`rw = ["~/b"]` で `root = "~/b/tree"`（`rw` の下位）も `path` で止まり、`root = "~/b"` と `root = "${worktree}"` は通る。

反例: 上の段の `rw` が下の段の`hide` と同じパスを指したとき、どちらが勝つかが段の順序以外で決まる。差し替えた飛び先が別の差し替えた項目によって正当化される。`ro` のリンクを `secrets/` の中へ向けると次の起動で秘密ファイルが読める。
