## 16. 公開ドキュメント

この章は、利用者へ何を説明し、どの補助物を届けるかを定める。シムとセットアップスキルの動作は、[シムの契約](shim.md)と[セットアップスキルの契約](setup-skill.md)に分けて記載する。

### 利用者がたどる文書

公開ドキュメントは、README（英語）と、README から直接リンクする `docs/` 以下の英語の文書から成る。README には、目的、コンテナや VM の代替ではないことの注意、対応環境、インストール、最短の起動手順、ポリシーファイルの最小の例、仕組みの概要（段の優先順位、指令、秘密・ネットワーク・環境変数）、シムの最短の例とセットアップスキルの案内、保証することとしないこと、各文書への導線、0.3 で作らないものの代表例を短く載せ、詳細は次の文書に分ける。

- `docs/getting-started.md`: 設定ディレクトリ、`init`、組み込みの既定、秘密の渡し方、入れた直後の起動。
- `docs/cli.md`: コマンドラインの使い方、計画、終了コードと診断。
- `docs/policy.md`: ポリシーファイルの書き方と、第 5.6 節の拒否の説明。
- `docs/shim.md`: シムの雛形とセットアップスキル。
- `docs/security.md`: 信頼境界、保証することとしないこと、既知の隙間、0.3 で作らないもの。

### 既知の隙間を隠さない

本仕様の他の節で「README に書く」「README に載せる」とあるものは、README か上の文書のいずれかに書くことを指す。既知の隙間は `docs/security.md` に載せ、README からその節へ直接リンクする。既知の隙間は次の 15 である。

1. `hide` したディレクトリの中のコマンドが「見つかった」と判定される（第 4.2 節）。
2. 起動後に現れたファイルは隠れない（第 6.2 節）。
3. 走査で隠したファイルが git に追跡されていると、隔離の中で空の変更として見える（第 6.3 節）。
4. bind mount やハードリンクによる別経路は隠せない。`hide` と `rw-copy` は指定した実体のパスにだけ
   効く。`rw-copy` の複製元と同じ inode へのハードリンクが `rw` の中にあれば、そこへの書き込みは
   ホストのファイルに届く。
5. マウントするパスと秘密ファイルのパスは bwrap の引数に載り、秘密の値は `/proc` を通してホストから
   読める（第 8 節）。
6. 名前が規則に合わないホストの認証情報の環境変数は `inherit` で隔離に入る（第 9 節）。
7. `TIOCLINUX`、端末の応答を使った注入、ディスプレイサーバ経由の入力合成は seccomp で塞がない
   （第 11 節）。同梱プロファイルは経路を `hide` と `unset` で消す。
8. 環境を空にした入れ子と、ホスト側で `KAKOI=1` を立てた起動（第 12.1 節）。
9. `kakoi` は起動された環境を信頼する（第 14 節）。カレントディレクトリも含む: `rw` の中を通る
   パスで `cd` し直してから起動すると、隔離の中で差し替えたリンクの先が作業場所になる。
10. `rw` で渡した領域は、利用者がホスト側で後から実行するものの置き場になりうる。`.git/hooks` と
    `.git/config` は利用者の `git` 操作で自動的に読まれる。隔離の設計では防げず、利用者が差分を
    見るしかない。
11. 32 ビットと x32 のバイナリは動かない（第 11 節）。
12. ワークツリーの `.git` を消すと、次回の起動でワークツリーの導出が祖先のリポジトリに変わりうる
    （第 6.5 節）。
13. `git init --separate-git-dir` で作ったメインのワークツリー（`.git` が通常ファイルで、指す先に
    `commondir` も `core.worktree` も無い）は、第 5.2 節の相互リンクのどちらの形にも当たらず `path` で
    止まる。
14. 第 5.6 節の根の項目の検査は今回の起動の書き込める項目を基準にする。ワークツリーの下位を字面で書いた
    項目（例: `rw = ["${worktree}", "~/work/a/b"]`）は、ワークツリーが `~/work` の起動の隔離の中で
    `~/work/a` をリンクに差し替えられ、次にワークツリーが別の場所になる起動ではその差し替えが見えず、
    リンクの先に `rw` が付く。項目のパス自身がリンクに差し替えられる形（`~/work/a/b` を差し替え、
    次の起動で `--workspace ~/work/a/b/inner` を別の場所から与える）も同じ。同じワークツリーから
    起動すれば止まる。閉じるには前回の起動の書き込める項目を覚える必要があり、第 14 節に反するので
    受け入れる。ワークツリーの下位は変数で書く。
15. `rw` の中にある `ro` と `hide` の項目の守りは完全ではない。リンクで書いた `ro` が守るのはリンク先の
    実体だけで、隔離の中でリンクを消して同じ名前の通常ファイルを置けば、同じ起動の中で読む側のパスの
    内容を変えられる（一時ファイルと rename で保存するエディタもリンクを置き換える）。リンク先が
    書き込める項目の外なら、そこは元から読み取り専用で、`ro` の項目は何も足していない。次の起動では
    リンクの差し替えで別の場所が読み取り専用になるか、削除で読み取り専用が外れる（新しく見えるもの
    は第 5.6 節の露出する組の検査が止める。リンクで書いた `hide` は根の項目の検査が 1 回目から止める）。
    リンクでなくても、祖先ディレクトリの改名と同じパスへの別ファイルの配置で、次の起動が読む内容を
    変えられる（第 5.6 節）。`ro` で守れるのは、エージェントが読む実体の内容が意図せず書き換わらない
    ことまでで、エージェントが別の内容を読むように仕向ける迂回は止められない。

### ポリシーの説明に含めること

#### 配置保護の理由と回避策

`docs/policy.md` は、第 5.6 節の拒否が直感に反しうることを認めたうえで、その理由（祖先の改名による差し替え）と、dotfiles のように設定ディレクトリの実体をワークツリーに含む場合の書き方（`--workspace` で下位ディレクトリを指し、`rw = ["${workspace}", "${git_common_dir}"]` とするプロファイル）を載せる。

`rw` のワークツリーの下位ディレクトリを `--workspace` で明示するときは、そこをカレントディレクトリにして起動すること（第 5.6 節の根の項目の検査の対象外になる）と、リンクを経由するパスを別の場所から `--workspace` で明示すると止まるので実体のパスを書くかそこで起動すること（エイリアスのリンク越しの `--workspace` も同じ）も載せる。

`rw` の中に置いたリンクのパスを `hide`、走査の `root`、`hide-mounts` の `under` に書くと着地先を問わず止まり、`rw`、`rw-file` に書くとリンク先がどの根の項目の中でもなければ止まるので、リンク先の実体のパスを書くこと、同じ形の `ro` は通るがその守りは既知の隙間 15 の水準であることも載せる。

#### rw-copyの説明

`rw-copy`（第 6.1 節）については、`hide` との対比（初期状態が空かホストの内容か）、用途の例を 1 つ（隔離の中の道具に設定ファイルを書き換えさせるが、その結果をホストに出さない）、複製の作られ方（シンボリックリンクはリンクのまま、モードは引き継ぐ、所有者と時刻とハードリンクの共有は引き継がない）、上限と失敗の扱い、そこに置いたポリシーファイルが拒否されないことを載せる。

#### 秘密と一時領域

秘密ファイルは設定ディレクトリの `secrets/` に置くこと、`/tmp/kakoi` は利用者かシムが作り`kakoi` は作らないこと、無ければその項目が飛ばされて `/tmp` が空のままになることも載せる。

### 同梱する既定プロファイル

`examples/profile/default.toml` に、WSL2 向けのプロファイルを置き、README から指す。内容は、現行のcodex 用 jail のマウント表を本仕様の形式に写したもの（パスは書かれたとおりで、リンクを実体に解決して書き直さない）に、次を加えたものである。

- `rw`: `${workspace}`、`${worktree}`、`${git_common_dir}`、`/tmp/kakoi`
- `hide`: `/tmp`、`/run/user`
- `.env` の走査、`/mnt` 以下の `9p` と `drvfs` の `hide-mounts`
- `env.unset`: `SSH_AUTH_SOCK`、`DISPLAY`、`WAYLAND_DISPLAY`、`XAUTHORITY`、`*_TOKEN`、`*_API_KEY`、
  `*_SECRET*`、`*_PASSWORD`、`AWS_*`、`GH_*`、`GITHUB_*`
- `secrets`: `${config_dir}/secrets/` 以下を指す書き方を、コメントにした 1 行で例示する。有効な項目は
  置かない。組み込みの既定で起動した利用者が、置いていない秘密ファイルの警告（第 9 節）を起動のたびに
  見ないためである。秘密を渡す利用者はコメントを外す

`/tmp` を `hide` にする理由（ホストのソケットが名前で隠せない）と、`/tmp/kakoi` がホストとの共有場所であることを `docs/policy.md` に書く。

### インストールから初回起動まで

README のインストールの節は、ビルドの道具を持たない利用者が最初に読む形を先頭に置く。リリースに添えた実行ファイルを入れる手順（インストーラで入れる形と、書庫を手で取る形）を先に書き、ソースからビルドする形はその後ろに置く。

インストールの直後に `kakoi -- COMMAND` が組み込みの既定で動くことを書き、`init` と `--print-plan` を最短の起動手順として示す。

`docs/getting-started.md`と`docs/shim.md`には、次を任意の調整として案内する。

- **プロファイル**：`kakoi init`で境界を手元のファイルへ書き出し、直せる。既定はWSL2を想定しており、中身はinitかprint-planで読める。
- **秘密**：GitHubの認証情報を渡す場合は、書き出したプロファイルのsecretsのコメントを外し、`secrets/gh-token`を置く。
- **シム**：同梱雛形を写し、先頭のツール節を埋めてPATHへ置く。同梱値はcodexの例である。
- **セットアップスキル**：`gh skill install`で導入できる。実行は隔離外に限る。シム導入前、`KAKOI_SHIM_OFF=1`、またはkakoiを通さないCLIを使う。

セットアップを隔離外で行うのは、配置保護が設定ディレクトリへの書き込みを認めないためである。その間エージェントは隔離されない。スキルには書き込みごとの差分承認を指示し、CLI側も承認を求めるモードで使うよう案内する。スキルの指示を守るかどうかはエージェントCLIの振る舞いに依存する。

#### 初期状態で見えないもの

入れた直後の起動では `/tmp/kakoi` が無いので `/tmp` は空で、`~/.config/gh` は隠れるので中の `gh` は未認証であることは、README と `docs/getting-started.md` の両方で述べる。

### 確認する結果

成功の観測条件: READMEだけを読み、インストールの直後に `kakoi -- COMMAND` を起動でき、`init` してプロファイルを直せる。雛形、スキル、既知の隙間が README から 1 回のリンクで辿れる。反例:既知の隙間が仕様書にしか書かれていない、または README から直接リンクされていない文書にしか無い。README を読んでも、起動の前にプロファイルを置く手順が要ると読める。
