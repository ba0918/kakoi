# 見せるものを選ぶモード

この章は、隔離の中に見せる場所と起動できるプログラムを、書いたものだけに絞る 2 つのモードを説明する。
マウントのモード `"listed"` は、`土台` と書いた場所だけを見せ、ほかの場所（ソケットや認証情報の置き場）を隔離の中に存在させない。
コマンドのモード `"listed"` は、`commands.allow` に書いたプログラムだけを起動できるようにする。
どちらも、書かなければ今までの形（`"host"`）になる。
今までの形の見え方は [マウントの解決](07-mounts.md) に、使い方を選ぶ規則は [コマンドのガードレール](13-command-guard.md) にある。

用語の `土台`、`見せた場所`、`隔離の中の最初のプロセス` の意味は [IR の用語集](../../ir/core/CONTEXT.md) にある。

## マウントのモード
<!-- @kotowari[REQ-467:56efc0a4, EX-902:bff66815, EX-903:90ca112c, EX-904:c6c5962c, EX-946:9e592263] -->

`mounts.mode` は `"host"` か `"listed"` で、どの段にも書かれていなければ `"host"` になる。
`mounts.system` は真偽値で、どの段にも書かれていなければ `true` になる。

```toml
[mounts]
mode   = "listed"
system = true
rw     = ["${workspace}", "${worktree}", "${git_common_dir}"]
ro     = ["~/.local/share/mise/installs/claude"]
```

どれかの段が `"listed"` にすると、上の段が `"host"` を書いても合成後は `"listed"` になる。
どれかの段が `mounts.system = false` にすると、上の段が `true` を書いても合成後は `false` になる。
ジョブごとのポリシーが誤っていても隔離がゆるまないようにするためで、`network.mode` や `env.mode` の「上の段が上書きする」とは規則が違う（[段の合成規則](05-policy.md#段の合成規則)）。

次のときはポリシーの読み込みに失敗し、種類 `policy` の診断で終わる（終了コード 125）。

- `mounts.mode` に `"host"` と `"listed"` 以外の値を書いた（例: `"clear"`）。
- `mounts.system` に真偽値以外を書いた。
- 合成後の `mounts.mode` が `"listed"` でないのに、`mounts.system` が `false` である。隠したつもりで全部見えている状態を作らないためである。

## listed で見える場所
<!-- @kotowari[REQ-468:203365f4, EX-905:5ed100ff, EX-906:72211ee3, EX-907:10e8377d, EX-908:7d744631, EX-909:2a0a4e7e, EX-942:60dbf3ec, EX-943:2ac0076b, EX-949:20ead556] -->

マウントのモードが `"listed"` のとき、隔離の中に見えるのは次のものだけで、ほかのパスは存在しない。

| 見えるもの | 見え方 |
|---|---|
| `土台`（`/usr`、`/bin`、`/sbin`、`/lib`、`/lib64`、`/etc`） | 合成後の `mounts.system` が `true` のとき、読み取り専用 |
| `rw`、`rw-file`、`rw-copy`、`ro` の項目 | `"host"` のときと同じ見え方 |
| `/tmp` | 隔離専用の空のディレクトリ（[/tmp](#tmp)） |
| 名前解決の設定の指す先 | 読み取り専用のファイル 1 つ（[名前解決の設定](#名前解決の設定)） |
| `/dev` と `/proc` | `"host"` のときと同じく隔離用のもの |

`/run` のソケット（docker.sock など）、`/mnt`、ホームのほかの場所は、書いていなければ隔離の中から調べても存在しない。
`mounts.system = false` なら `土台` も見せないので、`/usr` を書いていなければ `/usr` も存在しない。
`土台` のうちホストに無いディレクトリ（`/lib64` の無いディストリビューション）は、無いマウント項目と同じく理由を付けて計画に示して飛ばし、起動は止めない。

`見せた場所` の中の `hide` と走査は、`"host"` のときと同じに隠す。
`見せた場所` の外に向いたものは、元から存在しないので隠すものが無い。
重ねると存在しないはずの場所が書ける空のディレクトリとして現れてしまうので、次のものは重ねずに理由を付けて計画に示して飛ばす。

- `見せた場所` の外に向いた `hide`。書いたものも、秘密のファイルや設定ディレクトリの `secrets/`、走査から生成したものも同じである。設定ディレクトリを書いていなければ、その `secrets/` は存在せず、計画には飛ばした `hide` として出る。
- `見せた場所` の外を根とする走査と、`見せた場所` の外を `under` とする `hide-mounts`。

見張り役が包む本物は、その場所と実体が隔離の中に見えているものに限る。
`PATH` の先頭の見せていないディレクトリと `/usr/bin` の両方に `git` があれば、見張り役は `/usr/bin/git` を本物として起動する。

項目に書いたパスから辿った先の実体までにあるシンボリックリンクは、同じ行き先の文字列を持つ読み取り専用のリンクとして隔離の中に作り直す。
kakoi は項目をリンクを辿った先の実体のパスにマウントするので、作り直さないとリンクで管理する設定（dotfiles）をツールがいつものパスで見つけられない。
ホームの `a` が `b` を指すリンクで `~/a` を `ro` に書けば、隔離の中で `~/a` の下のファイルを読め、`~/a` は `b` を指すリンクで、そのリンクは書き換えられない。
項目に書いたパスがリンクなら、辿った先の実体がその項目として見えるので、指す先を別の項目として書かなくてよい。
見せたディレクトリの中にあるだけのリンク（どの項目のパスの途中にも無いもの）はホストのとおりに見えるが、その指す先は、そこを項目として書いたときだけ見える。

## 親のディレクトリと書ける場所
<!-- @kotowari[REQ-469:5f8fff88, EX-910:507c94ff, EX-911:3e11374a] -->

`見せた場所` の祖先のうち、ほかの `見せた場所` で覆われていないものは、`見せた場所` とその祖先だけを含むディレクトリとして kakoi が作る。
ホームの下の 1 つのディレクトリだけを書けば、隔離の中でホームの一覧を取ってもそのディレクトリだけが並ぶ。
隔離の根と、こうして作った祖先のディレクトリは読み取り専用で、新しいファイルは作れない。

隔離の中で書けるのは次のものだけである。

- `rw`、`rw-file`、`rw-copy` の項目
- `見せた場所` の中の `hide` で隠したディレクトリ
- `/tmp`
- `/dev` の中で隔離用に用意したもの

`"host"` のモードでも書いていない場所は読み取り専用なので、書ける場所の考え方はそろっている。

## /tmp
<!-- @kotowari[REQ-470:d16b9217, EX-912:e9bb29b4, EX-913:98721131] -->

マウントのモードが `"listed"` のとき、kakoi は隔離の中の `/tmp` に、中身の無い書けるディレクトリを隔離専用に用意する。
ホストの `/tmp` の中身（X11 や ssh-agent のソケット）は見せない。
隔離の中で `/tmp` に作ったファイルはホストの `/tmp` に現れず、終了とともに消える。

ポリシーが `/tmp` の下の場所（`/tmp/kakoi`）を `rw` に書いていれば、その場所は用意した `/tmp` の上にホストのものとして見え、書いたものはホストに残る。
ポリシーが `/tmp` そのものを項目に書いたときは、その項目の見え方が用意した `/tmp` に勝つ。

## 名前解決の設定
<!-- @kotowari[REQ-471:7cddb741, EX-914:7120aa96, EX-915:5db59867] -->

マウントのモードが `"listed"` で合成後の `mounts.system` が `true` のとき、ホストの `/etc/resolv.conf` が `土台` の外を指すシンボリックリンクなら、kakoi はリンクを辿った先のファイル 1 つだけを、隔離の中の同じパスに読み取り専用で見せる。
WSL2 の `/etc/resolv.conf` が `/mnt/wsl/resolv.conf` を指すなら、隔離の中で `/etc/resolv.conf` をホストと同じ中身で読める。
そのファイルを含むディレクトリのほかの中身は見せないので、隔離の中で `/mnt/wsl` の一覧を取っても `resolv.conf` だけがある。

辿った先がホストに無いときは、無いマウント項目と同じく理由を付けて飛ばす。
`/etc` の下のほかのリンクは扱わない。
ネットワークのモードが filtered のときは kakoi が `/etc/resolv.conf` を差し替えるので、このファイルは見せない。
差し替えたものは、`mounts.system` によらず隔離の中の `/etc/resolv.conf` で読める。

## 抽象 UNIX ソケット
<!-- @kotowari[REQ-472:dbe9042a, EX-916:584c4535, EX-917:982906c2] -->

抽象 UNIX ソケットはファイルシステムに無いので、マウントでは隠せない。
ネットワークの名前空間を分けない `"host"` では、デスクトップの D-Bus や X11 のようなホストのものに届いてしまう。

マウントのモードが `"listed"` でネットワークのモードが `"host"` のとき、kakoi は隔離の中のプロセスに Landlock の scope を掛け、隔離の外で作られた抽象 UNIX ソケットへの接続を止める。
隔離の中で作った抽象 UNIX ソケットには、隔離の中のプロセスどうしで繋がる。
ネットワークのモードが `"none"` と filtered のときは、名前空間が分かれていて元から届かないので scope を掛けない。

ホストの Landlock が抽象 UNIX ソケットの scope（ABI 6、Linux 6.12 以降）を持たないときは、コマンドを実行せず種類 `bwrap` の診断で 125 とする。
この確かめは bwrap の所在の段階で行い、計画表示でも行う。

## 作業ディレクトリとコマンドの探索
<!-- @kotowari[REQ-483:912e828e, REQ-484:b0149d04, EX-944:f696987b, EX-945:4da8b724, EX-950:e4169792, EX-951:33c60291] -->

マウントのモードが `"listed"` のとき、作業ディレクトリの実体がどの `見せた場所` の中にも無ければ、種類 `path` の診断で終わる。
見せていない作業ディレクトリは隔離の中に存在せず、bwrap の分かりにくい失敗になるためである。
この検査は計画表示でも行う。
`${workspace}` を `rw` に書いてワークスペースで起動すれば、コマンドを実行する。

起動するコマンドを隔離へ渡す `PATH` で探すとき（[実行するコマンドの探し方](03-cli.md#実行するコマンドの探し方)）は、その場所と実体が隔離の中に見えていない候補を飛ばして先を探す。
`PATH` の先頭の見せていないディレクトリと `/usr/bin` の両方に同じ名前のプログラムがあれば、`/usr/bin` のものが起動する。
見えている場所のどこにも無ければ、名前を説明とする `command not found` で 127 になる。
シム（mise や Safe Chain）を通したいときは、その置き場を見せる。

## コマンドのモード
<!-- @kotowari[REQ-474:d94a0b63, EX-920:e8f07d18, EX-921:bfdda88e] -->

`commands.mode` は `"host"` か `"listed"` で、どの段にも書かれていなければ `"host"` になる。
`commands.allow` はパスの一覧で、書き方はマウントの項目と同じ（絶対パス、`~` で始まるもの、4 つの変数で始まるもの）である。

```toml
[commands]
mode  = "listed"
allow = [
    "~/.local/share/mise/installs/claude",
    "/usr/bin/git",
    "/usr/lib/git-core",
    "/usr/bin/sh",
]
```

どれかの段が `"listed"` にすると、上の段が `"host"` を書いても合成後は `"listed"` になる。
`commands.allow` はほかのリストと同じく段をまたいで連結し、上の段が足す。
プロファイルが `"listed"` で git を許し、`--policy-file` が `"host"` で cat を許すと、合成後のモードは `"listed"` で、許すプログラムは git と cat になる。

次のときはポリシーの読み込みに失敗し、種類 `policy` の診断で終わる。

- `commands.mode` に `"host"` と `"listed"` 以外の値を書いた。
- 合成後の `commands.mode` が `"listed"` でないのに、`commands.allow` に項目がある。`allow` を書いただけで全部が止まる事故と、書いたのに効いていない状態の両方を避けるためである。`mode` と `allow` は一緒に書き、外すときは一緒に外す。

コマンドのモードはマウントのモードによらず使える。

## 許していないプログラムを止める
<!-- @kotowari[REQ-475:0dcb8ef1, EX-922:a53bce82, EX-923:6ff1020c, EX-924:5a7924b6, EX-947:5c536d6f, EX-948:0f389861] -->

コマンドのモードが `"listed"` のとき、bwrap はコマンドの代わりに `隔離の中の最初のプロセス` を起動する。
それは kakoi 自身の実行ファイルで、Landlock を掛けてからコマンドを起動する。
Landlock はマウントを禁じるので、bwrap がマウントを終えた後の隔離の中でしか掛けられないためである。
kakoi 自身の実行ファイルは見張り役と同じく kakoi だけの場所に読み取り専用で置くので、マウントのモードが `"listed"` で kakoi の場所を見せていなくても動く。

Landlock は、`commands.allow` の項目と、kakoi が自動で許すものだけに実行を許す。

- 項目は `隔離の中の最初のプロセス` が隔離の中のパスとして開く。
- 項目がディレクトリならその下のすべてに、ファイルならそのファイルに許す。
- シンボリックリンクの項目は、辿った先の実体に許す。リンクだけを許しても、リンクを辿った先の実体のパスで起動できる。
- 直接起動するスクリプト（`#!` で始まるもの。フック、`./gradlew`、`node_modules/.bin` の下のもの）は、インタプリタとスクリプト自体の両方に実行の許可が要る。インタプリタのほかに、スクリプトのファイルかそれを含むディレクトリを書く。エージェントが起動するフックやステータス行のスクリプト（`~/.claude/hooks`、`~/.codex/hooks`）もこれにあたる。インタプリタに渡して起動する（`sh ./script.sh`）ならインタプリタだけでよい。
- kakoi が自動で許すのは、動的リンカ `/lib64/ld-linux-x86-64.so.2` の実体と、kakoi 自身の実行ファイル（見張り役と `隔離の中の最初のプロセス` に使うもの）だけである。どちらも無いと何も起動しないためである。

`/bin/sh` と `/usr/bin/ls` を許せば、隔離の中の sh から ls を起動できる。
`/bin/sh` だけを許せば、sh から `/usr/bin/id` を起動しても失敗する。
コマンドそのものを許していないとき（`kakoi -- /usr/bin/id`）は、`隔離の中の最初のプロセス` がコマンドの名前と理由を示す種類 `command not executable` の診断を出して 126 で終わる。
コマンドの起動がほかの理由で失敗したときも同じである。
コマンドは、与えた名前を argv[0] として受け取る。

`隔離の中の最初のプロセス` が項目を開けなければ、その項目を許さずに進め、標準エラーに警告を 1 行出す。
動的リンカが隔離の中に無ければ、それを許さずに進める。
kakoi 自身の実行ファイルの場所が分からなければ、コマンドを実行せず種類 `bwrap` の診断で 125 とする。

これは境界ではなくガードレールである。
動的リンカを絶対パスで起動すれば読めるファイルをプログラムとして動かせ、許したインタプリタ（python、node）は読めるファイルをメモリ上で実行でき、memfd に写した実行ファイルも起動できる（[公開文書に載せる事項](../maintainer/public-docs.md#既知の隙間) の 18）。
コマンドのモードが `"listed"` の隔離の中では、`--nested=isolate` で中に隔離を作れない（同 19）。

## 許すプログラムがホストに無いとき
<!-- @kotowari[REQ-476:bb479541, EX-925:a1160a65, EX-926:e617910d] -->

`commands.allow` の項目のパスがホストに無いとき、または隔離の中に見えないときは、無いマウント項目と同じく、その項目を理由を付けて計画に示して飛ばし、起動を止めない。
無いプログラムは許しても許さなくても起動できないので、飛ばしても守りは弱まらず、道具をまだ入れていない機械でも同じプロファイルで起動できる。
飛ばした項目は何も許さないので、ホストに無いパスと `/bin/sh` を書いても、sh から許していないプログラムは起動できない。

## Landlock が使えないとき
<!-- @kotowari[REQ-477:27b550e4, EX-927:5e0f4e57, EX-928:6633b7e5] -->

コマンドのモードが `"listed"` で、ホストで Landlock が使えないときは、コマンドを実行せず種類 `bwrap` の診断で 125 とする。
指定したのに黙って効いていない状態を作らないためである。
この確かめは bwrap の所在の段階で行い、計画表示でも行う。
どの段も `commands.mode` を書いていなければ、Landlock の無いホストでもコマンドを実行する。

## 計画表示
<!-- @kotowari[REQ-473:018656ef, REQ-478:c1fca23f, EX-918:b1b93080, EX-919:f6ae50a7, EX-929:ee833963, EX-930:a8f99412] -->

計画の要約は、合成後のマウントのモードと `mounts.system` の値を 1 行で示し、それとは別の 1 行で、合成後のコマンドのモードと、`"listed"` のときは許すプログラムの項目の数を示す。

```text
mount mode: listed (system: false)
command mode: listed (2 allowed from commands.allow)
```

どの段もモードを書いていなければ、それぞれ `host` を示し、コマンドのモードの行は項目の数を示さない。
計画の JSON は、合成後の 2 つのモードと `mounts.system` の値、許すプログラムの項目を持つ。
数と項目は、[許すプログラムがホストに無いとき](#許すプログラムがホストに無いとき)で飛ばした項目を含まない。
`format_version` は 1 のままである。
鍵の名前は `docs/cli.md` の表にある。

## 同梱の見本
<!-- @kotowari[REQ-481:a00ef266, EX-935:ad320166, EX-936:b56f04cc] -->

見せるものを選ぶモードの見本として `examples/profile/listed.toml` を同梱し、`kakoi init NAME --example listed` で書き出せる（[init の見本の選択](03-cli.md#init-の見本の選択)）。
見本は今の同梱プロファイルと同じ前提（WSL2、mise で入れた claude と codex）で動く最小の形である。

- `mounts.mode` を `"listed"` にし、作業場所（`${workspace}`、`${worktree}`、`${git_common_dir}`）、`/tmp/kakoi`、`~/.local/share/mise/installs` の下の claude と codex、`~/.claude`、`~/.claude.json`、`~/.codex`、今の同梱プロファイルにあるパッケージのキャッシュを見せる。
- `commands.mode = "listed"` と、claude と codex 自身とそれらが起動時に呼ぶプログラム（git、sh、uname）、フックの置き場（`~/.claude/hooks`、`~/.codex/hooks`）を並べた `commands.allow` は、コメントとして一緒に置いて効かせない。効かせると cargo や npm のようなプロジェクトごとの道具がすべて止まるためである。外すときは両方を外す。
- 名前で起動した `ld.so` のすべての起動を止めるガードレールの規則を効かせる。規則は、どの語にも当たらない正規表現を 1 つ持つ `only` で書く。
- PATH のシム（Safe Chain、mise）とホームの外を指すリンクを使う利用者は、その置き場を足す。見本のコメントがそれを求める。

見本のままで claude が起動し、隔離の中で `~/.ssh` と `/run` が存在しないこと、`ld.so /usr/bin/git` を名前で起動すると止まることは、利用者が受け入れのときに確かめる。
