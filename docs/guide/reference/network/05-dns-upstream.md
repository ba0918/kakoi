# 上流 DNS と名前解決の上限

`filtered` の中のアプリが名前解決を求めると、kakoi-net はそれを受けて別の DNS サーバーへ問い合わせる。
この問い合わせ先を**上流 DNS** と呼ぶ。
この章は、上流 DNS をポリシーで明示する方法とホストの DNS 設定を使う場合の振る舞い、一つの名前解決にかける時間と問い合わせ回数の上限、同時に進める名前解決の数の上限を決める。
上流 DNS を明示したいとき、ホストの DNS 設定が変わったときの挙動を知りたいとき、名前解決が失敗する上限を調べたいときに読む。
DNS 応答の検査と許可の寿命は [DNS による許可](04-dns.md) が扱う。

## 上流 DNS に関わるキー
<!-- @kotowari[REQ-146:03e2abdc, REQ-117:26a5ca47, REQ-119:da7fff22, REQ-121:3d1f97d6, REQ-125:355ebda3, REQ-128:abb6c65e] -->

上流 DNS と名前解決の上限は、ポリシーの `network` 表の次の 7 つのキーで指定する。
数値のキーはすべて整数で、範囲の両端の値も受け付ける。

| キー | 型 | 既定 | 範囲 | 意味 |
|---|---|---|---|---|
| `network.dns-upstream` | 配列 | 無し（ホスト DNS を使う） | 平文と TLS を混在させない | 明示する上流 DNS の候補 |
| `network.dns-server-timeout-seconds` | 整数（秒） | 2 | 1〜300 | 上流の 1 候補の応答を待つ時間 |
| `network.dns-resolution-timeout-seconds` | 整数（秒） | 10 | 1〜3600 | 名前解決 1 件全体の期限 |
| `network.dns-max-cname-hops` | 整数（段） | 16 | 1〜128 | 別名（CNAME）を辿る段数の上限 |
| `network.dns-max-upstream-queries` | 整数（回） | 64 | 1〜4096 | 名前解決 1 件あたりの上流への問い合わせ回数の上限 |
| `network.dns-max-concurrent-resolutions` | 整数（件） | 256 | 1〜4096 | 環境ごとに同時に進める名前解決の数の上限 |
| `network.dns-max-waiters-per-resolution` | 整数（件） | 64 | 1〜1024 | 共有する名前解決 1 件の応答を待つ問い合わせの数の上限 |

`network.dns-upstream` の各候補は、接続する IP と、TLS の場合に証明書で照合する名前を別々に持つ。
候補の各要素に書くキーの名前と形は、IR がまだ定めていない（[未決事項](../../appendix/open-issues.md)を参照）。

### 数値キーの検査
<!-- @kotowari[EX-256:90c649fd, EX-257:a10cdb69, EX-262:4aea6488, EX-268:534315d2, EX-282:94bab5fa] -->

数値のキーに 0、無制限、小数、範囲外の値を書くと設定エラーになる。

| キー | 受け付ける例 | 設定エラーになる例 |
|---|---|---|
| `network.dns-server-timeout-seconds` | 1、300 | 0、301、小数、無制限 |
| `network.dns-resolution-timeout-seconds` | 1、3600 | 0、3601、小数、無制限 |
| `network.dns-max-cname-hops` | 1、128 | 0、129、小数、無制限 |
| `network.dns-max-upstream-queries` | 1、4096 | 0、4097、小数、無制限 |
| `network.dns-max-concurrent-resolutions` | 1、4096 | 0、4097、小数、無制限 |
| `network.dns-max-waiters-per-resolution` | 1、1024 | 0、1025、小数、無制限 |

### 数値キーの段の合成
<!-- @kotowari[REQ-118:4fd6a7f2, EX-258:6ee57f01, EX-259:b9437e76, EX-260:dc4bf2a6, EX-263:1f2f5307] -->

数値のキーは、ポリシーの段（[ポリシーファイル](../05-policy.md)を参照）の上位の指定を優先し、上位で省略したキーは下位の値を引き継ぐ。
どの段にも指定がなければ既定値を使う。
2 つの待ち時間のキーは別々に引き継ぐので、上位で片方だけを書くと、もう片方は下位の値のままになる。

```toml
# 下位の段
[network]
dns-server-timeout-seconds = 5
dns-resolution-timeout-seconds = 30
```

```toml
# 上位の段
[network]
dns-resolution-timeout-seconds = 60
```

この 2 段を合成すると、1 候補の待ち時間は 5 秒、全体の期限は 60 秒になる。
上位の値を 60 ではなく 3 にすると、1 候補の 5 秒が全体の 3 秒を超えるので設定エラーになる。
この大小の検査は、各段の値ではなく合成した後の値に対して行う。

`network.dns-max-cname-hops` も、下位で 32 を指定して上位で省略すれば 32 になる。

## 明示した上流

ポリシーに `network.dns-upstream` を書くと、kakoi-net はホストの DNS 設定を使わず、書いた候補へ問い合わせる。
書かなければホスト DNS を使う（[ホスト DNS を使う場合](#ホスト-dns-を使う場合)を参照）。

### 上流の候補の合成
<!-- @kotowari[REQ-146:03e2abdc, EX-324:b5c8605b, EX-325:095e39cd] -->

`network.dns-upstream` は、下位の段の配列の後ろに上位の段の配列をつなげて合成する。
上位に空の配列を書いても、下位の候補は消えない。
候補を丸ごと入れ替えたい場合は、別のプロファイルを使う。

一つの候補一覧に、平文の DNS と TLS の DNS を混在させない。
下位に TLS の候補があり、上位に平文の候補があると、合成した候補一覧は受け付けられない。

### すべての名前に共通の上流
<!-- @kotowari[REQ-111:34d799fd, EX-242:cada346c, EX-243:137e6d07] -->

明示した上流は、問い合わせる名前にかかわらず全問い合わせに共通に使う。
ポリシーの中で名前ごとに上流を分ける指定はない。

ホスト DNS を使う場合は、ホスト側に名前ごとの問い合わせ先が設定されていれば、その振り分けを引き継ぐ。

### 候補を試す順番と代替
<!-- @kotowari[REQ-112:a763c71b, REQ-113:3d001582, EX-244:6a72957b, EX-245:752f0a72, EX-246:b7ec28f8, EX-247:eea23cb1] -->

上流を複数書くと、問い合わせ先が応答しないときに、書いた別の候補を代わりに使える。
複数の候補を書くことは、列挙した全候補に同じ名前を問い合わせてよいという指定として扱う。

上流への問い合わせが必要になるたびに、候補を記載順に先頭から試す。
先の候補が切替の条件（応答しない場合を含む）に達するまで、次の候補へ同時に問い合わせることはしない。
前回の問い合わせで 1 番目が応答せず 2 番目で成功していても、次の問い合わせは再び 1 番目から始める。
切替の条件の詳細は未決である（[未決事項](../../appendix/open-issues.md)を参照）。

全候補が応答しなくても、明示した候補の外の DNS へは自動で切り替えない。

この順番の規則は明示した上流だけに適用し、ホスト DNS を使う場合の上流の選び方には適用しない。

### TLS の証明書の検証
<!-- @kotowari[REQ-147:0a62e9c1, EX-326:c5fc0801, EX-327:629fcb0b] -->

TLS の上流を使う場合、kakoi-net は起動時にホスト OS の CA 証明書を読み込み、上流の証明書をそれで検証する。
独自の CA を信頼させたい場合は、ホスト OS の側に登録する。
初版には、専用の CA ファイルを指定する手段も、証明書の検証を無効にする手段もない。

起動した後にホスト OS の CA 証明書が変わっても、実行中の環境には反映しない。
反映するには環境を起動し直す。

## ホスト DNS を使う場合

`network.dns-upstream` を書かないと、kakoi-net はホストの名前解決設定（`/etc/resolv.conf`）から上流を選ぶ。
この構成を**ホスト DNS** と呼ぶ。

### ホスト DNS の上流の選び方
<!-- @kotowari[REQ-396:49360a3d, EX-731:073a7379, EX-732:2b46cb47] -->

ホストの名前解決設定の `nameserver` を、記載順に通常の DNS の上流として使う。
例えば `nameserver 10.255.255.254` と `nameserver 192.0.2.53` がこの順で書かれていれば、この 2 つをこの順に使う。

例外として、`nameserver` が systemd-resolved のスタブ `127.0.0.53` だけの場合は、中継窓口の `127.0.0.54` へ問い合わせる。

### 起動時にホスト DNS を読めない場合
<!-- @kotowari[REQ-145:7ccb499b, EX-322:33791fb5, EX-323:8c71682d] -->

`filtered` で DNS 名の許可（[通信許可](02-allow.md)を参照）を使い、ホスト DNS を選んでいる場合に、起動時に次のどちらかに当たると起動エラーになる。

- ホストの名前解決設定を読めない。
- `nameserver` が一つも書かれていない。

このとき kakoi は上流 DNS を明示するよう案内し、公開 DNS へ勝手に切り替えることはしない。

DNS 名の許可を使わない構成では、ホスト DNS を必須にしない。
例えば `filtered` で許可と公開の指定が空で DNS 名の許可が無ければ、ホスト DNS に対応できないことだけを理由に起動を拒否しない。

起動した後に設定を取得できなくなった場合は、[変更後の設定を使えない場合](#変更後の設定を使えない場合)に従う。

### 実行中のホスト DNS の変更への追従
<!-- @kotowari[REQ-107:9381e5dd, EX-232:cf8ae9ce, EX-233:1b36de04] -->

ホスト DNS を使う構成では、実行中もホストの DNS 設定の変更に追従する。
変更を検知した後に始める上流への問い合わせには、新しい設定を使う。
追従に kakoi の再起動は要らない。
変更を検知する仕組みと、検知までの遅れは未決である（[未決事項](../../appendix/open-issues.md)を参照）。

ポリシーで上流を明示している構成は、この追従の対象外で、ホストの DNS 設定が変わっても明示した上流を使い続ける。

### 変更を検知したときの扱い
<!-- @kotowari[REQ-108:ac1e0d0b, REQ-109:212079d7, EX-234:aec19ec1, EX-235:48953636, EX-236:da00049c, EX-237:98b52ac8] -->

ホスト DNS の設定の変更を検知すると、kakoi-net は保持している情報と進行中の処理を次のように扱う。
古い応答を使い回すことと、すでに許した通信を続けることを分けて扱う。

| 情報、処理 | 変更を検知した後の扱い |
|---|---|
| kakoi-net が保存した古い DNS 応答 | 期限内でも破棄し、次の名前解決は新しい設定で行う |
| すでに与えた IP 許可 | 元の期限まで維持する |
| 確立済みの TCP と継続中の UDP | それぞれの既存の継続規則で扱う（[DNS による許可](04-dns.md)を参照） |
| アプリ自身が保存した解決結果 | kakoi が消すことは保証しない |
| 旧設定で始めて未完了の問い合わせ | 新しい設定で問い合わせ直す |

例えば、古い応答から得た IP 許可の期限まで 30 秒残っていれば、キャッシュを破棄した後もその許可は残り 30 秒のまま維持する。

変更の検知後に旧設定の問い合わせの応答が届いても、その応答は採用しない。
アプリへ返さず、キャッシュや IP 許可の追加と更新にも使わない。

### 問い合わせ直しと上限の引き継ぎ
<!-- @kotowari[REQ-109:212079d7, EX-238:1effb044] -->

設定の変更で問い合わせ直す場合も、元の名前解決の期限と残りの問い合わせ回数を引き継ぐ。
設定が続けて変わっても、上限をリセットしない。
そのため、設定の変更が続いても名前解決は元の上限の中で終わる。

### 変更後の設定を使えない場合
<!-- @kotowari[REQ-110:1399bafe, EX-239:30626421, EX-240:799b416a, EX-241:3043be21] -->

ホスト DNS の設定の変更を検知したが、新しい設定を取得できないか解釈できない間は、上流への問い合わせを失敗として扱う。
このとき旧設定や別の DNS へ自動で問い合わせることはしない。

設定を使えないことだけでは、環境全体を終了しない。
既存の IP 許可は元の期限を維持し、継続中の TCP と UDP は既存の継続規則で扱う。
アプリへ返す具体的な失敗応答と、設定の取得が回復したことを検知する方法は未決である（[未決事項](../../appendix/open-issues.md)を参照）。

## 名前解決の時間と問い合わせの上限

一つの名前解決が際限なく続かないように、時間、別名を辿る段数、上流への問い合わせ回数をそれぞれ制限する。
3 つの上限は独立に適用し、どれか一つに達すれば名前解決は失敗する。

| 上限 | 既定 | 数え方 | キー |
|---|---|---|---|
| 1 候補の待ち時間 | 2 秒 | 上流の候補ごと | `network.dns-server-timeout-seconds` |
| 全体の期限 | 10 秒 | 名前解決 1 件ごと | `network.dns-resolution-timeout-seconds` |
| 別名の段数 | 16 段 | 名前解決 1 件ごと | `network.dns-max-cname-hops` |
| 上流への問い合わせ回数 | 64 回 | 名前解決 1 件ごと | `network.dns-max-upstream-queries` |

2 つの待ち時間の既定値は製品として選んだ値であり、RFC の指定値や性能を実測した結果ではない。

### 候補ごとの待ち時間と全体の期限
<!-- @kotowari[REQ-116:24552592, EX-252:aca756b4, EX-253:8c4432aa, EX-254:5720eb44, EX-255:5f0672ea] -->

明示した上流の 1 候補を待つ時間は既定 2 秒で、応答が無ければその候補を打ち切って次の候補へ進む。
名前解決全体の期限は既定 10 秒で、開始から期限に達すると未完了でも打ち切る。
どちらもキーで変えられ、遅い環境では例えば 1 候補 5 秒、全体 30 秒にできる。

別の候補への切替、別名の参照、ホスト DNS の設定変更による問い合わせ直しのどれが起きても、全体の期限は延長しない。

ホスト DNS を使う場合も全体の期限を適用する。
1 候補の待ち時間の扱いは、上流の選び方で次のように分かれる。

| ホスト DNS の上流 | 1 候補の待ち時間 |
|---|---|
| kakoi-net が `nameserver` を記載順に試す場合 | 各候補に適用する |
| systemd-resolved の中継窓口だけを使う場合 | 適用せず、全体の期限まで待つ |

中継窓口だけを使う場合は、中継する側が問い合わせ先を選ぶためである。

### 別名を辿る段数
<!-- @kotowari[REQ-120:324261a9, EX-264:412c1963, EX-265:8663cf38, EX-266:542a864f] -->

名前から別名（CNAME）への 1 回の参照を 1 段と数える。
上限ちょうどの段数は許し、さらに参照が必要なら名前解決を失敗させる。
上限が 16 段なら、16 段の参照で最終的な IP に届けば成功し、17 段目の参照が必要になれば失敗する。

参照の循環を検出した場合は、段数の上限を待たずに名前解決を失敗させる。
例えば a から b を経て a に戻れば、その時点で失敗する。

### 上流への問い合わせ回数の数え方
<!-- @kotowari[REQ-122:fd60e59f, EX-270:7a86575e, EX-271:f64de7d8, EX-272:daca0986] -->

kakoi-net 自身が上流へ送る DNS 問い合わせを、1 回の送信ごとに 1 回と数える。
上限ちょうどの回数までは送れ、さらに送信が必要なら名前解決を失敗させる。

次の送信も回数に含め、数え直しはしない。

- 別の候補への切替
- 別名の参照
- 再送
- 通信方式を変えての問い合わせ直し
- 設定の変更による問い合わせ直し

一方、上流の DNS サーバーの内部の処理と、通信層によるパケットの再送は数えない。

例えば上限 64 回で 63 回送った後にホスト DNS の設定が変わって問い合わせ直す場合、送れるのはあと 1 回である。
回数に余裕があっても、全体の期限に達すれば名前解決は続けない。

### IPv4 と IPv6 を別に数える
<!-- @kotowari[REQ-124:8ae3b25f, EX-278:c32a00fd, EX-279:d2a6ccfa, EX-280:3db47190] -->

同じ名前に対する IPv4 用と IPv6 用の名前解決は、時間、別名の段数、上流への問い合わせ回数の上限をそれぞれ独立に持つ。
一方が上限を消費しても、他方の残りの時間や回数は減らない。

例えば問い合わせ回数の上限が 64 回で、IPv4 用が 60 回、IPv6 用が 5 回送った場合、合計 65 回でも回数の超過にはならない。
残りは IPv4 用が 4 回、IPv6 用が 59 回である。
IPv4 用が時間切れになっても、IPv6 用の残り時間はそのまま残る。

## 同時処理と共有

同じ問い合わせが重なると、許可と解決の条件が一致する範囲で上流の処理を共有する。
同時に進める名前解決の数と、一つの名前解決の結果を待つ問い合わせの数には、別々の上限がある。
例えば同じ環境から同じ条件の A 照会が 3 件重なれば、名前解決は 1 件、応答を待つ問い合わせは 3 件と数える。

### 同じ問い合わせの合流
<!-- @kotowari[REQ-127:4b4664b5, EX-286:d96e745f, EX-287:5d87ca5a, EX-288:92b1d2aa, EX-289:9562aa58, EX-290:569601a4] -->

同じ隔離環境で、名前、照会の種類、解決の条件が同じ問い合わせが重なると、後の問い合わせは進行中の名前解決に合流する。
上流への処理と同時処理の枠は 1 件のままである。

後から合流しても、元の名前解決の期限と問い合わせ回数の上限はリセットしない。
期限まで 2 秒、残り 3 回の名前解決に合流すれば、合流した問い合わせも 2 秒と 3 回の中で結果を待つ。

次の場合は合流しない。

- 別の環境で同じ名前と種類を問い合わせた場合
- 同じ環境でも、解決の条件が異なる場合

合流先があっても、問い合わせ元ごとの許可の確認は省かない。
許可を確認してから、合流できるかを判断する。
解決の条件が同じかどうかを判定する細部は未決である（[未決事項](../../appendix/open-issues.md)を参照）。

### 環境ごとの同時処理数
<!-- @kotowari[REQ-125:355ebda3, REQ-126:ca0bb39f, EX-283:c6b5285a, EX-284:dd5e73df, EX-285:b524560f] -->

同時に進める名前解決の数の上限は、環境ごとに既定 256 件で、`network.dns-max-concurrent-resolutions` で変えられる。
IPv4 用と IPv6 用の名前解決は別の件として数える。
上限は環境ごとに独立で、ある環境が 256 件を使っていても、別の環境の枠は減らない。
キーを下位で 512 と指定して上位で省略すれば、上限は 512 件になる。

新しい処理の枠が必要な問い合わせを、上限に達している間に受けると、待ち行列には入れずに SERVFAIL を返す。
進行中の名前解決と環境はそのまま続く。

### 一つの名前解決を待つ問い合わせ数
<!-- @kotowari[REQ-128:abb6c65e, REQ-129:02884742, EX-291:39966c14, EX-292:b9c1f5f7, EX-293:80cc4bd7, EX-294:ad93b2b2] -->

共有する名前解決 1 件の応答を待つ問い合わせの数の上限は、既定 64 件で、`network.dns-max-waiters-per-resolution` で変えられる。
最初の問い合わせも含め、個別に応答を返す問い合わせの数で数え、アプリの数では数えない。
同じアプリからの 2 件の問い合わせでも、応答先が別なら 2 件と数える。
上限 64 件なら、最初の問い合わせと追加の 63 件で 64 件になる。
キーを下位で 128 と指定して上位で省略すれば、上限は 128 件になる。

上限に達した名前解決に合流しようとする新しい問い合わせには SERVFAIL を返す。
その問い合わせのために別の名前解決を作って上限を回避することはしない。
既存の応答待ちと名前解決はそのまま続く。
