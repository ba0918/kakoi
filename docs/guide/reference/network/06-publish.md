# 公開

**公開**は、隔離環境の中で待ち受けるサービスへ、ホストから接続できるようにする仕組みである。
この章は、`filtered` モードの初版が提供する固定公開の書き方、公開が続く期間、段をまたぐ合成と競合、そして後続の動的公開として定義済みの契約を決める。
内側で起動した開発サーバーやレビュー画面をホストのブラウザーから開きたいときに読む。
隔離環境のアプリから外へつなぐ許可と、内側からホストで動くサービスへつなぐホスト宛て接続は、[通信許可](02-allow.md) が扱い、公開とは別に指定する。

## 初版の固定公開と後続の動的公開
<!-- @kotowari[REQ-390:8338cdd5, EX-722:ce30c55f] -->

公開には、初版で提供する**固定公開**と、後続で追加する**動的公開**の 2 つがある。
固定公開は、内側のポート番号とホストのポート番号を起動前に 1 対 1 で指定する方式である。
動的公開は、許可した範囲の中で待受を検出して自動で公開し、ホスト側の番号も空きから選ぶ方式である。

| 区分 | 現行か | この章の該当箇所 |
|---|---|---|
| 固定公開 | 初版で提供する（現行の契約） | [固定公開の書き方](#固定公開の書き方) から [段をまたぐ合成と競合](#段をまたぐ合成と競合) まで |
| 動的公開 | 後続。初版では使えない | [後続の動的公開](#後続の動的公開) 以降 |

初版の `filtered` は pasta（隔離環境のネットワークをホストへつなぐ外部の実行ファイル）を前提に、次の 5 つを提供する。

- 外向きの TCP と UDP の制限
- DNS 由来の IP の制限
- 明示したホスト宛て接続
- 固定ポートの公開
- 故障時の遮断

次の 3 つは後続へ分けてあり、初版には含まれない。

- 待受の自動検出
- ホスト側の番号が競合したときの別番号の割当
- 待受の寿命に応じた動的公開

初版は、pasta の実験的な動的制御の窓口や、限定的に修正した版を必須の依存にしない。
動的公開はこれらの機能を前提にするため、初版からは外してある。

## 動的公開を後から足すための分担
<!-- @kotowari[REQ-391:143015ae, EX-723:61730f2b] -->

kakoi は、公開の判断（どの内側の端点をホストのどの端点へつなぐか）と、pasta に固有の操作を分けて持つ。
将来の動的公開を、固定公開の意味を変えずに追加できるようにするためである。

動的公開の提供時期は、上流の pasta の正式な対応に左右される。
上流がいつ対応するか、修正が採用されるかは確約された事実ではなく、この文書もそう扱わない。
上流の UDP の削除と再利用に関する問題が解決していることは、その修正を必要とする動的公開を採用するときの条件になる。

## 初版の確認の順序
<!-- @kotowari[REQ-392:e56d6024, EX-724:3b29c256] -->

この節は保守者向けである。
初版の確認は、実装を始める前の確認と、提供する前の確認の 2 段階に分かれる。

| 時点 | 確認すること |
|---|---|
| 実装開始の前 | 上流で修正していない版の pasta で、初版の通信、固定公開、全経路の遮断、導入経路 |
| 提供の前 | 実際のコードでの DNS、監督、期限、終了の統合 |

過去に限定修正版で一部が確認できていても、それを初版全体の合格として扱わない。
実証の条件そのものは [ライブラリの責務と実証条件](../../maintainer/library.md) を参照する。

## 固定公開の書き方
<!-- @kotowari[REQ-394:5249a5b7, EX-727:39ffac20, EX-728:541149e7] -->

固定公開は、ポリシーの `[[network.publish]]` に 1 項目ずつ書く。
1 項目が「内側の 1 つのポートを、ホストの 1 つのポートへ」公開する。

| キー | 型 | 既定 | 意味 |
|---|---|---|---|
| `mode` | 文字列 | なし（必須） | 公開の方式。初版で受け付けるのは `"fixed"` だけ |
| `protocol` | 文字列 | なし（必須） | `"tcp"` または `"udp"` |
| `port` | 整数 | なし（必須） | 内側の転送先のポート番号。1〜65535 |
| `host-port` | 整数 | なし（必須） | ホスト側で公開するポート番号。1〜65535 |
| `target-family` | 文字列 | `"ipv4"` | 内側の転送先の IP 系統。`"ipv4"` または `"ipv6"`。内側はこの系統のループバックへ転送する |
| `host-family` | 文字列 | `"ipv4"` | ホスト側の公開先の IP 系統。`"ipv4"` または `"ipv6"`。公開先はホストの localhost に限る |

内側の 8000 番を、ホストの 18000 番で公開する例を示す。

```toml
[network]
mode = "filtered"

[[network.publish]]
mode = "fixed"
protocol = "tcp"
port = 8000
host-port = 18000
# target-family = "ipv4"  # 省略時 ipv4
# host-family = "ipv4"    # 省略時 ipv4
```

初版の転送は同じ IP 系統の間に限る。
IPv4 と IPv6 の両方で公開したい場合は、IPv4 用と IPv6 用の 2 項目を書く。

```toml
[[network.publish]]
mode = "fixed"
protocol = "tcp"
port = 8000
host-port = 18000

[[network.publish]]
mode = "fixed"
protocol = "tcp"
port = 8000
host-port = 18000
target-family = "ipv6"
host-family = "ipv6"
```

次の指定は、初版では起動前の検査で拒否する。
別の意味へ読み替えて受け付けることはしない。

| 指定 | 扱い |
|---|---|
| 必須キー（`mode`、`protocol`、`port`、`host-port`）のどれかが無い | 拒否。`mode` の省略も含む |
| `mode = "dynamic"` | 拒否。固定公開へ読み替えない |
| ポートの範囲、または自動割当の指定 | 拒否 |
| `host-family = "both"` | 拒否 |
| `target-family` と `host-family` が異なる | 拒否。系統をまたぐ転送は初版に無い |
| `protocol` が `tcp`、`udp` 以外、ポートが 1〜65535 の整数でない | 拒否 |

`mode = "fixed"` を書いた項目の意味は、将来に動的公開が加わっても変わらない。
固定公開のつもりで書いた項目が、後の版で自動選択に変わることはない。

## 公開が続く期間と起動時の確保
<!-- @kotowari[REQ-393:fbc31592, EX-725:1a40562b, EX-726:39b4ea85] -->

固定公開は、アプリの起動前にホスト側のポートを確保し、隔離環境が終わるまで同じ対応を保つ。
内側のサービスが待受を始めたか、終えたかには連動しない。

基本の動きは次のとおりである。

- 公開先はホストの localhost に限る。内側では `target-family` の系統のループバックへ転送する。
- 内側のサービスがまだ起動していなくても、公開用のポートを確保する。サービスが起動、終了、再起動を繰り返しても、隔離環境が動いている間は同じ対応を維持する。
- 公開したホスト側と内側の接続先の対応を通知する。通知の出力先は [プロセスの監督と通知](07-lifecycle.md) に従う。
- `[[network.publish]]` に書いていない待受は、自動では公開しない。

起動時の確保には次の規則がある。

- kakoi はアプリを起動する前に、ホスト側のポートを実際に確保できたことを確かめる。
- 確保に失敗した場合（指定したホスト側の番号が使用中の場合を含む）、起動エラーにしてアプリを起動しない。その環境のために確保済みの資源は回収する。
- 確保できない番号の代わりに、別の番号へ変えて公開することはしない。

実行中の故障から復帰するときも、同じ対応だけを確保し直す。
確保できない間は通信を遮断したまま、既存の復帰の規則に従う（[プロセスの監督と障害からの復帰](07-lifecycle.md)）。

旧仕様は固定公開について、内側の転送先と確保の証拠の扱いにも規則を定めていたが、今の実装で確かめられないため契約にしていない（[固定公開の 2 つの規則](../../appendix/open-issues.md#固定公開の-2-つの規則)）。

## ホスト側の待受アドレス
<!-- @kotowari[REQ-421:6a5bc7c7, EX-808:bf640e53, EX-809:636cde84] -->

固定公開のホスト側は、`host-family` の系統のループバックのアドレスだけで待ち受ける。

| `host-family` | ホスト側で待ち受けるアドレス |
|---|---|
| `"ipv4"`（既定） | `127.0.0.1` だけ |
| `"ipv6"` | `::1` だけ |

ホストの LAN 側のアドレスや、全アドレスでは待ち受けない。
`host-port = 8080` の IPv4 の公開なら、ホストの `127.0.0.1` の 8080 番へは接続できるが、ホストの LAN 側のアドレスの 8080 番へは接続できない。

## 一部だけ確保できたときと終了時の回収
<!-- @kotowari[REQ-422:0964ec7c, EX-810:405693b7, EX-811:ce493c59] -->

複数の固定公開を書いた場合、一部だけを確保できた状態ではアプリを起動しない。
起動エラーにして、確保できた公開も回収する。
例えばホストの 8080 番と 8081 番を公開するポリシーで 8081 番を別のプロセスが使っていれば、アプリを起動せず、8080 番も待受のまま残さない。

隔離環境が終わるときは、終了処理の中で公開を止め、ホスト側で確保した番号を回収する。
主コマンドが終了した場合も、SIGTERM で終了を求められた場合も、それぞれの終了処理の中で公開を止める（終了処理の手順は [filtered のプロセスの寿命と通信の障害](07-lifecycle.md)）。
終了した後、ホストの `127.0.0.1` の公開した番号は待受のまま残らない。

## アプリの標準出力
<!-- @kotowari[REQ-423:cc11ea09, EX-812:d5220c49, EX-813:03047751] -->

固定公開を使っても、kakoi はアプリの標準出力を書き換えない。
アプリが標準出力に `hello` を書けば、kakoi の標準出力も `hello` だけである。
公開の接続先の通知は標準エラーに出し、標準出力には混ぜない（通知の形は [filtered のプロセスの寿命と通信の障害](07-lifecycle.md)）。
そのため、アプリの標準出力を別のコマンドへパイプで渡していても、通知は流れ込まない。

## UDP の送信元ポートの制約
<!-- @kotowari[REQ-424:1014797a] -->

`filtered` の UDP の通信には、公開に限らず、pasta の振る舞いから来る既知の制約がある。
pasta は UDP の流れごとに、ホスト側のソケットにアプリ側の送信元ポートと同じ番号を使う。
その番号をホストの別のソケットが使っていると、pasta はその流れを作れず、同じ送信元からのデータグラムを捨て続ける。

アプリからは、応答の無いタイムアウトに見える。
kakoi はこの状態を通知しない。
UDP の通信が応答の無いままタイムアウトするときは、アプリの送信元ポートと同じ番号をホストで使っているプロセスが無いかを確かめる。

この制約は、公開文書の `docs/security.md` の `filtered` の制約にも載っている。

## 段をまたぐ合成と競合
<!-- @kotowari[REQ-395:e8bab658, EX-729:d85c7b32, EX-730:b265936a] -->

`network.publish` は段の間で連結する。
上の段は項目を追加するだけで、空配列を書いても下の段の項目は消えない。
段の合成の一般規則は [ポリシーの形式と合成](../05-policy.md) を参照する。

連結した後、次の順で検査する。

1. 正規化した結果が同じ項目は、1 つにまとめる。
2. 同じ内側の端点に、異なる公開の指定があれば拒否する。
3. 同じホスト側の端点に、異なる転送先があれば拒否する。

端点が同じかどうかは、通信方式（`protocol`）、IP 系統、ポート番号の 3 つで判断する。
2 と 3 の競合は、1 つの段の中でも、段をまたいでも同じく拒否する。
例えば、下の段がホストの TCP 18000 番を内側 8000 番へ、上の段が同じホスト TCP 18000 番を内側 9000 番へ公開しようとすると、起動前に拒否する。

`network.mode` が `host` または `none` のときも、`[[network.publish]]` の形式と項目同士の競合は検査する。
ただし、公開用のポートの実際の確保と、pasta の探索はしない。
モードごとの違いは [ネットワークモード](01-modes.md) を参照する。

## 後続の動的公開

ここから下は、後続の動的公開として定義済みの契約である。
初版では使えず、初版の固定公開にはそのまま当てはまらない。
書き方も固定公開とは異なる。`mode` を持たない下の形の項目は、初版では `mode` の省略として拒否する。

元の定義では、以下の契約が「初版」と書いている箇所がある。
それは動的公開を最初に提供する版を指し、この章で言う初版（固定公開の版）ではない。
この節では「動的公開の最初の提供」と書き換えている。

### 動的公開の書き方
<!-- @kotowari[REQ-079:ac9ddb40, EX-155:540dbf32, EX-156:eb077e03, EX-157:1fbfb743] -->

動的公開では、公開対象にする内側のポート範囲と、ホスト側で使ってよいポート範囲を別々に書く。
二つの範囲の対応は、待受を検出してから決まる。

| キー | 型 | 既定 | 意味 |
|---|---|---|---|
| `protocol` | 文字列 | なし（必須） | `"tcp"` または `"udp"` |
| `ports` | 文字列の配列 | なし（必須） | 公開対象にする内側のポート範囲 |
| `host-ports` | 文字列の配列 | なし（必須） | ホスト側で割り当ててよいポート範囲 |
| `host-family` | 文字列 | `"ipv4"` | ホスト側の公開先の系統。`"ipv4"`、`"ipv6"`、`"both"` |

`ports` と `host-ports` は、[通信許可のポートの記法](02-allow.md) と同じ文字列配列の記法と入力検査を使い、単一の番号、範囲、全ポートを書ける。
`host-ports` を省くと拒否する。

```toml
[[network.publish]]
protocol = "tcp"
ports = ["8000-8010"]
host-ports = ["18000-18010"]
```

この例は、内側の TCP 8000〜8010 番を公開対象にし、ホストの 18000〜18010 番を割当に使ってよい範囲とする。
二つの範囲を順番に 1 対 1 で対応させるわけではない。
内側 8001 番に待受があり、ホストの 18001 番が使用中で 18002 番が空いていれば、18001 番に固定せず範囲内の空きから選ぶ。

### 動的公開の重なりと段の合成
<!-- @kotowari[REQ-080:dbc6de34, REQ-081:67cfc6bd, EX-160:254d80d2, EX-163:4e35c3bf, EX-164:ad12e4f8] -->

同じ待受に一致する項目が複数ある場合、ホスト側の範囲と `host-family` が同じなら 1 つにまとめる。
どちらかが異なれば、起動前に拒否する。
同じ待受を、項目ごとに別々の場所へ公開することはしない。

`network.publish` は段の間で連結し、上の段が追加する。
空配列を書いても下の段の項目は消えない。
重複と競合は、合成した後に判定する。
段をまたいで同じ待受に異なるホスト範囲を指定した場合も、上書きせず起動前に拒否する。
公開を減らしたい場合は、別のプロファイルを使う。

### 公開対象にする待受と公開先の系統
<!-- @kotowari[REQ-136:44080143, REQ-072:51d29420, REQ-073:7301386a, REQ-074:a27c429c, EX-143:2a04539a] -->

公開対象は、隔離環境の中でループバックに待ち受けるサービスと、全インターフェースに待ち受けるサービスである。
ループバック以外の特定の IP だけに待ち受けるサービスは対象にしない。
ポートと TCP、UDP の許可範囲、そしてホスト側を localhost に限ることは変わらない。

ホスト側の公開先は、公開ごとに次の 3 つから選ぶ。

| `host-family` | ホスト側の公開先 |
|---|---|
| `"ipv4"`（既定） | 127.0.0.1 だけ |
| `"ipv6"` | ::1 だけ |
| `"both"` | 127.0.0.1 と ::1 |

`"both"` の場合は、許可範囲内の同じ番号を両方の系統で確保してから公開する。
両方に共通の空き番号が無ければ、その公開を失敗として通知し、再試行する。
アプリと他の公開は続ける。
片方の系統だけの公開へ自動で切り替えることはしない。

動的公開では、ホスト側と内側の系統が異なっても中継する。
ホストの IPv6 から内側の IPv4 へ、ホストの IPv4 から内側の IPv6 への両方向を、TCP と UDP のどちらでも動的公開の最初の提供から扱う。

### ホスト側の番号の選び方
<!-- @kotowari[REQ-034:00ec22ca, REQ-036:c5a5de73, REQ-137:5d901249, REQ-070:8b4fa324, EX-306:6853807c, EX-134:e48ec9a6, EX-135:723697c7] -->

動的公開のホスト側の番号は、事前に許可した範囲の中の空きから選ぶ。
アプリが申告しても、事前に定めた範囲の外へは広げない。

番号は次の優先順で選び、実際の公開先を kakoi が通知する。

1. 障害から復帰するときに同じ待受が続いていて、以前のホスト側の番号が許可範囲内で使えるなら、その番号を再利用する。
2. 内側と同じ番号が許可範囲内で空いていれば、その番号を使う。
3. それ以外（同じ番号が使用中、または許可範囲の外）は、許可範囲内の空き番号を小さい順に試す。

例えば、同じ番号が使えず、許可範囲に 18002 番と 18003 番の空きがあれば 18002 番から試す。
障害から復帰するとき、以前の番号が 45000 番なら、内側と同じ 40000 番が空いていても 45000 番を再利用する。
以前の番号が使えなければ、上の規則で別の許可済みの番号を選び、実際の公開先を知らせる。
競合の状況によって、選ばれる番号は変わりうる。

### 待受の自動公開
<!-- @kotowari[REQ-033:c123fcb3, REQ-035:721bafee, EX-057:c0c70631, EX-058:121c7202, EX-063:d506c5ae] -->

動的公開では、許可した範囲の中で待受を検出すると、ホストの localhost へ自動で公開する。
アプリの側で kakoi へ登録する処理は要らない。
同じ許可範囲で待ち受ける別のサービスも、同じ規則で公開対象になる。
許可範囲の外の待受は自動では公開しない。

公開先はホストの localhost に限り、LAN に向けたアドレスでは公開しない。
想定する用途の一つは、隔離環境の中で起動した kemi のレビュー画面を、ホストのブラウザーから開くことである。

### 1 件の公開として数える単位
<!-- @kotowari[REQ-075:8138fc22, REQ-076:b1ae901a, REQ-077:40ffb1d2, EX-147:376b4a9d, EX-149:09b95c72, EX-150:ba413009] -->

動的公開は、待受ソケットを単位に数える。

| 待受の形 | 公開の件数 |
|---|---|
| 1 つのソケットが IPv4 と IPv6 の両方を受ける | 1 件 |
| 同じプロセスでも、別々のソケットで `127.0.0.1:8000` と `[::1]:8000` を待ち受ける | 2 件 |
| 複数のソケットが同じ IP、通信方式、ポートを共有する | 1 件にまとめ、各ソケットへの配送は OS に任せる |

同じ通信方式とポート番号で、IPv4 と IPv6 に別々の待受があり両方が公開対象なら、許可範囲内で別々のホスト側の番号を割り当て、それぞれの転送先との対応を通知する。
各番号の IPv4 側と IPv6 側は、その番号に対応する同じ待受へ中継する。
二つの待受を、一つの番号の IPv4 側と IPv6 側へ振り分けてまとめることはしない。

### 公開用のポートが足りないとき
<!-- @kotowari[REQ-037:247c452c, REQ-038:18f4ee08, REQ-071:13683810, EX-067:96289b00, EX-137:3191f7c7, EX-138:fefcf4e3] -->

ホスト側の許可範囲に空きが無く公開できない場合、そのサービスの公開だけを失敗として通知する。
隔離環境の中の処理と、他の公開は続ける。
許可範囲の外に空きがあってもそこは使わず、ホストで動いている既存のサービスも止めない。

失敗した後、サービスの待受が続いている間は、間隔を置いて自動で再試行する。

| 項目 | 値 |
|---|---|
| 再試行までの待ち時間 | 失敗後 1、2、4、8、16 秒。以降は 30 秒ごと |
| 再試行をやめる条件 | 対象の待受が終わったとき（待ち時間の途中でも、次の試行をしない） |
| 通知する場面 | 初回の失敗、失敗の理由が変わったとき、公開に成功したとき |

同じ理由の失敗を繰り返し通知することはしない。
成功したときは公開先を通知する。

### 待受の終了と再起動
<!-- @kotowari[REQ-039:080be270, REQ-078:8bdb25d3, EX-070:00e7f675, EX-153:b885631b] -->

TCP の待受が終わったことを検出すると、その公開先で新しい接続を受け付けるのをやめる。
待受が終わったことだけを理由に、確立済みの接続は切らない。
サービスが最後の応答を送れるようにするためである。

待受が終わった後は、再起動に備えてホスト側の番号を予約しておくことはせず、解放する。
待受が再び現れたら、新しい公開として番号を選び直す。
番号の予約を片付けても、確立済みの TCP 接続は維持する。

### UDP の公開
<!-- @kotowari[REQ-040:b0c533a7, REQ-041:5b608712, REQ-042:f411b98c, EX-072:d55e8bf0, EX-075:98b03684] -->

動的公開は、最初の提供から UDP を扱う。
公開先はホストの localhost に限る。
TCP の公開を許可しただけでは、同じ番号の UDP は公開しない。

UDP の公開を許可した範囲の中で、ローカルのアドレスとポートが割り当てられたソケットを検出すると、自動公開の対象にする。
アプリの名前や用途では区別しないため、外向き通信の送信元として使うソケットも、ポートが範囲内なら対象になる。
範囲外のソケットは公開しない。

UDP の公開が続く期間は、外向きの UDP 通信の無通信期限とは別に決まる。

| 対象 | 続く条件 |
|---|---|
| 外向きの UDP 通信 | 同じ IP とポートの組で、無通信期限内であること |
| ホストへの UDP の公開 | 対象のソケットが開いていること |

対象のソケットが開いている間は、通信が無くても公開を続ける。
ソケットが閉じたことを検出したら、公開を止める。
外向きの UDP 通信の無通信期限については [DNS 応答の検査と許可の寿命](04-dns.md) を参照する。

### 公開先の通知と URL の読み替え
<!-- @kotowari[REQ-138:d8cd4dbd, EX-308:f3d352fa, EX-309:4ff56ea9] -->

動的公開の通知は、内側とホスト側の実際の IP、ポート、TCP か UDP かの対応を知らせる。
この規則は特定のアプリに限らず、公開対象のアプリ全般に当てはまる。
アプリの出力は書き換えない。

kakoi は、HTTP か HTTPS か、URL のパス、認証トークンを推測しない。
アプリから URL を受け取ってホスト向けの URL を表示する連携は、動的公開の最初の提供に含まない。
利用者は、アプリが表示した URL のホストとポートの部分だけを通知された対応に従って置き換え、パスとトークンはそのまま使う。

例えば、アプリが次の URL を表示したとする。

```text
http://localhost:8003/review?token=EXAMPLE_TOKEN
```

通知された対応が「内側 TCP 8003 番をホスト 127.0.0.1 の 18000 番」なら、ホストでは次を開く。

```text
http://127.0.0.1:18000/review?token=EXAMPLE_TOKEN
```
