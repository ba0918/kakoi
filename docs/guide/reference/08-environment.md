# 環境変数、秘密、Git の URL 書き換え

この章は、隔離の中のコマンドが受け取る環境変数を、kakoi がどの順でどう組み立てるかを定める。
対象のキーは `env` の 5 つ（`mode`、`pass`、`set`、`unset`、`path-prepend`）、`secrets`、`git.instead-of` である。
隔離に渡る変数を絞りたいとき、ファイルに置いた認証情報をコマンドに渡したいとき、Git の取得先を書き換えたいときに読む。
キーの書き方と段の合成の規則は[ポリシーファイルの形式と合成](05-policy.md)が持つ。
この章は、合成を終えたポリシーから環境がどう作られるかを扱う。

## 環境を組み立てる順序
<!-- @kotowari[REQ-268:8d0f5a74, REQ-269:af9d0ccd, EX-505:00bed946, EX-506:c6203d80] -->

kakoi は隔離の中の環境の最終形を自分で組み立て、次の 7 つの手順をこの順に適用する。
後の手順は前の手順の結果を上書きする。

| 順 | 処理 | 使うキー |
|---|---|---|
| 1 | 出発点を決める。`inherit` ならホストの環境全体、`clear` なら空の環境に `env.pass` の変数だけをホストから写したもの | `env.mode`、`env.pass` |
| 2 | 名前が一致する変数を消す | `env.unset` |
| 3 | 変数を入れる | `env.set` |
| 4 | 秘密を入れる | `secrets` |
| 5 | Git の URL 書き換えを入れる | `git.instead-of` |
| 6 | `PATH` の先頭に項目を足す | `env.path-prepend` |
| 7 | `KAKOI=1` を入れる | なし |

たとえば `env.unset` と `env.set` に同じ名前を書くと、手順 3 が手順 2 の後に来るので、`env.set` の値が最終の環境に入る。
最後の `KAKOI=1` は、隔離の中からもう一度 kakoi を起動したときに入れ子と判断する印になる（[入れ子、並列、出力、診断と終了コード](10-process.md)）。

組み立てた環境は、bwrap に環境としてそのまま引き継がせる。
環境変数の値を bwrap の引数には載せない。
引数はプロセスの一覧から他のプロセスに見えるためである。
秘密を含む環境でも、bwrap の引数列には環境を設定する引数も秘密の値も現れない。

一方で、次の 2 つは許容する。

- マウントするパスと秘密ファイルのパスが bwrap の引数に現れる。見えるのはパスであって値ではない。
- 隔離の中のプロセスの環境を、ホストが `/proc` から読める。ホストは信頼する側だからである。

## env.mode と env.pass
<!-- @kotowari[REQ-268:8d0f5a74] -->

`env.mode` は環境の出発点を選ぶ。

| 値 | 出発点 |
|---|---|
| `inherit` | ホストの環境全体 |
| `clear` | 空の環境。`env.pass` に列挙した変数だけをホストから写す |

`env.pass` はホストから写す変数名のリストで、`clear` のときにだけ意味を持つ。
合成後の `env.mode` が `inherit` なのに `env.pass` が空でなければ、`policy` の診断になる。
下の段が `inherit` で、上の段が `clear` と `pass` を両方書く形は通る。
合成の規則は[ポリシーファイルの形式と合成](05-policy.md)を参照。

```toml
[env]
mode = "clear"
pass = ["HOME", "PATH", "LANG", "TERM"]
```

`inherit` ではホストの認証情報も隔離に入る。
名前で落とす方法は[ホストから継承する認証情報](#ホストから継承する認証情報)を参照。

## env.unset
<!-- @kotowari[REQ-268:8d0f5a74] -->

`env.unset` に一致する名前の変数を、組み立ての手順 2 で消す。
項目にはシェルのワイルドカード `*`（0 文字以上の任意の並び）と `?`（任意の 1 バイト）を使える。
ワイルドカードの意味は[ポリシーファイルの形式と合成](05-policy.md)で定める。

```toml
[env]
unset = ["SSH_AUTH_SOCK", "*_TOKEN", "AWS_*"]
```

`env.unset` の後に `env.set`、秘密、Git の書き換えが入るので、同じ名前をそれらで入れれば最終の環境には残る。

## ホストから継承する認証情報
<!-- @kotowari[REQ-275:1b7a16ed, EX-512:bbff99d7] -->

`inherit` では、ホストの環境にある認証情報も隔離に入る。
名前で落とすのは `env.unset` のワイルドカードの役目で、どのパターンにも一致しない名前の変数は残る。
たとえば `env.unset` が `*_TOKEN` のとき、ホストの `TOKEN` は `_TOKEN` で終わらないので一致せず、隔離の中に残る。
この隙間は README に既知の隙間として書く。

確実に落としたい変数があれば、名前をそのまま `env.unset` に書くか、`clear` で必要な変数だけを `env.pass` で渡す。

## env.set
<!-- @kotowari[REQ-278:00184bbe, EX-515:8e79758f] -->

`env.set` は変数名をキー、値を値とするテーブルで、組み立ての手順 3 で変数を入れる。
値は書いたとおりの文字列として入る。
ポリシーの変数（`${worktree}` など）の展開はパスを取る値にだけ効くので、`env.set` の値には効かない。

```toml
[env.set]
MARKER = "${worktree}"
```

この例では、隔離の中の `MARKER` は文字列 `${worktree}` そのものになる。

kakoi が既存の環境変数の値を読んで別の変数の値を決める合成は、次の 2 つだけである。

- `GIT_CONFIG_COUNT` を読んで Git の設定の番号を続ける（[git.instead-of](#gitinstead-of)）。
- `PATH` を読んでその先頭に項目を足す（[env.path-prepend](#envpath-prepend)）。

合成後に `env.set` と `secrets` に同じキーがあれば、`policy` の診断になる（[ポリシーファイルの形式と合成](05-policy.md)）。

## env.path-prepend
<!-- @kotowari[REQ-270:84bbba58, EX-507:83faac33] -->

`env.path-prepend` はディレクトリのパスのリストで、組み立ての手順 6 で `PATH` の先頭に足す。
段をまたいだ連結では、上の段の項目が先頭側に来る。

| 状況 | 結果 |
|---|---|
| 項目の実体が存在する | 実体のパスで `PATH` の先頭に足す |
| 項目の実体が存在しない（値を持たない変数を含む場合を含む） | 飛ばし、計画に理由付きで表示する |
| 手順 6 の時点で `PATH` が無い | 足す項目だけが `PATH` になる |
| `PATH` が無く、足す項目も無い | `PATH` は無いままで、警告を出さない |

たとえば `clear` で `PATH` を `env.pass` に入れず、`env.path-prepend` も空なら、隔離の中に `PATH` は無く、警告も出ない。

```toml
[env]
path-prepend = ["~/.local/kakoi-bin"]
```

`env.path-prepend` の項目が隔離の中から書ける場所を経由して解決される場合は `path` の診断になる。
その規則は[ポリシーを保護する配置](06-policy-placement.md)が定める。

## secrets
<!-- @kotowari[REQ-271:c684c054, EX-508:dada20d2] -->

`secrets` は環境変数名をキー、秘密ファイルのパスを値とするテーブルである。
ファイルの内容を環境変数の値として隔離に渡し、ファイル自体は隠す。
**秘密**は、この変数名とファイルの組、およびファイルから読んだ値を指す（[用語](02-terms.md)）。

```toml
[secrets]
GH_TOKEN = "${config_dir}/secrets/gh-token"
```

項目は環境変数名のバイト順に処理し、各項目は次の 2 段階で動く。

1. その名前の環境変数を、由来（ホストからの継承、`env.set`）にかかわらず消す。
2. ファイルが存在すれば、その内容を値として環境変数を入れ、ファイルを `hide` にする。

ファイルが存在しなければ、変数は入れず、`kakoi: warning:` で始まる 1 行を標準エラーに出して起動を続ける。
手順 1 で消しているので、ホストに同じ名前の変数があっても隔離の中には残らない。
たとえばホストに `TOKEN` があり、`secrets` の `TOKEN` が指すファイルが無ければ、隔離の中に `TOKEN` は無く、警告が 1 行出る。
値を持たない変数を含むパスも、存在しないファイルとして同じ警告になる。

隔離の中から秘密ファイルを見ると、`hide` によって空として見える。
設定ディレクトリの `secrets/` は、`secrets` に書かれていないファイルも含めて常に隠される（[マウントの解決](07-mounts.md)）。

## 秘密ファイルの末尾の改行
<!-- @kotowari[REQ-272:df431149, EX-509:b08d85e0] -->

ファイル末尾の改行を 1 つだけ取り除いた内容を値にする。

| ファイル末尾 | 取り除くもの |
|---|---|
| LF | 最後の 1 バイト |
| CR LF | 最後の 2 バイトを 1 つの改行として |
| それ以外 | 何も取り除かない |

CR LF を 1 つの改行として扱うのは、Windows のエディタで書いたファイルの CR を値に残さないためである。
取り除くのは 1 回だけなので、`v` の後に LF が 2 個あるファイルでは、値は `v` と LF 1 個になる。

## 秘密の値の検査
<!-- @kotowari[REQ-273:d0cd2ac2, EX-510:8a287085] -->

改行を取り除いた後の値が次のどれかに当たると、`secret` の診断で終わる（終了コード 125）。

- ファイルを読めない。
- 値が空。
- 値に NUL バイトを含む。
- 値が 64 KiB を超える。

ちょうど 64 KiB の値は通る。
改行を取り除いた後の値が 65537 バイトなら `secret` で終わる。
64 KiB は、Linux の環境変数 1 個の長さの上限（名前と終端を含めて 128 KiB）の半分である。
kakoi がファイルを読む量の一般の上限（[実行時の境界](../maintainer/runtime.md)）より、この値の上限が先に効く。

秘密ファイルが通常ファイルでない場合も `secret` の診断になる（[実行時の境界](../maintainer/runtime.md)）。
複数の秘密が診断に当たるときは、名前のバイト順で最初のものを出す（[計画の表示](04-plan.md)）。

## 秘密の値を表示しない
<!-- @kotowari[REQ-274:74e685a1, EX-511:638d3be1] -->

秘密の値は、計画の表示、警告、診断のどこにも出さない。
表示するのは環境変数名とファイルパスだけで、値は伏せる。

秘密から得た `GIT_CONFIG_COUNT` が不正な場合も同じである。
たとえば秘密で入れた `GIT_CONFIG_COUNT` が数値でなければ `env` の診断になるが、その説明に値は含めない。

## git.instead-of
<!-- @kotowari[REQ-276:bb9f0905, EX-513:20a753ce] -->

`git.instead-of` は、元の URL の先頭をキー、置換先を値とするテーブルである。
ホストの Git の設定ファイルは書き換えず、Git が環境から読む設定の変数を足して、隔離の中の Git にだけ書き換えを効かせる。

```toml
[git.instead-of]
"git@example.com:" = "https://example.com/"
```

この例では、Git に設定 `url.https://example.com/.insteadof` を値 `git@example.com:` で渡す。
使う変数は `GIT_CONFIG_COUNT`、`GIT_CONFIG_KEY_n`、`GIT_CONFIG_VALUE_n`（`n` は 0 から始まる番号）である。

足し方は次のとおり。

1. 秘密の注入まで終えた環境の `GIT_CONFIG_COUNT` を読む。無ければ番号 0 から始める。
2. 既にある番号と設定の組は保持する。
3. `git.instead-of` のキーのバイト順に、続きの番号へ設定を足す。

たとえば `GIT_CONFIG_COUNT` が `1` で、`GIT_CONFIG_KEY_0` と `GIT_CONFIG_VALUE_0` が既にあれば、その組を残したまま、足す設定を番号 1 から振る。
隔離の中で `git config --list` を実行すると、足した設定とホストで設定していた組の両方が現れる。

## GIT_CONFIG_COUNT の検査
<!-- @kotowari[REQ-277:fa26254e, EX-514:85542ddd] -->

`git.instead-of` に項目が 1 つ以上あるときだけ、`GIT_CONFIG_COUNT` を検査する。

| `GIT_CONFIG_COUNT` の状態 | 結果 |
|---|---|
| 無い | 番号 0 から足す |
| 番号として読め、足した後も番号の上限内 | 続きの番号から足す |
| 空、符号付き、空白入り、数値でない、桁が多すぎる | `env` の診断（終了コード 125） |
| 数値だが、足すと番号の上限を超える | `env` の診断（終了コード 125） |

Git 自身は空の `GIT_CONFIG_COUNT` を 0 として読むが、kakoi は壊れた値を受け取ったものとして拒否する。
`git.instead-of` に項目が無ければ検査しないので、空の `GIT_CONFIG_COUNT` もそのまま隔離に渡る。

## この章に関わる診断
<!-- @kotowari[REQ-273:d0cd2ac2, REQ-277:fa26254e] -->

| 種類 | 終了コード | 条件 |
|---|---|---|
| `secret` | 125 | 秘密ファイルを読めない、改行を除いた値が空、NUL を含む、64 KiB を超える |
| `env` | 125 | `git.instead-of` があり、`GIT_CONFIG_COUNT` が不正、または足すと番号の上限を超える |
| `policy` | 125 | 合成後に `inherit` で `env.pass` が空でない、`env.set` と `secrets` に同じキーがある |

秘密ファイルが無いことは診断ではなく警告で、起動は続く。
これらの診断が検査のどの段階で出るかは[入れ子、並列、出力、診断と終了コード](10-process.md)を参照。
