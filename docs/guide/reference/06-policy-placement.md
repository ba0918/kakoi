# ポリシーを保護する配置

この章は、隔離の中からの書き換えで次回の起動の結果を変えられる配置を、kakoi がどう見つけて拒否するかを定める。
拒否の診断（種類 `path`、終了コード 125）が出たときに、何が当たったか、どう直すかを調べるために読む。
キーとパスの書き方そのものは [ポリシーファイルの形式と合成](05-policy.md) が定める。

## 何を守るか
<!-- @kotowari[REQ-158:af6b80e9, EX-364:78476eaf] -->

kakoi は起動のたびに、ポリシーに書かれたパスを実体へ解決してから隔離を組み立てる。
その解決が隔離の中から書き換えられる場所を通っていると、隔離の中のプログラムは次の起動に別のポリシーを読ませたり、指令を別の場所へ適用させたりできる。
たとえば `rw = ["~/cache"]` のとき、`~/cache` の中にポリシーファイルを置けば、隔離の中から次回のポリシーを書き換えられる。
ポリシーファイルが外にあっても、そこへ辿るシンボリックリンクが `~/cache` の中にあれば同じことが起きる。

この章の検査は、次の 4 つを守る。

| 対象 | 守ること | 節 |
|---|---|---|
| ポリシーファイル、設定ディレクトリ、秘密ファイル、`env.path-prepend` | 本体も、そこへ辿る途中の名前も差し替えられない | [読み込むものの置き場](#読み込むものの置き場) |
| 書かれた `rw`、`rw-file`、`hide`、`--workspace`、走査の起点 | 差し替えられても、書き換えられない場所の外へ出ない | [指令の着地先](#指令の着地先) |
| `hide` と走査の起点 | リンクや下位ディレクトリを消されて、隠す処理が外れない | [隠し先と起点](#隠し先と起点) |
| 項目どうしの重なり | 隠した内容が見えたり、複製への書き込みがホストへ通ったりしない | [隠したものを再び見せる組み合わせ](#隠したものを再び見せる組み合わせ) |

`rw-copy` の中は隔離の中の複製で、そこへの書き込みはホストのファイルにも、パスの解決が通る名前にも届かない。
そのため `rw-copy` はこの章の「書き込める項目」に数えない。
ポリシーファイル、設定ディレクトリ、秘密ファイルを `rw-copy` の中に置いた起動は、そのことを理由には拒否されない。

## 判定に使う言葉
<!-- @kotowari[REQ-158:af6b80e9] -->

| 言葉 | 意味 |
|---|---|
| 与えられたパス | 実体へ解決する前のパス。設定ディレクトリなら、`XDG_CONFIG_HOME` から組み立てた、実体化する前のパス |
| **書き込める項目** | 合成後の `rw` と `rw-file` の項目。その「中」は同一か子孫を指す |
| **解決が参照するもの** | パスを実体へ解決する途中で中身を見るディレクトリの実体（`..` で戻る前に通ったものを含む）と、辿るシンボリックリンクの置き場。パス自身の実体は含まない |
| **根の項目** | 書き込める項目のうち、自身の解決が書き込める項目の中（自身を含む）を一切参照しないもの |

用語の定義は [用語](02-terms.md) にもある。

書き込める項目は、原則として生成の段（走査や `hide-mounts` が足す `hide`。[マウント](07-mounts.md)）が書かれた項目を置き換えた後の集合である。
生成された項目は毎回の起動で事実から作り直すので、参照するものを持たず、根の判定の対象にもならない。
例外は走査の `root` と `hide-mounts.under` で、生成の前の集合で判定する（[検査の順序](#検査の順序)）。

同じ実体にまとまる書き込める形（`rw` か `rw-file` で書かれたもの）が複数あるときは、そのすべてが根の条件を満たすときだけ根の項目になる。
`ro` や `hide` で書かれた形は根の判定に関わらない（それ自身は書かれた項目として検査される）。

### 解決の記録

この章のすべての検査は、解決を同じ方法で記録する。
通るディレクトリは、同じ実体を 1 回ずつ記録する。
存在しない成分、読めない成分、先を読めないリンクに至ったら解決をそこで打ち切り、そこまでに参照したものを検査する（先を読めないリンクは、その置き場を記録する）。

## 読み込むものの置き場
<!-- @kotowari[REQ-158:af6b80e9, EX-365:1d7a1734] -->

次の保護対象は、その解決が書き込める項目の中にあるものを一切参照してはならない。

- 読み込んだすべてのポリシーファイル
- 設定ディレクトリ
- `secrets` の値が指す秘密ファイル
- `env.path-prepend` の項目

参照は含まないパス自身の実体も、書き込める項目の中にあってはならない。
kakoi は次の 3 つをこの順に調べ、最初に当たったもので種類 `path` の診断を出す（同じ条件の中では、最初に通ったもの）。

1. 与えられたパスの各前置き（各祖先ディレクトリと、パス自身）の実体が、書き込める項目の中にある。
2. 辿るシンボリックリンクの置き場が、書き込める項目の中にある。
3. 通るディレクトリの実体が、書き込める項目の中にある。

診断の説明は次の 3 つを含む。

- 当たったファイル、ディレクトリ、またはリンクのパス
- それを含む `rw` 項目のパス
- 「隔離の中から差し替えられるため」という理由

複数の保護対象が同時に当たるときにどれを出すかは [診断と終了コード](10-process.md) が定める。
同じ対象の中で複数の参照が同時に当たるとき、どれを名指すかは実装に委ねられている（[未決事項](../appendix/open-issues.md)）。

### まだ存在しないもの

| 状態 | 調べる範囲 |
|---|---|
| 秘密ファイルが存在しない（警告になる場合） | 存在する前置きと、存在しない成分に至るまでに参照したもの |
| 設定ディレクトリが存在しない（組み込みの既定で起動した場合） | 同上。隔離の中から設定ディレクトリを作ってプロファイルを植えられないようにする |
| `secrets` の値や `path-prepend` の項目が値を持たない変数を含む | 解決するパスが無いので対象外 |

存在しない名前自身は実体を持たないので調べない。
存在する最も深い祖先が書き込める項目の中にあれば止まる。

### 例

```toml
# プロファイル
[mounts]
rw = ["${worktree}"]
```

```console
$ cd ~/proj    # ワークツリー
$ kakoi --policy-file ~/proj/kakoi.toml -- make
kakoi: path: ...    # 終了コード 125
```

次の配置も同じ診断で止まる。

- `rw` の中を指す `secrets` の値。
- `rw` の外にあるポリシーファイルを、`rw` の中に置いたシンボリックリンク越しに指す。
- リンク先が `..` で `rw` の中のディレクトリを通り抜ける（`~/policies` が `~/cache/x/../../real/pol` を指し、`~/cache/x` が `rw` の中の実ディレクトリ）。

直すには、ポリシーファイルや秘密ファイルを書き込める項目の外（たとえば設定ディレクトリ）へ移し、途中のリンクも書き込める項目の外に置く。
`rw-copy = ["~/policies"]` の中にポリシーファイルを置いた起動は通り、同じ配置を `rw` にすると止まる。

## 指令の着地先
<!-- @kotowari[REQ-159:7c5830c2] -->

次の項目は、その解決が書き込める項目の中を参照するなら、実体がいずれかの根の項目の中に着地しなければならない。
外に着地すれば種類 `path` の診断で終わる。

- 書かれた `rw`、`rw-file`、`hide` の項目（どの段のものも、コマンドラインのものも）
- `--workspace` で与えたパス（[ワークスペース](#ワークスペース) の例外がある）
- 走査の `root` と `hide-mounts.under`

診断の説明は、そのパス、解決の途中で参照した（または `--workspace` から引き継いだ）`rw` 項目のパス、「隔離の中から差し替えられるため」という理由の 3 つを含む。

書き込めない場所だけを通る解決は、この検査の影響を受けない。
着地先が別の根の項目の中なら通る。
`rw` の項目は、別の根の項目の中へ着地しても新しく書けるようになるものが無いためである。

### 対象外の指令

書かれた `ro` と `rw-copy` はこの検査の対象外で、[隠したものを再び見せる組み合わせ](#隠したものを再び見せる組み合わせ) の検査だけを受ける。

- `ro` は、リンクを差し替えられても消されても、どこかが読み取り専用になるか外れるだけである。
- `rw-copy` は、差し替えられても動くのは複製の位置だけで、ホストには何も書かない。複製が見せるホストの内容は元から読み取り専用で見えている。差し替え先が大きければ複製の上限に当たって種類 `path` で止まる（[マウント](07-mounts.md)）。

隠されている場所への着地だけが新しく見えるものを生むので、それは組み合わせの検査が止める。

`hide` を対象に残すのは、`rw` の中のリンクで書いた `hide` が `rw` の外を指す配置では、隔離の中でリンクを消されると次の起動で項目が飛ばされ、隠し先がホストのまま見えるためである。
走査の `root` と `hide-mounts.under` を対象に含めるのは、差し替えられた起点が本物の木を走査せず、隠すべき `.env` やマウントが隠れないためである。

実体を持たない項目（存在しないもの、リンクを辿る上限を超えたもの）は飛ばされ、この検査の対象にならない。
次の起動で実体ができれば、そのときに検査される。

### 例

`rw = ["~/cache", "~/cache/pip/http"]` の正直な配置は通る。
隔離の中から `~/cache/pip` をホストの別の場所へのリンクに差し替えると、次の起動は `path` で止まる。
そうしなければ次の起動がその別の場所へ `rw` を適用する。

`rw = ["~/cache"]` の中の `rw-file` も、正直な配置は通り、差し替えると止まる。

`rw = ["~/a", "~/b"]` で `~/a/link` を `~/b/real` へ向けた `--rw ~/a/link` は通る（別の根の項目の中への着地）。

## 隠し先と起点
<!-- @kotowari[REQ-159:7c5830c2, REQ-160:5d8380ec, EX-366:29859294, EX-367:1c0c7db9] -->

### 書き込める場所に置いたリンクを辿らない

書かれた `hide`、走査の `root`、`hide-mounts.under` は、その解決が書き込める項目の中に置かれたシンボリックリンクを辿るなら、着地先を問わず種類 `path` の診断で終わる。
着地先が根の項目の中でも、`rw` のマウント点そのものでも同じである。

隔離の中でそのリンクを消されると、次の起動で項目や起点が存在しない扱いになって飛ばされる。
`hide` なら隠し先が見え、起点なら隠すべき木やマウントが隠れない。
深さ 1 のマウント点は改名できないので、実体のパスで書いた `hide` や起点なら外れない配置でも、リンクの形なら外れる。

実体のパスで書いた `rw` の中の `hide` はリンクを辿らないので通る。
ここで見るのは項目自身の解決だけで、ワークスペース由来の変数で引き継いだ参照は数えない（引き継いだリンクを消されると `--workspace` 自身が `path` で止まる）。

診断の説明は、その項目または起点のパス、辿ったリンクのパス、理由の 3 つを含む。
[指令の着地先](#指令の着地先) の検査（起点については下のマウント点の規則を含む）と両方に当たるときは、こちらの診断を出す。
辿ったリンクが、利用者の直す場所を直接指すためである。

### 起点は書き込めるマウント点そのものにする

走査の `root` と `hide-mounts.under` は、その解決が書き込める項目の中を参照するなら、実体が書き込める項目の実体と同一（`rw` のマウント点そのもの）でなければ種類 `path` の診断で終わる。

起点はマウントされないので、`rw` の下位を起点にすると、隔離の中で改名や向け直しができる。
すると次の起動は空の木を走査し、隠すべき `.env` が丸ごと隠れなくなる。
`rw` のマウント点そのものは改名できず、走査はそこから再帰するので外れない。
マウント点へリンク越しに書いた起点は、そのリンクを消せるので前項の規則に当たる。

診断の説明は、その起点のパス、参照した `rw` 項目のパス、理由の 3 つを含む。

### 例

| 配置 | 結果 |
|---|---|
| `rw = ["~/cache"]` の中を実体のパスで書いた `hide` | 通る |
| `rw = ["~/proj"]` で `~/proj/secrets` がどの項目でもない `~/vault` を指し、`hide = ["~/proj/secrets"]` | 1 回目の起動から `path` |
| `rw = ["~/a", "~/b"]` で `~/a/l` が `~/b/creds` を指し、`hide = ["~/a/l"]` | 1 回目の起動から `path` |
| `rw = ["~/a"]` で `~/a/link` がどの項目でもない `~/proj` を指し、`root = "~/a/link"` | `path` |
| `rw = ["~/b"]` で `root = "~/b/tree"`（`rw` の下位） | `path` |
| `rw = ["~/b"]` で `root = "~/b"`、または `root = "${worktree}"` | 通る |

直すには、リンクではなくリンク先の実体のパスを書く。
起点が `rw` の下位にあるなら、起点を `rw` のマウント点そのものにする。

## ワークスペース
<!-- @kotowari[REQ-160:5d8380ec, EX-368:35804d00, EX-369:2f8cf881] -->

`--workspace` の扱いは、与え方で分かれる。

| 与え方 | 扱い |
|---|---|
| `--workspace` を省略 | 検査の対象外で、参照するものを持たない。カレントディレクトリはカーネルが inode で保持している |
| 明示した実体が、カレントディレクトリの実体と同一 | 同じく対象外 |
| それ以外 | 自身の解決を検査する。ワークスペース由来の変数で展開した項目は、その参照を引き継ぐ |

既にそこにいるプロセスは、差し替えで移動しないので対象外にしている。

ワークスペース由来の変数は `${workspace}`、`${worktree}`、`${git_common_dir}` の 3 つで、引き継ぐ項目には走査の `root` と `hide-mounts.under` も含む。
対象外のときは、引き継ぐものも無い。

### リンクを辿る明示のワークスペース

対象外でない明示の `--workspace` の解決がシンボリックリンクを辿るなら、その実体は、ワークスペース由来の変数で展開した項目以外の根の項目の中になければならない。
外にあれば種類 `path` の診断で終わる。

書き込める項目の集合自体がワークスペースから導かれるので、差し替えたワークスペースを基準にすると、自分で自分を正当化できてしまう。
たとえば `rw = ["${worktree}"]` で前回 `rw` だった `~/proj` は、ワークスペースを差し替えた後の起動では書き込める項目に見えなくなる。
差し替えの手段はリンクに限られる（改名や移動では書き込める項目の外へ出られず、隔離の中から bind mount やディレクトリのハードリンクは作れない）ので、リンクを辿る解決だけを対象にしている。

字面の形とワークスペース由来の形が同じ実体にまとまった項目は、ワークスペース由来の項目として扱う。
リンクを辿る明示の `--workspace` は、そこには着地できない。

この診断の説明は、そのパス、辿ったリンクのパス、理由の 3 つを含む。
[指令の着地先](#指令の着地先) の検査と両方に当たるときは、着地先の検査の診断を出す（[隠し先と起点](#隠し先と起点) とは逆の優先順である）。

### 例

| 配置 | 結果 |
|---|---|
| `rw = ["${worktree}", "~/cache"]` に `--workspace ~/cache/proj` | 通る |
| 上の配置で、`proj` を別の場所へのリンクに差し替えた後 | `path` |
| `rw = ["${worktree}"]` だけのプロファイルで `--workspace ~/cache/proj`（`~/cache` はどの項目でもない） | 通る |
| 明示した `--workspace` がカレントディレクトリと同じ実体（`rw` のワークツリーの下位でも） | 通る |
| `rw = ["${worktree}"]` で `~/proj/sub` を別の場所へのリンクに差し替えた後、別のカレントディレクトリから `--workspace ~/proj/sub` | `path` |
| `rw = ["~/work"]` で `~/work` がリンクでも、`--workspace ~/work/proj` | 通る |

直すには、実体のパスを `--workspace` に書くか、そのディレクトリへ移動してから `--workspace` を省略して起動する。

## 隠したものを再び見せる組み合わせ
<!-- @kotowari[REQ-161:f47d19ec, EX-370:3d28eb4e, EX-371:2e8bf649] -->

解決が書き込める項目の中を参照した書かれた項目は（指令を問わず）、相手の項目と**露出する組**になるとき、種類 `path` の診断で終わる。
露出する組は、後から乗る項目が相手を無効にして、新しく読めるものや、ホストへ書けるものが生まれる組である。
リンクを辿らない実体のパスで書いた項目でも、その解決が書き込める項目の中を参照するなら対象になる。

| 後から乗る項目 | 無効にしてはいけない相手 |
|---|---|
| `rw`、`rw-file` | `hide`、`ro`、`rw-copy` |
| `ro`、`rw-copy` | `hide` |
| `hide` | なし（何も新しく見せない） |

`ro` が `ro` に重なっても、`rw-copy` が `ro` に重なっても、新しく見えるものは無い。
`rw-copy` を相手に数えるのは、利用者が書き込みを外に出さない場所として指定したところに差し替えられうる `rw` や `rw-file` が後から乗ると、その書き込みがホストへ通るためである。

相手は次の 2 か所で探す。

1. 同じ実体の、下の段。
   段の順に同一性の置き換え（[マウント項目の同一性と競合](05-policy.md)）を適用したとき、その項目の段の直前に同じ実体で残っていた項目。
2. 実体の真の祖先。
   全段（同じ段、上の段、生成の段を含む）を置き換えた後に、祖先を内側から見て最初に項目が効いている祖先だけで判定する。
   そこに残っているのが `rw` なら、その場所は既に見えているので止めない（実体のパスで書いた `rw` でも、書き込めない場所だけを通るリンク越しに書いた `rw` でも同じ）。

生成された `hide` は、同じ実体では書かれた項目を置き換えるので 1 の相手にはならないが、2 の祖先には数える。
設定ディレクトリの `secrets/` や `hide-mounts` で隠したディレクトリの中へ `ro` や `rw` がリンク越しに着地すると、狭い項目が後に乗り、隠していた中身が見えるためである。

`--workspace` 自身はこの検査の対象ではない。
ワークスペース由来の変数で展開した書かれた項目が、引き継いだ参照によって検査される。

診断の説明は、その項目のパス、無効にする相手のパス、「隔離の中から差し替えられるため」という理由の 3 つを含む。

### 例

| 配置 | 結果 |
|---|---|
| `rw = ["~/a", "~/b"]`、`hide = ["~/b/creds"]`、`~/a/l -> ~/b/x` で `ro = ["~/a/l/y"]` | 通る |
| 上の `l` を、どの項目でもない場所へ差し替えた後 | 通る（`ro` は新しく見せない） |
| 上の `l` を `~/b/creds` の中へ差し替えた後 | `path` |
| `rw = ["~/a", "~/b"]`、`hide = ["~/b/creds"]` で、`~/a/link -> ~/a/real` の `--rw ~/a/link` | 通る |
| 上の `~/a/link` を `~/b/creds` へ、または `~/b/creds/sub` へ向け直した後 | `path` |
| `rw = ["~/a", "~/b", "~/a/link"]` で `~/a/link` を `~/b/creds/sub` へ向け直し、`--hide ~/b/creds`（プロファイルに書いても同じ） | `path` |
| `rw = ["~/b"]`、`hide = ["~/b/creds"]` に `--hide ~/b/creds` または `--hide ~/b/creds/sub` | 通る |
| `rw = ["~/a", "~/b"]`、`hide = ["~/b/creds"]` に、`~/a/link -> ~/b/creds` の `rw-copy = ["~/a/link"]` を `--policy-file` で | `path` |
| 同じ形で、相手が `ro = ["~/b/creds"]` | 通る |
| `rw-copy = ["~/b/creds"]` に、`~/a/link -> ~/b/creds/k` の `rw-file = ["~/a/link"]` を `--policy-file` で | `path` |
| `rw = ["~/a"]` で `~/a/link -> ${config_dir}/secrets/other`（`secrets` に書いていないファイル）の `ro = ["~/a/link"]` | `path`（生成された `hide` の中への着地） |
| `hide-mounts` で隠した `/mnt/c` の中を指す、書き込める場所のリンク越しの `ro` | `path` |

何も参照しない項目はこの規則に当たらない。
たとえば実体のパスで書いた `rw = ["/tmp/kakoi"]` を `hide = ["/tmp"]` の中に置く形は通る。

直し方は相手の `hide` の位置で分かれる。

- `hide` が書き込める項目の外にあるなら、リンクではなく実体のパスを書けば通る。
- `hide` が `rw` の中にあるなら、実体のパスで書いてもその `rw` を参照するので、`rw` も `rw-file` も `ro` も通らない。項目を `hide` の中に置く配置そのものをやめる。

## 固定部分とホーム全体
<!-- @kotowari[REQ-161:f47d19ec] -->

次の 2 つは、参照の有無を問わず種類 `path` の診断で終わる。

| 条件 | 対象 | 理由 |
|---|---|---|
| 実体が `/` と同一、または `/dev` か `/proc` と同一かその中 | どの指令の項目も | `/proc` をホストのもので覆うとホストのプロセスが見え、`/dev` や `/` を覆うと隔離の土台が壊れる |
| 実体が `/`、ホームディレクトリ、ホームディレクトリの祖先のどれか | 合成後の `rw`、`rw-file`（どの段からの指定も） | ホーム全体を書けるようにする指定は受け付けない |

固定部分の診断の説明は、その項目のパスと理由を含む。
`ro = ["/proc"]` も、`~/a/link` を `/proc` へ向けた `ro = ["~/a/link"]` も止まる。

`rw-copy` は広さの拒否の対象にしない。
ホスト側のホームは書けるようにならないためである。
ただしホーム全体を `rw-copy` にすると、複製の上限に当たって種類 `path` で止まる（[マウント](07-mounts.md)）。

## 検査の順序
<!-- @kotowari[REQ-159:7c5830c2, REQ-160:5d8380ec, REQ-161:f47d19ec] -->

この章の検査は、起動の手順の中の 1 つの段階（[診断と終了コード](10-process.md)）で次の順に行う。
最初に当たった診断で終わる。

1. 走査の `root` を、合成後の並び順で検査する。
2. `hide-mounts.under` を、合成後の並び順で検査する。
3. 自動で生成する項目（走査、`hide-mounts`、秘密ファイル、`secrets/`）を求める。
4. [読み込むものの置き場](#読み込むものの置き場) を検査する。
5. 書かれた項目をマウントの適用順（[マウント](07-mounts.md)）で、次に `--workspace` を、着地先、組み合わせの順に検査する。
6. 固定部分への着地を拒否する。
7. 広すぎる書き込みを拒否する。

1 と 2 は生成の前に行うので、書き込める項目と根の項目は、書かれた段だけに同一性の置き換えを適用した集合で判定する。
生成は `hide` しか足さないので、この集合は生成後の集合を含み、参照の検出は厳しい側に倒れる。
一方、生成がこれから隠す `rw`（生成された `hide` と同一の実体の `rw`）の中への着地は通るが、その場所は結局隠されるので新しく見えるものは無い。

5 で項目をまたいで検査を交互に進める順は、実装に委ねられている（[未決事項](../appendix/open-issues.md)）。

## 拒否されたときの直し方
<!-- @kotowari[REQ-163:5c50ab13, REQ-165:f497d4cb] -->

診断は、当たったパスと、参照した書き込める項目（またはリンク）のパスを示す。
それを手がかりに、次の表で直し方を選ぶ。

| 診断が指すもの | 直し方 |
|---|---|
| ポリシーファイル、設定ディレクトリ、秘密ファイル、`path-prepend` が書き込める項目の中にある | 書き込める項目の外へ移す。複製でよければ親を `rw-copy` にする |
| それらへ辿る途中のリンクやディレクトリが書き込める項目の中にある | リンクを書き込める項目の外に置き直すか、実体のパスを書く |
| `rw`、`rw-file`、`hide` や起点が、`rw` の中のリンクを通って根の項目の外へ着地する | リンク先の実体のパスを書く |
| `hide` や起点が、`rw` の中のリンクを辿る | リンク先の実体のパスを書く |
| 起点が `rw` の下位にある | 起点を `rw` のマウント点そのものにする |
| `--workspace` がリンクを辿る | 実体のパスを書くか、そこへ移動して `--workspace` を省略する |
| 項目が `hide`（や `ro`、`rw-copy`）の中へ書き込める場所を通って着地する | 相手が書き込める項目の外なら実体のパスを書く。相手が `rw` の中なら、その配置をやめる |
| `/`、`/dev`、`/proc`、ホーム全体 | 狭い場所を指定する |

利用者が `rw` の中に置いたリンク（先がどの根の項目の中でもないもの。`hide` と起点は先を問わない）のパスを `rw`、`rw-file`、`hide`、走査の `root`、`hide-mounts.under` に書くと、正直な配置でも 1 回目の起動から拒否される。
リンク先の実体のパスを書けば通る。

同じリンクのパスを `ro` に書く配置（dotfiles へのリンクを `ro` にする形）は通る。
ただしその守りは弱い。
隔離の中でリンクを消して同じ名前の通常ファイルを置けば、同じ起動の中で読む側のパスの内容を変えられる（守られるのはリンク先の実体だけ）。
リンク先が書き込める項目の外なら、そこは元から読み取り専用に見えているので、`ro` の項目は何も足していない。

合成した結果は `--print-plan=full` で確かめられる（[計画の表示](04-plan.md)）。

## なぜ根の項目が要るか
<!-- @kotowari[REQ-162:06a45282, REQ-163:5c50ab13, REQ-164:8bf17cbf, REQ-166:acf1e78b] -->

この節は、上の規則がなぜその形なのかを、却下した単純な案と比べて説明する。

### 前置きの実体だけを見る案

前置きではない場所にあるリンクを張り替えられる。
`~/policies` が `~/cache/link/pol` を指し、`~/cache/link` が `rw` の中にある形がそうである。
そこでリンクの置き場も調べる。

### リンクの置き場まで見る案

リンク先が `..` で `rw` の中のディレクトリを通り抜ける形（`~/policies` が `~/cache/x/../../real/pol` を指し、`~/cache/x` が `rw` の中の実ディレクトリ）では、そのディレクトリをリンクに差し替えられる。
そこで通ったディレクトリも調べる。

### 保護対象だけを守る案

入れ子の項目（`rw = ["~/cache", "~/cache/pip/http"]`）で `~/cache/pip` をホストの別の場所へのリンクに差し替えると、次の起動がそこへ `rw` を適用する。
そこで書かれた指令の着地先も調べる。

### 着地先が「いずれかの書き込める項目の中」ならよいとする案

差し替えた着地先どうしが互いを正当化する。
`rw = ["${worktree}", "~/cache"]` で `--workspace` を `rw` の中のリンク越しに与えると、`${worktree}` の項目自身が着地先を正当化する。
ワークスペースからの参照の引き継ぎが無ければ、変数の値は実体のパスなので、その項目自身は書き込める項目の中を参照しないことになるためである。

根の項目は、この連鎖を「自身の解決が書き込める項目の中を参照しない項目」で断ち切る。
通った項目の中に限らず「いずれかの根の項目の中」とするのは、`rw` の項目については別の根の項目の中へ着地しても新しく書けるものが無いためである。

### 根の項目の中でも止める組み合わせ

着地先の根の項目の中に `hide` や `ro` で書いた項目があると、リンク越しに着地した項目がそれを無効にする。
同一の実体なら、上の段から着地した項目が同一性の規則で下の段の `hide` や `ro` を置き換える。
同一でなくても、`hide` や `ro` の中（真の子孫）へ着地すれば、狭い項目が後に乗るので隠していた中身が見える。
後者は段に依らず、下の段の `rw` がコマンドラインの `hide` の中へ着地しても起きる。
これが[露出する組](#隠したものを再び見せる組み合わせ) の検査の理由である。
何も参照しない項目は、この検査に当たらない。

### 秘密ファイルを守る理由

`rw` の中の秘密ファイルを、隔離の中からホストの任意のファイルへのシンボリックリンクに差し替えると、次の起動がその内容を環境変数として隔離に持ち込む。

### 入れ子を禁じない理由

`rw` の中の `ro` のような形を残すためである（[マウント](07-mounts.md)）。
`rw` の中の `hide` や `ro` の項目は、着地先を変えられると元の対象を隠せなくなる。
これは次の「読み取り専用で重ねるだけでは足りない理由」のとおり祖先の改名でも起きることで、この規則の穴ではない。

### 読み取り専用で重ねるだけでは足りない理由

保護対象に `ro` を重ねるだけでは守れない。
重ねたファイル自体は動かせないが、その祖先ディレクトリの改名は許され、同じパスに別のファイルを置けば次回の起動がそれを読む（bwrap 0.9.0 で実測）。

### 境界の反例

次のどれかが起きたら、この章の規則が守られていない。

- 上の段の `rw` が下の段の `hide` と同じパスを指したとき、どちらが勝つかが段の順序以外で決まる。
- 差し替えた着地先が、別の差し替えた項目によって正当化される。
- `ro` のリンクを `secrets/` の中へ向けると、次の起動で秘密ファイルが読める。
