# 入れ子、並列、出力、診断と終了コード

この章は、kakoi を呼び出した側から見える結果を定める。
隔離の中から kakoi を起動したとき（入れ子）と複数を同時に起動したときの動き、診断と警告の形、終了コード、検査を行う順序を扱う。
kakoi の失敗とコマンドの失敗を終了コードで見分けたいとき、ある入力でどの診断が出るかを知りたいときに読む。
計画の表示の内容は[計画の表示](04-plan.md)が、filtered の監督と終了は [filtered のプロセス監督と終了](network/07-lifecycle.md)が持つ。

この章の入れ子オプション、直接exec、診断の表示、数値の終了コードはCLIの契約を説明する。
組み込みAPIは設計草案で未実装であり、すべてのモードを監督して実行ハンドルを返し、終了結果と制御エラー、状態通知を構造化して返す（[設計契約](../../decision/brainstorm/2026-10-03-public-library-api-contract.md)）。
草案では入れ子でも新しい隔離を計画し、作れなければコマンドを起動せずエラーにする。
呼び出し元をexecで置き換えたり、制御エラーで終了させたりしない。
ガード子プロセスの診断とexec失敗の終了126は子プロセスの契約として残り、その標準エラーをすべて状態イベントへ変換するものではない。

## 入れ子で起動したとき
<!-- @kotowari[REQ-284:7568fc8e, EX-520:e45b9b61, REQ-455:d234e7b8, EX-884:bd2faf6f, EX-885:fdeecc3f] -->

**入れ子**は、kakoi が起動時に入れ子の印を見つけたことを指す（[用語](02-terms.md)）。
入れ子の印は、kakoi がどの隔離の中にも読み取り専用で置く空のファイル `/dev/kakoi-isolated` である。
隔離の中からは書くことも、`rm` や `mv` で消すこともできない。
kakoi はこのファイルがあるときだけ入れ子と判定し、環境変数 `KAKOI` の有無と値は見ない。
隔離の中の環境には今までどおり `KAKOI=1` を入れる（[環境変数、秘密、Git の URL 書き換え](08-environment.md)）が、これは中のプログラムへの目安であって境界ではない。
隔離の中で `KAKOI` を消してから kakoi を起動しても入れ子と判定し、ホストで `KAKOI=1` を立てて起動しても入れ子とは判定せずに隔離を作る。

入れ子の起動は `--nested` で扱いを選ぶ（[コマンドライン](03-cli.md)）。
`--nested=isolate` の動きは[入れ子の中で隔離を作るとき](#入れ子の中で隔離を作るとき)にある。
`--nested=exec`（`--nested` を省略したときを含む）では外側の隔離をそのまま使い、`init` と `--print-plan` を除き、kakoi は次のように動く。

- ポリシーを読まない。
- bwrap を起動しない。
- 環境を変えない。
- カレントディレクトリとホームディレクトリの検査を行わない。
- 内側のプロファイルが適用されないことを `kakoi: warning:` で始まる 1 行で標準エラーに出す。
- 受け取った環境のまま、コマンドを直接 exec する。

コマンドの解決はこの入れ子でも行い、kakoi が受け取ったホストの `PATH` で探す（[コマンドライン](03-cli.md)）。
結果は次のとおり。

| 状況 | 診断 | 終了コード |
|---|---|---|
| コマンドが見つからない | `command not found` | 127 |
| 見つかったが exec に失敗した | `command not executable` | 126 |
| exec した | なし | コマンドのもの |

`init` は入れ子かどうかを見ずに通常どおり動く（[コマンドライン](03-cli.md)）。

## 入れ子の中で隔離を作るとき
<!-- @kotowari[REQ-456:773fde93, REQ-457:216e2a72] -->

`--nested=isolate` を付けた起動は、入れ子かどうかによらず、入れ子でない起動と同じ手順でポリシーを読み、検査し、隔離を作ってからコマンドを実行する。
入れ子の警告は出さない。
違いはファイルの置き方だけで、入れ子の起動は共有ファイルの置き場を使わない（[実行時の境界](../maintainer/runtime.md)）。
外側の隔離の制限は中でもそのまま効き、中の隔離は外より広がらない。
たとえば外が `rw` にしていない場所を中のポリシーが `rw` にしても、中からそこには書けない。

隔離を作れないときは、コマンドを実行せずに原因の診断で終わり、隔離を作らずに実行する動きには移らない。
よくある原因は次の 2 つである。

- 外側の隔離が秘密ファイルを空にしているので、秘密を持つポリシーは `secret` の診断で止まる。
  秘密は外側の kakoi で渡すか、`env.pass` で外から受け継ぐ。
- filtered には `/dev/net/tun` が要る。外側のポリシーが `network.allow-nested-filtered` を許していなければ、中の filtered は作れない（[ネットワーク](network/01-modes.md)）。

外側の見張り役の置き場 `/dev/kakoi-guard` が起動時にあれば、それを中の隔離の同じ場所に読み取り専用でそのまま見せ、外の見張り役の規則を中でも効かせる（[コマンドのガードレール](13-command-guard.md)）。
このとき中の合成後のポリシーにも見張り役の規則があれば、種類 `policy` の診断で止まる。

計画を表示すると入れ子の表示が付き、その計画が使われること、外側の隔離の制限と重なって計画より狭くなりうることを示す。
JSON では `nested` が入れ子の判定の結果、`applied` が計画が使われるかを表す（[計画の表示](04-plan.md)）。

## 入れ子で計画を見るとき
<!-- @kotowari[REQ-285:4373d1ba, EX-521:01f68b2a] -->

`--nested=exec` の入れ子の `--print-plan` は、ポリシーを読んで計画を表示し、計画に入れ子の表示と、その計画は使われないことを付ける。
計画の 2 つの欄は、異なる `PATH` から作る。

| 欄 | 使う `PATH` |
|---|---|
| 環境の `PATH` | 隔離の中の値（ポリシーから組み立てたもの） |
| 解決したコマンド | kakoi が受け取ったホストの `PATH` |

解決したコマンドにホストの `PATH` を使うのは、この入れ子で実際に exec されるのはホストの環境のまま（受け取った環境のまま）だからである。

ポリシーを読むので、ポリシーの誤りは入れ子でも診断になる。
たとえば入れ子の印がある隔離の中で存在しない名前のプロファイルを指定して `--print-plan` を実行すると、計画を出さずに `policy` の診断で終わる。

## 入れ子の判定と入れ子の中の隔離の限界
<!-- @kotowari[REQ-286:2f6243a2, EX-522:1d489acc] -->

入れ子の印と入れ子の中の隔離には、次の限界がある。
どれも README から直接リンクする `docs/security.md` の既知の隙間に書く。

- 隔離の中のプロセスが自分で名前空間を作って `/dev` を覆うと、その中で起動した kakoi からは入れ子の印が見えず、入れ子でないと判定される。
- 入れ子の印を置かない古い版の kakoi の隔離の中では、新しい版の kakoi は入れ子と判定しない。
- `--nested=isolate` の入れ子（2 段目）の中でさらに `--nested=isolate` で隔離（3 段目）を作るとき、3 段目が、2 段目がデータから作って置いたファイル（`hide` のファイル、filtered の `/etc/resolv.conf`）と同じパスにマウントしようとすると、コマンドを実行せずに止まる。
  たとえば 2 段目がファイルを `hide` にしていて、3 段目も同じファイルを `hide` にすると止まる。
- 外の起動が共有ファイルの置き場を使えなかったときの 2 段目も、同じ理由で止まる。

## 並列に起動したとき
<!-- @kotowari[REQ-287:abf3191c, EX-523:a7867417] -->

コマンドを包む kakoi を同時に複数起動しても、互いに内部状態を共有せず、一方が終わっても他方を止めない。
共有ファイルの置き場は複数の起動が使うが、中身が決まったファイルだけを置くので、起動の結果を互いに左右しない。
それぞれの呼び出し元は、それぞれの結果を受け取る。
たとえば独立した 2 つの起動のコマンドが終了コード 5 と 6 を返せば、各呼び出し元にそれぞれ 5 と 6 が返る。

境界は次の 2 つである。

- 同じ `NAME` の `init` を同時に起動した結果は保証しない。
  書く内容は同じなので、どちらが書いても残るファイルは同じになる。
- filtered でホストに公開するポートは起動どうしで競合しうる。
  番号の変更や不足は[公開](network/06-publish.md)の割当と復帰の規則に従う。

## 診断と警告の形
<!-- @kotowari[REQ-288:4593d890, EX-524:9764e77c] -->

**診断**は、kakoi 自身の失敗を伝える標準エラーへの 1 行で、次の形をとる。

```text
kakoi: <種類>: <説明>
```

種類は契約で、呼び出し元が照合してよい文字列である（[診断の種類一覧](#診断の種類一覧)）。
説明は自由文で、字面は契約に含めない。

警告は次の形で、診断ではない。
警告が出ても起動は続く。

```text
kakoi: warning: <説明>
```

警告は、終了結果の表のどの行にも先行して標準エラーに出ることがある。
たとえば `policy` の診断で終わるとき、標準出力は空で、標準エラーには診断 1 行が出る。

## 表示する値の制御文字
<!-- @kotowari[REQ-289:5de7a9db, EX-525:eaf04556] -->

kakoi が自分で書く出力に埋め込む値（パス、キー名、変数名、コマンドラインの引数）に、制御文字 0x00〜0x1F と 0x7F が含まれていれば、見える表記に逃がして出す。
LF と CR もこの範囲に入る。
この規則により、診断と警告は末尾の LF 1 つのほかに改行を含まず、必ず 1 行になる。
たとえば秘密の名前に ESC が含まれていても、警告には生の ESC を出さず、警告は 1 行のままである。

境界は次のとおり。

- Unicode の行区切り（U+2028、U+2029、U+0085）は制御文字に数えない。
- 包んだコマンドの出力は変更しない。
- 見える表記の形と、JSON 以外の出力で UTF-8 として不正なバイト列をどう表すかは実装に委ねる（[未決事項、実装裁量](../appendix/open-issues.md)）。JSON の計画の扱いは[計画の表示](04-plan.md)が定める。

## 診断の種類一覧
<!-- @kotowari[REQ-290:fdf87de0, EX-526:c80acd80] -->

診断で終わるとき、標準出力には何も出さない。
終了コードは種類で決まる。

| 種類 | 終了コード | 主な発生条件 | 詳しい章 |
|---|---|---|---|
| `usage` | 125 | 受け付けない形の呼び出し、`COMMAND` の欠落、`--profile` や `init` の `NAME` が名前の制約に反する、`--help` や `--version` と他の引数の併用、`init` と `NAME` 以外の引数の併用、`--rw` と `--hide` 以外のオプションの繰り返し、コマンドラインの中で同じパスへの違う指令 | [コマンドライン](03-cli.md)、[マウントの解決](07-mounts.md) |
| `policy` | 125 | プロファイルや `--policy-file` の不在、TOML の解析失敗、未知の固定キー、必須キーの欠落や空、相対パスや `~ユーザー名`、未知の変数、同じ段の中で同じパスへの違う指令、`inherit` での `env.pass`、`env.set` と `secrets` の同じキー、ポリシーファイルが通常ファイルでないか読込量の上限を超える、ガードレールの規則の形の誤りや例の検証の失敗、外の見張り役を引き継ぐ `--nested=isolate` の起動で中のポリシーにも見張り役の規則がある | [ポリシーファイルの形式と合成](05-policy.md)、[コマンドのガードレール](13-command-guard.md) |
| `path` | 125 | カレントディレクトリを取得できない、ワークスペースが無いかディレクトリでない、設定ディレクトリの実体を得られない、Git の導出の失敗、マウントの種類の誤り、広すぎる範囲、保護対象の配置（共有ファイルの置き場を含む）、`rw-copy` の複製元の失敗や上限超過、`init` の書き出し先が既にある、書き込みの失敗 | [マウントの解決](07-mounts.md)、[ポリシーを保護する配置](06-policy-placement.md)、[コマンドライン](03-cli.md) |
| `secret` | 125 | 秘密ファイルを読めない、通常ファイルでない、改行を除いた値が空、NUL を含む、64 KiB を超える | [環境変数、秘密、Git の URL 書き換え](08-environment.md) |
| `env` | 125 | `HOME` が無い、空、絶対パスでない、実体を得られない、実体がディレクトリでない。`git.instead-of` があり `GIT_CONFIG_COUNT` が不正か足すと上限を超える | [用語](02-terms.md)、[環境変数、秘密、Git の URL 書き換え](08-environment.md) |
| `bwrap` | 125 | bwrap がホストの `PATH` に無い、bwrap に渡すファイル記述子を用意できない、host と none で bwrap 自身の exec に失敗した、見張り役を置くのに kakoi 自身の実行ファイルの場所が分からない、`network.allow-nested-filtered` が true でホストに `/dev/net/tun` が無い | [実行時の境界](../maintainer/runtime.md)、[bwrap を exec できないとき](#bwrap-を-exec-できないとき) |
| `command not found` | 127 | コマンドが見つからない。説明はコマンド名 | [コマンドライン](03-cli.md) |
| `command not executable` | 126 | `--nested=exec` の入れ子で見つかったコマンドの exec に失敗した、または見張り役が禁止にしなかった起動で本物の exec に失敗した。説明はそのパスとエラー | [入れ子で起動したとき](#入れ子で起動したとき)、[コマンドのガードレール](13-command-guard.md#禁止と通過) |
| `guard` | 126 | 隔離の中で、見張り役がガードレールの規則で起動を禁じた。説明はプログラム名、当たった語、理由 | [コマンドのガードレール](13-command-guard.md#禁止と通過) |

各条件の細部は、表の右の章の検査規則に従う。
filtered で通信制限を維持できずに終了するときの 125 は、この表の種類とは別に [filtered のプロセス監督と終了](network/07-lifecycle.md)が定める。

## 終了結果
<!-- @kotowari[REQ-291:153f4566, EX-527:a8bd654d] -->

呼び出し元が観測する結果は次のとおり。

| 状況 | 標準出力 | 標準エラー | 終了コード |
|---|---|---|---|
| `command not found`、`command not executable`、`guard` 以外の診断 | 無し | 診断 1 行 | 125 |
| `command not found` | 無し | 診断 1 行 | 127 |
| `command not executable`（`--nested=exec` の入れ子と、隔離の中の見張り役） | 無し | 診断 1 行 | 126 |
| `guard`（隔離の中の見張り役が禁じた） | 無し | 診断 1 行 | 126 |
| bwrap が報告する失敗（マウントの失敗、包んだコマンドの exec の失敗） | bwrap のもの | bwrap のもの | bwrap の終了コードをそのまま |
| コマンドが終了コード n で終わった | コマンドのもの | 警告があればそれとコマンドのもの | n |
| コマンドがシグナル s で終わった | コマンドのもの | 警告があればそれとコマンドのもの | 128 + s |
| `--print-plan` で診断なし（入れ子を含む） | 計画 | 警告があればそれ | 0 |
| `--print-plan` で診断あり | 無し | 診断 1 行 | 上の診断の行と同じ |
| `--version`、`--help` | 版または使い方 | | 0 |
| `init` で診断なし | 書いたファイルのパス 1 行 | | 0 |
| `--nested=exec` の入れ子（`--print-plan` なし） | コマンドのもの | 警告 1 行とコマンドのもの | コマンドのもの。見つからなければ 127、exec できなければ 126 |

たとえば host で起動した主コマンドが SIGTERM（シグナル 15）で終われば、終了コードは 143 になる。

host と none では、kakoi は bwrap を子プロセスとして待たず、bwrap へ exec する。
bwrap の失敗の出力と終了コードがそのまま呼び出し元に見えるのはこのためである。
通常の起動でコマンドの exec に失敗すると bwrap の失敗として返り、`--nested=exec` の入れ子では `command not executable` になる。
見張り役を通る起動では、bwrap が起動するのは見張り役なので、本物の exec の失敗は見張り役の `command not executable` になる。

filtered では kakoi が監督のために残り、SIGTERM や Ctrl-C の扱いと安全上の故障による 125 の優先は [filtered のプロセス監督と終了](network/07-lifecycle.md)が定める。
その規則はこの表より優先する。

## 計画を表示する前の検査
<!-- @kotowari[REQ-292:c544858e, EX-528:8e2e52d4] -->

`--print-plan` は bwrap を起動する直前までの処理をすべて行う。
ポリシーの読み込み、事実の収集、秘密の読み込み、bwrap の所在確認、指定した `COMMAND` の解決が含まれる。
診断が出る状況では計画を出さず、その診断で終わる。
診断が出なければ計画を標準出力に出し、終了コード 0 で終わる。

たとえばポリシーが不正なら、`--print-plan` は計画を出さずに `policy` の診断、終了コード 125 で終わる。

## 検査の段階
<!-- @kotowari[REQ-293:8d808bd9, EX-529:7a43441d] -->

検査は次の段階の順に行い、最初に当たった診断で終わる。
複数の診断が同時に成り立つ入力でも、出る診断はこの順で決まる。
段階は検査を行う時点を定めるもので、診断の種類は段階と独立である。
段階番号はコードやテストのコメントから「段階 7」のように参照される。

| 段階 | 検査 | 主な診断 |
|---|---|---|
| 1 | `--help` と `--version` の形。カレントディレクトリを必要としない | なし（終了コード 0） |
| 2 | 文法 | `usage` |
| 3 | カレントディレクトリの取得 | `path` |
| 4 | ホームディレクトリ | `env` |
| 5 | ポリシーファイルの読み込みと合成 | `policy` |
| 6 | ワークスペースと変数の導出 | `path` |
| 7 | マウントの解決（内訳は下の表） | `usage`、`policy`、`path`、`secret`、`env` |
| 8 | bwrap の所在（`network.allow-nested-filtered` が true のときのホストの `/dev/net/tun` を含む） | `bwrap` |
| 9 | コマンドの解決 | `command not found` |
| 10 | 起動 | `bwrap`、`command not executable` |

段階 2 の後の分かれ道は次のとおり。

- `init` は入れ子を見ず、段階 4 のホームディレクトリの検査だけを通り、書き込みを行って終わる（[コマンドライン](03-cli.md)）。
- `--print-plan` の無い `--nested=exec` の入れ子は、段階 3〜8 を飛ばし、入れ子の警告を出して段階 9 へ進む。
- `--nested=isolate` の起動は、入れ子でもすべての段階を順に通る。

段階 10 の中身は起動の形で変わる。

- 共有ファイルの置き場を使う起動は、まず置き場を確かめ、要れば作り直す（使えなければデータから作るファイルに切り替える。診断にはならない）。
- host と none は、bwrap に渡すファイル記述子を用意し（失敗は `bwrap`、125）、bwrap へ exec する（bwrap 自身の exec の失敗も `bwrap`、125）。
- filtered は通信の準備を終えてから、監督の下でコマンドを起動する（[filtered のプロセス監督と終了](network/07-lifecycle.md)）。
- `--nested=exec` の入れ子はコマンドを exec する（失敗は `command not executable`、126）。

たとえば `HOME` が不正で、同時にポリシーも不正なら、先の段階 4 の `env` の診断が出る。

## カレントディレクトリを取得できないとき
<!-- @kotowari[REQ-400:5c5b39af, EX-753:9d7489c9, EX-754:1d6389df] -->

段階 3 でカレントディレクトリを取得できないときは、種類 `path` の診断を出し、終了コード 125 で終わる。
削除されたディレクトリの中から起動した場合もこれに当たる。
標準出力には何も出さない。

カレントディレクトリを取得できれば、段階 3 では止まらない。
たとえば `HOME` が相対パスなら、次の段階 4 の `env` の診断で止まる。

## bwrap を exec できないとき
<!-- @kotowari[REQ-401:4a404510, EX-755:952cef4b, EX-756:f0920288] -->

host と none の段階 10 で bwrap 自身の exec に失敗したときは、種類 `bwrap` の診断を出し、終了コード 125 で終わる。
段階 8 で所在を確かめた後に bwrap が消された場合や、実行できない場合（例: 存在しないインタプリタを指すスクリプト）がこれに当たる。
exec に失敗した時点ではまだ kakoi が動いているので、kakoi が診断を出せる。

包んだコマンドの exec の失敗は、これと扱いが違う。
こちらは bwrap が報告するので、kakoi は診断を出さず、bwrap の失敗の出力と終了コードをそのまま返す（[終了結果](#終了結果)）。
たとえば、隔離の中に無いインタプリタを指すスクリプトがこれに当たる（隠された場所にあるコマンドは、exec の前に `command not found` になる。[実行するコマンドの探し方](03-cli.md#隠された候補を飛ばす)）。
`--nested=exec` の入れ子では kakoi がコマンドを直接 exec するので、同じ失敗が `command not executable`（終了コード 126）になる。
見張り役が本物を exec するときも同じで、見張り役は bwrap がコマンドを起動した後で動くので、bwrap はその失敗を報告できず、見張り役が `command not executable`（終了コード 126）を出す（[コマンドのガードレール](13-command-guard.md#禁止と通過)）。
起動の形によって同じ失敗の見え方が違うこの非対称は、受け入れている。

## 段階 7 の内訳
<!-- @kotowari[REQ-294:045d23f2, EX-530:40406d26] -->

段階 7（マウントの解決）の中は、次の順に検査する。
番号はコードやテストのコメントから「段階 7 の 9 番目」のように参照される。

| 順序 | 検査 | 診断の種類 |
|---|---|---|
| 1 | 展開と実体化の後のパスの同一性 | 同じポリシーの段の中なら `policy`、コマンドラインの中なら `usage` |
| 2 | 生成の前に、走査の `root`、次に `hide-mounts` の `under` の事前検査 | `path` |
| 3 | 走査と `hide-mounts` による項目の生成 | `path` |
| 4 | 項目の種類の検査 | `path` |
| 5 | ポリシーを保護する配置の検査（保護対象、根の項目、露出する組、固定部分への着地、広さ） | `path` |
| 6 | 位置とカレントディレクトリの検査 | `path` |
| 7 | 秘密の読み込み | `secret` |
| 8 | 環境の合成中の `GIT_CONFIG_COUNT` | `env` |
| 9 | `rw-copy` の複製元の読み込み | `path` |

`rw-copy` の読み込みを最後に置くのは、安く分かる誤りを先に示し、検査を通って実際に適用される項目だけを読むためである。
同一性の衝突、配置の違反、空の秘密が同時にある入力では、同一性の衝突の診断で止まる。

各検査の中身は[マウントの解決](07-mounts.md)と[ポリシーを保護する配置](06-policy-placement.md)、秘密と `GIT_CONFIG_COUNT` は[環境変数と認証情報](08-environment.md)を参照する。

### 生成と rw-copy の読み込みで止まる条件
<!-- @kotowari[REQ-403:2e27b8da, REQ-404:413c383a, EX-759:28ba5021, EX-760:1034b83a, EX-962:df8f625f, EX-761:dd5ea03e, EX-762:5d0f01e0] -->

3 番目の生成では、項目を生成するほかに次の 2 つを検査し、どちらも種類 `path` の診断で終わる。

- 走査で一致したシンボリックリンクの先が、書かれた `ro` の項目の中にあり、その `ro` の項目（先を囲む `ro` の項目が複数あれば、そのどれか一つ）が隔離の中から差し替えられるとき。
  差し替えられるとは、その項目の解決が書き込める項目を通ることを指す。
  このときリンクは隠さずに止まる。
- `mounts.hide-mounts` が書かれていて、マウントの一覧を読めないとき。
  隠すべきマウントを見落としうるためである。

9 番目の `rw-copy` の読み込みでは、適用する `rw-copy` の項目ごとに次の 3 つを検査し、どれも種類 `path` の診断で終わる。

| 検査 | 止まる条件 |
|---|---|
| 対象の種類 | 項目の実体がディレクトリでも通常ファイルでもない（例: 名前付きパイプ。内容を待たずに止まる） |
| 読めない複製元 | 一覧できないディレクトリか、読めないファイルがある |
| 量の上限 | 項目あたり 4096 エントリ、または通常ファイルの内容の合計 64 MiB を超える（[実行時の境界](../maintainer/runtime.md)の読み込みの上限） |

たとえば `rw-copy` のディレクトリが 4097 個のエントリを持てば、複製を始めずに `path` の診断で止まる。

## 同じ検査で複数の誤りがあるときに出る診断
<!-- @kotowari[REQ-295:786b1969, EX-531:00dc406c] -->

1 つの検査の中で複数の項目が診断に当たるときは、次の順で最初のものを出す。

| 対象 | 順序 |
|---|---|
| マウント項目 | 適用の順 |
| 環境変数と秘密 | 名前のバイト順 |
| ポリシーを保護する配置の保護対象 | プロファイル、`--policy-file`、設定ディレクトリ（それ自身の配置、続いてその中の書き込める項目）、秘密のファイル（名前のバイト順）、`path-prepend`（合成後の並び順）、共有ファイルの置き場 |

走査で一致した不正なリンクが `b`、`a` の順に見つかっても、名前のバイト順で先の `a` を診断する。

段階をまたぐ順序には次の 2 つの決まりがある。

- 走査の `root` と `hide-mounts` の `under` の検査は生成の前に行うので、その診断は書かれた項目の検査より先に出る。
- 根の項目の検査と露出する組の検査では、書かれた項目を適用の順に見て、最後に `--workspace` を見る。

2 つの検査を項目をまたいでどう交互に行うかは実装に任せている。
これで変わるのは最初に出る診断だけである。
