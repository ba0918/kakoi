# 入れ子、並列、出力、診断と終了コード

この章は、kakoi を呼び出した側から見える結果を定める。
隔離の中から kakoi を起動したとき（入れ子）と複数を同時に起動したときの動き、診断と警告の形、終了コード、検査を行う順序を扱う。
kakoi の失敗とコマンドの失敗を終了コードで見分けたいとき、ある入力でどの診断が出るかを知りたいときに読む。
計画の表示の内容は[計画の表示](04-plan.md)が、filtered の監督と終了は [filtered のプロセス監督と終了](network/07-lifecycle.md)が持つ。

## 入れ子で起動したとき
<!-- @kotowari[REQ-284:5510d1ae, EX-520:922923c5] -->

**入れ子**は、環境変数 `KAKOI=1` がある状態で kakoi が起動されることを指す（[用語](02-terms.md)）。
kakoi は隔離の中の環境に `KAKOI=1` を入れる（[環境変数、秘密、Git の URL 書き換え](08-environment.md)）ので、隔離の中のシムやエージェントが kakoi を呼ぶと入れ子になる。

入れ子では、外側の隔離をそのまま使う。
`init` と `--print-plan` を除き、kakoi は次のように動く。

- ポリシーを読まない。
- bwrap を起動しない。
- 環境を変えない。
- カレントディレクトリとホームディレクトリの検査を行わない。
- 内側のプロファイルが適用されないことを `kakoi: warning:` で始まる 1 行で標準エラーに出す。
- 受け取った環境のまま、コマンドを直接 exec する。

コマンドの解決は入れ子でも行い、kakoi が受け取ったホストの `PATH` で探す（[コマンドライン](03-cli.md)）。
結果は次のとおり。

| 状況 | 診断 | 終了コード |
|---|---|---|
| コマンドが見つからない | `command not found` | 127 |
| 見つかったが exec に失敗した | `command not executable` | 126 |
| exec した | なし | コマンドのもの |

`init` は入れ子かどうかを見ずに通常どおり動く（[コマンドライン](03-cli.md)）。

## 入れ子で計画を見るとき
<!-- @kotowari[REQ-285:27fc4014, EX-521:1c43400c] -->

`--print-plan` は入れ子でもポリシーを読んで計画を表示し、計画に入れ子であることを示す印を付ける。
計画の 2 つの欄は、異なる `PATH` から作る。

| 欄 | 使う `PATH` |
|---|---|
| 環境の `PATH` | 隔離の中の値（ポリシーから組み立てたもの） |
| 解決したコマンド | kakoi が受け取ったホストの `PATH` |

解決したコマンドにホストの `PATH` を使うのは、入れ子で実際に exec されるのはホストの環境のまま（受け取った環境のまま）だからである。

ポリシーを読むので、ポリシーの誤りは入れ子でも診断になる。
たとえば `KAKOI=1` の環境で存在しない名前のプロファイルを指定して `--print-plan` を実行すると、計画を出さずに `policy` の診断で終わる。

## 環境変数による入れ子の検出の限界
<!-- @kotowari[REQ-286:02be3b0c, EX-522:9e9da4fa] -->

入れ子の検出は環境変数 `KAKOI` だけに頼る。
このため次の 2 方向に隙間がある。

- 隔離の中で環境を空にしてから kakoi を起動すると、検出が外れ、隔離の中に二重の隔離を作ろうとする。
  二重の隔離は外側の隔離より広がらない。
  秘密ファイルは外側で空にされているので、秘密を持つポリシーでは `secret` の診断で起動できない。
- ホストで `KAKOI=1` を設定してから起動すると、隔離を作らずにコマンドが動く。
  その起動では入れ子の警告が必ず出るので、意図しない場合は標準エラーで気づける。

どちらの隙間も README に書く。

## 並列に起動したとき
<!-- @kotowari[REQ-287:f9ac79be, EX-523:a7867417] -->

コマンドを包む kakoi を同時に複数起動しても、互いに内部状態を共有せず、一方が終わっても他方を止めない。
それぞれの呼び出し元は、それぞれの結果を受け取る。
たとえば独立した 2 つの起動のコマンドが終了コード 5 と 6 を返せば、各呼び出し元にそれぞれ 5 と 6 が返る。

境界は次の 2 つである。

- 同じ `NAME` の `init` を同時に起動した結果は保証しない。
  書く内容は同じなので、どちらが書いても残るファイルは同じになる。
- filtered でホストに公開するポートは起動どうしで競合しうる。
  番号の変更や不足は[公開](network/06-publish.md)の割当と復帰の規則に従う。

## 診断と警告の形
<!-- @kotowari[REQ-288:4cac719a, EX-524:9764e77c] -->

**診断**は、kakoi 自身の失敗を伝える標準エラーへの 1 行で、次の形をとる。

```text
kakoi: <種類>: <説明>
```

種類は契約で、呼び出し元が照合してよい文字列である（[診断の種類一覧](#診断の種類一覧)）。
説明は自由文で、字面は契約に含めない。

警告は次の形で、診断ではない。
警告が出ても起動は続く。

```text
kakoi: warning: <説明>
```

警告は、終了結果の表のどの行にも先行して標準エラーに出ることがある。
たとえば `policy` の診断で終わるとき、標準出力は空で、標準エラーには診断 1 行が出る。

## 表示する値の制御文字
<!-- @kotowari[REQ-289:5de7a9db, EX-525:eaf04556] -->

kakoi が自分で書く出力に埋め込む値（パス、キー名、変数名、コマンドラインの引数）に、制御文字 0x00〜0x1F と 0x7F が含まれていれば、見える表記に逃がして出す。
LF と CR もこの範囲に入る。
この規則により、診断と警告は末尾の LF 1 つのほかに改行を含まず、必ず 1 行になる。
たとえば秘密の名前に ESC が含まれていても、警告には生の ESC を出さず、警告は 1 行のままである。

境界は次のとおり。

- Unicode の行区切り（U+2028、U+2029、U+0085）は制御文字に数えない。
- 包んだコマンドの出力は変更しない。
- 見える表記の形と、JSON 以外の出力で UTF-8 として不正なバイト列をどう表すかは実装に委ねる（[未決事項、実装裁量](../appendix/open-issues.md)）。JSON の計画の扱いは[計画の表示](04-plan.md)が定める。

## 診断の種類一覧
<!-- @kotowari[REQ-290:ad981827, EX-526:c80acd80] -->

診断で終わるとき、標準出力には何も出さない。
終了コードは種類で決まる。

| 種類 | 終了コード | 主な発生条件 | 詳しい章 |
|---|---|---|---|
| `usage` | 125 | 受け付けない形の呼び出し、`COMMAND` の欠落、`--profile` や `init` の `NAME` が名前の制約に反する、`--help` や `--version` と他の引数の併用、`init` と `NAME` 以外の引数の併用、`--rw` と `--hide` 以外のオプションの繰り返し、コマンドラインの中で同じパスへの違う指令 | [コマンドライン](03-cli.md)、[マウントの解決](07-mounts.md) |
| `policy` | 125 | プロファイルや `--policy-file` の不在、TOML の解析失敗、未知の固定キー、必須キーの欠落や空、相対パスや `~ユーザー名`、未知の変数、同じ段の中で同じパスへの違う指令、`inherit` での `env.pass`、`env.set` と `secrets` の同じキー、ポリシーファイルが通常ファイルでないか読込量の上限を超える | [ポリシーファイルの形式と合成](05-policy.md) |
| `path` | 125 | ワークスペースが無いかディレクトリでない、設定ディレクトリの実体を得られない、Git の導出の失敗、マウントの種類の誤り、広すぎる範囲、保護対象の配置、`rw-copy` の複製元の失敗や上限超過、`init` の書き出し先が既にある、書き込みの失敗 | [マウントの解決](07-mounts.md)、[ポリシーを保護する配置](06-policy-placement.md)、[コマンドライン](03-cli.md) |
| `secret` | 125 | 秘密ファイルを読めない、通常ファイルでない、改行を除いた値が空、NUL を含む、64 KiB を超える | [環境変数、秘密、Git の URL 書き換え](08-environment.md) |
| `env` | 125 | `HOME` が無い、空、絶対パスでない、実体を得られない、実体がディレクトリでない。`git.instead-of` があり `GIT_CONFIG_COUNT` が不正か足すと上限を超える | [用語](02-terms.md)、[環境変数、秘密、Git の URL 書き換え](08-environment.md) |
| `bwrap` | 125 | bwrap がホストの `PATH` に無い、bwrap に渡すファイル記述子を用意できない | [実行時の境界](../maintainer/runtime.md) |
| `command not found` | 127 | コマンドが見つからない。説明はコマンド名 | [コマンドライン](03-cli.md) |
| `command not executable` | 126 | 入れ子で、見つかったコマンドの exec に失敗した。説明はそのパスとエラー | [入れ子で起動したとき](#入れ子で起動したとき) |

各条件の細部は、表の右の章の検査規則に従う。
filtered で通信制限を維持できずに終了するときの 125 は、この表の種類とは別に [filtered のプロセス監督と終了](network/07-lifecycle.md)が定める。

## 終了結果
<!-- @kotowari[REQ-291:7572b444, EX-527:a8bd654d] -->

呼び出し元が観測する結果は次のとおり。

| 状況 | 標準出力 | 標準エラー | 終了コード |
|---|---|---|---|
| `command not found` と `command not executable` 以外の診断 | 無し | 診断 1 行 | 125 |
| `command not found` | 無し | 診断 1 行 | 127 |
| `command not executable`（入れ子のみ） | 無し | 診断 1 行 | 126 |
| bwrap 自身の失敗（マウントの失敗、コマンドの exec の失敗） | bwrap のもの | bwrap のもの | bwrap の終了コードをそのまま |
| コマンドが終了コード n で終わった | コマンドのもの | 警告があればそれとコマンドのもの | n |
| コマンドがシグナル s で終わった | コマンドのもの | 警告があればそれとコマンドのもの | 128 + s |
| `--print-plan` で診断なし（入れ子を含む） | 計画 | 警告があればそれ | 0 |
| `--print-plan` で診断あり | 無し | 診断 1 行 | 上の診断の行と同じ |
| `--version`、`--help` | 版または使い方 | | 0 |
| `init` で診断なし | 書いたファイルのパス 1 行 | | 0 |
| 入れ子（`--print-plan` なし） | コマンドのもの | 警告 1 行とコマンドのもの | コマンドのもの。見つからなければ 127、exec できなければ 126 |

たとえば host で起動した主コマンドが SIGTERM（シグナル 15）で終われば、終了コードは 143 になる。

host と none では、kakoi は bwrap を子プロセスとして待たず、bwrap へ exec する。
bwrap の失敗の出力と終了コードがそのまま呼び出し元に見えるのはこのためである。
通常の起動でコマンドの exec に失敗すると bwrap の失敗として返り、入れ子では `command not executable` になる。

filtered では kakoi が監督のために残り、SIGTERM や Ctrl-C の扱いと安全上の故障による 125 の優先は [filtered のプロセス監督と終了](network/07-lifecycle.md)が定める。
その規則はこの表より優先する。

## 計画を表示する前の検査
<!-- @kotowari[REQ-292:c544858e, EX-528:8e2e52d4] -->

`--print-plan` は bwrap を起動する直前までの処理をすべて行う。
ポリシーの読み込み、事実の収集、秘密の読み込み、bwrap の所在確認、指定した `COMMAND` の解決が含まれる。
診断が出る状況では計画を出さず、その診断で終わる。
診断が出なければ計画を標準出力に出し、終了コード 0 で終わる。

たとえばポリシーが不正なら、`--print-plan` は計画を出さずに `policy` の診断、終了コード 125 で終わる。

## 検査の段階
<!-- @kotowari[REQ-293:bb0accdd, EX-529:7a43441d] -->

検査は次の段階の順に行い、最初に当たった診断で終わる。
複数の診断が同時に成り立つ入力でも、出る診断はこの順で決まる。
段階は検査を行う時点を定めるもので、診断の種類は段階と独立である。
段階番号はコードやテストのコメントから「段階 7」のように参照される。

| 段階 | 検査 | 主な診断 |
|---|---|---|
| 1 | `--help` と `--version` の形。カレントディレクトリを必要としない | なし（終了コード 0） |
| 2 | 文法 | `usage` |
| 3 | カレントディレクトリの取得 | IR に定めなし（[旧仕様にだけあった規則](../appendix/open-issues.md#カレントディレクトリを取得できないときの診断)） |
| 4 | ホームディレクトリ | `env` |
| 5 | ポリシーファイルの読み込みと合成 | `policy` |
| 6 | ワークスペースと変数の導出 | `path` |
| 7 | マウントの解決（内訳は下の表） | `usage`、`policy`、`path`、`secret`、`env` |
| 8 | bwrap の所在 | `bwrap` |
| 9 | コマンドの解決 | `command not found` |
| 10 | 起動 | `bwrap`、`command not executable` |

段階 2 の後の分かれ道は次のとおり。

- `init` は入れ子を見ず、段階 4 のホームディレクトリの検査だけを通り、書き込みを行って終わる（[コマンドライン](03-cli.md)）。
- `--print-plan` の無い入れ子は、段階 3〜8 を飛ばし、入れ子の警告を出して段階 9 へ進む。

段階 10 の中身は起動の形で変わる。

- host と none は、bwrap に渡すファイル記述子を用意し（失敗は `bwrap`、125）、bwrap へ exec する。
- filtered は通信の準備を終えてから、監督の下でコマンドを起動する（[filtered のプロセス監督と終了](network/07-lifecycle.md)）。
- 入れ子はコマンドを exec する（失敗は `command not executable`、126）。

たとえば `HOME` が不正で、同時にポリシーも不正なら、先の段階 4 の `env` の診断が出る。

## 段階 7 の内訳
<!-- @kotowari[REQ-294:045d23f2, EX-530:40406d26] -->

段階 7（マウントの解決）の中は、次の順に検査する。
番号はコードやテストのコメントから「段階 7 の 9 番目」のように参照される。

| 順序 | 検査 | 診断の種類 |
|---|---|---|
| 1 | 展開と実体化の後のパスの同一性 | 同じポリシーの段の中なら `policy`、コマンドラインの中なら `usage` |
| 2 | 生成の前に、走査の `root`、次に `hide-mounts` の `under` の事前検査 | `path` |
| 3 | 走査と `hide-mounts` による項目の生成 | `path` |
| 4 | 項目の種類の検査 | `path` |
| 5 | ポリシーを保護する配置の検査（保護対象、根の項目、露出する組、固定部分への着地、広さ） | `path` |
| 6 | 位置とカレントディレクトリの検査 | `path` |
| 7 | 秘密の読み込み | `secret` |
| 8 | 環境の合成中の `GIT_CONFIG_COUNT` | `env` |
| 9 | `rw-copy` の複製元の読み込み | `path` |

`rw-copy` の読み込みを最後に置くのは、安く分かる誤りを先に示し、検査を通って実際に適用される項目だけを読むためである。
同一性の衝突、配置の違反、空の秘密が同時にある入力では、同一性の衝突の診断で止まる。

各検査の中身は[マウントの解決](07-mounts.md)と[ポリシーを保護する配置](06-policy-placement.md)、秘密と `GIT_CONFIG_COUNT` は[環境変数と認証情報](08-environment.md)を参照する。

## 同じ検査で複数の誤りがあるときに出る診断
<!-- @kotowari[REQ-295:09fedde9, EX-531:00dc406c] -->

1 つの検査の中で複数の項目が診断に当たるときは、次の順で最初のものを出す。

| 対象 | 順序 |
|---|---|
| マウント項目 | 適用の順 |
| 環境変数と秘密 | 名前のバイト順 |
| ポリシーを保護する配置の保護対象 | プロファイル、`--policy-file`、設定ディレクトリ、秘密のファイル（名前のバイト順）、`path-prepend`（合成後の並び順） |

走査で一致した不正なリンクが `b`、`a` の順に見つかっても、名前のバイト順で先の `a` を診断する。

段階をまたぐ順序には次の 2 つの決まりがある。

- 走査の `root` と `hide-mounts` の `under` の検査は生成の前に行うので、その診断は書かれた項目の検査より先に出る。
- 根の項目の検査と露出する組の検査では、書かれた項目を適用の順に見て、最後に `--workspace` を見る。

2 つの検査を項目をまたいでどう交互に行うかは実装に任せている。
これで変わるのは最初に出る診断だけである。
