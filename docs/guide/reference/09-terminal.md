# 端末の保護

この章は、隔離の中のプロセスが制御端末へキー入力を注入するのを、kakoi がどう塞ぐかを決める。
塞ぐのは `ioctl` の `TIOCSTI` による注入で、対話的なプログラムの操作は保つ。
隔離の中で端末の操作が失敗する理由を調べるとき、端末への注入に対して kakoi が守らない範囲を確かめるときに読む。

## 拒否する呼び出し
<!-- @kotowari[REQ-280:6fa0f5b4, REQ-281:d897b936, REQ-282:9ca7ab69, EX-516:bfeb8ddf, EX-517:52f25049, EX-518:f67a4e09] -->

kakoi は seccomp フィルタを bwrap の `--seccomp` で渡す。
フィルタの規則は次の 3 つである。

| 呼び出し | 隔離の中のプロセスに起きること |
|---|---|
| 呼び出しのアーキテクチャが x86_64 でないシステムコール | そのプロセス全体（全スレッド）が終了する |
| システムコール番号に x32 のビット（`0x40000000`）が立っているシステムコール | そのプロセス全体が `SIGSYS` で終了する |
| `ioctl` のうち、第 2 引数の下位 32 ビットが `TIOCSTI` に等しいもの | `EPERM` で失敗する |

アーキテクチャの検査は、フィルタの最初の判定である。
最初の 2 つの規則により、32 ビットと x32 のバイナリは隔離の中で動かない。

`TIOCSTI` の比較は第 2 引数の下位 32 ビットで行うので、上位ビットを立てた要求番号で呼んでも `EPERM` で失敗する。
カーネルは第 2 引数を 32 ビットとして受け取るので、64 ビット全体で比べると上位ビットを立てた呼び出しが素通りになるためである。

これらは隔離の中のプロセスに起きることで、kakoi の診断ではない。
kakoi は診断を出さず、主コマンドの終了をそのまま返す（[入れ子、並列、出力、診断と終了コード](10-process.md)）。

## 対象外と対話操作
<!-- @kotowari[REQ-283:6fce5664, EX-519:236ed658] -->

上の 3 つ以外のシステムコールは許す。
`ioctl` でも `TIOCSTI` 以外はフィルタが通すので、たとえば端末のサイズ取得の呼び出しは拒否されない。

bwrap の `--new-session` は使わず、隔離の中のプロセスは制御端末を持ち続ける。
制御端末との関係を切ると、対話的なプログラムの挙動が変わりうるためである。

次の 3 つの注入経路は、この保護の対象外である。

- 仮想コンソール向けの `TIOCLINUX`
- 端末への書き込みと、端末の応答を使った注入
- ディスプレイサーバを通した入力の合成

これらは既知の隙間として README に書く（[公開文書に載せる事項](../maintainer/public-docs.md)）。
最後の 1 つは、同梱プロファイルの `hide`（[マウントの解決](07-mounts.md)）と `unset`（[環境変数、認証情報、Git の URL 書き換え](08-environment.md)）で経路を消す。
同梱プロファイルの中身は [ポリシーファイルの形式と合成](05-policy.md) にある。

許す側の挙動（端末のサイズ取得が拒否されないことと、制御端末の維持）を直接確かめる検証には未決事項がある（[未決事項、実装裁量、IR 抽出で見つかった問題](../appendix/open-issues.md)）。
