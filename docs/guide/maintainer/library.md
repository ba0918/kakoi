# ライブラリの責務と実証条件

この章は、ネットワークの管理を担う 2 つのライブラリ（kakoi-core と kakoi-net）の分担と、filtered の製品実装を始める条件、提供する前の条件を定める。
filtered の実装を始める保守者、kakoi-net の責務や依存を変える保守者が読む。
ライブラリの責務は草案であり、実装の前に[実証の条件](#製品実装を始める条件)を満たす必要がある。

## 計画を作る処理と通信を動かす処理
<!-- @kotowari[REQ-150:fa54b04a, EX-332:d13209f6, EX-333:50f92d88] -->

CLI 以外の Rust プログラムからも通信の管理を使えるように、ポリシーから計画を作る責務と、その計画に従って環境を動かす責務を分ける。

![呼出元が kakoi-core の計画を kakoi-net へ渡し、kakoi-net が OS と通信経路を操作する。](../figures/library.svg)

| ライブラリ | 担当すること |
|---|---|
| kakoi-core | ポリシーの検査、合成、計画。パスの事実、マウント一覧、rw-copy の複製元を読み、bwrap に渡す記述子を用意して bwrap のコマンドを組み立てる |
| kakoi-net | 通信の起動、監督、停止。CLI 以外の Rust プログラムからも使える形にする |

CLI 以外の Rust プログラムは、CLI を経由せずに kakoi-net で通信の起動、監督、停止を行える。

kakoi-core がしないことは次の 5 つである。

- 引数を解釈しない。
- プロセスの環境変数とカレントディレクトリを読まない（値は引数として受け取る）。
- 標準出力と標準エラーに書かない。
- コマンドを実行しない（組み立てた bwrap のコマンドを実行するのは呼び出し側）。
- 通信を起動、監督、停止しない。

DNS 応答を採用するか、許可が期限切れか、という判断は、OS の操作と分けて検証できる構造にする（[検証の契約](verification.md)）。

図は呼び出しの責務を示すもので、新しい関数名や型を公開 API として確定するものではない。

## ガードレールの責務
<!-- @kotowari[REQ-454:1b77050d] -->

[コマンドのガードレール](../reference/13-command-guard.md)も、判断と実行時の操作を分ける。

| 置き場所 | 担当すること |
|---|---|
| kakoi-core | 規則の型、読み込み、段の合成、語の照合、例の検証、見張り役を置く計画 |
| kakoi の実行ファイル | 見張り役として起動されたときの処理（場所の対応を読む、引数と環境を受け取る、禁止の 1 行を出す、本物を exec する） |

例の検証と見張り役は、kakoi-core の同じ照合を使うので、例の結果と実際の結果がずれない。
見張り役のための新しいクレートは作らない。

## 製品実装を始める条件

この節と続く 2 節の条件は、初版の範囲の改訂と、実装計画のレビューで承認したものである。
過去の実証全体を合格に変えるものではない。

対象は、初版（[公開](../reference/network/06-publish.md)）で使う pasta の通常の起動時設定に絞る。
上流で修正されていない版で、次の 4 つが成り立つことを確認してから製品実装へ進む。

1. 公開なしで、IPv4 と IPv6 の外向きの TCP と UDP、および明示したホスト接続を使える。
2. 固定公開を起動前に準備でき、公開先はホストの localhost だけである。
   同一の IP 系統、競合の検出、UDP のサービスの再起動、環境の終了後の番号の再利用を確認する。
3. アプリの起動前から遮断を準備できる。
   外向き、ホスト接続、固定公開の各経路を、新規の通信と既存の通信、一方的なサーバーからの送信の両方向で遮断でき、内部の通信は維持できる。
4. 確認した版を利用者が導入でき、必要な権限と対応環境を説明できる。

同じ起動方式のケースは一組にまとめ、初版に含まれない動的公開の試験を追加し続けない。

修正されていない版で成り立たない場合は、修正版へ黙って切り替えず、方式と初版の範囲を判断し直す。
過去の限定的な修正版での合格は、この条件の代わりにならない。

## 提供する前の条件

製品実装を始めた後、製品の実際のコードで次の 6 つを確認する。
確認が終わるまでは、filtered の初版を提供済みとしない。

- 初版のすべての経路に許可の判定があり、アプリが制限を解除することも迂回することもできない。起動と復帰の途中に、すべてを許可する瞬間が無い。
- DNS 応答の検査、ホストの DNS の対応する構成と変更への追従、明示した上流と TLS、TTL がゼロの場合を含む有限の期限を守る。
- 制御役、監視役、更新役の故障、書き込みの失敗、応答の喪失、競合のときも、許可の範囲を広げない。遮断できるなら内部の処理を維持して復帰し、遮断できないなら合意した終了結果で回収する。
- 通信の遮断から、終了の猶予、すべての子プロセスの回収までを、実際の pasta と統合する。端末、シグナル、終了コード、通知の詰まりの規則を満たす。
- 固定公開の寿命、競合、終了時の回収と、複数の環境の独立性を満たす。
- 対応を表明する OS と依存の版の標準的な導入環境で、製品のテストと既存の回帰検査を通す。

それぞれの規則は、[filtered のプロセス監督](../reference/network/07-lifecycle.md)、[DNS 応答の検査](../reference/network/04-dns.md)、[上流 DNS](../reference/network/05-dns-upstream.md)、[公開](../reference/network/06-publish.md)が定める。

## 依存と対応環境

初版は pasta と nftables を前提とする。
pasta は外部の実行ファイルとして扱い、独自の通信スタックは実装しない。

記録するものは次の 3 つである。

- 標準のパッケージから導入できる OS とその版。
- 依存の版。
- TUN/TAP と user namespace の条件。

host と none には、追加の依存を必須にしない。

初版は、pesto による実行中の設定変更も、kakoi 独自の修正版の配布も必要としない。
将来、pesto の機能を使って動的公開を追加するときは、UDP の公開の削除と再利用の問題が上流で解決し、その版で実証し直せることを条件とする。
上流の正式な対応の時期は決まっていない。

## 将来の拡張と記録

動的公開と一斉送信は、初版の製品実装を始める条件に含めない。
将来のマルチキャストとブロードキャストには、転送経路をはじめとする拡張か、方式の差し替えが要る可能性があり、小さな変更で済むとは保証しない。

詳細な試験条件と部分的な観測は、実証記録（`docs/decision/brainstorm/2026-09-16-kakoi-net-evidence.md`）にある。
第 1 組から第 26 組までの履歴、失敗、全体が NOT_RUN であった記録は維持する。
今回の、製品実装を始める条件と提供する前の条件は、それぞれ対象の版、ソース、結果を付けて新しく判定する。
