# 公開文書に載せる事項

この章は、利用者に向けた公開文書（README と `docs/` 以下の英語の文書）が何を載せ、どの順で案内するかを定める。
README や公開文書を書き換える保守者、利用者に見える振る舞いを変えて公開文書への反映が要る保守者が読む。
シムとセットアップスキルの動作そのものは、[シム](../reference/11-shim.md)と[セットアップスキル](../reference/12-setup-skill.md)が定める。

## 公開文書の構成
<!-- @kotowari[REQ-358:e9f379d5, EX-656:727d5a9c, EX-657:3c19e8ac] -->

公開文書は、英語の README と、README から直接リンクする `docs/` 以下の英語の文書から成る。

README には次の 11 項目を短く載せる。

1. 目的。
2. コンテナや VM の代わりではないことの注意。
3. 対応環境。
4. インストール。
5. 最短の起動手順。
6. ポリシーファイルの最小の例。
7. 仕組みの概要（段の優先順位、指令、秘密とネットワークと環境変数）。
8. シムの最短の例と、セットアップスキルの案内。
9. 保証することと、しないこと。
10. 各文書への導線。
11. 作らないもの（対象外）の代表例。

詳細は次の 5 つの文書に分ける。

| 文書 | 載せる内容 |
|---|---|
| `docs/getting-started.md` | 設定ディレクトリ、`init`、組み込みの既定、秘密の渡し方、入れた直後の起動 |
| `docs/cli.md` | コマンドラインの使い方、計画、終了コードと診断 |
| `docs/policy.md` | ポリシーファイルの書き方と、[ポリシーを保護する配置](../reference/06-policy-placement.md)による拒否の説明 |
| `docs/shim.md` | シムの雛形とセットアップスキル |
| `docs/security.md` | 信頼の境界、保証することとしないこと、既知の隙間、作らないもの |

README だけを読んで、インストールの直後に `kakoi -- COMMAND` を起動でき、詳細の文書へ直接移れること。
起動の前に必ずプロファイルを置く手順が要ると読める README は、この契約に反する。

## 「README に書く」とされた事項の置き場
<!-- @kotowari[REQ-409:97c06ca5, EX-775:7f710dff, EX-776:ec471875] -->

IR が「README に書く」「README に載せる」とする事項は、README そのものか、README から直接リンクする詳細の文書のどれかに書けばよい。
たとえば README から直接リンクする `docs/shim.md` にある事項は、README に書いた事項として数える。
README からリンクをたどって行き着けない文書にだけある事項を、README に書いたと数えることはこの契約に反する。
ただし、README の特定の節に載せると決めた事項（[シム](../reference/11-shim.md)の節の 3 項目）は、その節そのものに載せる。

## pasta の導入手順の文書
<!-- @kotowari[REQ-434:6a13719b, EX-835:c050c974, EX-836:6d97c786] -->

`docs/pasta.md` に、`filtered` が使う pasta の導入手順を英語で載せる。
README の `filtered` の依存の記述から、この文書へリンクする。
kakoi の診断も、pasta が無いときと古いときにこの文書の URL を示す（[ネットワークモード](../reference/network/01-modes.md)）。

文書には次の 4 つを載せる。

| 事項 | 載せる内容 |
|---|---|
| 確かめ方 | 導入済みの pasta の `--help` の出力に、kakoi が長い名前で渡すオプションの名前がすべて載っているか。名前の一覧は、`crates/kakoi-net` の pasta の引数を組み立てる一覧の長い名前と一致させる |
| 必要な版 | オプションが揃う最低の版 `2024_10_30`、推奨する版 `2026_07_16` 以降、確かめた版 `2026_07_28.f8df3f1` |
| ソースビルドの手順 | 上流の passt の git からタグを指定してビルドし `~/.local/bin` に置く。`PATH` で古い pasta より前に来る必要がある |
| user 名前空間の制限 | Ubuntu 24.04 以降では制限を外す必要があるという一文と、`docs/getting-started.md` の該当節へのリンク |

podman-static から取り出す手順と、ディストリごとの例や版の一覧は載せない。
確かめ方の名前の一覧がコードとずれることも、この契約に反する。

ソースビルドの手順は、公開の前に書かれたとおりに実行し、置いた pasta の `--help` に文書が載せた名前がすべて載ることを観測する。
Ubuntu 24.04 の標準の pasta しか無い利用者が、確かめ方に従って足りないことを知り、手順を実行すれば、`~/.local/bin` の pasta の `--help` に名前がすべて載る。

## 既知の隙間
<!-- @kotowari[REQ-359:f8570fbc, TBL-160:eefe7bb9, EX-658:e16908e6, EX-659:87f89b7b, EX-736:bd8c616a, EX-737:388f8b31] -->

既知の隙間は `docs/security.md` に載せ、README からその節へ直接リンクする。
README から 1 回のリンクで、次の 16 件の具体的な限界を読めること。
既知の隙間が IR にしか無いことは、この契約に反する。

載せる 16 件は次のとおりで、どれも省かない。

1. `hide` したディレクトリの中のコマンドが「見つかった」と判定される（[コマンドライン](../reference/03-cli.md)のコマンドの解決）。
2. 起動後に現れたファイルは隠れない（[マウントの解決](../reference/07-mounts.md)）。
3. 走査で隠したファイルが Git に追跡されていると、隔離の中で空の変更として見える（[マウントの解決](../reference/07-mounts.md)）。
4. bind mount やハードリンクによる別の経路は隠せない。
   `hide` と `rw-copy` は、指定した実体のパスにだけ効く。
   `rw-copy` の複製元と同じ inode へのハードリンクが `rw` の中にあれば、そこへの書き込みはホストのファイルに届く。
5. マウントするパスと秘密ファイルのパスは bwrap の引数に載り、秘密の値は `/proc` を通してホストから読める（[環境変数と認証情報](../reference/08-environment.md)）。
6. 名前が規則に合わないホストの認証情報の環境変数は、`inherit` で隔離に入る（[環境変数と認証情報](../reference/08-environment.md)）。
7. `TIOCLINUX`、端末の応答を使った注入、ディスプレイサーバを経由した入力の合成は、seccomp で塞がない（[端末の保護](../reference/09-terminal.md)）。
   同梱のプロファイルは、これらの経路を `hide` と `unset` で消す。
8. 環境を空にした入れ子と、ホスト側で `KAKOI=1` を立てた起動（[入れ子、並列、出力](../reference/10-process.md)）。
9. kakoi は起動された環境を信頼する（[実行時の境界](runtime.md)）。
   カレントディレクトリも含む。
   `rw` の中を通るパスで `cd` し直してから起動すると、隔離の中で差し替えたリンクの先が作業場所になる。
10. `rw` で渡した領域は、利用者がホスト側で後から実行するものの置き場になりうる。
    `.git/hooks` と `.git/config` は、利用者の `git` の操作で自動的に読まれる。
    隔離の設計では防げず、利用者が差分を見るしかない。
11. 32 ビットと x32 のバイナリは動かない（[端末の保護](../reference/09-terminal.md)）。
12. ワークツリーの `.git` を消すと、次回の起動でワークツリーの導出が祖先のリポジトリに変わりうる（[マウントの解決](../reference/07-mounts.md)）。
13. `git init --separate-git-dir` で作ったメインのワークツリー（`.git` が通常ファイルで、その指す先に `commondir` も `core.worktree` も無いもの）は、[ポリシーファイルの形式と合成](../reference/05-policy.md)が定める相互リンクのどちらの形にも当たらず、`path` で止まる。
14. [ポリシーを保護する配置](../reference/06-policy-placement.md)の根の項目の検査は、今回の起動で書き込める項目を基準にする。
    ワークツリーの下位を字面で書いた項目（例: `rw = ["${worktree}", "~/work/a/b"]`）は、ワークツリーが `~/work` である起動の隔離の中で `~/work/a` をリンクに差し替えられる。
    次にワークツリーが別の場所になる起動ではその差し替えが見えず、リンクの先に `rw` が付く。
    項目のパス自身がリンクに差し替えられる形（`~/work/a/b` を差し替え、次の起動で `--workspace ~/work/a/b/inner` を別の場所から与える）も同じである。
    同じワークツリーから起動すれば止まる。
    閉じるには前回の起動で書き込めた項目を覚える必要があり、永続する状態を持たないという[実行時の境界](runtime.md)に反するので、この隙間は受け入れる。
    ワークツリーの下位は変数で書く。
15. `rw` の中にある `ro` と `hide` の項目の守りは完全ではない。
    リンクで書いた `ro` が守るのは、リンク先の実体だけである。
    隔離の中でリンクを消して同じ名前の通常ファイルを置けば、同じ起動の中で、読む側のパスの内容を変えられる（一時ファイルと rename で保存するエディタも、リンクを置き換える）。
    リンク先が書き込める項目の外なら、そこは元から読み取り専用であり、`ro` の項目は何も足していない。
    次の起動では、リンクの差し替えで別の場所が読み取り専用になるか、削除で読み取り専用が外れる。
    新しく見えるものは、ポリシーを保護する配置の露出する組の検査が止める。
    リンクで書いた `hide` は、根の項目の検査が 1 回目の起動から止める。
    リンクでなくても、祖先ディレクトリの改名と、同じパスへの別のファイルの配置で、次の起動が読む内容を変えられる（[ポリシーを保護する配置](../reference/06-policy-placement.md)）。
    `ro` で守れるのは、エージェントが読む実体の内容が意図せず書き換わらないことまでで、エージェントが別の内容を読むように仕向ける迂回は止められない。
16. シムの雛形は、包む対象のどのオプションが値を取るかを知らない。
    そのため、写す対象のオプションと同じ名前の語を、別のオプションの値でも位置引数でも、どこにあってもそのオプションとして読む（[シム](../reference/11-shim.md)）。
    その結果、`--workspace` や `--rw` が、その語に続く語まで広がりうる。
    例: `codex -m --cd /etc exec` は kakoi に `--workspace /etc` を渡す。
    この誤読は受け入れる。
    写しの誤りが取りこぼしの向きだけだと読める説明は、この契約に反する。

## 配置保護の説明
<!-- @kotowari[REQ-360:cc80b6a5, EX-660:c22170cc, EX-661:8225229f] -->

`docs/policy.md` は、[ポリシーを保護する配置](../reference/06-policy-placement.md)による拒否が直感に反しうることを認めたうえで、次を載せる。

- 拒否の理由（祖先ディレクトリの改名による差し替えで、保護を迂回できること）。
- dotfiles のように設定ディレクトリの実体をワークツリーに含む場合の書き方。
  `--workspace` で下位ディレクトリを指し、`rw = ["${workspace}", "${git_common_dir}"]` とするプロファイルを例に示す。
- `rw` のワークツリーの下位ディレクトリを `--workspace` で明示するときは、そこをカレントディレクトリにして起動すること。
  そうすれば根の項目の検査の対象外になる。
- リンクを経由するパスを別の場所から `--workspace` で明示すると止まるので、実体のパスを書くか、そこで起動すること。
  エイリアスのリンク越しに与える `--workspace` も同じである。
- `rw` の中に置いたリンクのパスを `hide`、走査の `root`、`hide-mounts` の `under` に書くと、着地先を問わず止まること。
- `rw` の中に置いたリンクのパスを `rw`、`rw-file` に書くと、リンク先がどの根の項目の中でもなければ止まること。
  どちらの場合もリンク先の実体のパスを書けばよいこと。
- 同じ形の `ro` は通るが、その守りは既知の隙間の 15 件目の水準であること。

利用者がリンクを使った配置の拒否を調べたとき、拒否の理由と、実体のパスでの指定かカレントディレクトリでの起動という回避の方法が分かること。
`ro` にすればリンク元の差し替えも防げると説明することは、この契約に反する。

## rw-copy と一時領域の説明
<!-- @kotowari[REQ-361:dc026de0, EX-662:fb48b239, EX-663:9395c2cf] -->

`docs/policy.md` は、`rw-copy`（[マウントの解決](../reference/07-mounts.md)）について次を載せる。

- `hide` との対比。`hide` の初期状態は空で、`rw-copy` の初期状態はホストの内容である。
- 用途の例を 1 つ。隔離の中の道具に設定ファイルを書き換えさせるが、その結果をホストに出さない使い方である。
- 複製の作られ方。シンボリックリンクはリンクのまま複製し、モードは引き継ぐ。所有者、時刻、ハードリンクの共有は引き継がない。
- 上限と、失敗したときの扱い。
- `rw-copy` の中に置いたポリシーファイルは、配置の検査で拒否されないこと。

設定ファイルだけを隔離の中で変えたい利用者が読んで、`rw-copy` の初期内容と、終了時に消える性質が分かること。
`rw-copy` が終了時にホストへ書き戻すと読める説明は、この契約に反する。

同じ `docs/policy.md` に、秘密と一時領域について次を載せる。

- 秘密ファイルは、設定ディレクトリの `secrets/` に置く。
- `/tmp/kakoi` は利用者かシムが作る、ホストとの共有場所である。kakoi は作らない。
  無ければその項目は飛ばされ、`/tmp` は空のままになる。
- `/tmp` を `hide` にする理由。ホストのソケットは名前がランダムで、名前で隠せないためである。

同梱する既定のプロファイルの中身は、[ポリシーファイルの形式と合成](../reference/05-policy.md)が定める。

## インストールから初回起動までの案内
<!-- @kotowari[REQ-362:b39f6822, EX-664:0e264329, EX-665:12cfa8a9] -->

README のインストールの節は、ビルドの道具を持たない利用者が最初に読む形を先頭に置く。
次の順に並べる。

1. リリースに添えた実行ファイルを入れる手順（インストーラで入れる形と、書庫を手で取る形）。
2. ソースからビルドする形。

ソースからのビルドしか案内しないことは、この契約に反する。

インストールの直後に、`kakoi -- COMMAND` が組み込みの既定で動くことを書く。
`init` と `--print-plan` を、最短の起動手順として示す。

`docs/getting-started.md` と `docs/shim.md` には、次の 4 つを任意の調整として案内する。

| 調整 | 案内する内容 |
|---|---|
| プロファイル | `kakoi init` で境界を手元のファイルへ書き出し、直せる。既定は WSL2 を想定しており、中身は `init` か `--print-plan` で読める |
| 秘密 | GitHub の認証情報を渡すときは、書き出したプロファイルの `secrets` のコメントを外し、`secrets/gh-token` を置く |
| シム | 同梱の雛形を写し、先頭のツールの節を埋めて `PATH` に置く。同梱の値は codex の例である |
| セットアップスキル | `gh skill install` で導入できる。実行は隔離の外に限る（[セットアップスキルを隔離の外で動かす案内](#セットアップスキルを隔離の外で動かす案内)） |

入れた直後の起動で見えないものを、README と `docs/getting-started.md` の両方に書く。

- `/tmp/kakoi` が無いので、`/tmp` は空である。
- `~/.config/gh` は隠れるので、中の `gh` は未認証である。

## セットアップスキルを隔離の外で動かす案内
<!-- @kotowari[REQ-363:4ded0723, EX-666:6ad99fb6, EX-667:cf6f03ab] -->

公開文書は、セットアップスキルを隔離の外で動かすと説明する。
配置保護が、設定ディレクトリへの書き込みを隔離の中から認めないためである。
隔離の外で動かす経路として、次の 3 つを示す。

- シムを導入する前に動かす。
- `KAKOI_SHIM_OFF=1` を与えて動かす。
- kakoi を通さない CLI を使う。

その間、エージェントは隔離されない。
そのため公開文書は次の 2 つを案内する。

- スキルに、書き込みごとに差分の承認を求めさせる。
- スキルの指示を守るかどうかはエージェントの CLI の振る舞いに依存するので、CLI の側も承認を求めるモードで使う。

利用者がセットアップスキルの手順を読んで、隔離の外で操作していることと、承認の境界を認識できること。
隔離の中からの設定の編集を当然にできるものとして案内することは、この契約に反する。

## ガードレールの案内
<!-- @kotowari[REQ-452:d11f1d9b] -->

`docs/policy.md` と `docs/security.md` は、[コマンドのガードレール](../reference/13-command-guard.md)について次を示す。

- ガードレールが境界ではなく、悪意があれば迂回できる事故防止の柵であること。
- 見張れないもの。見張り役を置いていない場所やハードリンクからの起動、置き直した本物を探しての直接起動、プログラムを起動せずに同じ操作をするライブラリ、設定ファイルや環境変数で作った別名、組み込みのコマンド、長いオプションの省略形、語の並びの途中のオプション。
- `guard-absolute-path` を有効にすると、自分の場所から資源を探すプログラムが壊れうること。
- `git.instead-of` と `GIT_CONFIG_*` の禁止を一緒に使えないこと。
- 本当に止めるには、権限の狭いトークンや filtered の通信の許可を使うこと。
- プログラムそのものを使わせないには `hide` で隠し、守るべき資源（たとえば docker のソケット）があればそれを隠すこと。
