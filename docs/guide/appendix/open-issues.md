# 未決事項、実装裁量、IR 抽出で見つかった問題

この付録は、まだ決めていない事項、実装する側が選んでよい事項、IR を抽出したときに見つかった問題を集める。
本文の章が断定を避けている箇所の背景を確かめるとき、実装の選択が契約の範囲に収まるかを判断するときに読む。

## 別の作業で判断する事項

次の 2 つは、今回の文章整理では決定しない。

- 同梱のプロファイルにある `ro ~/.codex/skills` は、codex の公式文書（2026-09-07 時点）がスキルの探索先として挙げていないパスである。
  公式文書が挙げているのは `.agents/skills`、`~/.agents/skills`、`/etc/codex/skills` である。
  この改訂の範囲外として、別の作業で保守側が決める。
  それまで、同梱のプロファイルは現行の jail の写しのままとする。
- [セットアップスキル](../reference/12-setup-skill.md)で、エージェント CLI でない包む対象に固有の手順。
  事例が出たときに、別の作業で決める。
  それまで、スキルは「包む対象のコマンド」の一般の手順だけを持つ。

## 実装する側が決めてよい事項

次の事項は、各章が定める振る舞いを保つ範囲で、実装する側が選べる。

| 事項 | 選べる範囲と、契約として残る条件 |
|---|---|
| 内部のモジュール構成 | 自由。TOML の読み込みに使うライブラリも選べる |
| seccomp フィルタを bwrap に渡すファイル記述子 | 作り方（パイプかメモリ上のファイルか）と番号の割り当てを選べる |
| 計画の表示の整形 | [計画の表示](../reference/04-plan.md)が定める内容を含むことだけが条件 |
| 警告と診断の説明部分の文言 | 接頭辞と種類、および[ポリシーを保護する配置](../reference/06-policy-placement.md)と[マウントの解決](../reference/07-mounts.md)の生成される項目の規則が検査ごとに要求する要素（多くは 3 つ、固定部分への着地の拒否は 2 つ）だけが契約 |
| 走査の探索順と並列化 | 結果は[マウントの解決](../reference/07-mounts.md)の順序の規則で並べ直し、走査の中で出る診断が名指すリンクはパスのバイト順で決まるので、順序は結果に影響しない |
| `rw-copy` の複製元を読む順と並列化 | 引数に並ぶ順（ディレクトリが先、同じディレクトリの中はエントリ名のバイト順）は[マウントの解決](../reference/07-mounts.md)の契約なので、どう読んでも結果は同じ |
| 制御文字の見える表記の形と、UTF-8 として不正なバイト列の表し方 | [入れ子、並列、出力](../reference/10-process.md)が定める範囲で選べる。どの形でも「1 行、制御文字なし」は保たれる |
| ポリシーを保護する配置と、生成される項目の診断に出すパスの形 | 書いたまま、展開後、実体のどれでもよい。検査ごとに要求する要素が含まれることだけが契約 |
| ポリシーを保護する配置で、根の項目の検査と露出する組の検査を項目をまたいでどう交互に行うか | 項目ごとに 2 つの検査を行ってから次の項目へ進むか、検査ごとに全項目を見るかを選べる。変わるのは最初に出る診断だけ |
| ポリシーを保護する配置の診断の細部 | 名指すリンクや書き込める項目が複数あるときの選び方、保護対象の 3 つの規則のどれを出すか、通ったディレクトリがディレクトリでない成分だったときの名詞、理由の文言を選べる（どれを出すかは[保護対象の診断順位が裁量の記述と競合する](#保護対象の診断順位が裁量の記述と競合する)で未整理） |
| `--print-plan` で組み込みの既定を使ったことを示す文言 | 文字列 `kakoi init` を含むことだけが契約（[計画の表示](../reference/04-plan.md)） |
| `--print-plan=json` の 1 行の中の空白と、オブジェクトのキーの順序 | [計画の表示](../reference/04-plan.md)が定めるキーと値の意味、1 行であることだけが契約 |
| `init` が `profile/` と `secrets/` を作る順と、書き込みの途中で失敗したときに作ったディレクトリを残すか消すか | どちらでも、次の `init` の結果は同じ |

実装する側は、ここに無い新しい観測可能な振る舞いを黙って選ばない。
必要になったら、契約（IR とこのガイド）に戻して決める。

## ネットワークの実装裁量

合意した挙動を変えない範囲で、内部の構造、関数名、内部の型、処理の手順と検証の方法は、担当する側が決める。
許可の範囲、安全性、対応環境、ポリシーの意味、公開 API の責務が変わる判断は、利用者へ戻す。
まだ実証していない条件を満たせなければ、[ライブラリの責務と実証条件](../maintainer/library.md)に従い、製品実装へ進まない。

## IR 抽出で見つかった問題

以下は、本体の既存の仕様とテストを照合したときに見つかった事項である。
不具合の断定でも、新しい仕様の判断でもない。
今回、製品とテストの動作は変えていない。

問題の種類は次の 3 つで表す。

| 種類 | 意味 |
|---|---|
| 検証の不足 | 要求に対して、テストが確かめていない部分がある |
| 記述の矛盾 | 仕様の記述どうし、または記述と観測が食い違う |
| 記述の曖昧さ | 記述の範囲が定まらず、適否の判断が分かれる |

### 配置の診断の理由が一部しか検証されていない
<!-- @kotowari[FLAG-001:e8bf05e4] -->

種類は検証の不足で、[ポリシーを保護する配置](../reference/06-policy-placement.md)の保護対象の検査に関わる。

`tests/placement.rs` の `a_policy_file_inside_a_writable_area_is_rejected_with_the_three_reasons` は、`assert_path_diagnostic` に、問題のパスと書き込める項目のパスだけを渡す。
診断に求める 3 つ目の要素である「隔離の中から差し替えられるため」という理由は確かめていない。
テストに要求の対応が付いていても、理由の説明が欠ける退行をこのテストだけでは検出できない。

実装の不具合は確認していない。
後続の修正では、自由な説明文の字面を固定せず、契約上の理由を伝えていることを検証する。

### 保護対象の診断順位が裁量の記述と競合する
<!-- @kotowari[FLAG-002:b1d52798] -->

種類は記述の矛盾で、[ポリシーを保護する配置](../reference/06-policy-placement.md)の保護対象の検査に関わる。

旧仕様のポリシーを保護する配置の節は、保護対象の 3 つの規則を「この順」に検査し、最初に当たったものを出すと定める。
一方、旧仕様の実装裁量の節（この付録の[実装する側が決めてよい事項](#実装する側が決めてよい事項)）には、「保護対象の 3 つの規則のどれを出すか」が含まれる。
複数の規則に当たるときの診断が固定か裁量かで、2 つの記述が競合する。

今回はどちらにも寄せず、既存の記述を保持した。
利用者に見える診断の順位を決めるときに、整理が要る。

### シムの検出手順で command -v の説明が不正確
<!-- @kotowari[FLAG-003:015ad4c8] -->

種類は記述の矛盾で、[セットアップスキル](../reference/12-setup-skill.md)の実行可能ビットと経路の確認に関わる。

旧仕様は「`command -v` はシェルの関数と alias を見ない」と説明する。
しかし、この環境の Bash で関数 `kakoi_probe_function` を定義して `command -v kakoi_probe_function` を実行すると、パスではなく関数名を返した。
少なくとも「関数を見ない」という説明は成り立たない。

alias の扱いを含め、対象とするすべてのシェルでの確認はしていない。
関数と alias による横取りを別に調べる既存の手順は維持し、今回は新しい探索の手順を決めない。

### ro の既存テストの名前とコメントが古い
<!-- @kotowari[FLAG-004:29406b13] -->

種類は記述の曖昧さで、[ポリシーを保護する配置](../reference/06-policy-placement.md)の再露出の拒否に関わる。

`tests/placement.rs` の `an_ro_written_through_a_writable_link_is_accepted_wherever_it_lands_outside_hide_and_ro` の名前とコメントは、`ro` に `ro` を重ねる形も露出として拒否すると読める。
既存の仕様と `a_referenced_ro_replacing_a_lower_layer_ro_is_accepted` は、その形を許可する点で一致している。

assert どうしの動作の矛盾は確認していない。
後続の作業で、名前とコメントの更新を検討する。

### init の既存ファイルの拒否で、書かない範囲が曖昧
<!-- @kotowari[FLAG-005:85b84208] -->

種類は記述の曖昧さで、[コマンドライン](../reference/03-cli.md)の `init` の出力と上書きの拒否に関わる。

旧仕様のコマンドラインの文法の節は、書き出し先が既にあれば「何も書かず」に拒否すると定める。
一方、`src/init.rs` の `write_built_in_default` は、`secrets/` の作成と `chmod 0700` を済ませてから、書き出し先が既にあるかを判定する。
`tests/cli.rs` の `init_refuses_to_overwrite_an_existing_profile` は、プロファイルの内容が変わらないことだけを確かめる。
「何も」が出力ファイルだけを指すのか、ディレクトリの作成とモードの変更も含むのかで、適否が変わる。

今回の抽出では、この語の範囲を決めていない。
実測では、既存のプロファイルを保ったまま `path` と 125 で終了し、`secrets/` のモードが 0755 から 0700 に変わった。
製品の副作用は確認済みだが、それが契約違反かどうかは、文言の範囲の判断として残る。

### 通常の端末操作が許されることを直接検証していない
<!-- @kotowari[FLAG-006:96aec97e] -->

種類は検証の不足で、[端末の保護](../reference/09-terminal.md)の保護の範囲に関わる。

既存のテストは、`TIOCSTI` と x32 の拒否を確かめている。
しかし、端末サイズを取得する ioctl が許されることと、制御端末が維持されることを直接確かめるテストは、今回の対応付けでは見つからなかった。
拒否の対象を広げすぎて通常の端末操作を壊す退行を、検出しきれない可能性がある。
実際に壊れているという証拠ではない。

### 既存のテストが仕様より細かいことを確かめている
<!-- @kotowari[FLAG-007:2811d11e] -->

種類は検証の不足で、[ポリシーファイルの形式と合成](../reference/05-policy.md)のワイルドカードと、[マウントの解決](../reference/07-mounts.md)の生成される `hide` に関わる。

`tests/mounts.rs` の `a_name_the_isolation_planted_cannot_stall_a_pattern_with_many_stars` は、星の多いパターンが 255 文字の名前に一致しないという結果に加えて、1 秒以内に終わることを確かめる。
既存の仕様は照合の意味を定めるが、1 秒という上限は定めていない。

`a_mount_point_with_a_byte_that_is_not_utf8_does_not_empty_the_mount_list` は、UTF-8 でないマウント名を保持することを確かめる。
既存の仕様は、その入力の境界を明示していない。

両テストの動作は維持する。
特定の上限や表現を今回の新しい要求として追認しないため、これらのテストには印を付けていない。
テストが無いのではなく、テストと明文化された要求の対応が足りないという問題である。

### ホーム全体の複製が必ず上限を超えるとは限らない
<!-- @kotowari[FLAG-008:7c9ffcd0] -->

種類は記述の曖昧さで、[ポリシーを保護する配置](../reference/06-policy-placement.md)の広すぎる書き込みの拒否と、[マウントの解決](../reference/07-mounts.md)の複製の上限に関わる。

旧仕様のポリシーを保護する配置の節は、ホーム全体の `rw-copy` は複製の上限に当たって `path` で止まると断定する。
しかし複製の上限は 4096 エントリ、64 MiB であり、それ以内に収まる小さなホームまで必ず拒否されるとは導けない。

ホームの `rw-copy` を広さの拒否の対象から外す規則は保持する。
上限の超過が典型例の説明なのか、別の無条件の拒否を意図したものなのかは、今回の文章整理では決めない。

### JSON の出所の列挙がどの欄に適用されるか曖昧
<!-- @kotowari[FLAG-009:4f0cf0e5] -->

種類は記述の曖昧さで、[計画の表示](../reference/04-plan.md)の JSON の出所に関わる。

旧仕様の出力の節は、出所の `kind` を `profile` をはじめとする 8 種類で列挙する。
一方、`tests/cli.rs` の JSON のテストは、項目の `origin.kind` が `profile` と `secret` であること、`policy_sources[0].kind` が `file` であることを確かめる。
列挙が項目の `origin` だけを指すのか、`policy_sources` も含むのかが、原文では明確でない。

今回は `kind` の追加もテストの変更も行わず、内側の JSON の契約を明確にする課題として残す。

### 全形式と名付けた表示のテストが全量の形式を確かめていない
<!-- @kotowari[FLAG-010:0487e548] -->

種類は検証の不足で、[計画の表示](../reference/04-plan.md)の全量の表示に関わる。

`tests/cli.rs` の `rw-copy` の表示のテストは `every_form` という名前を持つが、実際の呼び出しは `summary` と `json` で、`full` を含まない。
全量の形式にも複製の説明と項目が出るという条件を、このテストだけでは確かめられない。
印とテスト名を、網羅の完全な証拠として扱わない。

## 旧仕様にだけあった規則

旧仕様を削除する前に、旧仕様にはあって IR には無い規則を洗い出した。
ほとんどは今の振る舞いのまま IR の要求にし、このガイドの各章が説明している。
今の実装で確かめられず、要求にしなかったものだけをここに残す。

### 固定公開の 2 つの規則
<!-- @kotowari[FLAG-019:d31d0a33] -->

関わる章は[公開](../reference/network/06-publish.md)。

旧仕様は固定公開について、次の 2 つも定めていた。

- 内側の転送先は指定した系統のループバックで、そのアドレスに接続できる全アドレスの待受も使える。
- 設定の一覧や外部コマンドの成功終了だけを、ポートを実際に確保した証拠にしない。

前者は実装もテストも見つからない。
後者について、kakoi はホスト側のポートを直接確かめるコードを持たない。
どちらも今の実装で確かめられないので、要求にしていない。

## IR の照合で見つかった問題

### 動的公開のための責務分離の区切り方
<!-- @kotowari[FLAG-027:c0c247e7] -->

関わる章は[公開](../reference/network/06-publish.md)と[ライブラリの責務と実証条件](../maintainer/library.md)。

IR は、将来の動的公開を追加できるよう、公開の判断と pasta に固有の操作を分けると定めている。
ただし、その元になった決定は「動的公開を追加できる責務の分離を初版から設ける」ことだけを述べていて、何と何を分けるかを書いていない。
区切り方を決定として記録するか、要求の文を決定の範囲まで狭めるかは、まだ決めていない。
