# 却下した代替案

この付録は、検討して採らなかった案と、採らなかった理由を記録する。
ここにあるのは歴史的な不採用の理由であり、確定した要求ではない。
現在の契約は各章が定める。
同じ案をもう一度検討するときに、以前どこで行き詰まったかを確かめるために読む。

## 製品の範囲

- blocklist 型の hook をコマンドにする案。
  完全な防御が不可能で、筋が悪い。
- `@anthropic-ai/sandbox-runtime`（srt）を採用する案。
  Linux 版が `.env*` のパターン指定を持たず、ディレクトリのシンボリックリンクを読み取り禁止にすると bwrap が起動時に落ち、無制限のネットワークを指定できない（2026-09-03 の実測）。
- 0.1 を、現行の jail の挙動を保存するだけに限定する案。
  ネットワーク、環境変数、認証情報を後から入れると、ポリシーの形式と CLI の変更になる。

## ポリシーと秘密

- プロファイルを単一のファイルで完結させ、合成しない案。
  グローバルとプロセスの 2 段の方が利便性で勝る。
- `default.toml` を常に読む合成。
  プロファイル単体で隔離の全体像が読めなくなる。
- 段の合成に削除の演算子を設ける案。
  順序への依存が生まれ、上書きで足りる。
- 旧 0.3 でドメイン単位の通信許可を対象外にした判断。
  今回の改訂で filtered を追加するため、対象外の判断を更新する。
  現在の契約は[ネットワークモード](../reference/network/01-modes.md)を参照する。
- カレントディレクトリからポリシーファイルを自動で探す案。
  clone した時点で他人のポリシーが効く経路になる。
- 同じ環境変数名の秘密を 2 つの段で書いたらエラーにする案。
  ワークスペースごとに秘密を差し替える用途が塞がる。
  キー付きのテーブルで上の段が勝つ形に置き換えた。
- ポリシーファイルを `hide` で守る案。
  ワークツリーの中のファイルだと Git に空の変更として見え、空のファイルがコミットされうる。
- ポリシーファイルと設定ディレクトリを `ro` で守る案。
  祖先ディレクトリの改名による差し替えを防げず、参照されない秘密ファイルを平文で見せる。
  [ポリシーを保護する配置](../reference/06-policy-placement.md)による拒否と、`secrets/` の `hide` に置き換えた。
- `/tmp` を丸ごと `rw` で渡す案。
  ホストの X11 と ssh-agent のソケットが見え、名前がランダムなので `hide` できない。
  `/tmp` の `hide` と、共有用のサブディレクトリの `rw` に置き換えた。
- `.git/hooks` と `.git/config` を `ro` にする案。
  `core.hooksPath` で迂回でき、`config` を `ro` にすると `git push -u` が壊れる。
  既知の隙間として明記する（[公開文書に載せる事項](../maintainer/public-docs.md)）。

## 端末と入れ子

- bwrap の `--new-session`。
  制御端末を切ると、対話的なプログラムの挙動が変わりうる（未検証）。
  seccomp で `TIOCSTI` の経路だけは塞げる。
- `TIOCSTI` への対策を、sysctl の確認と警告だけにする案。
  カーネルの素の設定では `TIOCSTI` は有効のままで、塞いだことにならない。
- 現行の jail の順序の規則（`rw` を覆う `hide`、`rw`、他の `hide`、`ro` の順）。
  `ro` の祖先が、`hide` した秘密ファイルを再び見せてしまう。
- 入れ子で実際に二重の bwrap を作る案。
  外側が空にした秘密ファイルを内側が読んで、起動に失敗する。
  内側で狭める価値より、規則の増加の方が大きい。
- CI と配布物の作り方を仕様に含める案。
  別の製品で、検証の検証が発生した。

## 入力と診断

- `--help` と `--version` を、他の引数があっても優先させる案（GNU の慣習）。
  併用したときに他のオプションを検査するか、という次の問いが生まれる。
  排他にする方が単純である。
- `--policy-file` は利用者が明示したパスなので、読み方の防御をしない案。
  境界は破れないが、無言のハングは[診断と終了コード](../reference/10-process.md)の契約に反し、防御は数行で足りる。
- `--workspace` がファイルなら、その親ディレクトリを使う案。
  指定の誤りである可能性が高く、意図が読めない。
- `XDG_CONFIG_HOME` の空文字と相対パスを、字面どおりに使う案。
  XDG Base Directory の慣習に反し、相対の設定ディレクトリを使う意味が無い。
  結果として、作らないもの（[kakoi とは](../reference/01-overview.md)）に挙げたカレントディレクトリからのポリシーの探索と同じ経路にもなる。
- `${config_dir}` の実体化を、展開のときに任せる案。
  変数の間に非対称が残り、[ポリシーを保護する配置](../reference/06-policy-placement.md)の検査で実体化を忘れる余地ができる。
- 共通の読み込み量の上限（[実行時の境界](../maintainer/runtime.md)）を 64 KiB にする案。
  大きな `config` を持つリポジトリでの誤爆を避けたい。
  1 MiB でも桁で余裕がある。
- `HOME` が無い、または存在しない実行専用のアカウントでの起動を支える案。
  `~` の展開先、設定ディレクトリ、[マウントの解決](../reference/07-mounts.md)が行うホームとの比較の前提が覆る。
  0.3 では、[用語](../reference/02-terms.md)の定めのとおり、起動時に種類 `env` の診断で止める。
- 秘密ファイルを[ポリシーを保護する配置](../reference/06-policy-placement.md)の対象にせず、[実行時の境界](../maintainer/runtime.md)の根拠の文だけを直す案。
  `rw` の中の秘密ファイルをリンクに差し替える漏洩の経路が残る。
- 診断の順序を実装に委ねる案。
  テストが診断の種類を観測する以上、順序で結果が変わる。
  [kakoi とは](../reference/01-overview.md)が定める決定性を、診断にも及ぼす。
- 秘密の値に上限を置かず、exec の失敗（E2BIG）を[診断と終了コード](../reference/10-process.md)の表に足す案。
  種類 `secret` で「大きすぎる」と伝える方が、利用者に親切である。
- `~` を `HOME` の字面に展開し、実体化を比較とマウントの時点に任せる案。
  パスを取る値は、すべて実体で一貫させる。
  字面を `PATH` に見せたい場面が無い。

## パスの差し替えへの対策

- `ro` の項目にも根の項目の検査を課す案（0.1 の当初の形）。
  dotfiles へのリンクを `ro` に書く配置が、1 回目の起動から拒否される。
  また `ro` は、差し替えられても消されても、露出する組の形以外で新しく見えるものが無い。
  `ro` については、露出する組の検査（生成された `hide` と固定部分のマウント先を含む）に置き換えた。
- `hide` の項目も根の項目の検査から外す案。
  `rw` の中のリンクで書いた `hide` は、リンクを消されると隠し先が見えるようになり、着地点しか見ない露出する組の検査では止まらない（2026-09-06 に実測）。
- 書き込める項目の中のリンクを辿る `hide` を、着地が根の項目の中なら通す案（0.1 の当初の形）。
  同じ仕組み（リンクを消す、項目が飛ばされる、隠し先が見えるようになる）で外れる。
  深さ 1 のマウント点なら、実体のパスで書いた `hide` は改名できず外れないのに、リンクの形は外れる（2026-09-06 に実測）。
  着地先を問わず止める。
- 走査の `root` と `hide-mounts` の `under` を、書き込める項目の中を参照しても、着地が根の項目の中なら通す案。
  起点はマウントされないので、`rw` の下位を起点にすると、改名や向け直しで走査が空振りし、`.env` の隠しが丸ごと外れる（2026-09-06 に実測）。
  `rw` のマウント点そのものに限る。
- 走査で、起点の外へのリンクを一切辿らない案。
  起点の外にある本物の秘密へのリンク（`.env -> ~/shared/.env`）が隠れなくなる。
  `ro` の項目の中を指すリンクだけを別に扱う形に置き換えた。
- 走査で、`ro` の項目の中を指すリンクを、差し替えられるかどうかを問わず隠さない案。
  差し替えられる `ro` を走査の隠し先へ向け直すと、本物の秘密の隠しが外れる（2026-09-06 に実測）。
  差し替えられうる `ro` の中は `path` で止める形に置き換えた。
- `ro` と `hide` の項目を実体のパスで書き直す運用（利用者の側でプロファイルを生成する）で凌ぐ案。
  リンクを足すたびにプロファイルを直す運用になり、診断が 1 回の起動で 1 行なので、項目を 1 つずつ潰す体験が残る。

## 起動と初期設定

- 入れ子で見つかったコマンドの exec の失敗を、`command not found` の 127 のまま返す案。
  シェルの慣習（見つからなければ 127、実行できなければ 126）と食い違い、原因が分かりにくい。
- 記述子の soft 上限を、必要なときだけ上げる案。
  同じ入力で包んだコマンドの上限が変わり、[kakoi とは](../reference/01-overview.md)が定める決定性に反する。
  常に上げる。
- 包んだコマンドの argv[0] を、解決した絶対パスにする案（0.1 の当初の実装）。
  argv[0] で振る舞いを変えるコマンドが打ったとおりに動かず、シェルの慣習とも違う。
  `--argv0` で与えた文字列を渡す。
- 組み込みの既定を持たず、README の手順でプロファイルを置かせる案（0.1 の当初の形）。
  入れた直後の起動が `policy` で止まり、「入れてすぐ使える」にならない。
- `kakoi edit NAME`（`$EDITOR` で開く）。
  利便性が `$EDITOR <パス>` と同じで、`bwrap` 以外の外部コマンドを起動する面が増える。
  `init` がパスを出力すれば足りる。
- 組み込みの既定で起動するたびに通知を出す案。
  警告は問題の合図として残したい。
  毎回出る 1 行は、`init` を促す効果より邪魔の方が勝る。
  `--print-plan` で見えれば足りる。

## シムとセットアップ

- シムの雛形に、隔離を外す環境変数を置かない案。
  ホストは信頼する側であり、既知の隙間の 8 件目で既に外せるので、安全は増えず、実体のパスを探す手間だけが残る。
- 同梱のプロファイルの `secrets` を、有効な項目のまま置く案。
  入れた直後の起動で毎回、置いていない秘密ファイルの警告が出る。
- LLM ごとに内容の違う組み込みの既定を持つ案（`init codex` で codex 専用の内容を書き出す形）。
  外側の隔離の中で別の CLI が入れ子で動くので、外側のプロファイルは、中で動きうる CLI 全部を知っている必要がある。
  1 つを育てる（`init NAME` は同じ内容を別名で書き出すだけにする）。
- シムが入れ子を自分で検出して、kakoi を通さない案。
  [入れ子、並列、出力](../reference/10-process.md)の「ホストで `KAKOI=1` を立てれば必ず警告が出る」が、シムの利用者には成り立たなくなる。
  入れ子でも kakoi を呼ぶ（許可リストによる素通しは利用者が承認した例外なので、この理由は及ばない）。
- シムがサブコマンドごとにモデルが動くかを調べ、「隔離に入れる」と「素通し」に振り分ける案（0.1 の当初の形）。
  包む対象の版が上がるたびに調べ直しが要り、見落としが隔離の外に漏れる（`codex review` で 2026-09-08 に実測）。
  既定をすべて隔離にし、素通しは利用者が承認した例外だけにした。
- シムが子プロセスとして起動して失敗を見届け、足す一覧のヒントを出す案。
  対話セッションの端末の扱いと、終了コードの引き継ぎが増えて、シムが厚くなる。
  ヒントは文章だけにする。
- 許可リストを環境変数に置く案。
  承認した記録が、シムを読んでも分からない。
- 許可リストを設定ディレクトリの別のファイルに置く案。
  シムが読むファイルが増え、それが[ポリシーを保護する配置](../reference/06-policy-placement.md)の保護対象に入るかという問いが新しく生まれる。
- `--help` と `--version` を、シムの素通しの特別扱いのまま残す案。
  例外の判断が 1 つ増える。
  失うのは、診断が出る状態では `--help` も 125 で止まることだが、診断は直すべきものなので受け入れる。
- セットアップスキルが、利用者の申告した正本のパス（プロファイルやシムの正本が他所にある場合）を、3 つ目の書き先として差分の承認の下で書く案。
  隔離の外で動くエージェントが書く場所を、利用者の設定のリポジトリまで広げない。
  行の提案で足りる。
  プロファイルがリンクのときにリンク先を書く案も同じである。
- プロファイルが他所の生成物であることを、ファイルの先頭の印で判定する案。
  生成する側に印を書かせる契約が増える。
  利用者の申告で足りる。
- シムの雛形に、位置引数の写し（先頭の非オプションの語を `--workspace` にする）を足す案。
  先頭の語がサブコマンドかディレクトリかを、雛形は区別できない。
  `tool exec` は `--workspace exec` になって `path` の診断で止まり、`tool /etc` は `/etc` が書ける側に広がる（雛形のヘッダーが言う、緩む向きの誤読と同じ）。

## rw-copy

- 「隔離の中で書けるが外に出ない」を、`ro` と `hide` の組み合わせで表す案。
  `ro` は書けず、`hide` はホストの内容で始まらない。
  どちらも要求を表せない。
  [マウントの解決](../reference/07-mounts.md)の `rw-copy` を足した。
- `rw-copy` の通常ファイルを、bwrap の `--file FD DEST` で作る案。
  `--file` は newroot の中のパスに実体を書くので、DEST の親が `rw` の bind mount だと、ホスト側のファイルに書き抜ける（2026-09-10 に bwrap 0.9.0 で実測）。
  守っているつもりで素通しになる。
  `--bind-data FD DEST` に置き換えた。
  これは内容を bwrap 自身の tmpfs 上のファイルに書いてから DEST に bind するので、親が何であっても書き抜けない。
  ディレクトリの複製の中では、直前に重ねた自前の tmpfs が親になるので、`--file` を使ってよい（そちらは各エントリがマウント点にならず、改名も削除もできる利点がある）。
- `rw-copy` のディレクトリをオーバーレイで作る案。
  [kakoi とは](../reference/01-overview.md)が下限とする bwrap 0.9.0 に、オーバーレイの引数が無い（`--overlay-src` は Unknown option。2026-09-10 に実測）。
  起動時に tmpfs へ流し込む形にした。
- `rw-copy` の複製で、複製元のシンボリックリンクを辿って内容を写す案。
  複製が木の外へ広がり、循環と展開の爆発がありうる。
  リンクの先を隔離の中で解決させる形（リンクのまま複製する）に置き換えた。
  木の外を指すリンクの先が書けるかどうかは、そこにポリシーが与えたもので決まり、隔離の中のどこからでも同じにできることなので、新しい経路にはならない。
- `rw-copy` を、[ポリシーを保護する配置](../reference/06-policy-placement.md)の書き込める項目に数える案。
  中への書き込みはホストに届かないので、次の起動が読むものも、解決の結果も変えられない。
  数えると、`rw-copy` の中にポリシーファイルや設定ディレクトリを置いた正直な配置が、理由なく拒否される。
  露出する組の相手側に入れることで、必要な守り（書き込みをホストへ通す `rw` の重なり）は残した。
- `rw-copy` に、ディレクトリ用とファイル用の 2 つの指令を作る案（`rw` と `rw-file` の対に倣う形）。
  この 2 つが分かれているのは bwrap の bind の対象の違いによるもので、`rw-copy` は複製を作るので、`ro` と同じく両方を 1 つで受けられる。
  指令を増やさない。
- `rw-copy` の複製に上限を置かない案。
  複製の内容は記述子と隔離の tmpfs に二重にメモリへ載るので、`~/.cache` のような複製元を指した指定が機械を止めうる。
  項目あたりの上限（[マウントの解決](../reference/07-mounts.md)）で先に止める。
- `rw-copy` の複製元が読めないときに、そのエントリを飛ばして起動を続ける案。
  ホストの内容で始まるという約束を、黙って下回る。
  種類 `path` で止める形にした。
  ソケットや FIFO のように複製に意味の無い種類だけは、計画に出して続ける。
- `rw-copy` の複製を、終了時にホストへ書き戻す案。
  この指令の目的は、書き戻さないことである。
  書き戻しが要るなら `rw` を使う。
