# 公開APIの内部設計案

この文書は[合意記録](./2026-10-03-public-library-api.md)に基づく設計担当の提案であり、まだ実装指示として確定していない。
利用者向けの要求は[入力](../../ir/library/library-input.md)、[寿命](../../ir/library/library-lifecycle.md)、[観測](../../ir/library/library-observation.md)、[組み込み](../../ir/library/library-integration.md)の仕様草案を参照する。

## クレートの依存方向

依存先を右側に記す。
逆向きの依存と循環を作らない。

```text
kakoi-policy  -> プロジェクト内の依存なし
kakoi-plan    -> policy
kakoi-linux   -> plan, policy
kakoi-net     -> linux, plan, policy
kakoi-runtime -> net, linux, plan, policy
kakoi         -> runtime（CLI用の接続を含む）
```

policyは型、解析、検証、合成とガード規則の照合を所有する。
planは渡された事実から隔離の構成を計算する。
両クレートは実行中のOS状態を自ら読まず、ファイルへの書込み、プロセス起動、シグナル操作を行わない。

linuxは観測とLinux操作を所有する。
ファイル読込み、パス観測、memfd、Landlock、bwrap起動支援を扱い、設定の合成規則やマウントの優先順位は決めない。
runtimeは計画手順を所有し、linuxの観測結果をplanへ渡す。
netは通信の判断と実行を所有し、DNSの純粋な判断を内部モジュールとしてOS操作から分ける。

既存coreからの移動はファイル単位ではなく責務単位で行う。
layersの合成とファイル読込み、shared_filesの型と書込み、plan内の判断とbwrap引数生成をそれぞれ分離する。
runtimeの公開入口から内部Planや変更可能なCommandを受け取って起動する抜け道を作らない。
内部クレート間で必要な型は、利用者向けのruntimeから一括再公開しない。

## 利用者が持つ値

署名とエラーの表現は[公開APIの設計契約](./2026-10-03-public-library-api-contract.md)に記す。
この文書では内部の所有権と処理の配置を定める。

| 値 | 責務と所有権 |
|---|---|
| Policy | 共通検証を通ったポリシー。Rust型の構築とTOML読込みが同じ検証へ到達する |
| HostContext | 呼び出し側が明示した環境と作業ディレクトリ。プロセスから収集する便利関数も明示的に呼ぶ |
| RunRequest | Policy、コマンドと引数、HostContext、標準入出力の指定を所有する |
| PreparedRun | 検証済み計画と準備した資源の所有者。Cloneを提供せず、spawnが消費する |
| PlanDescription | 表示と検査に使う読み取り用の説明。実行用計画へ逆変換する入口を提供しない |
| Running | 起動した隔離の唯一の公開所有者。Cloneを提供せず、Dropが停止を開始する |
| StopHandle | 別スレッドから停止を要求するための非所有ハンドル。保持してもRunningの寿命を延ばさない |
| Events | イベント受信の非所有ハンドル。保持しても隔離の寿命を延ばさない |
| RunOutcome | 主コマンドの結果、終了理由、後処理の確認状況を分けた最終結果 |

要求の構築中は値を編集できる。
PreparedRunの生成後は内部を編集できず、説明のコピーを編集しても実行条件は変わらない。
コマンド、パス、環境のOS文字列はUTF-8へ強制変換しない。
既存CLIの秘密値の表示抑制を、計画の説明とDebugでも維持する。

## 計画と起動の手順

多数のマウント元を保持するとファイル記述子数が増える。
呼び出し元のファイル数上限を変えずに保持するため、準備段階から再実行したワーカープロセスへ資源を置く。
この段階では対象コマンド、隔離のネットワーク、pastaを起動しない。

1. 利用側mainの先頭で補助処理を振り分ける。
2. prepareはワーカーを起動し、明示された要求を渡す。
3. ワーカーはポリシーを検証し、ホストの事実を集めて計画する。
4. ワーカーがマウント元の記述子と読み込んだデータを保持し、親へ計画の説明を返す。
5. 親はPreparedRunを保持し、説明を確認する。
6. spawnはPreparedRunを消費し、ワーカーへ起動を要求する。
7. ワーカーが成立条件を再確認し、隔離と補助処理を準備する。
8. 必要な通信制御と補助処理の成立を確認してから対象コマンドを起動する。
9. ワーカーは実行中の監督を続け、親はRunningで操作する。

計画のためにワーカーを使うことと、対象コマンドを起動することは区別する。
準備だけで破棄された場合も、保持した記述子とワーカーを回収する。
通信やコマンドの起動途中で失敗した場合は、部分的に確保した資源を回収し、原因と回収の確認状況を分けて返す。

## マウント元の同一性

bind系のマウント元は、観測時に開いたO_PATH記述子で対象を保持する。
起動直前に元の指定の解決結果を保持対象と照合し、不一致なら再計画エラーとする。
起動に使う参照はbind-fdまたはro-bind-fdとし、単なるパスへの戻し変換を行わない。
bwrap側のマウント後の同一性確認で競合を検出した場合も対象コマンドを起動しない。

通常のディレクトリの子孫とファイル内容はライブのままである。
rw-copyは既存のコピー規則に従って取得した内容を使う。
hideと専用のtmpfsはホストの通常ファイルを公開する参照とは分ける。
外側から引き継ぐガード領域も記述子で保持するが、新しいガードとの同時配置を認めない既存の制約は維持する。
bind-fdとro-bind-fdにdev-bind相当の機能がない場合、明示的なデバイス公開は既存のdev-bindで配置し、隔離内initが公開後のdevice、inode、型、rdevを保持した観測値と照合する。
不一致なら対象コマンドを起動せず失敗する。照合前にそのデバイスを対象コマンドへ使わせない。
照合対象は要求で明示したマウント元のルートと生成した補助ファイルで、通常のマウント配下の全子孫を列挙して固定するものではない。
マウントが後続のhideや別マウントで覆われる場合は、最終的に見える配置について照合する。意図して覆った対象の見えなさを異常としない。
起動時のinitへ渡す照合表は読み取り専用とし、利用側のコマンドが実行される前に検査を完了する。

## 回収担当と公開ハンドルの分離

呼び出し元には実行ごとの回収担当を置き、ワーカーのChildと結果受信を所有させる。
Runningと待機FutureはChildを直接所有しない。
回収担当はRunningの破棄後も継続し、ワーカーをwaitしてゾンビとして残さない。
呼び出し元のシグナル設定は[A28](./2026-10-03-public-library-api.md#A28)を反映した[REQ-library-201](../../ir/library/library-lifecycle.md#REQ-library-201)に従う。
アプリケーションが利用可能なハンドラと呼び出し元のマスクを変更せず、スレッドランタイム・libc自身による内部予約シグナルの初期化だけを例外とする。
内部予約の範囲は使用するランタイム・libcに従い、kakoiによる予約シグナルの操作や初期化の隠蔽・復元は行わない。
他の子プロセスに対するwaitは変更しない。

隔離の所有権を表す生存確認用接続は、RunningまたはPreparedRunだけが親側の端を所有する。
StopHandle、Events、結果を保持する共有状態、回収担当にはその端を複製しない。
所有者が破棄された場合と呼び出し元が強制終了された場合は、ワーカーが接続の切断を検知して停止を開始する。
ワーカーが強制終了された場合は既存の親死亡追従と通信の監視を利用し、親の回収担当は確認できなかった後処理を成功扱いしない。

## 同期と非同期の待機

回収担当が結果を一度確定し、同期の待機とFutureへ通知する。
Futureは実行の所有者を借用し、キャンセル時に待機登録を解除する。
停止要求はStopHandleから送れるため、別スレッドで同期wait中でも停止できる。
非同期イベント待機は、[A27](./2026-10-03-public-library-api.md#A27)に従い、Pendingからのキャンセルだけで未取得のイベントを取り除かない。
保持上限による欠落は、キャンセルとは別に通知する。

標準ライブラリのMutex、Condvar、Future、Wakerを組み合わせる。
状態確認と待機登録を同じロックの下で行い、登録と通知の間の取りこぼしを防ぐ。
待機Futureのために新しい監督スレッドを起動しない。

## イベントと最終結果

イベントには実行ごとに増加する番号を付け、保持量に上限を設ける。
受信が追いつかない場合は古い履歴を捨て、欠落を受信側へ示す。
現在状態と最終結果はイベント履歴と別に保持し、履歴の欠落で最終結果が失われないようにする。

ワーカーから回収担当への通知も監督を停止させない。
非ブロッキングの送信と有限の保留領域を使い、更新が多い診断はまとめる。
所有者の生存確認をイベントの受信確認で代用しない。
最終結果の受信前にワーカーが死亡した場合は、観測できた事実と未確認の項目を区別する。

RunOutcomeの通信遮断は、確認済み、未確認、モード上の対象外を区別する。
主コマンドの終了コードだけを根拠に、通信遮断や全子孫の回収を確認済みにはしない。
CLI用の終了コード変換は既存の優先順位を維持する。

## CLIとの共用範囲

CLIのhostとnoneは従来のexec形態を維持する。
ポリシー検証、計画の判断、bwrap構築、ガード規則の評価をライブラリと共用する。
既存CLIと新しい組み込みAPIでは、マウント元の渡し方と呼び出し元プロセスの寿命に異なる契約があるため、最終的な起動方法を分ける。
filteredの監督の判断は既存の実装から共用し、CLI表示への変換を外側へ出す。

ガードの役割が決まった後の処理を共用する。
CLIの既存の名前に基づく判別を、任意名の組み込みバイナリの判別に流用しない。
[A24](./2026-10-03-public-library-api.md#A24)に従い、初期版は役割付きイメージをro-bind-dataで配置先ごとにコピーする。
ガード共有のための二段bwrapと準備用namespaceは追加しない。
計画のためのワーカーは引き続き呼び出し元と同じホストのファイルを観測し、保持した対象を起動用bwrapへ渡す。
輸送用のmemfdは内容の保持に用い、匿名の実行ファイルとして直接マウントしない。
各コピー用の入力は独立した読取り位置を持たせる。同じopen-file descriptionのdupだけでは読取り位置も共有するため、代用しない。

ro-bind-dataで配置したガードはそれぞれ異なるinodeになる。
listedの実行許可には実際に配置した全ガードを含め、通常アプリやfirst-processのinodeの許可で代用しない。
役割識別は/proc/self/exe自体から読み、リンク文字列を開き直さない。
局所実証ではリンク文字列に「 (deleted)」が付いたため、既存のガード表の配置先照合をそのまま移さない。
役割をGuardと判定した後、自己パスの完全一致を先に調べ、見つからなければ末尾の「 (deleted)」を一つだけ除いたパスを候補にする。
候補はガード表の配置先に限り、そのパスを開いて実行中の/proc/self/exeとdevice、inodeが一致する場合だけ採用する。
完全一致の候補で同一性が違う場合も、接尾辞を除いた候補を確認する。
表の欠落、候補なし、同一性の不一致、役割情報の不正は終了126とし、通常アプリに戻さない。
これにより実際のファイル名が「 (deleted)」で終わる場合も、名前だけで別のガード規則を選ばない。

runtimeの利用者向け型には、ガードイメージのinode、共有ハンドル、配置戦略の選択肢を公開しない。
ガード規則と起動要求から内部で配置を決めることで、将来共有方式へ変更しても利用側の呼出し手順を変えない。
将来の共有方式のためだけのtraitや設定スイッチは初期版に設けない。

## 役割の振り分けと起動の確認

guardは実行イメージの役割情報で判定する。KAKOIやargvの名前からGuardへ推測で振り分けない。
隔離内initも利用側イメージの役割付きコピーを一つ配置し、役割情報と専用の制御FDで識別する。制御FDがないinit用コピーは通常アプリへ戻らない。
listedで自動的に実行を許す対象は配置した補助用コピーであり、元の利用側アプリ全体をその理由だけで許可しない。
外側のワーカーは、ライブラリが付けた内部起動指定と専用の制御FDで識別する。
内部起動指定があるのに制御FDがない、通信の版が違う、要求が不正という場合はエラーで終了し、通常アプリへ戻さない。
ワーカーの内部起動指定と補助役の制御FD番号は予約した環境変数で渡し、アプリ向け環境へは除去する。CLIの公開オプションは増やさない。
ワーカーは起動直後にFD以外から通常のアプリ入力を読まず、親との接続を確認してから要求を受け取る。

隔離内initはマウント後の照合を行い、全ガードと必要な補助処理の実行許可対象を開いてlistedの実行制限を適用する。
その制限を継承した子でガードの起動確認を行い、すべて成功してから対象コマンドを解放する。
起動確認で利用側のmain前の初期化が子孫を作った場合も、initがそれらを終了・回収してから対象コマンドを解放する。回収できない場合は起動を失敗させる。
ガード起動確認は同じ配置ファイルと実行環境で行い、専用の確認要求へ応答して終了する。
通常のガード起動で確認要求のFDが存在しない場合はガード規則の処理を行い、確認専用の指定だけがありFDがない場合は拒否する。
この経路も通常アプリを呼ばない。
必要なガードのいずれかがmainへ到達できなければ、対象コマンドの前に起動エラーとする。

## 停止と失敗時の回収

停止理由と現在の段階を入力に、資源所有者が逆順で終了処理を行う。
filteredは通信遮断の処理を開始してからアプリ側へ終了を要求し、既存の猶予と強制終了の規則を使う。
hostとnoneにも隔離内initを置き、対象コマンドの終了と残る子孫の回収を監督する。
呼び出し元の端末のシグナル設定とプロセスグループを変更せず、監督自身が先に消えるシグナルは監督側だけで扱う。
シグナル設定の保証にはREQ-library-201の適用範囲を用いる。
実行ごとのPID namespaceと制御接続を使い、別の実行のPIDやプロセスグループへ停止を送らない。

子孫の終了とbwrapの終了を確認し、filteredの補助処理を回収した後、ワーカーが結果を返して終了する。
親の回収担当がそのワーカーをwaitした時点で最終結果を確定する。
ワーカー死亡や待機の失敗で確認が足りない場合はUnconfirmedとする。
通信が切れた後に結果を作るため、終了結果の保持はワーカー内だけでなく親側にも置く。
親は回収できる自分の子を最後まで回収し、外側の監督を失った隔離は親死亡追従で終了させる。
SIGKILLされたプロセスが自身の子をwaitしたと見なすことはせず、孤児の回収まで自分が確認できなければConfirmedReapedとは報告しない。

## 実装へ渡す前の確認

この設計案の既存IRへの反映対象は、少なくともREQ-150のcoreとnetへの責務割当て、REQ-475の自分自身の実行ファイルの扱い、REQ-305からREQ-309のCLIと組み込みAPIへの適用範囲である。
承認前に指す実装場所と保証の適用範囲を改訂し、CLIの意味を変えない。

外部の利用側パッケージで、公開APIのみを使う通常実行、ガード、listed、filtered、並行実行、停止、所有者死亡、Futureのキャンセルを確認する。
別途、既存CLIの回帰検査で表示、終了コード、端末、入れ子の挙動を確認する。
局所実証の成功を製品全体の検証成功とは扱わない。
