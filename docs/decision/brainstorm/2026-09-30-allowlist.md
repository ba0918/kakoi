# 見せるものを選ぶ方式（許可リスト）

## Context

kakoi の隔離は、ポリシーに書いていない場所をホストのまま読み取り専用で見せ、見せたくないものを `hide` で一つずつ隠す。
この方式では、一覧に無い場所にあるソケットや認証情報が残る。新しいツールが知らない場所にソケットを作るたびに穴が開く。
network の filtered と env の clear は、既に「全部止めて、許すものを選ぶ」形になっている。
ファイルの見え方とコマンドにも同じ形を持たせるかを決める（利用者の提案、2026-09-29）。

事実（2026-09-29、この環境、kakoi 0.5.0、利用者の既定のプロファイル）: 隔離の中から `/run/docker.sock` に繋がり、読むだけの `/version` に応答があった（利用者は docker グループ）。herdr、codex、zed のソケットも見えていた。利用者はプロファイルの `hide` に `/run/docker.sock` を手で足した。
事実（2026-09-30、同上）: WSL2 の `/mnt/wslg/distro` は `/` と同じファイルシステムの別のマウントで、`hide` した `~/.ssh` が隔離の中からそこ経由で見えた。同梱プロファイルに `/mnt/wslg` の `hide` を足して塞いだ（[A1 (hide-wslg)](./2026-09-30-hide-wslg.md#A1)）。
事実（2026-09-30、この環境）: `/etc` の下で土台の外を指すリンクは `/etc/resolv.conf`（`/mnt/wsl/resolv.conf` へ）と `/etc/mtab`（`/proc` の下へ）の 2 つだった。
事実（2026-09-30、この環境）: 利用者の `~/.claude/hooks` の中身の多くは `~/develop/dotfiles/ai/shared/hooks` へのリンクで、フックは `run-if-present`（mise のシム）、`python3`（Safe Chain のシム）、`~/develop/claude-notify` を使って起動する。PATH のシムの置き場を見せないと、`python3` や `npm` は `/usr/bin` の本物に解決され、Safe Chain の検査を黙って素通りする。
事実: claude の実行ファイルは `~/.local/share/mise` の下にあり、ホームを丸ごと隠すと動かない。
事実（2026-09-30、この環境、WSL2 のカーネル 6.18）: Landlock がカーネルに組み込まれていて（`CONFIG_LSM` の先頭）、ABI の版は 7 だった。Landlock は特権なしで、パスごとに「実行してよいか」を絞れる。ほかのホストで使えるかは確かめていない。
実測（2026-09-30、別コンテキストの実験、この環境、Landlock ABI 7）: 実行を許すパスを絞ると、許していない `/usr/bin/id` は直接でも sh からでも EACCES になった。共有ライブラリには実行の許可が要らなかった。動的リンカ（ld.so）を許さないと動的リンクのプログラムは一つも起動せず、ld.so を許すと `ld.so /usr/bin/id` で許していないプログラムが動いた（0644 のコピーも動いた）。python3 を許した状態で、許していないファイルの `mmap(PROT_EXEC)`、memfd に写した実行ファイルの `fexecve` はどれも止まらなかった。`#!` のスクリプトはスクリプトとインタプリタの両方に実行の許可が要るが、`sh script` の形ならスクリプト側は要らない。ルールはパスではなく実体（inode）に付き、シンボリックリンクを経由しても実体に効く。WSL の `.exe` は `/init` と `/mnt/c` の根を許さないと起動しなかった。
実測（同上）: `/etc` の下にソケットは無く、利用者の権限で読めるファイルに秘密鍵は見つからなかった（`/etc/shadow`、ssh のホスト鍵、`/etc/ssl/private` は root だけが読める）。中身はトークンやパスワードまでは網羅的に探していない。
実測（同上、通信を切り設定ディレクトリを空にして起動）: claude は起動時に `/init` 経由で Windows の `reg.exe`、`git`、`sh`、`uname` を起動した（`rg` は claude 本体を別名で起動したもの）。codex は `sh`、`lsb_release`、`getconf`、`git`（`git-remote-https` を含む）、`bash -lc`（利用者の bashrc が呼ぶもの）、`bwrap` を起動した。利用者の設定のフックやステータス行が起動するものはこれに加わる。
実測（2026-09-30、別コンテキストの実験、この環境）: Landlock で実行ファイルの置き場の読み取り（READ_FILE）も許可リストにすると、`ld.so` 経由で許していないプログラムを起動することも、python からそれを読むことも EACCES になった（実行には READ_FILE と EXECUTE の両方が要る）。読める作業場所に置いたファイルは `ld.so` 経由で動いた。非特権の名前空間で書ける場所を noexec で再マウントすると、その下のファイルは直接実行、`ld.so` 経由、`mmap(PROT_EXEC)`、dlopen のどれも止まったが、匿名メモリに写したコードと memfd の `fexecve` は止まらなかった。bwrap 0.9.0 には noexec の指定が無い。
実測（同上）: Landlock ABI 6（カーネル 6.12 以降）の scope（`LANDLOCK_SCOPE_ABSTRACT_UNIX_SOCKET`）を立てると、領域の外で作られた抽象 UNIX ソケットへの接続が EPERM になった。このホストの `/proc/net/unix` の抽象ソケットは 6 個で、どれも待ち受けではなかった（接続できるものは 0 個）。デスクトップの Linux では D-Bus や X11 の抽象ソケットがあるはずだが確かめていない。
一次資料（同上が確認）: `AT_EXECVE_CHECK` と `SECBIT_EXEC_RESTRICT_FILE`（Linux 6.14）はインタプリタ自身が強制する仕組みで、python、bash、dash、node、glibc の ld.so は上流で対応していない（この環境でも効かなかった）。Landlock で `mmap(PROT_EXEC)` や memfd の実行を絞る案は上流で未マージである。
実測（2026-09-30、この環境）: 実行の許可だけを扱う Landlock の制限の下では、bwrap は "Failed to make / slave: Operation not permitted" で止まり、`unshare -Urm` もマウントの伝播を変えられなかった（Landlock はファイルシステムの権利を扱う制限の下でマウントを禁じる）。抽象 UNIX ソケットとシグナルの scope だけの制限の下では、bwrap は動いた。
事実: コマンドのガードレールは禁止の規則を並べる形で、境界ではない（同じことを別のコマンドや python で行えば止まらない）。

Position: 照合を 3 回で終えた（3 回目の指摘 0 件）。承認待ち。

## Agreements

- A1 今の「ポリシーに書いていない場所をホストのまま読み取り専用で見せる」形は残し、見せるものを選ぶ形は、それと並ぶ厳格なモードとして選べるようにする（env の inherit と clear の関係）。同梱プロファイルをどちらにするかは、形が決まってから別に決める。
  - why: 今の設定を壊さない。利用者は厳格なモードとして使う。
  - decided_by: 利用者（推奨を採用）
- A2 この仕様はファイルの見え方とコマンドの両方を扱う。コマンドは「実行してよいプログラムを選ぶ」形を境界として、「使い方を選ぶ」形をガードレールとして扱い、文書でもこの強さの違いを分けて書く。
  - why: 利用者はコマンドも選べるほうがよいと判断した。実行を許したプログラム自身（sh、python3、claude）は他のプログラムを呼ばずに何でもできるので、プログラムを選ぶ形でも守れるのは道具を減らすところまでで、ソケットと認証情報を守るのはマウントとネットワークの許可リストである。
  - rejected: コマンドを別の仕様に回す案。利用者が一緒に扱いたいと判断した。
  - decided_by: 利用者（推奨を採用）
  - superseded_by: [A13](#A13)
- A3 見せるものを選ぶモードでは、システムの土台（`/usr`、`/bin`、`/sbin`、`/lib`、`/lib64`、`/etc`）をまとめて読み取り専用で見せ、それ以外は利用者が書いたものだけを見せる。土台はまとめて外せる。
  - why: 土台が無いと何も起動せず、土台には普通はソケットも認証情報も無いので、1 つずつ書かせても守りは増えず手間だけが増える。ソケットが置かれる場所（`/run`、`/tmp`、ホーム、`/mnt`）は丸ごと消える。
  - rejected: 土台も含めて全部を 1 つずつ書かせる案。
  - decided_by: 利用者（推奨を採用）
- A4 どれかの段で見せるものを選ぶモードにしたら、上の段では今までの形に戻せない。
  - why: ジョブごとのポリシーが誤っていても隔離がゆるまない。下の段を上の段で消せない原則（[REQ-155](../../ir/core/core-policy.md#REQ-155)）と、壊れた厳しいプロファイルで黙って広い既定を使わない原則（[REQ-154](../../ir/core/core-policy.md#REQ-154)）にそろう。`env.mode` と `network.mode` は上の段が上書きする（[TBL-152](../../ir/core/core-policy.md#TBL-152)）ので、それとは違う規則になる。
  - decided_by: 利用者（推奨を採用）
- A5 見せるものを選ぶモードでも、今の指令（`rw`、`rw-file`、`rw-copy`、`ro`、`hide`、走査）の意味は変えない。`rw`、`rw-file`、`rw-copy`、`ro` に書いた場所と土台だけが見え、見えている場所の中では `hide` と走査が今までどおり隠す。書いていない場所は存在しない。見せた場所の親ディレクトリは、見せたものだけを含むディレクトリとして作る。
  - why: 書いていない場所はあるかどうかも分からなくなり、`ls ~` でほかのツールの設定や鍵が並ばない。利用者は今のプロファイルの `rw` と `ro` を持ってきて足りない分を足すだけで済み、新しい書き方を覚えなくてよい。
  - decided_by: 利用者（推奨を採用）
- A6 見せるものを選ぶモードの見本のプロファイルをもう 1 つ同梱し、`kakoi init` でどの見本を書き出すかを選べるようにする。見本は今の同梱プロファイルと同じ前提（WSL2、mise で入れた claude と codex）で動く最小の形にし、環境に合わせて直す場所をコメントで示す。
  - why: 利用者が、使いやすい形のプリセットがあれば参考にしやすいと提案した。ツールの置き場は人によって違うので、組み込みの既定として動かすより、ファイルとして書き出して直してもらう形が合う。
  - rejected: `--profile strict` だけで組み込みの見本が動く案。
  - decided_by: 利用者（推奨を採用）
- A7 見せるものを選ぶモードは `[mounts]` の `mode` で選び、書かなければ今までの形になる。土台は `[mounts]` の `system = false` で外し、どれかの段で外したら上の段で戻せない。
  - why: env の `mode` と同じく 1 つのキーで形を選べる。土台を外す設定の合成は A4 と同じ理由でそろえる。値の名前は利用者が `clear` を分かりにくいとしたので別に決める。
  - decided_by: 利用者（推奨を採用。値の名前は保留）
- A8 見せるものを選ぶモードでは、kakoi が空の書ける `/tmp` を隔離専用に用意し、ホストの `/tmp` は見せない。
  - why: `/tmp` が無いと動かないツールが多く、毎回書かせてもつまずくだけである。ホストの `/tmp` の X11 や ssh-agent のソケットには届かない。ホストと共有する場所は今までどおり `rw` に書く。
  - decided_by: 利用者（推奨を採用）

  - why: 名前解決はほぼすべてのツールが使い、壊れると原因が分かりにくい。この環境で土台の外を指すリンクは `resolv.conf` と `/etc/mtab`（隔離にもある `/proc` を指す）だけで、ほかは利用者が `ro` に書けば足りる。network の filtered は resolv.conf を差し替えるので、関係するのは host のときである。

  - rejected: `"clear"`（土台まで消えるように読める）、`"allowlist"`（kakoi では「許す」が network の `allow` の意味で使われている）、`"strict"`（何が厳しいのかが名前から分からず、別の厳しさを足すときに困る）。

- A13 この仕様はファイルの見え方とコマンドの両方を扱う。コマンドは「実行してよいプログラムを選ぶ」形（Landlock で許していないプログラムの起動を止める）と「使い方を選ぶ」形の両方を作り、どちらもガードレールとして扱う。止め漏れる形（絶対パスの動的リンカ、許したインタプリタからの読み込みやメモリ上の実行ファイル）は文書に書く。
  - why: 実測で、動的リンカを許すと許していないプログラムを動かせ、python3 からの `mmap(PROT_EXEC)` と memfd の実行も止まらなかった。境界にはならないが、見張り役を置いたコマンドしか止められない今のガードレールと違い、知らないコマンドを全部止められるのはこの形だけである。利用者は、厳密に止めたいなら python や node を許さないことになり、許すことは穴を開けることだと確認した。
  - decided_by: 利用者（推奨を採用）

  - why: 使いみちがワークスペースでビルドしない決まったコマンドだけの使い方に限られ、noexec が動的リンカ経由の実行を止めるかも実測していない。今回の形を使ってから、それでも穴が気になるかで決める。今回の形は後から足すのを妨げない。

- A17 実行してよいプログラムは `[commands]` の `allow` にパスで書く。ファイルでもディレクトリでもよく、ディレクトリはその下をすべて許す。動的リンカと kakoi 自身（見張り役、隔離の中の最初のプロセス）は kakoi が自動で許す。
  - why: Landlock はファイルの実体に効くので、名前で書くと PATH の探し方しだいで別の実体を指すおそれがある。シンボリックリンクを書いてもリンク先の実体に効く（実測）。動的リンカと kakoi 自身が無いと何も起動しないので、書かせても手間が増えるだけである。
  - decided_by: 利用者（推奨を採用）

  - why: ジョブごとのポリシーは足せるが、下の段で絞ったものは外せない。`"host"` のままコマンドだけ絞る使い方もできる。
