# 旧仕様にだけあった規則の要求化

## Context

旧仕様 `docs/spec` を削除したとき、旧仕様にだけあって IR に無い規則を FLAG-011〜026 に退避した（[決定記録](./2026-09-25-kakoi-spec-retirement.md#A2)）。
正本の IR が欠けたままでは、実装とテストが従っている振る舞いを契約として確かめられない。
特に FLAG-026 では、要求 REQ-355、REQ-356、REQ-359 が、削除した旧仕様の一覧を参照しており、IR だけでは要求の中身が決まらない。
件ごとに、IR の要求にするか、FLAG のまま残すかを決める。
あわせて、IR の記述の小さな誤り（混入した文、例の対象の誤り、使わない語、古い未決の注記）を直す。

Position: IR を書き終え、ガイドの該当節を書き直す段階。

## Agreements

- A1 旧仕様の第 15.1 節の検証項目、第 15.2 節の観測項目、第 16 節の既知の隙間を、IR の表として core-verification と core-public-docs に置き、REQ-355、REQ-356、REQ-359 はその表を参照する文に改める。表の各行の内容は、ガイドに移した一覧をそのまま使う。
  - why: 正本の IR が削除した旧仕様の一覧に依存していると、IR だけで要求の中身が決まらないため
  - rejected: 一覧の各項目を個別の要求にする案。要求とテストの印付けが数十件に広がり、一覧を一覧として読めなくなる
  - decided_by: the user (took the recommendation)
- A2 シムの雛形は写す対象と同じ名前の語をどこにあってもそのオプションとして読み、`--workspace` や `--rw` が広がりうることを、受け入れた性質として REQ-372 に書き、既知の隙間の 16 件目として公開文書の `docs/security.md` にも載せる。
  - why: 旧仕様は取りこぼしの向きしか書いておらず、緩む向きの唯一の誤読が雛形のヘッダーにしか無かった。境界を広げうる性質は既知の隙間として利用者に示すべきであるため
  - rejected: REQ-372 にだけ書く案。利用者が保証の範囲を調べる入口（既知の隙間）から見えない
  - decided_by: the user (took the recommendation)
- A3 IR の記述の小さな誤りを意味を変えずに直す。REQ-199 に混入した無関係な 3 文を消し、EX-515 の対象と見出しを合わせ、ネットワークの IR の「レイヤ」「継承」を用語集の語に改め、古い未決の注記から決まった点を除く。
  - why: 正本の IR に誤りや使わない語が残ると、ガイドと読み比べたときに食い違いとして読まれるため
  - decided_by: the user (took the recommendation)

- A4 FLAG-011〜018、021、023、024 が記録した旧仕様の規則を、今の振る舞いのまま IR の要求に書き写す。FLAG-016 には、plain と tls の上流を混ぜると拒否する規則も含める。テストの無い条件は、テストで確かめる要求として書き、テストは実装の工程で足す。
  - why: 実装とテストが従っている振る舞いを、正本の IR で確かめられるようにするため。裏取りの調査で、各規則がコードにあることを確かめた
  - decided_by: the user (took the recommendation)
- A5 REQ-020 の「署名付き」は TSIG と DNSSEC の署名（RRSIG）の両方を指し、REQ-398 の「メッセージ署名付き」は TSIG だけを指すと、要求の文に明記する。
  - why: 実装は応答の絞り込みを両方の署名で止め、TTL を揃えないのは TSIG のときだけにしている。RRSIG 付きでも TTL を揃えることはテストが確かめている
  - decided_by: the user (took the recommendation)
- A6 固定公開について、ホスト側は 127.0.0.1 か ::1 だけで待ち受けること、公開の一部だけが成功した状態では起動せず、確保済みの公開もその場で回収すること、終了時は既存の順序で公開を止めて回収すること、アプリの標準出力を書き換えないことを要求にする。
  - why: どれも実装にあり、前の 3 つはテストがある
  - rejected: 内側の全アドレスの待受も使えること、設定の一覧や外部コマンドの成功終了だけを確保の証拠にしないことも要求にする案。前者は実装もテストも見つからず、後者は kakoi がポートを直接確かめるコードを持たないので、今の実装では確かめられない
  - decided_by: the user (took the recommendation)
- A7 filtered でホスト自身のアドレスを起動時に一度だけ読み、それをホストの非ループバック IP として扱い、起動後にホストが得たアドレスは他の宛先と同じく dns の許可だけで開きうることを、振る舞いの要求にする。pasta の UDP の送信元ポートの制約（pasta は UDP の流れごとにホスト側のソケットへアプリ側の送信元ポートと同じ番号を使い、その番号がホストの別のソケットで使用中なら流れを作れず、同じ送信元からのデータグラムを捨て続ける。アプリからは応答の無いタイムアウトに見え、kakoi は通知しない）は `docs/security.md` に載せる文書の要求にする。
  - why: 前者は kakoi の振る舞いで、後者は pasta の振る舞いを利用者に知らせる事項であるため。どちらも公開文書には既に載っている
  - decided_by: the user (took the recommendation)
- A8 filtered の入力の誤りの診断を今の振る舞いのまま要求にする。ポリシーの読み込みと合成で見つかる誤りは種類 policy、filtered の起動の処理で見つかる誤り（ポリシーが原因の、host-interface を含む宛先の拒否と、ホスト DNS を使うときにホストの名前解決設定に nameserver が無い場合を含む）は種類 bwrap で、どちらも終了コード 125 とする。
  - why: 実装は検出する場所で種類を分けており、振る舞いを変えるのは今回の範囲の外であるため
  - rejected: ポリシーが原因の誤りをすべて policy にする案。製品の変更になり、実装の工程が要る
  - decided_by: the user (took the recommendation)

- A9 合成後に network.mode をどの段も書いていなければ host、env.mode をどの段も書いていなければ inherit とする。ネットワークの追加のキー（REQ-087 の条件に当たるもの）をどれかの段が書いたときは network.mode の既定値を使わず、どの段にも network.mode が無ければ種類 policy の診断で終わる。（FLAG-011）
  - why: A4 のとおり、旧仕様にあり実装が従っている振る舞いを書き写すため
  - decided_by: the user (took the recommendation)

  - why: A4 のとおり、旧仕様にあり実装が従っている振る舞いを書き写すため
  - decided_by: the user (took the recommendation)
- A11 host と none で bwrap 自身の exec に失敗したとき（所在確認の後に消された、実行できない）は、まだ kakoi が動いているので種類 bwrap の診断を出して 125 で終わる。包んだコマンドの exec の失敗は bwrap が報告し、bwrap の失敗の出力と終了コードをそのまま返す。入れ子では kakoi がコマンドを直接 exec するので、同じ失敗が command not executable の 126 になる。この非対称は受け入れる。（FLAG-013）
  - why: A4 のとおり、旧仕様にあり実装が従っている振る舞いを書き写すため

- A13 network.dns-upstream の候補 1 件には transport、ip、port を必須とする。transport は通常 DNS の plain か TLS の tls、ip は IP アドレスそのもの、port は 1〜65535 の整数とする。tls では証明書の照合に使う tls-name も必須とし、国際化名を ASCII に正規化し、ワイルドカードは指定できない。plain に tls-name を書いたポリシーは拒否する。候補一覧は記載順と重複を保ち、1 つのポリシーファイルの中でも段を合成した後でも plain と tls が混在すれば拒否する。（FLAG-016）
