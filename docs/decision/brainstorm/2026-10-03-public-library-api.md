# 外部利用向けの公開APIとクレート境界

## Context

別のRustプログラムから隔離の仕組みを利用できるよう、公開APIと責務の配置を検討する。
現在はkakoi-coreとkakoi-netがあるが、起動に必要な補助処理の一部はCLIパッケージにもある。
外部利用者が引き受ける処理と、ライブラリが所有する処理を決めてからクレート境界を確定する。
既存の責務については[以前の決定](./2026-09-25-library-boundary.md)があり、変更する場合は改訂として扱う。

Position: Q22からQ24の合意を反映し、既存IRとガイドを整合させた。差分から抽出した105項目の合意照合を終え、設計全体の承認を待つ。

## Agreements

- A1 外部利用者が使いやすい公開APIの設計と、既存クレートの責務ごとの細分化を検討する。
  - why: 別のRustプログラムで隔離の仕組みを再利用するため
  - decided_by: the user

- A2 初期段階は外部パッケージからpath依存で実験利用できるAPIと実例を整える。最終的にはcrates.ioへ公開するが、公開作業は次段階とする。
  - why: 実際の利用を通じてAPIを確かめてから配布するため
  - decided_by: the user (took the recommendation)
- A3 host、none、filtered、listed、コマンドガードを含む既存機能を設計対象とする。実装は段階化できるが、CLIと外部利用者は同じ実行処理を利用できる構成を目指す。
  - why: 外部利用で既存機能を欠落させず、実行処理の重複を避けるため
  - decided_by: the user (took the recommendation)
- A4 CLIの挙動と設定形式を維持し、現在の未安定なRust APIへの破壊的変更を認める。
  - why: 現状の配布対象はバイナリのみであり、Rust APIの後方互換性を維持する必要がないため
  - decided_by: the user
- A5 組み込み用の主入口はメモリ上の明示的なポリシーを受け取り、ホームの既存設定を暗黙に読み込まない。設定ファイルの探索・読み込み・合成は明示的に選ぶ別入口とし、CLIも同じ検証・計画処理を利用する。
  - why: 組み込み側が指定した条件が既存profileによって意図せず変わることを避けるため
  - decided_by: the user (took the recommendation)
- A6 起動後は制御用ハンドルを返し、呼び出し元の待機・イベント受信に依存せず監督を継続する。停止要求の受付と終了・回収完了を区別し、呼び出し元プロセス全体のシグナル設定を暗黙に変更しない。
  - why: 組み込み先が別の処理を並行して実行でき、通知の扱いが隔離の制御を妨げないようにするため
  - decided_by: the user (took the recommendation)

  [A28](./2026-10-03-public-library-api.md#A28)でシグナル設定を変更しない保証の適用範囲を明確化した。
- A7 補助処理の基本方式は利用側バイナリの再実行とする。利用側はmainの先頭で、非同期ランタイム等のアプリ初期化より前に公式の振り分け関数を呼ぶ。別helperの配置・パス指定を基本利用の必須手順としない。
  - why: 補助処理とライブラリを同じビルドに含め、単一バイナリで配布できる利便性を優先するため
  - decided_by: the user (took the recommendation)
- A8 実行ハンドルのDropで停止処理を開始し、回収完了の確認には明示的なwaitを要求する。呼び出し元が異常終了した場合も監督側が検知して隔離を終了する。所有者を失っても実行を継続する切り離しは提供しない。
  - why: 管理されなくなった実行を残さず、停止の要求と回収確認を区別するため
  - decided_by: the user (took the recommendation)
- A9 同一プロセスから複数の隔離を並行起動できることを初期APIの要件とする。一方の停止は他方を終了させない。起動ごとに環境と作業ディレクトリを渡し、呼び出し元のグローバルな状態を書き換えない。同一ホスト側公開ポート等の実際の資源競合は起動エラーとする。
  - why: 組み込み先が独立した複数の処理を並行実行できるようにするため
  - decided_by: the user (took the recommendation)
- A10 実行用計画は生成完了時点で内容が固定された不変な型とし、利用者は内部を書き換えられない。読み取り用の説明を提供し、条件変更時は要求から再計画する。起動時に計画を消費し、同じ計画の反復起動は提供しない。ホストのファイルを固定する保証とは区別し、起動直前に必要な確認を行う。
  - why: 検証後にポリシーと実行引数が別々に変更されることを防ぐため
  - decided_by: the user (Immutableという解釈を確認して採用)
- A11 終了結果は主コマンドの結果、終了理由、通信遮断とプロセス回収の確認状況を区別する。コマンド成功と回収未確認を単なる成功に集約しない。CLIは結果を従来の終了コードに変換する。通信遮断の保証はfilteredに適用し、hostに同じ保証を与えない。
  - why: 利用側が主コマンドの結果と隔離の終了処理の結果を別々に判断できるようにするため
  - decided_by: the user (took the recommendation)
- A12 イベントは構造化し、全履歴の無制限な保持を保証せず、履歴の取りこぼしを検知できる方式とする。現在状態と最終結果は別途取得でき、受信の遅延は監督・停止処理を止めない。
  - why: 利用側の通知処理が隔離の制御やメモリ使用量を左右しないようにするため
  - decided_by: the user (took the recommendation)
- A13 ポリシーはRustの型とメモリ上のTOMLの両方から構築でき、共通の検証を通す。新しいRust構築APIではマウント・ネットワーク・環境の各モードを明示させる。既存TOMLの省略時の意味は維持する。
  - why: 呼び出し側にTOML文字列や一時ファイルを生成させず、入力経路による検証の違いを防ぐため
  - decided_by: the user (took the recommendation)
- A14 標準入出力は継承、パイプ、破棄、呼び出し側が用意したファイル・記述子に対応し、Rust標準のStdioに近い指定方法とする。組み込みAPIは指定を明示させ、CLIは従来の端末継承を維持する。パイプの読み書きは利用側が担当し、状態イベントと別経路にする。未読の出力による主コマンドのパイプ待ちと、監督処理の停止は区別する。
  - why: 対話利用とプログラムからの入出力制御の両方を支え、出力量が監督を妨げないようにするため
  - decided_by: the user (took the recommendation)
- A15 正式な利用者向け入口はruntimeとpolicyに絞る。基本利用はruntimeの依存追加で済み、必要なポリシー型はruntimeから再公開する。policyのみの直接利用も提供する。内部クレートの細かな操作は正式な利用方法とせず、crates.io公開時は依存解決に必要な内部クレートも配布する。
  - why: 内部の責務分割を利用者の依存先選択や起動手順の負担にしないため
  - decided_by: the user (took the recommendation)
- A16 初期APIは特定の非同期ランタイムへ依存させず、同期のprepare、spawn、waitと、完了を待たない停止要求、結果照会、イベント照会を基本とする。専用のawait APIは初期範囲に含めない。
  - why: 現在の同期処理を利用し、利用側の非同期ランタイムを限定しないため
  - decided_by: the user (took the recommendation)
  - superseded_by: [A17](./2026-10-03-public-library-api.md#A17)
- A17 終了待機とイベント待機は同期版と非同期版を初期段階から提供し、非同期版は特定ランタイムへの依存を必須にしないFutureを返す。待機Futureのキャンセルは待機のみをやめ、実行ハンドルが残っていれば隔離を継続する。実行ハンドルの破棄はA8どおり停止を開始する。計画と起動は同期APIとし、パイプの非同期I/Oは別途判断する。
  - why: 非同期アプリでタイムアウトや他イベントとの同時待機を扱いやすくし、待機のキャンセルと実行の終了を混同させないため
  - decided_by: the user (took the revised recommendation)
- A18 組み込みAPIは既存の隔離内でも要求された新しい隔離を作り、作れなければコマンドを起動せずエラーにする。暗黙に隔離を省略せず、外側の制限も引き続き適用される。CLIの既定の入れ子exec動作は維持する。
  - why: 組み込みAPIへ渡したポリシーが実行場所によって暗黙に適用されなくなることを防ぐため
  - decided_by: the user (took the recommendation)
- A19 起動直前の検査で計画の成立条件を満たさないと判明した場合は起動エラーにし、利用側へ再計画を求める。マウント元のリンク先が変わっていた場合に別の対象を黙って公開せず、自動的に許可範囲を変えない。通常のマウント先の内容を固定する保証は設けない。保持する対象と再確認する対象は設計で具体化する。
  - why: 利用者が確認した計画と実行される条件の不一致を、暗黙の再計画で隠さないため
  - decided_by: the user (took the recommendation)
- A20 パイプの非同期I/Oは所有権付きのパイプまたは記述子を利用側へ渡し、利用側が非同期ランタイムの型へ変換する。公式の接続例を用意し、所有権の移動と非ブロッキング設定を確認する。初期APIに独自の非同期ストリーム抽象を設けない。
  - why: 利用側が選んだ非同期I/O実装へ接続でき、ランタイムごとのストリーム実装をkakoiに持ち込まずに済むため
  - decided_by: the user (took the recommendation)

- A21 自己再実行に必要な動的リンカと共有ライブラリを、ポリシー外から自動公開しない。補助処理を動かせない場合は対象コマンドを起動する前にエラーにする。利用側は必要なファイルを明示的に公開するか静的リンクを選び、静的リンク自体は必須にしない。依存ファイルが既に見える構成では追加設定を要求しない。
  - why: 自己再実行の利便性を理由に、利用者が指定したファイル公開の条件を暗黙に変えないため
  - decided_by: the user (took the recommendation)
- A22 新しい組み込みAPIはbwrapのbind-fdとro-bind-fdを必須とする。版名だけに頼らず機能を確認し、不足時は起動エラーにする。既存CLIの従来の対応条件は維持する。
  - why: 計画時に確認した対象を記述子で保持し、起動時にもその対象との同一性を確認して使うため
  - decided_by: the user (took the recommendation)
- A23 組み込みAPIは読み取り可能な自己実行ファイルを要求する。ガード使用時は、役割識別情報を付けた利用側バイナリのコピーを変更不能な実行可能memfdに保持し、同じ実行内のガードで共有する。禁止環境ではエラーにし、ディスク退避やOS設定変更を自動実行しない。コピーコストはバイナリサイズに依存する。main前の初期化処理も再実行されることを利用条件に明記する。既存CLIの従来経路は維持する。
  - why: 設定表を失ったガードが通常アプリへ戻ることを防ぎつつ、任意名の利用側バイナリを扱うため
  - decided_by: the user (took the recommendation。方式の成立検証を要する)
  - superseded_by: [A24](./2026-10-03-public-library-api.md#A24)
- A24 初期版の組み込みAPIのガードは、役割識別情報付きの利用側バイナリを配置先ごとにbwrapのro-bind-dataでコピーし、読み取り専用の実行ファイルとして配置する。同一inodeの共有は要求せず、コピーコストはバイナリサイズと配置数に依存する。読み取り可能な自己実行ファイルと、main前の初期化処理も再実行されるという利用条件を維持する。輸送用memfd自体を実行することは要求せず、配置したファイルを実行できなければ起動エラーにする。ディスクへの自動退避、OS設定変更、ポリシー外の依存公開は行わない。設定表を失ったガードは通常アプリへ戻らず終了126とし、既存CLIの従来経路は維持する。配置方式は公開APIの契約に含めず、将来の共有化に公開APIの変更を要求しない設計とする。
  - why: 初期版の起動と回収を単純にし、実際の外部利用でコピー負担が問題になった段階で共有方式を検討するため
  - decided_by: the user (took the recommendation)

- A25 組み込みAPIでも既存の共有ファイルの作成規則を共用する。非入れ子の起動では、要求に渡された環境から決めたXDG_RUNTIME_DIR以下のkakoiディレクトリに、既存規則に従って空ファイルと固定内容のresolverファイルを準備する。ガード用実行ファイルはそこへ保存しない。
  - why: ホスト書込みの既存の限定された例外を共用し、組み込み専用の別方式を増やさないため
  - decided_by: the user (took the recommendation)
- A26 組み込みAPIでは、利用側アプリ自身がガード対象として指定された場合も、そのガード規則を適用する。自己再実行するバイナリであることを理由に暗黙に対象から除外しない。CLIのkakoi自身に対する既存の除外は維持する。
  - why: 利用側が指定した規則をライブラリの実装方式を理由に省略しないため
  - decided_by: the user (took the recommendation)
- A27 イベント待機FutureがPendingのままキャンセルされた場合、未取得イベントを消費しない。次の待機で取得できるようにし、保持上限を超えた履歴の欠落は取りこぼしとして別に通知する。
  - why: タイムアウトや他処理との同時待機で待機を中断しても、キャンセルそのものを原因にイベントが失われないようにするため
  - decided_by: the user (took the recommendation)
- A28 A6のシグナル設定を変更しない保証から、スレッドランタイム・libc自身による内部予約シグナルの初期化だけを除外する。アプリケーションが利用可能なシグナルのハンドラと、呼び出し元のシグナルマスクは引き続き変更しない。内部予約の範囲は使用するランタイム・libcに従い、特定のLinuxシグナル番号を全環境で例外にしない。この例外はkakoiによる予約シグナルの任意の操作や、呼び出し元のハンドラ・マスクの引き取りを認めない。事前のスレッド起動で変化を隠すことや、libcのハンドラを元に戻すことも認めない。
  - why: 設計担当はkakoiを使わない通常のstd::threadの生成でもglibcが内部予約シグナル33のハンドラを初期化することを再現した。[nptl(7)](https://man7.org/linux/man-pages/man7/nptl.7.html)もglibcの内部予約シグナル32・33はアプリケーションが利用できないと説明している。ランタイム自身の初期化と、kakoiが利用側のシグナル設定を変更することを区別するため。
  - decided_by: the user (took the recommendation; 「推奨で」と回答)

  製品試験への反映案（未実施）: prepare前後および起動・終了前後で、アプリケーションが利用可能なシグナルのハンドラと呼び出し元のマスクの不変を検証する。
  生の/proc/self/statusのビット集合の一致だけを保証全体の判定には使わず、差分があれば使用するランタイム・libcの予約範囲と通常のスレッド生成による初期化の観測に照合する。
  予約範囲に含まれるという理由だけで任意の差分を無視しない。

- A29 組み込みAPIへ名前で渡した対象コマンドは、要求の環境にポリシーを適用した隔離用の実効PATHで解決する。env.setのPATH、path-prepend、既存規則によるガード配置を反映し、ガードの本物選びと配置・省略は既存の[REQ-446・REQ-449](../../ir/core/core-command-guard-runtime.md)に従う。ホスト側で起動するbwrapは、ポリシー適用前の要求のHostContextのPATHから探す。相対コマンドパスはD13どおり要求のcwdを基準に解決する。既存CLIの挙動とガード配置規則は変更しない。
  - why: 設計契約の「要求のPATH」が対象コマンドにも未加工のHostContextのPATHを指すと読めたため。隔離内の対象コマンド探索とホスト側のbwrap探索を区別し、ポリシーによる環境変更と既存ガード規則を維持するため。
  - decided_by: the user (took the recommendation; 「OKです」と回答)

  - why: 内部構造の設計は設計担当への依頼に含まれるが、未合意の動作を実装役へ決めさせないため
  - decided_by: 設計担当（D1の担当範囲を明記）
- D3 自己再実行する利用側バイナリが動的リンクする場合の依存ファイルの扱いは、A7だけでは決まっていない。設計担当はlisted内で依存ファイルが見えず補助処理を起動できない場合を仕様の不足として記録し、依存ファイルを暗黙に公開するかをユーザーへ確認する。
  - why: 実行ファイルの記述子を渡しても動的リンカと共有ライブラリの読み込みは別に必要であり、自動公開の有無がポリシーの意味を変えるため
  - decided_by: 設計担当（独立レビューの指摘をコードと照合）
- D4 ガード用の役割識別情報を付けたELFは、bwrapのro-bind-dataで配置した場合に起動でき、設定表消失時にも通常処理へ戻らないことを局所実証した。一方、sealed memfdをro-bind-fdで直接配置する試行は失敗した。この結果をA23の共有方式が成立した証拠とは扱わず、方式の改訂をユーザーへ確認する。
  - why: 内容のコピーで動くことと、変更不能な同じ実行イメージを各ガードで共有できることは異なるため
  - decided_by: 設計担当（Solのプローブのソースと結果を確認し、同じcontrollerを再実行）
- D5 配置先ごとのコピーを採用する前に、実行イメージを共有する方式を追加調査する。
  - why: ユーザーがQ21への回答として共有方式の調査を指定したため
  - decided_by: the user
- D6 二段bwrapの共有方式では、準備用tmpfsにリンクされた通常ファイルを一度作り、最終隔離の各ガードへ同じinodeをbindできることを局所実証した。準備前FDの単純継承は失敗したため、A19を維持する資源準備と受渡しの設計は未解決として残す。
  - why: 同一inodeの共有と実際の起動制限との接続は確認できたが、計画から起動まで保持した対象を使う全経路は確認できていないため
  - decided_by: 設計担当（Solの実証とcontrollerの再実行に基づく）

## クレート境界の設計案

以下は設計担当の提案であり、仕様として確定していない。
現在のcoreを責務ごとに分け、全体はCLIと5つのライブラリで構成する候補とする。

| クレート名の候補 | 所有する責務 | プロジェクト内の依存先 |
|---|---|---|
| kakoi-policy | ポリシーの型、構築、TOML解釈、検証、段の合成、ガード規則の照合 | なし |
| kakoi-plan | 与えられた事実からマウント、環境、コマンド配置を決める純粋な計算と計画用の型 | policy |
| kakoi-linux | ファイルやカーネルの観測、記述子の準備、bwrap起動支援、Landlock適用などのLinux操作 | plan、policy |
| kakoi-net | DNSの判断、通信の準備、監督、遮断、復帰 | linux、plan、policy |
| kakoi-runtime | 公開する要求と不変な実行用計画、各段階の組み立て、実行ハンドル、補助処理の振り分け、結果と通知 | net、linux、plan、policy |
| kakoi | CLIの引数、明示的なホスト環境取得、表示、終了コードへの変換 | runtimeと公開された型 |

ファイルの読み込みと計画の計算は交互に必要となる。
既存のplanning::plan_forに相当する手順はruntimeが所有し、linuxによる観測とplanによる判断を呼び分ける。
planからlinuxを呼ばず、linuxからruntimeを参照しない。
実行用計画の非公開な内部表現と、利用者が読む説明を分ける。
内部クレート間で必要なpub項目を、すべて正式な利用者向けAPIとして再公開することはしない。

DNS判断はまずnet内の純粋なモジュールとして整理する。
独立したDNSライブラリの利用者は現在の合意にいないため、net-logicという追加クレートは現段階では設けない案とする。
同様に、guardやinitごとのクレートは設けず、判断とOS操作と起動の振り分けを上表の責務へ配置する。

### 実行プロセスの候補

組み込み先のプロセスは要求の構築、計画の確認、ハンドルの操作を行う。
起動時に同一バイナリを監督用として再実行し、公式の振り分け関数から実行処理へ入る方式を検討する。
隔離内のinitやガードも同じ振り分け関数から各役割へ入る。
監督プロセスと隔離内の補助処理は異なる権限で動き、通信制御の権限は隔離内へ渡さない。

[launch](../../../crates/kakoi-core/src/launch.rs)は現在、呼び出したプロセスのファイル数上限を変更する。
[run](../../../crates/kakoi-net/src/run.rs)にもプロセス全体のシグナル設定を変更するCLI用関数がある。
これらの副作用を監督側へ閉じ込めることで、A6とA9を実現する候補とする。
CLIのhost/noneの既存exec方式と、組み込み用の監督方式は、低位の準備と起動処理を共用しつつ呼び出し元の生存期間を区別する必要がある。

相対パスの解決では[executables](../../../crates/kakoi-core/src/executables.rs)と[mount_facts](../../../crates/kakoi-core/src/mount_facts.rs)が現プロセスのcwdを参照する箇所も確認した。
組み込みAPIでは要求ごとのcwdを基準に解決する必要があり、型の移動だけではA9を満たさない。

| 単位 | 現時点の判断と理由 |

### マウント元の保持に関する局所実証

上流の[bubblewrap v0.9.0](https://github.com/containers/bubblewrap/blob/v0.9.0/bubblewrap.c)と[v0.10.0](https://github.com/containers/bubblewrap/blob/v0.10.0/bubblewrap.c)を読み、0.9.0にはbind-fdがなく、0.10.0にはbind-fdとro-bind-fdがあることを確認した。
0.10.0は記述子のパスを解決してからマウントし、マウント後のdeviceとinodeを記述子と照合して差し替えを拒む。
単に通常のbindへproc経由の記述子パスを渡すだけでは、この照合を利用できない。

ローカルのbwrapは版名として0.9.0を返すが、helpには両機能を掲載している。
この実行ファイルで、ファイルをO_PATHで開き、別名へ移動し、元のパスに別の内容のファイルを作ってから、ro-bind-fdで隔離内へ渡した。
終了コードは0で、隔離内から読めたのは保持した元のファイルの内容だった。
これは1つのファイルの保持と利用を確認する実証であり、競合の全パターンやマウント先の差し替え耐性を検証したものではない。

### ガードの役割識別に関する比較

別コンテキストの読み取り調査では、同じELFのコピー末尾に役割識別情報を付けてsealed memfdに保持する案を推奨した。
ガードは表の所在と独立して自分の役割を識別でき、表が失われた場合にも通常アプリのmainへ戻らない。
argvと環境変数だけの識別、表だけの識別、子孫が保持するとは限らない継承FDだけの識別では、この条件を満たせない。
外側の監督とinitは専用の制御接続で、listedの最初のプロセスは専用の配置場所で識別できるため、役割付きコピーの必要範囲はガードへ絞る案とする。
コピーを作る場合は各ガードで共有し、コマンド数ごとにELF全体を複製しない。
この比較時点ではELF末尾追加、sealと実行、bind後の自己パスの組合せは未実証だった。後続の局所実証の結果は次節に記す。
main前に動く利用側や共有ライブラリの初期化処理も再実行されるため、その初期化が補助処理の起動時にも成立することが利用条件になる。

### ガードの役割識別の局所実証結果

Solが使い捨てのRust製利用側バイナリとPython製controllerを作り、設計担当もソースを確認してcontrollerを再実行した。
製品の実装コードは変更していない。

| 観測対象 | 結果 |
|---|---|
| 任意名の元のバイナリをKAKOI=1で起動 | 通常アプリとして終了0 |
| 末尾にGuardの識別情報を付け、PATH上と任意の絶対パスへ配置 | ro-bind-dataによるコピーではGuardとして起動。通常処理へ戻らない |
| 入れ子のbwrapが/devを交換し設定表が消失 | 終了126。通常処理の出力なし |
| sealed memfdへの書込み、縮小、拡張 | すべてEPERMで拒否 |
| 起動後のFD一覧 | 調べた時点ではイメージと表のFDが残っていない |
| 元のバイナリ | 実証前後のSHA-256が一致 |
| sealed memfdのro-bind-fdによる直接配置 | ソースパス解決で終了1。実行イメージの共有は未実証 |

成功した配置方法は、bwrapの「--perms 0555 --ro-bind-data FD DEST」による内容のコピーである。
コピー先の実行ファイルに元のmemfdのsealが引き継がれたとは扱わない。
実行中の/proc/self/exeは配置先名に「 (deleted)」を付けた文字列を返したが、/proc/self/exe自体を開けば役割情報を読み取れた。
既存ガード表との配置先照合では、この違いの処理が必要になる。
ホストのルートを読み取り専用で見せたプローブであり、listedの最小構成、実際のガード規則、全起動経路のFD漏洩、異なるカーネルでの成立は未検証である。
配置ごとにro-bind-dataを使う改訂案ではコピー量が増えるため、A23を暗黙に置き換えずU24で確認する。

### 共有方式の追加調査

bwrapはbind元をroot構築前に解決し、元のrootを基準に配置する。
同じ呼出し内でfileにより作った新しいファイルを、後続bindの元として扱う公開された方法は確認できなかった。
根拠は上流[v0.9.0のsource解決](https://github.com/containers/bubblewrap/blob/v0.9.0/bubblewrap.c#L1523-L1568)と[root構築順序](https://github.com/containers/bubblewrap/blob/v0.9.0/bubblewrap.c#L3074-L3109)である。

代わりに、外側のbwrapの私有tmpfsへfileで役割付きELFを一度作り、その領域を読み取り専用にした。
内側のbwrapはその通常ファイルを二つのガード配置先へbindした。
両配置先と実行中の自己実行ファイルのdevice番号とinode番号が一致し、自己パスは各配置先を示した。
削除済みを表す接尾辞は付かなかった。
ガードへの書込みとtruncateは拒否され、設定表を隠す試験では終了126となった。

最初の試験では準備領域が元の/dev/shmを隠したため、追加試験では外側の新しいrootの/hostへ元のホストrootを置き、/stageを独立した準備領域にした。
内側のrootを/hostから構成することで、元の/dev/shmの同一性と、明示したrwファイルへの書込みを維持できた。
最終隔離の/hostと/stageは元のホストの状態と一致し、この試験では準備領域の追加公開は観測されなかった。
絶対シンボリックリンクの元は準備前に正規化してから/hostへ対応付けた。正規化後の競合全般を検証したものではない。

Landlockは一方のガードのinodeだけにEXECUTEを許可し、もう一方のガードも実行できた。
未許可の/usr/bin/trueはEACCESで拒否された。
動的ローダーと検証用プログラムには別途EXECUTEを許可しており、ガード以外を一切許可しない試験ではない。

準備前に保持したO_PATH記述子を外側へ継承し、内側で同じ番号をro-bind-fdへ渡す単純な方法は失敗した。
この失敗から、別の受渡し方法まで不可能とは判断しない。
準備用namespace内のワーカーが計画の観測と記述子保持を担当する案も含め、A19との接続は残件とする。

二つのcontrollerは設計担当も再実行し、共有・source view・Landlockの成功とFD受渡しの失敗を確認した。
ELFサイズをS、配置数をNとすると、この配置方式はガード用の実体を一つにし、N個のbindを作る。配置先ごとにSバイトをコピーしない。
輸送用memfdと準備用ファイルは別であり、総メモリ量が厳密にSだけになるという意味ではない。
準備用のnamespaceと起動段階が増える。実証ではuserとPIDのnamespaceも二段で作ったが、製品で必要な種類と寿命は未確定である。
filteredの通信、実際のCLI互換性、全マウント形態、呼び出し元死亡時の回収まで含む製品検証は行っていない。

### 配置ごとのコピーとの比較計測

Solが使い捨ての比較controllerを作成し、設計担当が内容を確認した。
各条件で1回の予備実行と5回の計測を行い、条件と方式の順序は固定seedで混ぜた。
イメージは小さな利用側ELFにデータを追加してサイズを調整したもので、実際の大規模アプリの初期化時間は測定していない。

| イメージサイズ | 配置数 | コピーの中央値 | 共有の中央値 | 配置したイメージの割当量、コピー / 共有 |
|---|---:|---:|---:|---:|
| 約4.4 MiB | 1 | 9.11 ms | 12.68 ms | 約4.4 / 4.4 MiB |
| 約4.4 MiB | 4 | 17.16 ms | 13.23 ms | 約17.6 / 4.4 MiB |
| 約4.4 MiB | 16 | 49.30 ms | 17.12 ms | 約70.4 / 4.4 MiB |
| 16 MiB | 1 | 15.54 ms | 20.44 ms | 16 / 16 MiB |
| 16 MiB | 4 | 42.34 ms | 21.24 ms | 64 / 16 MiB |
| 16 MiB | 16 | 197.36 ms | 25.44 ms | 256 / 16 MiB |
| 64 MiB | 1 | 38.43 ms | 50.05 ms | 64 / 64 MiB |
| 64 MiB | 4 | 167.54 ms | 50.44 ms | 256 / 64 MiB |

時間にはbwrapの起動、配置、最終環境での同じstatとtrueの実行、終了回収を含む。
元のイメージ生成と役割情報の付与、FDを開く処理、controllerの結果解析は含めない。
共有方式は二段とも含むが、計測では簡略化した準備領域を使い、元のホストのsource viewを保つ製品向け構成の費用を含めていない。
割当量は同じdeviceとinodeを重複して数えず、statのblocksを合計した。RSSやプロセス全体のメモリ量ではない。
両方式とも輸送用memfdが別に存在する。
copyの個々の入力FDは独立したopen-file descriptionを持たせ、オフセット共有で空のコピーになることを避けた。

予備実行を含む96試行と、別に行った両方式のガード起動は成功した。
設計担当は約4.4 MiB・4配置を3回ずつ再計測し、コピー16.63 ms、共有13.40 msの中央値と、異なる4 inode対同一1 inodeを確認した。
この少数の計測だけで「4配置から必ず共有が有利」という一般的なしきい値は設けない。

コピー方式は準備用namespaceを増やさず、同じ起動処理で全配置を作れる利点がある。
共有方式はバイナリが大きい、多数のガードがある、複数隔離を並行実行する場合に重複した実体を減らせる。
一方、namespace、元パスの対応付け、FD受渡し、二段の失敗時回収を実装し検証する負担がある。
現在の計測は共有方式を採用する動機を示すが、未解決の製品接続を省いて標準方式に決める根拠にはしない。
