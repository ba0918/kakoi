# 組み込みAPIでポリシーが示すデバイスの扱い

## Context

リリース前のレビューで、組み込みAPIがポリシーのro、rw、rw-fileに書かれた文字デバイスとブロックデバイスをdev-bindで配置していることが分かった。
読み取り専用マウントはデバイスへの書込みのopenを止めないため、roに書いたデバイスにも隔離内から書き込めた。
CLIは同じ項目をbwrapの--ro-bindと--bindで配置し、bwrapはnodevを付けるので、隔離内ではデバイスが見えても開けない（2026-10-03に実測）。
同じポリシーでCLIと組み込みAPIの意味が食い違い、roの指定が効かないので、リリース前に扱いを決める。

## Agreements

- A1 組み込みAPIは、ポリシーのマウント項目が示すデバイスをCLIと同じくnodevで配置し、隔離内で見えるが開けないものとする。dev-bindで配置するのは、計画自体がdev-bindを指定する項目（入れ子のfilteredに見せる`/dev/net/tun`）だけとする。
  - why: roの指定が書込みを止めないのは隔離の約束を破る。[REQ-library-402](../../ir/library/library-integration.md#REQ-library-402)はCLIと組み込み先が実行処理を共用し既存CLIの挙動を維持すると定めており、CLIと同じ意味に揃えるのが最も穴が小さい。[公開APIの内部設計](./2026-10-03-public-library-api-design.md)の「明示的なデバイス公開は既存のdev-bindで配置」は、計画が既にdev-bindとする項目を指すものと読み、ポリシー項目のデバイスには広げない。マウント後の同一性照合は引き続き全ての保持項目に行う。bwrap 0.9.0はbind-fdでもマウント元のパスの差し替えを反映しうることを試験で確認しており、その検出はこの照合が担う。
  - rejected: rw-fileのデバイスだけdev-bindで読み書き可能にする案は、CLIとの意味のずれが残るため採らない。組み込みAPIでデバイスを拒否する案は、新しい受け入れ境界を決めることになり、CLIとも揃わないため採らない。
  - decided_by: 利用者（推奨案を選択）
