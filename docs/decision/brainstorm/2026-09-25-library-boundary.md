# kakoi-core が環境に触れる範囲と、動的公開のための責務分離の区切り方

## Context

REQ-150 は「kakoi-core は設定の検査・合成・計画を担当し、環境へ直接アクセスしない」と定める。
実装の kakoi-core は、パスの事実（存在、種類、実体、リンク）、マウント一覧、rw-copy の複製元を自分で読み、bwrap に渡す記述子を作り、開けるファイル数の上限を上げている。
一方、kakoi-core の説明文（lib.rs）は、引数の解釈、プロセスの環境変数とカレントディレクトリの読み取り、標準出力と標準エラーへの書き込み、実行をしない、と狭く定めている。
「環境」の範囲が決まっていないため、要求と実装が食い違って読める。
あわせて、FLAG-027（REQ-391 の「公開の判断と pasta 固有の操作を分ける」という区切り方に決定の根拠が無い）を決める。

Position: 決定の木を歩き終えた。

## Agreements

- A1 kakoi-core がしないことを次の 5 つとする。引数を解釈しない。プロセスの環境変数とカレントディレクトリを読まない。標準出力と標準エラーに書かない。コマンドを実行しない。通信を起動、監督、停止しない。パスの事実とマウント一覧と rw-copy の複製元を読むこと、bwrap に渡す記述子を用意すること、bwrap のコマンドを組み立てることは kakoi-core の責任として認める。
  - why: 「環境へ直接アクセスしない」の範囲が決まっておらず、今の実装と kakoi-core の説明文が定める狭い契約とが食い違って読めた。決定 A153 の目的は計画と通信の実行を分けることで、狭い契約でその目的を満たす
  - rejected: 文面どおりにホストの状態を読むことも kakoi-core の外へ出す案。大きな作り直しになり、計画と実行を分ける目的には要らない
  - decided_by: the user (took the recommendation)
- A2 動的公開を追加できるようにする責務の分離は、何を公開するかの判断（入力の形、段の合成、競合の検査）を kakoi-core に、pasta の引数への変換と pasta の起動を kakoi-net に置く区切り方とする。
  - why: REQ-391 の区切り方に決定の根拠が無かった（FLAG-027）。今の実装はこの区切り方になっている
  - rejected: REQ-391 を「責務分離を設ける」まで狭めて区切り方を決めない案。確かめる対象が定まらない
  - decided_by: the user (took the recommendation)
