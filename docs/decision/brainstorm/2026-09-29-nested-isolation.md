# 入れ子の中での隔離

## Context

kakoi は隔離の中で `KAKOI=1` を立て、それを見つけた kakoi は隔離を作らずにコマンドをそのまま実行する（入れ子の実行）。
botti（利用者 1 人用のローカル常駐ツール）はジョブごとに policy を渡して kakoi を起動するが、botti 自身が kakoi の中で動くと、ジョブごとの制限が一つも効かない。
botti のセッションから、入れ子でも中で隔離を作り直し、外と中の制限を重ねる機能の提案が来た（2026-09-29）。
既定の動きを変えるか、何で頼むか、中で作れない制限をどう扱うかを決める。

事実（botti の実測、kakoi 0.5.0、WSL2）: 外の kakoi の中で `env -u KAKOI kakoi --profile botti --policy-file <p> --workspace <w> -- ...` を実行すると、二重の bwrap が起動し、hide と rw は効いた。外で rw にしていない場所は、中で rw にしても書けなかった。network の filtered は `pasta exited during startup: Failed to open() /dev/net/tun` で止まり、コマンドは実行されなかった。env の clear は試していない。
事実: kakoi は bwrap に `--dev /dev` を渡すので、隔離の中に `/dev/net/tun` が無い（crates/kakoi-core/src/plan.rs）。

実測（2026-09-29、別コンテキストの実験、この環境。外の bwrap に "--dev-bind /dev/net/tun /dev/net/tun" を足すラッパーで kakoi 0.5.0 をそのまま起動）: 外に tun を見せると、入れ子の filtered は外が host でも filtered でも動いた。外が filtered のとき、中は外より狭く絞れ、外の許可リストも効き続けた（中の pasta の出口は外の netns の普通のソケットで、外の nft を通る）。外が none のとき中の pasta は起動するが出口が無い。外が filtered のときは tun のほかに 3 つの障害があった。外が秘密のファイルを空にしていて中のグローバルプロファイルの secret で 125 になる。外の resolv.conf は "--ro-bind-data"（削除済みファイルのマウント）で見せていて、中の bwrap がその上にマウントできない（素の bwrap でも再現。原因はカーネルの挙動と推測）。外の中の resolv.conf は "nameserver 127.0.0.53" で、中の kakoi が systemd-resolved の規則で 127.0.0.54 に読み替えるが、外の resolver は 127.0.0.53 でしか待ち受けておらず DNS の許可規則がすべて失敗する。
実測（同上）: 外の中のプロセスは 3 モードとも CapEff=0 で、tun の新規作成、外の netns の "ip link"・"nft" の操作はすべて EPERM だった。外が filtered のとき pasta の tap（app0）への TUNSETIFF は EBUSY だった。owner 未設定か uid が一致する永続の tun/tap には、CAP_NET_ADMIN の無い子 userns からでも接続できた（使い捨ての netns で実測）。外が host のときだけ、ホストの netns にそういう装置があれば読み書きできることになる（今のホストには無い。ホストの "/dev/net/tun" は 666 で、隔離の外の同じ利用者には元からできる）。tun の fd は開いた時点の netns に固定されるので外から渡す案は使えず、外の nft に規則を足す案も EPERM だった。
実測（2026-09-29、この環境、素の bwrap 0.9.0 の二重起動）: 外が "--ro-bind-data" で置いたファイルの上には、中の bwrap は "--ro-bind-data" でも "--ro-bind" でもマウントできず、"Unable to mount source on destination: No such file or directory" で止まる。外が "--ro-bind" でホストの実在のファイルを置いた場合は、中から上にマウントできる。kakoi は "--ro-bind-data" を、filtered の resolv.conf のほか、ファイルの "hide"（空のファイル）と "rw-copy" で写すファイルにも使っている。ガードレールの規則の表も "--ro-bind-data" だが、中の kakoi は "/dev" を作り直すので重ならない。
Position: 照合を 3 回終え（3 回目で指摘 0 件）、承認待ち。

## Agreements

- A1 入れ子の実行の既定の動き（隔離を作らずにコマンドをそのまま実行する）は変えない。
  - why: シムで包んだコマンドは隔離の中からも kakoi を通る（"examples/shim/codex" は入れ子を見ずに kakoi を exec し、入れ子の扱いを kakoi に任せている。2026-09-29 に確認）ので、既定を変えるとそれらが全部二重に隔離され、今の使い方が壊れる。
  - decided_by: 利用者（推奨を採用）
- A2 呼ぶ側が明示したときは、入れ子でも中で隔離を作り、外と中の制限を重ねる。
  - why: 入れ子で動く呼ぶ側（botti）が、ジョブごとの制限を効かせられるようにする。中の隔離は外の隔離の中にあるので、外より広がることはない。
  - decided_by: 利用者（推奨を採用）
- A3 明示したのに中で作れない制限があるときは、コマンドを実行せずに失敗する。外の隔離だけでコマンドを実行する動きには落とさない。
  - why: 呼ぶ側が困るのは、頼んだ守りが黙って効かなくなることである。守りが薄くなる方向には倒さない。
  - decided_by: 利用者（推奨を採用）
- A4 外の隔離の側から、入れ子の kakoi に中の隔離を強制する仕組みは作らない。中の隔離を作るかは呼ぶ側が決める。
  - why: 外の隔離の中のエージェントは kakoi を通らずにコマンドを実行できるので、外からの強制は守りにならない。守りの境目は外の隔離そのものである。
  - decided_by: 利用者（推奨を採用）

  - rejected: policy のキーにする。
  - decided_by: 利用者（推奨を採用）

  - why: 作り方が一つで済み、中で作れないもの（tun が無い、外で空にされた secrets）はいつもの失敗のしかたで止まるので、A3 が追加の仕組み無しで成り立つ。ホストで `KAKOI=1` が立っていても隔離されるので、その起動では known gap 8 の「ホストで `KAKOI=1` を立てると隔離されない」穴が塞がる。
  - decided_by: 利用者（推奨を採用）

  - rejected: この版では何も直さず known gap に書く（新しい機能に最初から穴を開けて出すことになる）。
