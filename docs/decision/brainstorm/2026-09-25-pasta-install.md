# pasta の導入を楽にする

## Context

filtered は pasta（passt パッケージ）を前提にするが、kakoi が渡すオプション（`--host-lo-to-ns-lo`、`--map-host-loopback`）を持たない古い pasta が主要ディストリの標準に残っている。
Ubuntu 24.04 標準の passt 0.0~git20240220.1e6f92b-1 で filtered を起動すると、種類 bwrap の診断に pasta の使い方の全文が改行を `\n` のまま詰めて出て、終了コード 125 で終わる（2026-09-25 にこの環境で実測）。
利用者本人も、最新の pasta をどこからどう入れるのが最適か分からない。kakoi の利用者も同じ状況に陥ると想定する。
導入の手間は filtered を使う上での大きな障壁なので、失敗の見え方、案内、セットアップスキルの支援の範囲を決める。

Position: 照合を 3 回終え、承認待ち。3 回目に残った EX-826、EX-841 は前提を Given に書いて直し、扱いを利用者に返した。

## Agreements

- A1 kakoi が必要とするオプションを持たない pasta で filtered を起動したとき、kakoi は pasta が古いことを専用の診断で伝える。診断は足りないオプションの名前と導入手順の置き場所を示し、pasta の使い方の全文は出さない。
  - why: 今の出力（種類 bwrap の診断に使い方の全文を詰めたもの）では、原因にも直し方にもたどり着けない。
  - decided_by: 利用者（推奨を採用）
- A2 公開文書に pasta の導入手順を載せる。専用の文書を 1 本置き、README と A1 の診断からそこへ案内する。
  - why: README は確かめた版を書くだけで入れ方が無く、利用者本人も最適な入れ方が分からなかった。
  - decided_by: 利用者（推奨を採用）
- A3 セットアップスキルは、導入済みの pasta が kakoi の必要とするオプションを持つかを調べ、導入手順を示すところまで行う。導入の実行は利用者が行う。
  - why: パッケージの導入には管理者権限が要り、スキルの書き先を設定ディレクトリと承認したシムの置き場に限る契約（REQ-379）を大きく超える。導入方法がディストリごとに違い、誤ったときの害も大きい。
  - rejected: スキルが版を調べて承認付きで導入する（R3）
  - decided_by: 利用者（推奨を採用）
- A4 古い pasta は、pasta が起動中に終了したときだけ見分ける。そのとき `pasta --help` を実行し、必要なオプション名が出力に載っているかを確かめ、足りなければ古いと判定する。起動に成功したときは確かめない。
  - why: 成功した起動の手間を増やさない。毎回の事前検査は起動ごとにプロセスが増え、検査順の契約に段が増える。版の番号は Ubuntu 24.04 の pasta が `unknown version` を返すため比べられない（実測）。
  - rejected: 起動の前に毎回確かめる。`--version` の版で比べる。
  - decided_by: 利用者（推奨を採用）
- A5 A1 の診断の種類は bwrap、終了コードは 125 とし、説明文に足りないオプション名と導入手順の文書の URL を含めることを契約にする。
  - why: pasta が PATH に無いときも種類は bwrap で、種類を足すと種類の一覧の契約が変わる。テストで説明文の 2 点を確かめるため契約として宣言する。
  - rejected: 新しい種類を足す。
  - decided_by: 利用者（推奨を採用）
- A6 pasta が PATH に無いときの既存の診断にも、導入手順の文書の URL を含める。
  - why: 入っていない利用者も古い版しか無い利用者も同じ文書にたどり着けるようにする。
  - decided_by: 利用者（推奨を採用）
- A7 導入手順の文書は "docs/pasta.md" に英語で置き、対応する版の条件と導入手順を載せる。診断は GitHub の main ブランチ上のその文書の URL（"https://github.com/ba0918/kakoi/blob/main/docs/pasta.md"）を示す。
  - why: バイナリだけを入れた利用者の手元にはリポジトリが無い。main を指すとリリース後のディストリの変化も反映できる。README と "docs/security.md" が英語である。
  - rejected: 版のタグの URL を示す（リリース後の手順の更新が届かない）。
  - decided_by: 利用者（推奨を採用）
- A8 kakoi は pasta を今までどおりホストの PATH だけから探し、場所を指定する設定は足さない。新しい pasta を PATH の前の方に置く方法は A7 の文書に書く。
  - why: PATH で足りる。ポリシーで場所を選べると、ホストで実行されるプログラムをポリシーから選ぶ新しい入り口になる。
  - rejected: 環境変数やポリシーで pasta の場所を指定できるようにする。
  - decided_by: 利用者（推奨を採用）
- A9 セットアップスキルは、利用者が filtered を使うか使いたいときだけ pasta を調べる。調べ方は `pasta --help` に必要なオプション名が載っているかで、導入手順はスキルに写さず A7 の文書を読んで示す。
  - why: 手順の置き場所を 1 か所にすれば、ディストリの事情が変わっても直すのは 1 か所で済む。
  - decided_by: 利用者（推奨を採用）

- A10 A4 で確かめるオプション名は、kakoi が pasta に渡すオプションの全部とし、引数を組み立てるときと同じ一覧から取る。kakoi は pasta の版の番号では判定しない。必要な版の目安は人間向けに "docs/pasta.md" に書く。
  - why: 足りないと分かった 2 つに絞ると、kakoi が新しいオプションを使い始めたときに一覧の直し忘れで同じ失敗に戻る。版の番号は Ubuntu 24.04 の pasta が `unknown version` を返し、Debian は "0.0~git20260728.f8df3f1-1~bpo13+1"、上流のタグは "2026_07_28.f8df3f1" と書き方が揃わず（実測と上流の命名）、版からはどのオプションが無いかも分からない。
  - rejected: `--version` の版を最低版と比べて判定する。足りないと分かった 2 つだけを確かめる。
  - decided_by: 利用者（推奨を採用）
  - superseded_by: [A20](#A20)

- A11 pasta が起動中に終了し、`pasta --help` が失敗したとき、または必要なオプション名が全部載っていたときは、今の診断（種類 bwrap に pasta が出した理由を付けたもの）のままにする。pasta の出力がそのまま長く出る問題は今回の範囲に含めない。
  - why: 権限や AppArmor のような古さ以外の原因を推測で決めつけると、誤った方向へ案内する。
  - decided_by: 利用者（推奨を採用）

- A12 "docs/pasta.md" は必要な版を 3 段で書く。オプションが揃う最低の版は 2024_10_30、推奨する版は 2026_07_16 以降、確かめた版は 2026_07_28.f8df3f1。kakoi の診断は最低の版を満たさないものだけを見分け、最低の版から推奨する版の手前までは黙って通すことを受け入れる。
  - why: `--host-lo-to-ns-lo` と `--map-host-loopback` がそろうのは上流のタグ 2024_10_30.ee7d0b6 から。`--host-lo-to-ns-lo` の意味は 2026_07_16.090d739 で変わり、上流は実際の差は出ないと説明するが、それより前の版は確かめていない（上流の git の log とタグで確認）。
  - decided_by: 利用者（推奨を採用）
- A13 ディストリの版が足りない利用者には、上流の passt の git からタグを指定してソースビルドし `~/.local/bin` に置く手順を第一に案内し、podman-static の配布物から pasta を取り出す手順を代わりの手段として載せる。
  - why: ソースビルドは信頼する相手が上流だけで、arm64 でも同じ手順で入り、`/usr/bin` の外に置くためディストリの AppArmor のプロファイルが当たらない。gcc と make だけで約 15 秒で終わる（実測）。podman-static は GPG 署名つきで、コンパイラを入れたくない利用者の手段になる。
  - rejected: 上流の非公式の静的ビルドを取得する（R4）。Debian の .deb を別のディストリに入れる（R5）。第三者の PPA を使う（R6）。
  - decided_by: 利用者（推奨を採用）
  - superseded_by: [A17](#A17)
- A14 "docs/pasta.md" はディストリごとの版の一覧表を持たない。導入済みの pasta を `pasta --help` に 2 つのオプションが載っているかで確かめる方法、公式パッケージで足りるディストリの例を時点の日付つきで少し、足りなければ A13 の手順を書く。
  - why: 一覧表はディストリの更新ですぐ古くなる。確かめ方は kakoi の判定と同じ見方にそろえる。
  - decided_by: 利用者（推奨を採用）
  - superseded_by: [A17](#A17)

- A15 AppArmor が効いた環境での確認は、既存の CI の userns-restriction ジョブ（GitHub の ubuntu-24.04 の VM で、`/usr/bin` の外に取り出した f8df3f1 の pasta を PATH から使って filtered の通信を確かめる）で済んだものとして扱う。A13 のビルドと `~/.local/bin` への配置の手順は、公開前にこの環境で実際に打って確かめる。CI は自分でビルドした pasta に差し替えない。
  - why: Docker のコンテナはホストのカーネルを使い、この WSL2 のカーネルでは AppArmor が動いていない（`/sys/kernel/security/lsm` が無い）ため、AppArmor が効いた環境は作れない。CI のジョブは A13 と同じく AppArmor のプロファイルが当たらない置き場所の pasta を、同じコミットで確かめている。ビルドの手順は AppArmor に左右されない。
  - rejected: Docker で検証環境を作る。CI を自分でビルドした pasta に差し替える。
  - decided_by: 利用者（推奨を採用）
- A16 "docs/pasta.md" は、Ubuntu 23.10 以降では pasta を入れた後も非特権の user 名前空間の制限を外す必要があることを一言書き、"docs/getting-started.md" の該当節へリンクする。手順は写さない。
  - why: pasta を入れ終えた利用者が次に確実に当たる壁で、手順の置き場所は 1 か所にする。
  - decided_by: 利用者（推奨を採用）

- A17 "docs/pasta.md" は、導入済みの pasta を `pasta --help` で確かめる方法、A12 の必要な版、足りなければ上流の git からタグを指定してソースビルドし `~/.local/bin` に置く手順、A16 のリンクだけを載せる。podman-static から取り出す手順と、公式パッケージで足りるディストリの例は載せない。
  - why: 利用者が文書の厚さに疑問を出した。古くなりやすいものを持たない基準で削る。podman-static の手順は配布物の構成が変わると壊れ、版の更新も podman のリリースに従う。コンパイラが無い利用者には gcc と make を入れる一言で足りる。ディストリの例は時点つきでもすぐ古くなり、確かめ方があれば利用者が自分で判断できる。
  - rejected: podman-static から取り出す手順を代わりの手段として載せる（A13 の一部）。公式パッケージで足りるディストリの例を時点の日付つきで載せる（A14 の一部）。
  - decided_by: 利用者（推奨を採用）

- A18 A4 の `pasta --help` は、標準出力と標準エラーを合わせた出力を読む。実行できなかったとき、または出力が空だったときを失敗とし、終了コードでは判定しない。
  - why: Ubuntu 24.04 の pasta の `--help` は使い方を標準出力に出して 0 で終わり、標準エラーは空だった（実測）。起動の診断が読む標準エラーだけを読むと、新しい pasta でも全部が足りないと判定される。終了コードを使うと、0 以外で終わりつつ使い方を出す版を見逃す（そうした版があるかは未確認）。
  - decided_by: 利用者（推奨を採用）
- A19 A4 の「起動中に終了した」は、準備完了の合図より前に pasta のプロセスが終了したときを指し、起動用のパイプが先に閉じてから終了を確かめた場合を含む。タイムアウト、PID の不正、取り消しでは確かめない。対象は filtered の最初の起動だけで、通信障害から立ち直るときの pasta の再起動には適用しない。
  - why: 古い pasta が即座に終了すると、パイプが先に閉じて見えることがある（実装を読んだ推測）。一度動いた pasta の再起動の失敗は古さが原因ではない。
  - decided_by: 利用者（推奨を採用）
- A20 A4 で確かめるのは、filtered の 2 段の pasta に kakoi が長い名前（`--` で始まる名前）で渡すオプションを合わせたものとする。名前は、前後が空白、カンマ、行の端のどれかである出現を載っているとみなす。短い名前で渡すオプションは確かめない。
  - why: 短い名前は長い名前の一部に必ず含まれ（`-i` は `--interface` に含まれる）、確かめる意味を持たない。kakoi が短い名前で渡すオプションは上流に 2021 年からある。
  - rejected: 短い名前も含めて渡すオプションすべてを確かめる（A10 の一部）。
  - decided_by: 利用者（推奨を採用）
- A21 "docs/pasta.md" の確かめ方は、A20 で確かめる名前をすべて載せ、その一覧がコードの一覧と同じであることをレビューで確かめる。セットアップスキルは確かめる名前をこの文書から取る。
  - why: 2 つの名前だけを載せると、kakoi が新しいオプションを使い始めたときに文書とスキルは足りると答え、kakoi だけが古いと診断する食い違いが起きる。全部を載せればどれが大事かの判断が要らない。
  - decided_by: 利用者（推奨を採用）
- A22 `--print-plan` は pasta の所在も古さも確かめない。pasta と nft がともに PATH に無いときは pasta を先に報告する。古い pasta の診断（A1）は pasta の出力を一切含めない。
  - why: どれも今の実装どおりで、決めておかないと実装者が迷う。古い pasta の診断は足りない名前と URL で足りる。
  - decided_by: 利用者（推奨を採用）

## Rejected

- R1 静的ビルドした pasta を kakoi の配布物に同梱する。
  - why: pasta は GPL-2.0+ でソース提供の義務が生じ、上流の脆弱性修正に合わせた再配布とアーキテクチャごとのビルドを kakoi が背負う。どれも kakoi の保守範囲を超える。
  - decided_by: 利用者（推奨を採用）
- R2 古い pasta でも動くように kakoi 側を合わせる。
  - why: `--host-lo-to-ns-lo` と `--map-host-loopback` はホストのループバックへの接続と固定公開に使っており、古い版での代替手段は確かめていない。確かめていない組み合わせを増やすだけになる。
  - decided_by: 利用者（推奨を採用）
- R3 セットアップスキルが pasta の版を調べ、利用者の承認を得て導入まで実行する。
  - why: A3 の理由のとおり。
  - decided_by: 利用者（推奨を採用）

- R4 上流が置く静的ビルド（"https://passt.top/builds/latest/x86_64/"）を案内する。
  - why: 上流自身が非公式と説明し、x86_64 だけで、チェックサムも署名も無く、最新の git から作るため版を固定できない。
  - decided_by: 利用者（推奨を採用）
- R5 Debian の .deb（trixie-backports）を Ubuntu に入れる手順を案内する。
  - why: apt が管理する `/usr/bin` を上書きし、確かめていない pasta 用の AppArmor のプロファイルを新しく効かせる。
  - decided_by: 利用者（推奨を採用）
- R6 第三者の PPA（ppa:sejug/podman、ppa:cmorve/podman）を案内する。
  - why: Ubuntu 公式でも上流でもなく、podman 一式まで置き換えるため取り込みの絞り込みが要る。
  - decided_by: 利用者（推奨を採用）
