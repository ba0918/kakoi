## Requirements

### REQ-158: 保護対象と参照経路の検査
- kind: ubiquitous
- source: docs/decision/brainstorm/2026-09-16-kakoi-spec-readability.md#A1
- verification: unit

この節は、起動時に実体へ解決するパスについて、隔離の中からの書き換えで解決の結果を変えられないことを求める。「解決が参照するもの」と「根の項目」は第 2 節の用語である。「合成後の "rw" または "rw-file" の項目」は、第 6.3 節の生成の段が書かれた項目を置き換えた後の集合を指す。生成された項目は毎回の起動で事実から作り直すので、参照するものを持たず、根の判定の対象にもならない。

"rw-copy" の項目もこの集合に含めない。本節が守るのは「次の起動が読むもの」と「次の起動が指令を適用する先」であり、"rw-copy" の中は隔離のマウント名前空間の中の複製で、そこへの書き込みはホストのファイルにも、パスの解決が通る名前にも届かないためである（第 6.1 節）。ポリシーファイルや設定ディレクトリや秘密ファイルを "rw-copy" の中に置いた起動は、下の保護対象のパスの検査を通る。

「書き込める項目の中」は同一か子孫を指す。「与えられたパス」は解決前のパスであり、設定ディレクトリについては第 2 節の規則で組み立てた実体化する前のパスである。第 5.4 節で同じ実体にまとまる書き込める形（"rw" または "rw-file" で書かれたもの）が複数あるときは、そのすべてが根の項目の条件（書き込める項目の中にあるものを参照しない）を満たすときだけ根の項目とする。

"ro" や "hide" で書かれた形は根の判定に関わらない（それ自身は書かれた項目として検査される）。保護対象のパスの検査。 読み込んだすべてのポリシーファイル、設定ディレクトリ、"secrets" の値が指す秘密ファイル、"env.path-prepend" の項目について、その解決は合成後の "rw" または "rw-file" の項目の中にあるものを一切参照してはならない。

参照すれば種類 "path" の診断で終わる。加えて、与えられたパス自身の実体も書き込める項目の中にあってはならない（参照するものにはパス自身が入らないため、別に求める）。次の 3 つをこの順に検査し、最初に当たったものを出す（通ったディレクトリの中では最初に通ったもの）。

条件1：与えられたパスの各前置き（各祖先ディレクトリと、そのパス自身）の実体が書き込める項目の中にある。

条件2：辿るシンボリックリンクの置き場が書き込める項目の中にある。

条件3：通るディレクトリの実体が書き込める項目の中にある。

秘密ファイルが存在しない（第 9 節の警告になる）ときも、存在する前置きと、存在しない成分に至るまでに参照したものについて同じ検査を行う。設定ディレクトリが存在しない（組み込みの既定で起動した）ときも同じで、存在しない名前自身は検査せず、存在する前置きと、存在しない成分に至るまでに参照したものについて同じ検査を行う（隔離の中から設定ディレクトリを作ってプロファイルを植えられないため）。

値を持たない変数を含む "secrets" の値と "path-prepend" の項目は解決するパスを持たないので、検査の対象にならない（第 5.2 節。"secrets" は第 9 節の警告、"path-prepend" は飛ばし）。存在しない前置きは実体を持たないので検査の対象にならず、存在する最も深い祖先が書き込める項目の中にあれば止まる。

この診断の説明は、そのファイル、ディレクトリ、またはリンクのパス、それを含む "rw" 項目のパス、「隔離の中から差し替えられるため」という理由の 3 つを含む。複数の保護対象が同時に当たるときの順は第 13 節が定める。解決の記録は次のとおり（本節のすべての検査に共通）。通るディレクトリは同じ実体を 1 回ずつ記録する。

存在しない成分、読めない成分、先を読めないリンクに至ったら解決をそこで打ち切り、そこまでに参照したもの（先を読めないリンクはその置き場）を検査する。複数の参照が同時に当たるとき、どれを診断に名指すかは第 20 節で委譲する。

### REQ-159: 根への着地と隠し先・起点のリンク
- kind: ubiquitous
- source: docs/decision/brainstorm/2026-09-16-kakoi-spec-readability.md#A1
- verification: unit

それ以外の解決されるパス（根の項目の検査）。 書かれた "rw"、"rw-file"、"hide" のマウント項目（どの段のものも、コマンドラインのものも）、"--workspace" で与えたパス、走査の "root"、"hide-mounts" の"under" について、その解決が合成後の "rw" または "rw-file" の項目の中にあるものを参照するなら、そのパス自身の実体はいずれかの根の項目の中になければならない。

外にあれば種類 "path" の診断で終わる。書かれた "ro" と "rw-copy" の項目だけはこの検査の対象外で、下の露出する組の検査だけを受ける。"ro" はリンクを差し替えられても消されても、どこかが読み取り専用になるか読み取り専用が外れるだけで、新しく見えるものが生まれるのは露出する組の形に限られるためである。

"rw-copy" も同じで、差し替えられても動くのは複製の位置だけで、ホストには何も書かない。複製が新しく見せるのはホストの内容であり、それは"--ro-bind / /" で元から読み取り専用に見えている（隠されている場所へ着地する形だけが新しく、それは露出する組の検査が止める）。差し替え先が大きければ第 6.1 節の複製の上限に当たって種類 "path" で止まるので、際限なく読み込まされることもない。

"hide" は対象に残す: "rw" の中のリンクで書いた "hide" が "rw" の外を指す配置は、隔離の中でリンクを消されると次の起動で項目が飛ばされ、隠し先がホストのまま見える（2026-09-06 に bwrap 0.9.0 で実測）。走査の "root" と "hide-mounts" の"under" を対象に含めるのは、差し替えられた起点は本物の木を走査せず、隠すべき ".env" やマウントが隠れないためである。

この 2 つの検査は第 6.3 節の生成（走査、"hide-mounts"、秘密ファイル、"secrets/" のすべて）の前に行い、書き込める項目と根の項目は、書かれた段だけに第 5.4 節の置き換えを適用した集合（生成の段を適用する前）で判定する。生成は "hide" しか足さないので、この集合は生成後の集合を含み、参照の検出は厳しい側に倒れる。

着地の判定は、生成がこれから隠す書き込める項目（生成された "hide" と同一の実体の "rw"）の中への着地を通す点で緩いが、そこは結局隠されるので新しく見えるものは無い。この2 つの診断は、書かれた項目の検査より先に出る（第 13 節）。書かれた "hide" の項目と、走査の "root" と "hide-mounts" の"under" は、さらに、その解決が書き込める項目の中に置かれたシンボリックリンクを辿るなら、着地先を問わず（根の項目の中でも、"rw" のマウント点そのものでも）種類 "path" の診断で終わる。

隔離の中でそのリンクを消されると次の起動で項目や起点が飛ばされ、"hide" なら隠し先が露出し、起点なら隠すべき木やマウントが隠れないためである（2026-09-06 に bwrap 0.9.0 で実測。深さ 1 のマウント点は改名できないので、実体のパスで書いた "hide" や起点なら外れない配置でも、リンクの形は外れる）。

実体のパスで書いた "rw" の中の"hide"（第 6.4 節の表の形）はリンクを辿らないので通る。ここで見るのは項目自身の解決だけで、ワークスペース由来の変数で引き継いだ参照は数えない（引き継いだリンクを消されると "--workspace" 自身が種類 "path" で止まる）。この診断の説明は、その項目または起点のパス、辿ったリンクのパス、理由の 3 つを含む。

書かれた"hide" や起点が根の項目の検査（起点については下のマウント点の規則を含む）とこの規則の両方に当たるときは、この規則の診断を出す（辿ったリンクが利用者の直す場所を直接指すため。明示の "--workspace" の先例とは逆）。走査の "root" と "hide-mounts" の "under" は、さらに、その解決が書き込める項目の中を参照するなら、その実体が書き込める項目の実体と同一（"rw" のマウント点そのもの）でなければ種類 "path" の診断で終わる。

### REQ-160: 起点のマウント点とワークスペースの例外
- kind: ubiquitous
- source: docs/decision/brainstorm/2026-09-16-kakoi-spec-readability.md#A1
- verification: unit

起点はマウントされないので、"rw" の下位を起点にすると隔離の中で改名や向け直しができ、次の起動が空の木を走査して隠すべき ".env" が丸ごと隠れなくなる（2026-09-06 に bwrap 0.9.0 で実測）。"rw" のマウント点そのものは改名できず、走査はそこから再帰するので外れない（マウント点へリンク越しに書いた起点は、そのリンクを消せるので上のリンクの規則に当たる）。

この診断の説明は、その起点のパス、参照した "rw" 項目のパス、理由の 3 つを含む。実体を持たない項目（存在しないもの、第 14 節のリンク追跡の上限を超えたもの）は第 6.2 節どおり飛ばし、この検査の対象にならない（次の起動でそこに実体ができれば、その時に検査される）。"--workspace" は次の 2 つの場合に検査の対象外で、参照するものを持たない: 省略したとき（カレントディレクトリはカーネルが inode で解決する）と、明示した実体がカレントディレクトリの実体と同一なとき。

それ以外のとき、ワークスペース由来の変数（"${workspace}"、"${worktree}"、"${git_common_dir}"）で展開した項目（走査の "root" と "hide-mounts" の "under" を含む）は "--workspace" の解決が参照したものを引き継ぐ。

対象外のときは引き継ぐものが無い。除外されない明示の "--workspace" については、さらに、その解決がシンボリックリンクを辿るなら、その実体はワークスペース由来の変数で展開した項目以外の根の項目の中になければならない。外にあれば種類 "path" の診断で終わる。書き込める項目の集合自体がワークスペースから導かれるため、差し替えられたワークスペースを基準にすると、差し替え前に書き込めた場所（例: "rw = ["${worktree}"]" で前回"rw" だった "~/proj"）が書き込める項目に見えなくなる。

差し替えの手段はリンクに限られる（改名や移動では書き込める項目の外へ出られず、隔離の中から bind mount やディレクトリのハードリンクは作れない）ので、リンクを辿る解決だけを対象にする。実体のパスを書くか、そこをカレントディレクトリにして起動すれば通る。字面の形とワークスペース由来の形が第 5.4 節で同じ実体にまとまった項目は、ワークスペース由来の変数で展開した項目として扱う（リンクを辿る明示の "--workspace" はそこに着地できない）。

明示の"--workspace" が根の項目の検査とリンクを辿る規則の両方に当たるときは、根の項目の検査の診断を出す。この診断の説明は、そのパス、解決の途中で参照した（または "--workspace" から引き継いだ）"rw" 項目のパス、「隔離の中から差し替えられるため」という理由の 3 つを含む。

リンクを辿る "--workspace" の診断では2 つ目の要素は辿ったリンクのパスとする。検査の順は、走査の "root" を合成後の並び順で、次に"hide-mounts" の "under" を合成後の並び順で（この 2 つは第 13 節の段階 7 で生成の前に先に見る）、次に書かれた項目を第 6.4 節の順序で、次に "--workspace"。

### REQ-161: 再露出・固定マウント・広すぎる書き込みの拒否
- kind: ubiquitous
- source: docs/decision/brainstorm/2026-09-16-kakoi-spec-readability.md#A1
- verification: unit

露出する組の検査。 解決が書き込める項目の中を参照した書かれた項目（指令を問わない）は、次のどちらかで "hide"、"ro"、または "rw-copy" の項目と露出する組（第 2 節。項目が "rw" または "rw-file" で無効にする先が "hide"、"ro"、または "rw-copy" のとき、および項目が "ro" または "rw-copy" で無効にする先が "hide" のとき）になるとき、種類 "path" の診断で終わる。

リンクを辿らない実体のパスの項目でも、その解決が書き込める項目の中を参照するなら対象である。

条件1：その項目の実体が、下の段の "hide"、"ro"、または "rw-copy" の項目の実体と同一である。「下の段の   項目」は、第 5.4 節の置き換えを段の順に適用したときに、その項目の段の直前にその実体で残っている   項目を指す。

条件2：その項目の実体の真の祖先のいずれかに、段を問わず（同じ段と上の段、生成の段を含む）"hide"、"ro"、   または "rw-copy" の項目が効いている。祖先に効いている項目は、すべての段に第 5.4 節の置き換えを適用した後にその   実体に残っている項目であり、真の祖先を内側から順に見て、最初に項目が効いている祖先だけで判定する。

   そこに残っているのが "rw" なら、その場所は既に露出しているので止めない。実体のパスで書いた "rw" でも、   書き込めない場所だけを通るリンク越しに書いた "rw" でも同じである。この診断の説明は、その項目のパス、無効にする先の "hide"、"ro"、または "rw-copy" の項目のパス、「隔離の中から差し替えられるため」という理由の 3 つを含む。

第 6.3 節で生成した "hide" は、同一の実体では書かれた項目を置き換える（第 6.3 節）ので規則 1 の相手にならないが、規則 2 の祖先に効いている項目には数える。設定ディレクトリの "secrets/" や "hide-mounts" で隠したディレクトリの中へ "ro" や "rw" の項目がリンク越しに着地すると、第 6.4 節の順序で狭い項目が後に乗り、隠していた中身が見えるためである。

"--workspace" 自身はこの検査の対象でなく、ワークスペース由来の変数で展開した書かれた項目が、引き継いだ参照によって検査される。理由と境界の例は下の「なぜ根の項目という考え方が要るか」に書く。固定部分への着地の拒否。 どの指令の項目でも、その実体が "/" と同一か、"/dev" または "/proc" と同一かその中（第 14 節の固定部分がマウントする場所）であるときは、参照の有無を問わず種類 "path" の診断で終わる。

"/proc" の上に "ro" を重ねると隔離用の "/proc" がホストのもので覆われ、ホストのプロセスが見える（2026-09-06 に bwrap 0.9.0 で実測）。"/dev" や "/" に重ねると隔離の土台が壊れる。この診断の説明は、その項目のパスと理由を含む。広さの拒否。 合成後の "rw" または "rw-file" の項目の実体が、"/"、ホームディレクトリ、ホームディレクトリの祖先のいずれかであるときも、種類 "path" の診断で終わる。

ホーム全体を書けるようにする指定は、どの段からも受け付けない。"rw-copy" はこの拒否の対象にしない。ホスト側のホームは書けるようにならないためである。ホーム全体を "rw-copy" にする指定は、第 6.1 節の複製の上限に当たって種類 "path" で止まる。第 13 節の段階 7 の中では、走査の "root" と "hide-mounts" の "under" の根の項目の検査（生成の前）、生成、保護対象のパス、書かれた項目と "--workspace" の根の項目の検査と露出する組の検査（書かれた項目ごとにこの順。項目をまたぐ交互の順は第 20 節で委譲）、固定部分への着地の拒否、広さの拒否の順に検査する。

### REQ-162: 根の項目と露出する組の根拠
- kind: ubiquitous
- source: docs/decision/brainstorm/2026-09-16-kakoi-spec-readability.md#A1, docs/decision/brainstorm/2026-09-25-u5-and-review-checks.md#A4
- verification: review
- how_to_verify: 本文に挙げた差し替えの形（前置きでない場所のリンク、".." で "rw" の中のディレクトリを通り抜ける形、入れ子の項目の差し替え、飛び先同士の正当化、"--workspace" を "rw" の中のリンク越しに与える形）が、REQ-158からREQ-161の規則で止まることを規則と突き合わせて確かめる。露出する組の指令の組み合わせと、実体のパスで書けば通る配置・諦める配置が、REQ-161の検査と一致することを確かめる。

なぜ根の項目という考え方が要るか。書き込める項目の中にあるものを参照して解決されるパスは、隔離の中からその参照先を書き換えることで、次の起動に別の実体を読ませたり、別の実体へ指令を適用させたりできる。前置きの実体だけを見ると、前置きではない場所にあるリンク（"~/policies" が "~/cache/link/pol"を指し、"~/cache/link" が "rw" の中）を張り替えられる。

リンクの置き場まで見ても、リンク先が ".." で"rw" の中のディレクトリを通り抜ける形（"~/policies" が "~/cache/x/../../real/pol" を指し、"~/cache/x"が "rw" の中の実ディレクトリ）では、そのディレクトリをリンクに差し替えられる。保護対象だけを守っても、入れ子の項目（"rw = ["~/cache", "~/cache/pip/http"]"）は "~/cache/pip" をホストの別の場所へのリンクに差し替えると、次の起動がそこへ "rw" を適用する。

飛び先が「いずれかの書き込める項目の中」であればよいとすると、差し替えた飛び先同士が互いを正当化し、"rw = ["${worktree}", "~/cache"]" で "--workspace" を"rw" の中のリンク越しに与えた場合は "${worktree}" の項目自身が飛び先を正当化する。

この例では引き継ぎが無ければ、変数の値は実体のパスなのでその項目自身は書き込める項目の中を参照しないことになる。カレントディレクトリと、それと同じ実体の "--workspace" を対象外にするのは、既にそこにいるプロセスは差し替えで移動しないためで、第 14 節で受け入れた起動環境への信頼（カレントディレクトリを含む）と同じ水準である。

根の項目は、この連鎖を「自身の解決が書き込める項目の中を参照しない項目」で断ち切る。通った項目の中に限らず「いずれかの根の項目の中」とするのは、"rw" の項目については別の根の項目の中へ着地しても新しく露出するものが無い、と考えたためである。ただし、飛び先の根の項目の中に "hide" または "ro" で書いた項目があると、リンク越しに着地した項目がそれを無効にする。

同一の実体なら、上の段から着地した項目が第 5.4 節の同一性で下の段の "hide" や "ro" を置き換える。同一でなくても、"hide" や "ro" の中（真の子孫）に着地すれば、第 6.4 節の順序で狭い項目が後に乗り、隠していた中身が見える。後者は段に依らない:下の段の "rw" がコマンドラインの "hide" の中へ着地しても、同じ順序で後に乗る。

新しく露出するのは、着地した項目が "rw" または "rw-file" で無効にする先が "hide"、"ro"、または "rw-copy" のとき、および着地した項目が "ro" または "rw-copy" で無効にする先が "hide" のときである（"hide" は何も露出せず、"ro" が "ro" に重なっても、"rw-copy" が "ro" に重なっても新しく見えるものは無い）。

"rw-copy" を相手側に数えるのは、利用者が「書き込みが外に出ない場所」として指定したところに、差し替えられうる "rw" や"rw-file" が第 6.4 節の順序で後から乗ると、その書き込みがホストへ通ってしまうためである。この形を「露出する組」と呼び、検査の規則は上の「露出する組の検査」に定める。

別の根の項目の中へ飛ぶこと自体（下の観測条件の「別の根の項目への着地」の形）は残す。何も参照しない項目（実体のパスで書いた "rw = ["/tmp/kakoi"]" を "hide = ["/tmp"]" の中に置く第 6.4 節の表の形）はこの規則に当たらない。正直な配置で項目を "hide" の中へリンク越しに置きたいとき、その "hide" が書き込める項目の外にあるなら、実体のパスを書けば通る。

"hide" が "rw" の中にあるなら、実体のパスで書いてもその "rw" を参照するので、"rw" も "rw-file" も "ro" も通らない（規則 2）。そこでは項目を "hide" の中に置く配置そのものを諦める。

### REQ-163: 残る配置上の隙間と受け入れる形
- kind: ubiquitous
- source: docs/decision/brainstorm/2026-09-16-kakoi-spec-readability.md#A1, docs/decision/brainstorm/2026-09-25-u5-and-review-checks.md#A4
- verification: review
- how_to_verify: 本文の配置（"rw" の中の "ro" の入れ子、"rw" の中に置いたリンクのパスを "rw"、"rw-file"、"hide"、走査の "root"、"hide-mounts" の "under" に書く配置とリンク先の実体のパスを書く配置、同じリンクのパスを "ro" に書く配置）でkakoiを起動し、それぞれ本文のとおり通るか1回目の起動から止まるかを観測する。"ro" で書いたリンクの守りの限界が表 TBL-160 の既知の隙間15と一致すること、秘密ファイルが保護対象のパスに含まれることをREQ-158と突き合わせて確かめる。

"rw" の中の "hide"・"ro" の項目は着地先を変えられると元の対象を隠せなくなるが、それは下の「読み取り専用で重ねるだけでは足りない理由」のとおり祖先の改名でも起きることで、この規則の穴ではない。入れ子を禁じないのは、第 6.4 節の表にある "rw" の中の "ro" のような形を残すためである。

利用者が "rw" の中に置いたリンク（先がどの根の項目の中でもない。"hide" と走査の "root"・"hide-mounts" の "under" は先を問わない）のパスを"rw"、"rw-file"、"hide" の項目や走査の "root"、"hide-mounts" の "under" に書くと、正直な配置でもこの規則に当たって 1 回目の起動から拒否される。

リンク先の実体のパスを書けば通る。同じリンクのパスを "ro" の項目に書く配置（dotfiles へのリンクを "ro" にする形）は通るが、その守りは第 16 節の既知の隙間 15 の水準である: 隔離の中でリンクを消して同じ名前の通常ファイルを置けば、同じ起動の中で読む側のパスの内容を変えられ（守られるのはリンク先の実体だけ。2026-09-06 に実測）、リンク先が書き込める項目の外なら"--ro-bind / /" で既に読み取り専用なので "ro" の項目は何も足していない。

秘密ファイルを保護対象にするのは、"rw" の中の秘密ファイルを隔離の中からホストの任意のファイルへのシンボリックリンクに差し替えると、次の起動がその内容を環境変数として隔離に持ち込むためである。

### REQ-165: 配置保護の受け入れ例と拒否例
- kind: ubiquitous
- source: docs/decision/brainstorm/2026-09-16-kakoi-spec-readability.md#A1, docs/decision/brainstorm/2026-09-25-u5-and-review-checks.md#A4
- verification: review
- how_to_verify: 本文に挙げた各配置を用意してkakoiを起動し、通るとされた配置が通り、止まるとされた配置が理由付きの診断（書かれた項目と "--workspace" では種類 "path"）で止まることを一つずつ観測する。合成結果が "--print-plan=full" に表示されること、削除の演算子に相当する書き方がどの段でも読み込みに失敗することを観測する。

成功の観測条件: 上の表の規則で合成した結果が "--print-plan=full" に表示され、削除の演算子に相当する書き方はどの段でも読み込み失敗になり、ワークツリーの中に置いたポリシーファイルを "--policy-file" で指すと理由付きの診断で止まり、"rw" の中を指す "secrets" の値も同じ診断で止まり、"rw" の外にあるポリシーファイルを "rw" の中に置いたシンボリックリンク越しに指しても同じ診断で止まり、リンク先が ".." で"rw" の中のディレクトリを通り抜ける形でも同じ診断で止まる。

書かれた項目と "--workspace" については次の対がそれぞれ観測される: "rw = ["~/cache", "~/cache/pip/http"]" の正直な配置は通り、"~/cache/pip" をホストの別の場所へのリンクに差し替えると "path" で止まる。"rw = ["~/a", "~/b"]" と "hide = ["~/b/creds"]"と "~/a/l -> ~/b/x" で "ro = ["~/a/l/y"]" は通り、"l" をどの項目でもない場所へ差し替えても通り（"ro" は新しく露出しない）、"l" を "~/b/creds" の中へ差し替えると止まる。

"rw = ["${worktree}", "~/cache"]" に"--workspace ~/cache/proj" は通り、"proj" を別の場所へのリンクに差し替えると止まる。"rw = ["~/cache"]"の中の "rw-file" は、正直な配置は通り、差し替えると止まる。"rw = ["~/cache"]" の中の実体のパスで書いた"hide" は通る。

"rw = ["~/proj"]" で "~/proj/secrets" がどの項目でもない "~/vault" を指す"hide = ["~/proj/secrets"]" も、"rw = ["~/a", "~/b"]" で "~/a/l" が "~/b/creds" を指す "hide = ["~/a/l"]" も、1 回目の起動から止まる。

書き込めない場所だけを参照する解決は影響を受けない: "rw = ["${worktree}"]" だけのプロファイルで "--workspace ~/cache/proj"（"~/cache" はどの項目でもない）は通る。明示した "--workspace" がカレントディレクトリと同じ実体なら、"rw" のワークツリーの下位でも通る。

リンクを辿る明示の "--workspace" については: "rw = ["${worktree}"]" で"~/proj/sub" を別の場所へのリンクに差し替えた後、別のカレントディレクトリから "--workspace ~/proj/sub" を与えると "path" で止まり、"rw = ["~/work"]" で "~/work" がリンクでも "--workspace ~/work/proj" は通る。

"rw = ["~/a", "~/b"]" と "hide = ["~/b/creds"]" のプロファイルに、"~/a/link" が "~/a/real" を指す正直な配置で"--rw ~/a/link" は通り、"~/a/link" を "~/b/creds" へ向け直しても "~/b/creds/sub" へ向け直しても "path" で止まる。

"rw = ["~/a", "~/b", "~/a/link"]" のプロファイルで "~/a/link" を "~/b/creds/sub" へ向け直し、"--hide ~/b/creds" を与えても "path" で止まり、同じ "hide" をプロファイルに書いても止まる。"rw = ["~/b"]" と "hide = ["~/b/creds"]" のプロファイルに "--hide ~/b/creds" も "--hide ~/b/creds/sub" も通る。

"rw-copy" については次の対が観測される: "rw-copy = ["~/policies"]" の中にポリシーファイルを置いた起動は通り（保護対象のパスの検査の対象にならない）、同じ配置を "rw" にすると "path" で止まる。

### REQ-166: 複製・生成・起点に関する境界例
- kind: ubiquitous
- source: docs/decision/brainstorm/2026-09-16-kakoi-spec-readability.md#A1, docs/decision/brainstorm/2026-09-25-u5-and-review-checks.md#A4
- verification: review
- how_to_verify: 本文に挙げた各配置（"rw-copy" と "rw-file" の組、別の根の項目への着地、生成された "hide" の中への着地、固定部分、走査の起点）を用意してkakoiを起動し、通るとされた配置が通り、止まるとされた配置が種類 "path" の診断で止まることを一つずつ観測する。

"rw = ["~/a", "~/b"]" と "hide = ["~/b/creds"]" のプロファイルに、"~/a/link" を "~/b/creds" へ向けた"--policy-file" の "rw-copy = ["~/a/link"]" は "path" で止まり、同じ形で相手が "ro = ["~/b/creds"]" なら通る。

逆向きに、"rw-copy = ["~/b/creds"]" のプロファイルに、"~/a/link" が "~/b/creds/k" を指す"rw-file = ["~/a/link"]" を "--policy-file" で足すと "path" で止まる。別の根の項目への着地: "rw = ["~/a", "~/b"]" で "~/a/link" を "~/b/real" へ向けた "--rw ~/a/link" は通る。

生成された "hide" の中への着地: "rw = ["~/a"]" と "~/a/link" が "${config_dir}/secrets/other"（"secrets" に書かれていないファイル）を指す "ro = ["~/a/link"]" は "path" で止まり、"hide-mounts" で隠した "/mnt/c"の中を指す "ro" も止まる。

固定部分: "ro = ["/proc"]" と、"~/a/link" を "/proc" へ向けた"ro = ["~/a/link"]" は "path" で止まる。走査の起点: "rw = ["~/a"]" で "~/a/link" がどの項目でもない"~/proj" を指す "root = "~/a/link"" は "path" で止まり、"rw = ["~/b"]" で "root = "~/b/tree""（"rw" の下位）も "path" で止まり、"root = "~/b"" と "root = "${worktree}"" は通る。

反例: 上の段の "rw" が下の段の"hide" と同じパスを指したとき、どちらが勝つかが段の順序以外で決まる。差し替えた飛び先が別の差し替えた項目によって正当化される。"ro" のリンクを "secrets/" の中へ向けると次の起動で秘密ファイルが読める。
